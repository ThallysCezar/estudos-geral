01

Por que containers existem

Antes de qualquer comando: o problema real que o Docker resolveu — e o que ele não é.

O problema: "na minha máquina funciona"

essenciala origem
💻 INCIDENTE REAL DE PRODUÇÃO

Cenário hipotético: um serviço funciona no notebook, mas falha no servidor por diferença de bibliotecas nativas. Empacotar aplicação e dependências em uma imagem reduz esse tipo de divergência, mas não cria paridade absoluta: kernel, arquitetura da CPU, configuração, secrets, permissões e serviços externos ainda podem diferir. Reproduza também a arquitetura de destino e teste a imagem em ambiente representativo.

🎯 1. O que é?

Um container empacota a aplicação junto com todo o ambiente de que ela necessita para executar: binários do sistema operacional, bibliotecas compartilhadas (.so), runtime da linguagem (como OpenJDK 21), variáveis de ambiente e arquivos de configuração. O artefato imutável que roda na estação de trabalho do desenvolvedor é literalmente idêntico, bit a bit, ao executado nos servidores de homologação e produção.

O ponto fundamental que redefine o modelo mental: container não é máquina virtual. Ele não possui um sistema operacional próprio nem executa um hypervisor com kernel isolado — é estritamente um processo Linux comum, rodando no kernel do host, porém confinado por uma visão restrita dos recursos da máquina.

≈

Analogia do mundo real: Pense no contêiner marítimo padronizado (ISO). Antes dele, sacas de café, barris e caixotes eram embarcados individualmente, exigindo que cada guindaste e armazém soubesse manipular cada formato. O contêiner padronizou a caixa externa: navios, trens e caminhões não precisam saber o que está lá dentro. No software, o servidor de produção não precisa saber se o app usa Java 21, Python ou uma versão específica de libssl; ele apenas manipula o container.

🚀 2. Para que serve?

Serve para eliminar de forma definitiva a discrepância entre ambientes de desenvolvimento e produção:

  • Dependências sob demanda: Permite subir instâncias isoladas de PostgreSQL, Redis ou RabbitMQ localmente em segundos, sem poluir o sistema operacional do desenvolvedor.
  • Paridade estrita no CI/CD: A esteira automatizada executa os testes unitários e de integração exatamente sob as mesmas dependências e glibc do ambiente final.
  • Entrega padronizada: Entrega a aplicação como imagem auto-contida, extinguindo manuais gigantescos de instalação e passos manuais de configuração.

💎 4. Porque importa?

Historicamente, isolamento de processos existia no Linux desde os anos 2000 (com namespaces e cgroups consolidados no kernel e utilizados pelo LXC). O que o Docker criou em 2013 não foi a tecnologia de isolamento em si, mas a experiência de desenvolvedor (DX): formato de imagem em camadas, arquivo declarativo (Dockerfile), registry público e o comando docker run.

Veio substituir: Servidores configurados à mão via planilhas de passo a passo, VMs pesadas dedicadas a isolar aplicações simples e longas filas de chamados para o time de infraestrutura instalar pacotes.

🛠️ 3. Como usar / Como aplicar?

Comandos básicos para subir dependências isoladas sem instalar ferramentas no sistema host:

# Subir PostgreSQL 16 isolado com porta mapeada e volume temporário
docker run -d --name pg-dev \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=orderflow \
  -p 5432:5432 \
  postgres:16-alpine

# Subir RabbitMQ com painel de gerenciamento exposto
docker run -d --name rabbit-dev \
  -p 5672:5672 -p 15672:15672 \
  rabbitmq:3-management-alpine
⚙️ 5. Como funciona por baixo dos panos?

Quando você executa docker run, nenhum hardware virtual é inicializado e nenhuma BIOS ou bootloader é acionado. O daemon Docker solicita ao runtime de baixo nível (runc) que faça chamadas de sistema (syscalls) nativas do Linux:

  1. Invoca a syscall clone() com flags especiais como CLONE_NEWPID, CLONE_NEWNET e CLONE_NEWNS para criar uma nova árvore de isolamento.
  2. Monta um sistema de arquivos raiz em camadas (OverlayFS) sobre a imagem base.
  3. Cria diretórios de restrição no /sys/fs/cgroup/ e adiciona o PID do processo nas regras de cgroup.
  4. Executa o binário do app dentro dessa jaula lógica. Como o kernel é compartilhado, o overhead é virtualmente nulo e a inicialização ocorre na velocidade de criação de um processo nativo.

⚠️ 7. Onde "quebra" em produção? (Falhas Reais & Armadilhas)
  • Tratar Container como Servidor Físico (Pet vs Cattle): Acessar o container via docker exec, instalar pacotes na mão e alterar configurações sem recriar a imagem. Qualquer restart ou rescheduling destrói essas alterações, pois a camada do container é efêmera.
  • Falsa Sensação de Segurança (Container não é Sandbox Estrita): Containers compartilham o mesmo kernel do host. Um container executando como root (UID 0) sem User Namespace ativado, se explorar uma vulnerabilidade no kernel ou montar o Docker socket, obtém controle irrestrito do host.
  • Expectativa de que Container Resolva Falhas de Arquitetura: Containerizar um monolito com vazamentos graves de memória ou locks transacionais apenas resulta em um monolito problemático rodando empacotado.

Síntese de Fixação: A Morte do 'Na Minha Máquina Funciona'

O Problema das Dependências Implícitas

Antes dos contêineres, uma aplicação dependia de versões específicas de bibliotecas C (glibc), variáveis de ambiente do SO, pacotes instalados e permissões locais não documentadas.

Contêiner vs Máquina Virtual (VM)

VMs virtualizam o hardware físico (hipervisor + kernel de SO convidado completo = gigabytes e minutos para subir). Contêineres compartilham o kernel do hospedeiro, isolando apenas processos = megabytes e milissegundos para subir.

Reprodutibilidade Hermética

O contêiner empacota o código + runtime + dependências do SO em uma imagem imutável. O mesmo artefato binário exato roda no laptop do desenvolvedor, na esteira de CI e no cluster de produção.

⚠️
Achar que Contêiner é uma 'VM Leve':

Contêiner NÃO é uma máquina virtual! Um contêiner é apenas um processo Linux comum rodando no kernel da máquina hospedeira com visibilidade restrita por namespaces e limites de recursos por cgroups. Se o kernel entrar em pânico, todos os contêineres caem juntos.

💡
Modelo Mental de Decisão Técnica:

Pense em imagens de contêiner como um arquivo .tar.gz contendo uma raiz de sistema de arquivos Linux + metadados de execução (qual comando rodar e variáveis de ambiente).

Namespaces e cgroups: o isolamento por dentro

essencialmecanismo
💻 INCIDENTE REAL DE PRODUÇÃO

Uma aplicação Node.js com vazamento de memória (memory leak) rodava em container sem limitação de recursos no host compartilhado. O processo consumiu 31 GB dos 32 GB de RAM física da máquina, forçando o OOM Killer do Linux do host a derrubar processos vitais do sistema operacional, incluindo o daemon do Docker e o agente de monitoramento. A imposição de limites rígidos de cgroup (`--memory=2g` e cgroups v2) isolou o consumo e impediu que um único container derrubasse o servidor inteiro.

🎯 1. O que é?

Namespaces e Cgroups (Control Groups) são as duas primitivas fundamentais do kernel Linux sobre as quais todos os containers modernos são construídos. Namespaces determinam o que o processo enxerga (quais outros processos, quais interfaces de rede, quais pontos de montagem e quais usuários existem). Cgroups determinam o quanto de recursos ele pode consumir (limites rígidos ou flexíveis de CPU, memória RAM, I/O de disco e largura de banda).

≈

Analogia do mundo real: Como um quarto de hotel em um grande edifício. O Namespace é a fechadura e as paredes: você só enxerga a sua cama e o seu banheiro, sem ver os outros hóspedes ou o corredor. O Cgroup é o medidor e limitador de água e energia daquele quarto: garante que um hóspede tomando um banho de duas horas não esgote a água quente de todo o condomínio.

🚀 2. Para que serve?

Serve para governar e isolar a execução de múltiplos processos independentes sobre um mesmo hardware físico:

  • Isolamento de Visão (Namespaces): PID (processos), NET (placas de rede/portas), MNT (árvore de diretórios), IPC (memória compartilhada), UTS (hostname) e USER (mapeamento de UID/GID).
  • Controle de Recursos (Cgroups): Estabelece limites estritos de memória para evitar que um processo com vazamento derrube outros serviços (OOM - Out of Memory).
  • Limite e disputa por CPU: cgroups permitem configurar quotas e pesos; o scheduler distribui tempo de CPU conforme política e carga do host. Isso não garante latência ou justiça perfeita entre containers; monitore throttling, requests/limits e contenção.

💎 4. Porque importa?

Os namespaces foram introduzidos gradualmente no kernel a partir de 2002. Os cgroups foram criados por engenheiros do Google em 2007 para viabilizar sua infraestrutura interna Borg. Entender ambos explica por que o container tem PID 1 (e por que o sinal SIGTERM exige cuidado), por que portas precisam ser mapeadas e como a JVM calcula o tamanho da Heap.

Veio substituir: O antigo chroot (que isolava apenas a raiz do sistema de arquivos e era facilmente contornado por ataques) e máquinas virtuais pesadas como único meio de limitar memória.

🛠️ 3. Como usar / Como aplicar?

Comandos práticos para definir cotas de cgroup e inspecionar os limites no host Linux:

# Limitar container a 512MB de RAM e 1.5 núcleos de CPU
docker run -d --name api-limitada \
  --memory=512m \
  --cpus=1.5 \
  minha-app:v1

# Inspecionar o namespace isolado de dentro do container
docker run --rm -it alpine sh -c 'ps aux'     # Vê apenas seus próprios processos
docker run --rm -it alpine sh -c 'ip addr'    # Possui sua própria interface eth0

# Inspecionar os limites de cgroup v2 aplicados pelo kernel no host
cat /sys/fs/cgroup/system.slice/docker-*.scope/memory.max
⚙️ 5. Como funciona por baixo dos panos? (A JVM e os Cgroups)

Historicamente (Java 8 antes do update 131), a JVM consultava as syscalls tradicionais do Linux (como sysconf(_SC_PHYS_PAGES)) para descobrir a quantidade de RAM disponível. No container com limite de 512MB em um host com 64GB, a JVM acreditava ter 64GB e configurava a Heap inicial em 16GB. Quando o app alocava mais de 512MB, o subsistema de Cgroups acionava o OOM Killer do kernel, que enviava um SIGKILL brutal, matando o container sem gerar log ou stack trace.

Nas JVMs modernas (Java 17 e 21+), a JVM detecta automaticamente os limites de Cgroup v1 e v2 (via flag -XX:+UseContainerSupport, ativada por padrão) e dimensiona a Heap em relação à cota do container, respeitando -XX:MaxRAMPercentage.

☕ 6. Exemplo de dimensionamento correto de memória para JVM em container
CÓDIGO & PRÁTICA

Configuração de flags para garantir que a memória total (Heap + Metaspace + Threads + Buffers nativos) não estoure o cgroup:

# Dockerfile da aplicação Spring Boot
FROM eclipse-temurin:21-jre-alpine

ENV JAVA_OPTS="-XX:MaxRAMPercentage=75.0 \
               -XX:InitialRAMPercentage=50.0 \
               -XX:+ExitOnOutOfMemoryError"

ENTRYPOINT ["sh", "-c", "exec java $JAVA_OPTS -jar /app.jar"]
⚠️ 7. Onde "quebra" em produção? (Falhas Reais & Armadilhas)
  • Container sem Limite de Memória Definido: O container consumirá memória indefinidamente. Em caso de vazamento, o kernel acionará o OOM Killer contra outros processos do host, podendo derrubar daemons essenciais (como o próprio Kubelet ou Docker daemon).
  • PID 1 e o Encerramento Gracioso Travado (Graceful Shutdown): O processo com PID 1 possui tratamento especial no Linux: se ele não registrar um tratador explícito para SIGTERM, o kernel ignora o sinal. O docker stop aguarda 10 segundos de timeout e emite um SIGKILL forçado, corrompendo transações em andamento.
  • Heap Dimensionada em 100% da Cota do Container: Esquecer que a JVM consome memória nativa fora da Heap (Metaspace, CodeCache, threads stacks e buffers NIO). Definir Heap de 512MB em um container de 512MB causa OOMKilled imediato assim que a aplicação sobe conexões de rede.

Síntese de Fixação: Namespaces e cgroups (A Mágica Por Baixo do Capô)

Linux Namespaces (O Que Eu Posso Enxergar)

Isole a visão do processo: PID (o processo acha que é o PID 1), NET (sua própria interface eth0 e tabela de roteamento), MNT (seu próprio sistema de arquivos raiz), IPC, UTS (hostname) e USER.

Control Groups - cgroups (O Quanto Eu Posso Usar)

Regula o consumo de recursos físicos: limites de CPU (shares e quotas), memória RAM (evita que um contêiner monopolize a máquina) e I/O de disco.

chroot e Pivot Root

Troca o diretório raiz / do processo para a pasta onde os arquivos da imagem foram descompactados, impedindo que o processo acesse o sistema de arquivos do host.

⚠️
O OOM Killer (Out Of Memory) do Kernel:

Se o processo dentro do contêiner exceder o limite de memória definido no cgroup (ex: --memory 512m), o kernel do Linux invoca o OOM Killer e mata o processo instantaneamente com Exit Code 137 (SIGKILL).

💡
Modelo Mental de Decisão Técnica:

Contêiner não é uma tecnologia mágica nova: é a combinação elegante de 3 recursos do kernel Linux criados nos anos 2000: Namespaces + cgroups + chroot/OverlayFS.

Imagem e container: molde e instância

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Um desenvolvedor salvou arquivos de configuração e certificados TLS diretamente dentro do container em execução (`docker exec`) sem alterar a imagem base nem usar volumes. Duas semanas depois, após uma reinicialização de segurança do host, o container antigo foi recriado a partir da imagem original e todas as alterações manuais sumiram, tirando a autenticação do ar por 3 horas. O time aprendeu que imagens são moldes imutáveis e que o ciclo de vida de containers exige configuração declarativa externa.

🎯 1. O que é?

A Imagem é o molde estático, imutável e de leitura exclusiva (read-only), identificado criptograficamente por um hash SHA-256 do seu conteúdo. O Container é uma instância isolada em execução desse molde, com uma fina camada gravável (writable layer) empilhada no topo, cujo ciclo de vida está acoplado ao ciclo do próprio container.

≈

Analogia do mundo real: Como Classe e Objeto na orientação a objetos. A Imagem é a classe: existe apenas uma definição no disco, compilada e imutável. O Container é a instância (o objeto em memória): você instancia centenas de objetos a partir da mesma classe. Cada objeto tem seu estado volátil em execução, e quando ele é descartado pelo Garbage Collector, seus dados em memória somem.

🚀 2. Para que serve?

Serve para desacoplar a definição imutável da infraestrutura do seu estado em tempo de execução:

  • Conteúdo Endereçável (Content-Addressable): Como imagens são puramente hashes de camadas imutáveis, provedores e nós fazem cache agressivo sem risco de conflito.
  • Escalabilidade Horizontal Instantânea: Uma única imagem de 200MB pode alimentar 50 réplicas ativas no host ocupando apenas a RAM de execução e uma finíssima camada de escrita temporária.
  • Auditoria e Rastreabilidade: Permite comprovar que a versão que passou na esteira de segurança é com exatidão matemática a mesma implantada em produção.

💎 4. Porque importa?

A imutabilidade da imagem extinguiu o conceito de "servidor que apodrece com o tempo" (Configuration Drift), em que administradores instalavam patches pontuais diretamente na máquina até ninguém mais saber como replicar o ambiente do zero.

Veio substituir: Servidores mutáveis tratados como animais de estimação ("pets"), substituídos por instâncias descartáveis e idênticas de gado ("cattle").

🛠️ 3. Como usar / Como aplicar?

Comandos essenciais para inspecionar imagens (moldes) e containers (instâncias):

# Listar os moldes imutáveis locais
docker images

# Listar instâncias em execução e finalizadas
docker ps -a

# Prova da efemeridade da camada gravável do container:
docker run --rm -it alpine sh -c 'echo "dado volátil" > /tmp/teste.txt; cat /tmp/teste.txt'
docker run --rm -it alpine sh -c 'cat /tmp/teste.txt'
# Retorno: cat: can't open '/tmp/teste.txt': No such file or directory
⚙️ 5. Como funciona por baixo dos panos? (Copy-on-Write)

O Docker utiliza drivers de armazenamento como o OverlayFS (ou Overlay2). O sistema de arquivos do container é composto por:

  1. LowerDir (Camadas da Imagem): Uma série de diretórios somente leitura empilhados.
  2. UpperDir (Camada do Container): Um diretório gravável no disco do host (localizado sob /var/lib/docker/overlay2/).
  3. MergedDir (Visão Unificada): A união que o container enxerga. Quando a aplicação tenta modificar um arquivo existente na imagem, o OverlayFS realiza um Copy-on-Write (CoW): copia o arquivo original da camada inferior para o upperdir e aplica a modificação lá. O arquivo original permanece intocado. Ao remover o container (docker rm), o diretório upperdir é apagado.
☕ 6. Exemplo de persistência correta vs camada volátil do container
CÓDIGO & PRÁTICA

Para dados que precisam sobreviver ao container (como logs ou uploads), utiliza-se montagem de volumes externos:

# Criar volume gerenciado fora da camada do container
docker volume create dados-pedidos

# Montar o volume no container da aplicação Spring Boot
docker run -d --name order-service \
  -v dados-pedidos:/app/storage \
  -p 8080:8080 \

⚠️ 7. Onde "quebra" em produção? (Falhas Reais & Armadilhas)
  • Armazenar Banco de Dados ou Uploads na Camada do Container: Todo dado escrito no sistema de arquivos padrão do container morre no momento em que ele é recriado em um deploy. Além disso, o driver OverlayFS tem performance de I/O muito inferior ao disco bruto.
  • Usar docker commit para Gerar Imagens em Produção: Gerar imagens a partir de containers alterados manualmente cria caixas-pretas impossíveis de auditar, rastrear no Git ou reproduzir na esteira de CI. Imagens devem ser construídas estritamente via Dockerfile versionado.
  • Confundir docker stop com docker rm: Parar o container preserva sua camada de escrita no disco. Em servidores com alto turnover de containers sem flag --rm, o disco do host é gradualmente lotado por containers mortos.

Síntese de Fixação: Imagem vs Contêiner (Molde e Instância)

Imagem (Classe / Molde Imutável)

Conjunto estático de camadas somente-leitura (Read-Only Layers) empacotadas com metadados. Não gasta CPU, vive no disco ou no registry.

Contêiner (Objeto / Instância Viva)

Uma imagem em execução. O Docker acopla uma fina camada de escrita (Read-Write Container Layer) no topo das camadas somente-leitura e inicia o processo.

Copy-on-Write (CoW)

Se 10 contêineres rodarem a partir da mesma imagem de 500MB, eles compartilham os mesmos 500MB no disco! O contêiner só aloca espaço extra se modificar algum arquivo existente.

⚠️
Persistir Dados na Camada de Escrita do Contêiner:

Gravar dados do banco de dados na camada Read-Write efêmera do contêiner é fatal: quando o contêiner for recriado ou atualizado com uma nova imagem (docker rm e docker run), todos os dados gravados são apagados para sempre!

💡
Modelo Mental de Decisão Técnica:

Trate contêineres como gado (Cattle), não como animais de estimação (Pets). Eles devem poder ser destruídos e recriados a qualquer segundo sem perda de dados ou dor emocional.

O que é o mecanismo Copy-on-Write (CoW) utilizado pelo Docker e qual sua grande vantagem?

Dica: Pense no compartilhamento de camadas somente-leitura entre múltiplos contêineres →

Docker, containerd e a OCI: quem faz o quê

aprofundamento
💻 INCIDENTE REAL DE PRODUÇÃO

Durante uma atualização do Docker Daemon em um servidor crítico, o serviço `dockerd` foi reiniciado e todas as 40 aplicações em produção caíram simultaneamente porque a flag `live-restore` estava desativada. A separação moderna entre o daemon Docker e o runtime desacoplado `containerd` com especificação OCI permite que os containers continuem executando sem interrupção mesmo se o daemon de gerenciamento superior for reiniciado ou atualizado.

🎯 1. O que é?

O ecossistema contemporâneo de containers é modular e dividido em especificações abertas governadas pela OCI (Open Container Initiative). O "Docker" deixou de ser um monolito: o Docker CLI é a interface com o usuário; o Docker Daemon (dockerd) gerencia a API REST e a rede de alto nível; o containerd supervisiona o ciclo de vida dos containers e o download das imagens; e o runc é o runtime de baixo nível que efetivamente interage com o kernel Linux para criar os namespaces e cgroups.

≈

Analogia do mundo real: Como pedir uma refeição via aplicativo de entrega. Você usa o app no celular (o CLI), que envia o pedido para a central da empresa (o daemon). A central despacha para a cozinha do restaurante (o containerd), que comanda o cozinheiro na chapa (o runc) para preparar a comida. Você interage apenas com o aplicativo, mas quem cozinha é o cozinheiro — e é por isso que o restaurante consegue trocar a central de entrega sem trocar a frigideira.

🚀 2. Para que serve?

Serve para assegurar interoperabilidade universal e independência de fornecedor:

  • Padronização OCI: Define especificações imutáveis para Formato de Imagem (Image Spec) e Formato de Runtime (Runtime Spec).
  • Portabilidade Irrestrita: Uma imagem construída pelo Docker CLI roda de forma idêntica no Kubernetes, Podman, containerd, AWS ECS ou Google Cloud Run.
  • Runtimes Especializados: Permite substituir o runc padrão por runtimes seguros baseados em micro-VMs (como Kata Containers ou gVisor) sem alterar a imagem da aplicação.

💎 4. Porque importa?

O Kubernetes removeu o dockershim na versão 1.24 e passou a integrar runtimes de nó por meio da CRI (Container Runtime Interface), como containerd e CRI-O. Isso mudou a integração entre o kubelet e o runtime; não significa que imagens criadas com Docker deixaram de funcionar. O formato e a compatibilidade dependem da imagem e do runtime usados.

Veio substituir: a integração mantida pelo Kubernetes especificamente para o Docker Engine como runtime de nó. A remoção não foi uma promessa de ganho fixo de CPU ou memória; simplificou a manutenção da interface de runtime.

⚙️ 5. Como funciona por baixo dos panos? (A Cadeia de Execução)

O fluxo de execução detalhado desde o comando do desenvolvedor até o processo no kernel:

  1. docker run: O CLI empacota a instrução em JSON e envia via socket Unix (/var/run/docker.sock) para o dockerd.
  2. dockerd: Processa autenticação, aloca IP no bridge de rede e repassa a criação do container para o containerd via gRPC.
  3. containerd: Puxa a imagem do registry se necessário, descompacta as camadas OverlayFS e invoca o runc.
  4. runc: Cria os cgroups, executa clone() com os namespaces definidos na OCI Runtime Spec e entrega o controle ao containerd-shim.
  5. containerd-shim: Permanece rodando como pai do processo para coletar stdout/stderr e status de saída, permitindo reiniciar o containerd/dockerd sem derrubar o container ativo!

Camadas: por que a ordem do Dockerfile importa tanto

essencialo pulo do gato
💻 INCIDENTE REAL DE PRODUÇÃO

Um Dockerfile colocava a instrução `COPY . .` antes do comando de instalação de dependências. Como qualquer alteração em arquivos de código ou documentação invalidava o cache da camada no início do arquivo, cada build no pipeline de CI baixava 800 MB de pacotes da internet do zero, demorando 18 minutos por commit. A reordenação copiando apenas os manifestos de dependência antes da compilação reduziu o tempo de build do CI de 18 minutos para 45 segundos por reuso de cache.

🎯 1. O que é?

Cada instrução modificadora em um Dockerfile (como RUN, COPY e ADD) gera uma camada intermediária imutável, indexada criptograficamente por um hash SHA-256 de seu conteúdo. Durante o docker build, a engine verifica se os arquivos ou comandos daquela instrução (e de todas as instruções antecedentes) sofreram alteração: se nada mudou, ela reaproveita a camada do cache local instantaneamente. Se um único byte mudar, aquela camada e todas as camadas subsequentes são invalidadas e reconstruídas do zero.

≈

Analogia do mundo real: Como uma pilha de lâminas de transparência para retroprojetor. Cada transparência adiciona um desenho ou camada de texto sobre a anterior. Se você precisa alterar a lâmina do meio, todas as lâminas que ficam por cima dela precisam ser redesenhadas e alinhadas novamente. Se você colocar a lâmina que muda todo dia (o código Java) na base da pilha, você será forçado a redesenhar todas as transparências (baixar todas as dependências do Maven) todos os dias.

🚀 2. Para que serve?

Serve para maximizar a reutilização e minimizar o tempo de ciclo da esteira de engenharia:

  • Aceleração de Builds no CI/CD: Transforma compilações diárias que levariam 5 minutos baixando JARs repetidos em builds cirúrgicos de 20 segundos.
  • Deduplicação de Armazenamento: Dez imagens distintas baseadas em eclipse-temurin:21-jre compartilham as mesmas camadas da JRE no disco do host, sem duplicar espaço.
  • Transferência de Rede Fracionada: Ao subir uma tag nova para o registry, apenas a camada modificada (alguns megabytes do seu JAR) é transferida pela rede.

💎 4. Porque importa?

O sistema de arquivos em camadas (derivado de Union Filesystems como OverlayFS) viabilizou a distribuição de software em escala planetária. Sem ele, cada deploy exigiria o upload e download de imagens monolíticas de centenas de megabytes ou gigabytes.

Veio substituir: Imagens monolíticas completas de VM (VMDK/OVA/VHD) que precisavam ser copiadas integralmente a cada pequena alteração de código.

🛠️ 3. Como usar / Como aplicar? (A Ordem de Ouro do Cache)

⚙️ 5. Como funciona por baixo dos panos? (A Regra da Não-Diminuição)

Uma camada no Docker nunca diminui de tamanho. Se você executar RUN apt-get update && apt-get install -y build-essential em uma instrução e depois executar RUN apt-get remove -y build-essential && rm -rf /var/lib/apt/lists/* na linha seguinte:

  • A primeira camada grava os 300MB de arquivos no disco e gera um hash SHA-256 imutável.
  • A segunda camada apenas grava marcadores especiais chamados whiteout files no OverlayFS que escondem os arquivos da visão do container, mas os 300MB continuam fisicamente armazenados na primeira camada da imagem final!
  • Conclusão: toda operação de instalação, compilação temporária e limpeza de lixo DEVE acontecer dentro do mesmo bloco RUN concatenado com &&. Da mesma forma, se você copiar uma chave de API secreta em uma camada e apagá-la na seguinte, o segredo continua intacto e facilmente recuperável no histórico da imagem!

Cada Instrução é uma Camada

Comandos RUN, COPY e ADD geram novas camadas somente-leitura. O Docker calcula o hash de cada instrução para reaproveitar em cache.

Multi-stage: construir num lugar, entregar em outro

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Uma aplicação Go foi compilada em um Dockerfile de estágio único usando a imagem oficial `golang:1.22`. A imagem final entregue em produção tinha 1.2 GB e continha o compilador Go, git, compiladores C e o código-fonte inteiro da aplicação, sendo reprovada em auditoria de segurança com 84 vulnerabilidades críticas (CVEs). A refatoração para multi-stage build compilou no estágio `builder` e copiou apenas o binário compilado estático para uma imagem final `distroless` de 28 MB, zerando as vulnerabilidades.

🎯 1. O que é?

O padrão Multi-stage Build permite utilizar múltiplas instruções FROM em um mesmo Dockerfile. Cada FROM inicia um estágio isolado com uma imagem base própria. Você pode compilar e testar o código em um estágio pesado (contendo JDK completo, Maven, Gradle, compiladores C e ferramentas de análise estática) e, em seguida, copiar estritamente o artefato final compilado (o arquivo .jar) para uma imagem final enxuta contendo apenas a JRE mínima necessária para a execução.

≈

Analogia do mundo real: Como uma marcenaria e a sala de estar da sua casa. Serras elétricas, lixadeiras, pregos, formões e montanhas de serragem são indispensáveis para esculpir uma mesa de jantar de madeira maciça. Porém, ninguém coloca a marcenaria inteira dentro da sala de estar: você entrega apenas a mesa pronta, limpa e polida. Entregar uma imagem contendo JDK e Maven em produção é o equivalente a entregar a mesa cercada de ferramentas perigosas e serragem.

🚀 2. Para que serve?

Serve para gerar imagens de produção de altíssima eficiência e segurança defensiva:

  • Redução Drástica de Tamanho: Reduz imagens Java de ~850MB (com JDK e repositório Maven) para ~180MB (JRE Alpine/Distroless).
  • Superfície de Ataque Mínima: A imagem final não contém ferramentas de compilação, compiladores, nem código-fonte original.
  • Pull Rápido no Kubernetes: Durante eventos de autoscaling (HPA), nós do cluster baixam e iniciam a aplicação em frações de segundo.

💎 4. Porque importa?

Antes de 2017, utilizava-se o "Builder Pattern" com dois Dockerfiles separados e scripts Bash amarrando o fluxo — um processo frágil e propenso a erros. O Multi-stage Build tornou a construção atômica, reprodutível e nativa na engine Docker.

Veio substituir: Imagens gigantescas repletas de código-fonte e compiladores levadas indevidamente para servidores de produção.

⚙️ 5. Como funciona por baixo dos panos? (Segurança Defensiva)

A grande vantagem do Multi-stage Build vai muito além da economia de banda: o ganho real e decisivo é de Segurança Ofensiva e Defensiva:

  1. Se um atacante explorar uma falha de RCE (Remote Code Execution, como Log4Shell) dentro do container, sua primeira ação automatizada é tentar baixar um script ou compilar um exploit localmente.
  2. Na imagem final de multi-stage, não existem compiladores (javac, gcc), não existe Maven, nem gerenciadores de pacotes como apt ou apk. O invasor se depara com um ambiente estéril sem utilitários para pivotar ou escalar privilégios.
  3. Além disso, scanners de vulnerabilidades (Trivy, Grype, Snyk) analisam as bibliotecas do sistema operacional da imagem: eliminar ferramentas desnecessárias do SO elimina centenas de alertas falsos-positivos de CVEs.

ENTRYPOINT, CMD e o processo PID 1

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Um container Java iniciava a JVM através de um script shell wrapping (`CMD ["/start.sh"]`) sem usar `exec java -jar app.jar`. Como o shell `/bin/sh` assumiu o PID 1 e não repassava sinais POSIX, quando o orquestrador enviou `SIGTERM` para encerramento gracioso, o processo Java não recebeu o sinal e continuou rodando até sofrer `SIGKILL` após 30 segundos, corrompendo 140 transações bancárias em voo. O uso de `exec "$@"` no script garantiu que o Java assumisse o PID 1 e tratasse o desligamento gracioso.

🎯 1. O que é?

O ENTRYPOINT define o executável imutável do container, enquanto o CMD define os argumentos padrão repassados a esse executável (que podem ser livremente sobrescritos ao rodar o container). O processo principal iniciado torna-se o PID 1 (Process ID 1) dentro do namespace de processos do container, assumindo um papel singular no kernel Linux quanto à propagação de sinais de término (como SIGTERM e SIGKILL).

≈

Analogia do mundo real: Como uma televisão e o controle remoto. O ENTRYPOINT é o televisor físico: ele sempre liga a tela e o circuito de áudio. O CMD é o canal pré-configurado de fábrica em que ela liga por padrão. Você pode facilmente usar o controle remoto (argumentos de linha de comando no docker run) para mudar para outro canal, sem precisar abrir a carcaça da TV nem trocar de aparelho.

🚀 2. Para que serve?

Serve para definir com precisão o contrato de inicialização e desligamento da aplicação:

  • Flexibilidade Operacional: Permite imagens especializadas (ex: CLI do PostgreSQL) em que o ENTRYPOINT é psql e o usuário apenas passa os argumentos de conexão.
  • Encerramento Gracioso (Graceful Shutdown): Garante que o processo da JVM receba o sinal SIGTERM do Docker e do Kubernetes para concluir transações em andamento antes de desligar.
  • Eliminação de Zumbis: O PID 1 tem o dever de adotar e fazer o reap (coleta de status de saída) de processos filhos órfãos.

💎 4. Porque importa?

A maior causa de desligamentos forçados (com timeout de 10s no Docker e 30s no K8s) e corrupção de dados é a confusão entre a Forma Shell e a Forma Exec. Usar a forma shell faz o Linux subir um /bin/sh como PID 1, que descarta sinais e impede que o Spring Boot realize o shutdown gracioso.

Veio substituir: Antigos scripts de inicialização que precisavam de armadilhas manuais (trap) complexas para repassar sinais do sistema operacional.

⚡ Ponte de Arquitetura: Ciclo de vida do PID 1, Sinais POSIX e Graceful Shutdown

Quando o Kubernetes encerra um Pod (durante um rollout ou scale-down), ele envia um SIGTERM e aguarda terminationGracePeriodSeconds (padrão: 30s) antes de desferir um impiedoso SIGKILL.

Com a forma shell (ENTRYPOINT java -jar ...), o /bin/sh vira PID 1 e descarta o sinal. O Spring Boot com server.shutdown=graceful nunca recebe o aviso: requisições HTTP ativas são abortadas no meio do processamento de pagamento e mensagens do RabbitMQ/Kafka em voo são interrompidas sem confirmação (ack), gerando inconsistências no banco.

Para fechar a cadeia de confiabilidade: 1) Use sempre a forma exec JSON ou um gerenciador como tini / dumb-init; 2) No Spring, configure spring.lifecycle.timeout-per-shutdown-phase=20s (sempre menor que o grace period do K8s); 3) Implemente probes de readiness que param de receber tráfego antes de o processo drenar.

🛠️ 3. Como usar / Como aplicar? (Forma Exec vs Forma Shell)

Sempre utilize a Forma Exec com colchetes JSON:

Forma Shell — Sinais Perdidos & Kill Forçado
# ERRADO: Forma Shell
ENTRYPOINT java -jar /app/app.jar

# Por baixo dos panos vira:
# /bin/sh -c "java -jar /app/app.jar"
# PID 1 = /bin/sh (que NÃO repassa SIGTERM!)
# java é PID 2.
# -> docker stop espera 10s
# -> kernel envia SIGKILL brutal
Forma Exec — Sinais Entregues & Shutdown Gracioso
# CORRETO: Forma Exec (Array JSON)

# A JVM executa diretamente como PID 1!
# Recebe SIGTERM imediatamente
# Spring fecha conexões de banco e drena HTTP
# -> docker stop encerra em 2s sem perda
⚙️ 5. Como funciona por baixo dos panos? (Tini e Processos Zumbis)

O kernel Linux trata o PID 1 com uma regra especial de segurança: ao contrário dos demais processos, o PID 1 não possui manipuladores de sinal padrão. Se ele não instalar um tratador de sinal explícito, o kernel simplesmente ignora SIGINT e SIGTERM.

Se você precisar executar um script shell preliminar de inicialização (entrypoint.sh), você DEVE finalizar o script com a instrução exec:

#!/bin/sh
# Executa preparações preliminares...
echo "Iniciando aplicação..."

# O comando exec SUBSTITUI o processo do shell pelo processo Java mantendo o PID 1!
exec java -jar /app/app.jar

Caso sua aplicação gere subprocessos filhos que possam ficar órfãos (zumbis), utilize o init leve Tini (embutido no Docker via flag docker run --init ou no Dockerfile).

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

🎯 1. O que é?

Uma imagem de container de nível de produção deve aderir ao princípio do Menor Privilégio e Mínima Superfície de Ataque. Isso significa conter exclusivamente os binários estritamente necessários para executar o processo da aplicação — sem gerenciadores de pacotes (apt/apk), sem compiladores, sem shells de comando desnecessários, sem segredos ou credenciais embutidas e executando sob um usuário sem privilégios (non-root).

Serve para proteger a infraestrutura contra explorações maliciosas e otimizar a operação:

  • Conformidade de Segurança (Hardening): Aprovação imediata em esteiras de varredura estática de segurança (SAST/Container Scanning) da organização.
  • Impedimento de Escalação de Privilégios: Um container comprometido que roda sob usuário comum (UID 1000) não consegue alterar arquivos do sistema do host.
  • Velocidade Extrema de Deploy: Imagens de 100MB são baixadas simultaneamente por dezenas de nós em segundos, viabilizando autoscaling ágil.

💎 4. Porque importa?

Historicamente, imagens baseadas em distros completas (como Ubuntu completo de 1GB) vinham abarrotadas de utilitários como curl, netcat, wget, editores e compiladores. Quando um app era invadido, o invasor tinha todas as armas prontas para fazer download de malwares e escanear a rede interna.

Veio substituir: Imagens gigantescas e inseguras derivadas de distribuições generalistas com dezenas de CVEs conhecidas.

⚙️ 5. Como funciona por baixo dos panos? (Distroless)

As imagens Distroless (mantidas pelo Google) levam o isolamento ao limite extremo: elas contêm estritamente a aplicação e suas dependências de runtime (como a glibc e a JVM). Não contêm gerenciadores de pacotes, nem shells (como /bin/sh ou /bin/bash).

Se um invasor conseguir injeção de comandos dentro do app, a syscall execve("/bin/sh") falha com ENOENT (No such file or directory), neutralizando o ataque imediatamente.

Registry, tags e a promoção da imagem

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Uma equipe utilizava a tag `:latest` em seu manifesto de deploy no Kubernetes. Um desenvolvedor subiu uma versão com bug acidentalmente sob a tag `:latest` no registry durante a madrugada. Na manhã seguinte, após um Pod reiniciar e executar o `imagePullPolicy: Always`, a versão quebrada foi puxada para produção sem passar pela esteira de QA, gerando 1h30 de indisponibilidade. A adoção de tags imutáveis com hash SHA-256 e versão semântica (`v1.4.2@sha256:...`) garantiu reprodutibilidade estrita.

🎯 1. O que é?

O Registry (como Docker Hub, AWS ECR, GCP Artifact Registry ou Harbor) é o repositório centralizado de armazenamento e distribuição de imagens de containers. A Tag (como :1.4.2 ou :prod) é apenas um ponteiro móvel e mutável que referencia uma versão. O Digest (como @sha256:3f9c...) é a identidade criptográfica imutável do manifesto da imagem.

≈

Analogia do mundo real: Como o número do chassi de um automóvel versus o ano do modelo. "Civic 2026" é a Tag: um rótulo comercial legível que pode sofrer alterações de lote. O número do chassi gravado a laser no metal é o Digest: identifica de forma física, inviolável e definitiva aquela exata unidade. Ao registrar um sinistro ou recall na seguradora, você utiliza o chassi — nunca apenas o nome do modelo.

🚀 2. Para que serve?

Serve para governar a distribuição e a progressão segura de artefatos entre ambientes:

  • Esteira de Promoção Contínua: A mesmíssima imagem testada e aprovada em QA/Staging progride para Produção sem sofrer recompilação.
  • Rollback Determinístico: Se a versão 1.4.2 apresentar anomalias, retornar para a 1.4.1 é instantâneo porque o digest anterior está intacto no registry.
  • Controle de Acesso e Assinatura Digital: Registries corporativos integram-se ao IAM e exigem assinaturas digitais (Cosign / Sigstore) para autorizar a execução no cluster.

💎 4. Porque importa?

A regra de ouro que previne os incidentes mais catastróficos de deploy: construa a imagem uma única vez no pipeline de CI e promova exatamente esse artefato binário por todos os ambientes. Reconstruir a imagem para produção significa que o artefato testado em homologação não é o que subiu em produção (uma dependência transitiva pode ter atualizado silenciosamente).

Veio substituir: Artefatos distribuídos por servidores FTP ou compartilhamentos de rede desprovidos de garantia de integridade e proveniência.

🛠️ 3. Como usar / Como aplicar?

Comandos padronizados para etiquetagem, publicação e promoção segura de imagens:

             -t registry.empresa.com/order-service:${COMMIT_SHA} .

# 2. Promover para produção: retaguear a MESMA imagem sem fazer rebuild
docker pull registry.empresa.com/order-service:1.4.2

# 3. No manifesto de produção do Kubernetes, use o Digest para garantir imutabilidade:
# image: registry.empresa.com/order-service@sha256:7f8e87b...
⚙️ 5. Como funciona por baixo dos panos? (Image Manifest)

No protocolo OCI Distribution Spec, uma imagem não é um arquivo único, mas um Manifest JSON que aponta para uma lista de camadas (blobs) com seus respectivos hashes e o arquivo de configuração da imagem:

{
  "schemaVersion": 2,
  "mediaType": "application/vnd.docker.distribution.manifest.v2+json",
  "config": {
    "digest": "sha256:a1b2c3d...",
    "size": 7023
  },
  "layers": [
    { "digest": "sha256:e3b0c44...", "size": 28144000 },
    { "digest": "sha256:4f53cda...", "size": 18500200 }
  ]
}

O Digest da imagem é o SHA-256 desse documento Manifest inteiro. Ao referenciar pelo Digest, é matematicamente impossível alguém adulterar qualquer camada sem alterar o digest.

docker run e o ciclo de vida do container

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Um container de produção executando um gateway de pagamento caiu silenciosamente às 3h da manhã devido a uma exceção não capturada. Como o comando havia sido iniciado sem política de reinicialização (`--restart unless-stopped` ou `--restart on-failure:5`), o container permaneceu em estado `Exited (1)` por 5 horas até o primeiro operador acordar. A definição de políticas explícitas de restart no Docker garantiu a autorrecuperação imediata de processos com falha efêmera.

🎯 1. O que é?

O comando docker run é um atalho de alto nível que encapsula três operações distintas em um único comando atômico: 1) Executa o download da imagem do registry se ela não existir localmente (docker pull); 2) Cria uma instância de container alocando namespaces, cgroups e a camada gravável de Copy-on-Write (docker create); 3) Inicia o processo principal configurado no ENTRYPOINT/CMD dentro da jaula isolada (docker start). Compreender essa separação em três fases é a chave para resolver 90% dos comportamentos inesperados.

≈

Analogia do mundo real: Como alugar um veículo em uma locadora. 1) Buscar o modelo desejado no depósito central (o pull da imagem); 2) Assinar o contrato e receber as chaves de um carro específico no pátio com placa atribuída (o create da instância); 3) Girar a ignição e sair acelerando pela rua (o start do processo). Tudo acontece em sequência no balcão, mas se o carro não ligar, você precisa saber se faltava combustível na fábrica ou se a bateria arriou na partida.

🚀 2. Para que serve?

Serve para inicializar, parametrizar e conectar instâncias de containers sob demanda no terminal:

  • Provisionamento Imediato: Subir instâncias prontas de bancos de dados relacionais, brokers de mensageria e caches em milissegundos sem instalador local.
  • Mapeamento de Portas e Redes: Expor serviços do container para portas específicas da máquina hospedeira.

⚙️ 5. Como funciona por baixo dos panos? (Tempo de Vida do Processo)

O ciclo de vida de um container é estritamente vinculado ao PID 1:

  1. O container permanece no estado Running enquanto o processo definido no ENTRYPOINT/CMD estiver ativo.
  2. No instante em que o processo principal encerra sua execução (seja com retorno exit 0 de sucesso ou por uma exceção não tratada exit 1), o container transiciona imediatamente para o estado Exited.
  3. Containers não continuam "rodando no vácuo" sem um processo ativo. Se você subir um container baseado em alpine sem um processo contínuo (como um daemon ou servidor web), ele roda o comando padrão (/bin/sh sem terminal interativo) e finaliza em 2 milissegundos.

Volumes e bind mounts: onde os dados sobrevivem

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Um banco de dados PostgreSQL foi iniciado via Docker sem montar um volume gerenciado para o diretório `/var/lib/postgresql/data`. Quando o time executou `docker rm -f pg-prod` para atualizar a versão do banco, todos os dados de clientes gravados na camada de gravação efêmera (writable layer) do container foram permanentemente apagados do disco. A utilização mandatória de Named Volumes (`docker volume create pg-data`) desacoplou a persistência do ciclo de vida dos containers.

🎯 1. O que é?

Como a camada gravável de Copy-on-Write de um container é efêmera e destruída junto com ele, a persistência de dados exige desacoplamento através de montagens no kernel. Existem dois mecanismos principais: Volumes Gerenciados (diretórios criados e governados exclusivamente pela engine Docker dentro de /var/lib/docker/volumes/, imunes a exclusões acidentais) e Bind Mounts (ligações diretas que montam um caminho absoluto arbitrário do sistema de arquivos da máquina hospedeira para dentro do container).

≈

Analogia do mundo real: Como o armário do quarto de hotel versus a sua mala de viagem. O que você deixa solto na gaveta do quarto de hotel é recolhido e descartado no momento do seu check-out (a camada do container). O que você guarda na sua mala (o volume) vai com você para qualquer outro hotel no futuro. O volume gerenciado é o serviço de guarda-volumes do hotel: o hotel toma conta, controla o acesso e garante que seus pertences sobrevivem mesmo que você troque de quarto todos os dias.

🚀 2. Para que serve?

Serve para isolar o estado persistente do ciclo de vida volátil das instâncias:

  • Volumes Nomeados (Produção/Dados): Armazenar os arquivos de banco de dados (Postgres, MySQL, MongoDB) garantindo alto throughput de disco e portabilidade.
  • Bind Mounts (Desenvolvimento Ágil): Montar o diretório de código-fonte src/ no container para permitir hot-reload imediato sem reconstruir imagens.
  • Injeção Externa de Configurações: Montar arquivos de propriedades (ex: application.yml) em modo somente leitura (:ro) no startup.

💎 4. Porque importa?

Bancos de dados rodando diretamente sobre o driver OverlayFS sofrem séria degradação de desempenho em I/O randômico por conta das cópias intermediárias de blocos. Volumes contornam o OverlayFS montando blocos de disco diretamente, alcançando a velocidade nativa de I/O do hardware físico.

Veio substituir: A perda catastrófica de dados em restarts de containers e a necessidade de instalar bancos de dados diretamente no sistema operacional da máquina de desenvolvimento.

🛠️ 3. Como usar / Como aplicar? (Bind Mount vs Volume)

Comparação direta entre os dois tipos de armazenamento:

Bind Mount — Foco em Desenvolvimento

  -v $(pwd)/src:/app/src \\
  minha-app:dev

# Características:
# - Aponta para um caminho local da sua máquina
# - Excelente para hot-reloading de código
# - PÉSSIMO em produção: depende de caminhos
#   absolutos e cria problemas de permissão UID
Volume Nomeado — Foco em Dados & Produção

docker volume create pgdata
docker run -d \\
  -v pgdata:/var/lib/postgresql/data \\
  postgres:16-alpine

# Características:
# - Gerenciado exclusivamente pela engine Docker
# - Portável entre containers e ambientes
# - Suporta drivers de storage de rede (NFS/EBS)
⚙️ 5. Como funciona por baixo dos panos? (UIDs e Permissões POSIX)

O maior causador de frustração em bind mounts é o conflito de UID/GID POSIX:

  1. No Linux, arquivos pertencem a um identificador numérico (UID), não a nomes de usuário. Na sua máquina de desenvolvimento, seu usuário comum costuma ter UID=1000.
  2. Se o container executa com um usuário interno appuser cujo UID=1001, ou como postgres (UID=999), quando esse processo tenta gravar na pasta montada via bind mount, o kernel Linux verifica as permissões do sistema de arquivos do host.
  3. Como 1001 não é dono da pasta de 1000, o processo recebe o erro EACCES (Permission denied).
  4. Solução: Alinhar o UID na inicialização passando --user $(id -u):$(id -g) ou ajustar a propriedade do diretório no host com chown -R 1001:1001 ./dados.

A Efemeridade do Contêiner

O sistema de arquivos de um contêiner é descartável. Destruir o contêiner destrói todos os dados gravados nele. Para persistir estado, usamos montagens externas.

⚠️

Redes: como containers se enxergam

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Dois containers (uma API Java e um Redis) foram iniciados na rede padrão de bridge (`docker0`) sem criar uma rede customizada. A aplicação tentava conectar em `redis:6379`, mas a resolução de nomes por DNS interno falhava, pois a rede bridge padrão do Docker não oferece DNS resolution automático por nome de container. A criação de uma bridge customizada (`docker network create app-net`) ativou o DNS resolver embutido e normalizou a comunicação entre serviços.

🎯 1. O que é?

O subsistema de redes do Docker conecta containers utilizando interfaces de rede virtuais (veth pairs), bridges virtuais do Linux e regras de iptables/nftables para NAT. Containers conectados a uma mesma rede customizada (User-Defined Bridge) possuem resolução de nomes automática via DNS interno embutido na engine Docker: eles conversam entre si utilizando diretamente o nome do container ou alias de serviço, sem necessidade de IPs fixos.

≈

Analogia do mundo real: Como os ramais internos de telefonia de uma empresa. Para falar com o departamento financeiro, você simplesmente digita o ramal "financeiro" e a central telefônica interna (o DNS do Docker) comuta a ligação imediatamente. Você não precisa saber em qual mesa física ou em qual andar o atendente sentou hoje. E tentar discar "para mim mesmo" ligando para o ramal próprio conecta com você mesmo — que é exatamente o que localhost faz dentro de um container!

🚀 2. Para que serve?

Serve para isolar topologicamente e orquestrar a conectividade entre múltiplos serviços:

  • Resolução por Nome (Service Discovery): A aplicação Spring Boot conecta-se ao PostgreSQL usando jdbc:postgresql://pedidos-db:5432/pedidos, imune a trocas de IP causadas por restarts.
  • Segregação de Tráfego: Containers de pagamento ficam em uma rede isolada, enquanto a API pública reside em outra, impedindo comunicação lateral indevida.
  • Eliminação de Exposição Desnecessária: Bancos de dados e caches não precisam publicar portas no host (-p) para conversar com a aplicação que compartilha a mesma rede interna.

💎 4. Porque importa?

No início do Docker utilizava-se a flag arcaica --link, que injetava variáveis de ambiente estáticas e manipulava o arquivo /etc/hosts na inicialização. Se o container do banco reiniciasse com outro IP, a aplicação parava de funcionar até ser recriada.

Veio substituir: A flag --link, hacks manuais de /etc/hosts e a necessidade arriscada de expor todas as portas de bancos no localhost do host.

🛠️ 3. Como usar / Como aplicar?

Criação de rede customizada e conexão declarativa entre banco e aplicação:

# 1. Criar uma rede bridge isolada definida pelo usuário
docker network create orderflow-net

# 2. Subir o PostgreSQL na rede (sem precisar publicar a porta 5432 no host!)
docker run -d --name pedidos-db \\
  --network orderflow-net \\
  -e POSTGRES_PASSWORD=postgres \\
  postgres:16-alpine

# 3. Subir a aplicação Spring conectando pelo NOME do container
docker run -d --name pedidos-api \\
  --network orderflow-net \\
  -p 8080:8080 \\
  -e SPRING_DATASOURCE_URL=jdbc:postgresql://pedidos-db:5432/pedidos \\
  minha-app:v1

# 4. Prova do DNS embutido resolvendo o nome internamente
docker exec -it pedidos-api getent hosts pedidos-db
⚙️ 5. Como funciona por baixo dos panos? (O Servidor DNS 127.0.0.11)

Quando você cria uma rede customizada (docker network create):

  1. O daemon Docker cria uma bridge de rede virtual no host (ex: br-a1b2c3d...) e aloca uma sub-rede privada (ex: 172.20.0.0/16).
  2. Para cada container anexado, o Docker cria um par de interfaces virtuais (veth pair): uma ponta fica dentro do network namespace do container como eth0, e a outra ponta fica plugada na bridge virtual do host.
  3. O Docker injeta automaticamente o endereço nameserver 127.0.0.11 no arquivo /etc/resolv.conf do container.
  4. Sempre que a aplicação tenta resolver um hostname (como pedidos-db), a consulta DNS UDP na porta 53 é interceptada pelo resolver embutido do Docker daemon, que retorna o IP atualizado do container correspondente.

⚠️ 7. Onde "quebra" em produção? (Falhas Reais & Armadilhas)
  • Usar a Rede Bridge Padrão (Default Bridge): Containers que sobem sem a flag --network caem na rede bridge padrão (chamada apenas de bridge). Na rede padrão, o DNS interno por nome é DESATIVADO por razões históricas! A resolução por nome só funciona em redes criadas explicitamente por você.

  • Anotar IPs Fixos no Código da Aplicação: Fixar 172.17.0.2 nas configurações quebra a cada recriação de container, pois a alocação de IPs do Docker é dinâmica. Use estritamente hostnames.

A Rede Padrão Bridge vs Redes Customizadas

A rede 'bridge' padrão do Docker NÃO possui resolução de DNS por nome de contêiner (exige IPs frágeis ou links legados). Redes customizadas (User-Defined Bridge) fornecem DNS interno automático por nome do contêiner!

Drivers de Rede Clássicos

Bridge (padrão para comunicação entre contêineres no mesmo host), Host (remove isolamento de rede; o contêiner usa as portas da máquina diretamente), None (isolamento total sem rede) e Overlay (para clusters swarm/multi-host).

Comunicação por Nome de Serviço

Ao criar uma rede com docker network create minha-rede, a API consegue conectar no banco simplesmente usando a URL jdbc:postgresql://meu-postgres:5432/db!

⚠️
Tentar Acessar 'localhost' de Dentro do Contêiner:

Dentro do contêiner, 'localhost' aponta para o próprio contêiner (seu próprio Network Namespace)! Se sua aplicação tentar conectar no banco pelo endereço localhost:5432, a conexão falhará. Use o nome do contêiner do banco ou host.docker.internal (para acessar a máquina física).

💡
Modelo Mental de Decisão Técnica:

Nunca conecte contêineres usando endereços de IP efêmeros (ex: 172.17.0.2). Crie sempre uma rede bridge definida pelo usuário e comunique-se usando nomes DNS estáveis dos contêineres.

Configuração e segredos: o que entra por fora

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Uma chave privada de API externa foi mantida diretamente em um arquivo `.env` commitado na imagem Docker. A imagem foi enviada para o Docker Hub em repositório público por engano, e em menos de 20 minutos a credencial foi usada para consumir R$ 15.000 em créditos de serviços na nuvem. A extração de toda configuração para variáveis de ambiente injetadas em tempo de execução via `--env-file` ou Kubernetes Secrets blindou as imagens contra vazamentos de segredos.

🎯 1. O que é?

De acordo com o terceiro princípio da metodologia The Twelve-Factor App (III. Configurações), a imagem deve ser estritamente imutável e agnóstica a ambientes; tudo o que varia entre Desenvolvimento, Homologação e Produção deve ser injetado externamente em tempo de execução. No entanto, há uma fronteira crítica de segurança: Configurações comuns (perfis ativos, URLs, timeouts) são injetadas via Variáveis de Ambiente; Segredos e Credenciais (senhas de banco, certificados TLS, chaves de API) nunca devem ser passados como variáveis de ambiente em texto puro, devendo ser fornecidos via arquivos montados em memória ou cofres de segredos.

≈

Analogia do mundo real: Como um mesmo smartphone fabricado em escala global. O aparelho de hardware e o sistema operacional que sai da esteira da fábrica são exatamente idênticos para o Brasil, Japão ou Alemanha. O que muda entra externamente: o chip da operadora (SIM card) e o adaptador da tomada na caixa. Fabricar um smartphone diferente para cada cliente seria uma loucura econômica — e é o equivalente a compilar uma imagem Docker diferente para cada ambiente.

🚀 2. Para que serve?

Serve para assegurar portabilidade universal e proteção criptográfica de credenciais:

  • Reutilização Absoluta do Artefato: A mesmíssima imagem testada e aprovada pelo time de QA é promovida para produção, alterando apenas os parâmetros de injeção.
  • Prevenção de Vazamento de Segredos: Impede que senhas sejam gravadas em logs de auditoria, históricos de shell ou expostas na saída de comandos de inspeção.

⚙️ 5. Como funciona por baixo dos panos? (O Processo no Linux)

  1. Qualquer processo executando no host com privilégios suficientes para ler o /proc ou ferramentas de monitoramento/APM podem despejar todas as variáveis de ambiente em logs de auditoria.

essencialmétodo
💻 INCIDENTE REAL DE PRODUÇÃO

🎯 1. O que é?

O diagnóstico profissional de containers baseia-se em um método científico e determinístico de quatro etapas sucessivas: 1) docker ps -a para inspecionar o status e o código de saída numérico do processo; 2) docker logs para inspecionar o stdout/stderr antes do encerramento; 3) docker inspect para checar os metadados efetivamente injetados (variáveis, montagens, rede e binds); 4) docker exec para entrar na jaula e auditar o ambiente interno.

≈

Analogia do mundo real: Como diagnosticar um automóvel que não dá partida pela manhã. Primeiro você olha as luzes do painel de instrumentos para ver códigos de erro (o ps -a). E somente se nada disso esclareceu o defeito, você abre o capô com uma chave de fenda (o docker exec). Quem começa abrindo o capô sem olhar o painel perde horas substituindo peças desnecessariamente.

🚀 2. Para que serve?

Serve para identificar e erradicar a causa-raiz de falhas de inicialização em menos de 2 minutos:

  • Interpretação Imediata de Códigos de Saída: 137 (OOMKilled por estouro de memória), 143 (SIGTERM gracioso), 1 (Exceção interna do app) e 127 (Comando/binário não encontrado).
  • Detecção de Loops de Reinicialização (CrashLoopBackOff): Isolar a mensagem de falha original no primeiro restart em vez de se perder no volume de logs repetidos.
  • Diagnóstico de Conectividade: Identificar se o erro é recusa de conexão na porta TCP ou falha de resolução DNS.

💎 4. Porque importa?

O instinto amador de desenvolvedores diante de um container que falha é tentar reconstruir a imagem repetidas vezes torcendo para que funcione. O método dos 4 passos elimina o achismo e localiza o erro exato na primeira tentativa.

⚙️ 5. Como funciona por baixo dos panos? (Tabela de Códigos de Saída do Linux)

O código de saída retornado pelo kernel Linux explica o que ocorreu com precisão matemática:

Códigos de Saída Típicos

  • Exited (0): O processo finalizou com sucesso voluntariamente. Se era um serviço que deveria ficar ligado, o executável foi disparado em background ou a thread principal morreu.
  • Exited (1): Erro genérico da aplicação (ex: NullPointerException no startup do Spring ou falha de sintaxe de configuração).
  • Exited (127): Command Not Found. O executável declarado no ENTRYPOINT não existe no PATH da imagem.
  • Exited (137): 128 + 9 (SIGKILL). O processo foi sumariamente assassinado pelo kernel Linux por OOMKilled (Out of Memory) ou por docker kill.
  • Exited (143): 128 + 15 (SIGTERM). O container recebeu sinal de término gracioso e finalizou normalmente.

Causas Mais Frequentes de Falha

  • Variável de Ambiente Ausente: Falta DB_PASSWORD e o Spring aborta o startup.
  • Uso de localhost: Aplicação tenta conectar em localhost:5432 em vez do nome do container de banco.
  • Escuta em 127.0.0.1 em vez de 0.0.0.0: A aplicação sobe perfeitamente mas não responde na porta publicada porque escuta apenas no loopback interno.
  • Permissão em Volume: Falha de escrita no diretório montado por divergência de UID POSIX.

🛠️ 3. Como usar / Como aplicar? (Compose Declarativo de Produção Local)

Estrutura profissional de compose.yaml com healthchecks e dependências condicionais:

services:

    image: postgres:16-alpine
    environment:
      POSTGRES_DB: pedidos
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d pedidos"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 5s

  broker:
    image: rabbitmq:3-management-alpine
    ports:
      - "15672:15672" # Painel web liberado no host
    healthcheck:
      test: ["CMD", "rabbitmq-diagnostics", "check_port_connectivity"]
      interval: 5s
      timeout: 3s
      retries: 10

  api:
    build: .
    depends_on:
      db:
        condition: service_healthy     # AGUARDA O BANCO ESTAR PRONTO PARA QUERIES!
      broker:
        condition: service_healthy   # AGUARDA O BROKER ACEITAR CONEXÕES!
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/pedidos
      SPRING_RABBITMQ_HOST: broker
    ports:
      - "8080:8080"

volumes:
  pgdata:

O pulo do gato: condition: service_healthy. O depends_on comum apenas garante a ordem de inicialização do processo (o docker start). Sem service_healthy, a API Spring Boot sobe, recebe Connection Refused no DataSource e morre com erro!

⚙️ 5. Como funciona por baixo dos panos?

Ao executar docker compose up:

  1. O Compose cria automaticamente uma rede bridge dedicada com o nome do diretório do projeto (ex: meuapp_default).
  2. Inicia cada container anexando-o a essa rede com DNS aliases correspondentes aos nomes dos serviços definidos no YAML (db, broker, api).
  3. O Compose avalia a DAG (Directed Acyclic Graph) das dependências declaradas em depends_on.
  4. Dispara os probes de healthcheck em loop. Assim que o container do banco retorna status healthy (exit 0 no comando pg_isready), o Compose libera a inicialização do serviço dependente (a API Spring Boot).

Onde o Compose para — e por que existe Kubernetes

essenciala virada
💻 INCIDENTE REAL DE PRODUÇÃO

Uma empresa colocou um arquivo `docker-compose.yml` em uma única VM de produção para rodar um e-commerce. Durante uma queima de estoque, o tráfego saturou a máquina e o host travou. Como o Compose não faz gerenciamento de múltiplos nós, não possui agendamento distribuído, nem autorrecuperação entre servidores físicos, todo o site permaneceu fora do ar até a VM ser reiniciada manualmente. O incidente forçou a transição para um orquestrador de clusters (Kubernetes).

🎯 1. O que é?

O Docker Compose é um orquestrador de host único (single-node) voltado para produtividade de desenvolvimento. O Kubernetes (K8s) é uma plataforma de orquestração distribuída para clusters de múltiplos servidores (multi-node), fundamentada no paradigma de Reconciliação Contínua de Estado Desejado (Desired State Control Loop). Enquanto o Compose dispara processos e "espera que eles fiquem vivos", o Kubernetes monitora incessantemente a saúde dos nós físicos e das aplicações, aplicando autocura automática (self-healing), balanceamento de carga, escalabilidade horizontal dinâmica e deploys sem indisponibilidade (zero-downtime).

≈

O cluster: estado desejado e quem faz acontecer

A ideia que organiza todo o Kubernetes — e as peças que a executam.

Estado desejado: você declara, o cluster persegue

essenciala ideia central
💻 INCIDENTE REAL DE PRODUÇÃO

Um analista de suporte tentou corrigir um bug em um Pod do Kubernetes executando comandos manuais diretamente dentro do container (`kubectl exec`). Minutos depois, o nó do Kubernetes sofreu uma oscilação e o Pod foi reescalado em outro nó, eliminando todas as modificações manuais. O time compreendeu o princípio da reconciliação do control plane: no Kubernetes, qualquer alteração deve ser declarada no manifesto Git (GitOps) para que o reconciler persiga e mantenha o estado desejado.

🎯 1. O que é?

O Estado Desejado (Desired State) é o princípio fundacional do Kubernetes. Você nunca emite instruções imperativas ordenando o cluster a "iniciar um container agora" ou "adicionar uma máquina". Em vez disso, você submete um manifesto declarativo registrando como o mundo deveria ser (exemplo: replicas: 3 da imagem orderflow:1.4.2). Um conjunto de Laços de Controle de Reconciliação (Reconciliation Loops) compara ininterruptamente o estado desejado com o estado real observado no hardware, executando ações atômicas para fechar qualquer discrepância — para sempre.

≈

Analogia do mundo real: Como o termostato de um sistema de ar-condicionado central. Você não fica ligando e desligando o compressor na mão a cada minuto: você apenas define a temperatura alvo em "22°C". O sensor mede a temperatura real, compara com o alvo e aciona o motor. Se alguém abrir uma janela e o calor entrar, o termostato reage automaticamente até atingir os 22°C de novo. Não existe um "comando de esquentar": existe um estado alvo e um laço de realimentação contínuo.

🚀 2. Para que serve?

Serve para assegurar resiliência autônoma e convergência determinística de infraestrutura:

  • Autocura Imediata (Self-Healing): Se um nó físico falhar ou um Pod sofrer crash, o cluster recria a instância em outro servidor saudável sem intervenção humana.
  • Idempotência Total: Aplicar o mesmo arquivo YAML dez vezes consecutivas resulta em zero alterações se o estado do cluster já estiver em conformidade com o arquivo.
  • Fundação do GitOps: O repositório Git passa a ser a única fonte da verdade; qualquer divergência aplicada manualmente no cluster é corrigida pelo operador.

💎 4. Porque importa?

Em clusters massivos com milhares de servidores, roteiros imperativos falham pela metade (por exemplo, na etapa 4 de 7), deixando o sistema em um limbo operacional onde ninguém sabe o que foi configurado e o que falhou. O modelo declarativo é imune a isso: se uma tentativa falhar, o laço simplesmente tenta convergir novamente na iteração seguinte.

Veio substituir: Scripts imperativos de deploy via SSH que abortavam no meio do caminho deixando ambientes de produção corrompidos.

⚙️ 5. Como funciona por baixo dos panos?

O Kube-Controller-Manager abriga dezenas de controladores independentes (DeploymentController, ReplicaSetController, NodeController, etc.):

  1. O controlador assina uma fila de eventos (Informer / Watch API) do kube-apiserver.
  2. Quando o Kubelet avisa que um Pod morreu, um evento PodDeleted entra na fila de trabalho (WorkQueue).
  3. O ReplicaSetController processa o evento: consulta a contagem de Pods saudáveis no cache local (ex: 2) e compara com spec.replicas (3).
  4. Como a diferença é -1, o controlador envia uma requisição HTTP POST para o kube-apiserver solicitando a criação de um novo objeto Pod desassociado de nó.
  5. O Scheduler detecta o Pod pendente e escolhe o nó; o Kubelet do nó selecionado puxa a imagem e sobe o container.

Anatomia do cluster: control plane e nodes

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Um cluster Kubernetes de homologação teve um dos nós do control plane com disco cheio, travando o banco de dados `etcd`. Como o `etcd` perdeu o consenso de gravação, o `kube-apiserver` parou de responder, impedindo qualquer comando `kubectl` ou novos deploys na empresa. A separação do `etcd` em discos SSD dedicados de alta performance (IOPS garantido) e monitoramento contínuo de latência de gravação de snapshot estabilizaram o control plane.

🎯 1. O que é?

Um cluster Kubernetes é estruturado em duas camadas rigorosamente segregadas: o Control Plane (Plano de Controle), que é o cérebro que toma todas as decisões arquiteturais (composto por kube-apiserver, etcd, kube-scheduler e kube-controller-manager); e os Worker Nodes (Nós de Trabalho), que são os servidores físicos ou virtuais que efetivamente executam as cargas de trabalho dos Pods (compostos por kubelet, kube-proxy e o Container Runtime como o containerd). Toda e qualquer comunicação entre componentes passa obrigatoriamente pelo kube-apiserver — nenhum componente fala diretamente com outro.

≈

Analogia do mundo real: Como uma grande central de frota de táxis ou ambulâncias. O kube-apiserver é o operador do rádio e o balcão central de chamados. O etcd é o livro-razão contábil onde cada corrida e cada placa de carro estão registradas em cofre. O kube-scheduler é o despachante logístico: avalia o trânsito e escolhe qual táxi deve atender cada passageiro. O kubelet é o motorista dentro do carro: recebe a ordem do rádio, liga o motor e transporta o passageiro. Nenhum motorista combina corridas diretamente com outro pelo rádio; tudo passa obrigatoriamente pela central.

🚀 2. Para que serve?

Serve para separar a governança distribuída da execução pesada de containers:

  • Extensibilidade Total: Como toda entidade é manipulada via REST API padronizada no kube-apiserver, operadores customizados (CRDs) podem ser criados sem alterar o código do kernel do K8s.
  • Segurança Centralizada: Autenticação (mTLS, OIDC), Autorização (RBAC) e Admission Controllers (validação de políticas) são aplicados em um único ponto de estrangulamento.
  • Resiliência a Falhas do Control Plane: Se o control plane ficar temporariamente inacessível, os Pods em execução nos nodes continuam atendendo tráfego normalmente.

💎 4. Porque importa?

Orquestradores antigos utilizavam topologias em malha descentralizada (mesh), onde cada agente conversava com todos os outros. Isso gerava divergências de estado (split-brain) e tornava auditorias impossíveis. O Kubernetes resolveu isso adotando o api-server como a única e irrestrita fonte da verdade.

Veio substituir: Orquestradores legados baseados em sincronização de malha caótica e agentes que alteravam configurações locais sem registro central.

🛠️ 3. A Divisão de Responsabilidades no Cluster

Control Plane (O Cérebro que Decide)

  • kube-apiserver: A porta de entrada universal. Autentica requisições, valida esquemas e grava no etcd.
  • etcd: Banco de dados distribuído chave-valor altamente consistente (protocolo Raft). Guarda todo o estado do cluster.
  • kube-scheduler: Filtra nós capazes e pontua (score) o melhor nó físico para abrigar novos Pods.
  • kube-controller-manager: Executa os loops de reconciliação de deployments, réplicas e nós.

Worker Node (Os Músculos que Executam)

  • kubelet: O agente do nó. Comunica-se com o api-server, comanda o runtime para subir containers e reporta status de saúde.
  • CRI Runtime (containerd): Puxa imagens do registry, monta volumes e executa o processo isolado via runc.
  • kube-proxy: Gerencia regras de iptables/IPVS no nó para viabilizar o balanceamento de carga de Services.
⚙️ 5. Como funciona por baixo dos panos? (Queda do Control Plane)

O que acontece se todas as máquinas do Control Plane (ou o etcd) caírem ou sofrerem manutenção de rede?

  • O Tráfego de Usuários CONTINUA FUNCIONANDO: Os processos dos containers continuam rodando no kernel Linux de cada Worker Node. O tráfego de rede continua sendo roteado pelas regras de iptables já programadas pelo kube-proxy.
  • O que fica suspenso é a capacidade de MUTAÇÃO: Com o api-server fora do ar, você não consegue executar kubectl, novos Pods não podem ser agendados, escalabilidade horizontal (HPA) fica pausada e se um nó físico morrer, seus Pods não poderão ser re-agendados em outro lugar.
  • Saber disso muda a prioridade em salas de crise: queda do control plane é uma emergência de gestão, mas não causa indisponibilidade imediata das aplicações ativas!

🎯 1. O que é?

Toda entidade manipulada dentro do ecossistema Kubernetes — seja uma aplicação (Deployment), um endereço de rede (Service), um volume persistente (PVC) ou um segredo criptográfico (Secret) — é representada como um Recurso Declarativo em formato YAML estruturado obrigatoriamente sobre quatro atributos fundamentais: apiVersion (grupo e versão da API REST), kind (tipo do recurso), metadata (nome, namespace e labels de identificação) e spec (o estado desejado que o cluster deve garantir). O binário kubectl é estritamente um cliente HTTP REST especializado que serializa esses manifestos e conversa com o kube-apiserver.

≈

Analogia do mundo real: Como formulários padronizados de um órgão público ou cartório. Não importa se você está solicitando uma certidão de nascimento, abertura de empresa ou passaporte: o cabeçalho do formulário é rigorosamente padronizado (qual é o formulário, quem é o requerente e o número do protocolo). Uma vez que você aprende a preencher o cabeçalho, qualquer formulário novo que você receba é apenas um corpo de campos diferente.

🚀 2. Para que serve?

Serve para unificar sob uma mesma sintaxe a gestão completa de infraestrutura e aplicação:

  • Consistência de API: Qualquer comando (get, describe, apply, delete) opera com a mesma semântica para qualquer recurso do cluster.
  • Auditoria e Code Review de Infraestrutura: Toda alteração de portas, limites de memória ou réplicas passa por aprovação via Pull Request no Git.
  • Documentação Embutida Offline: O comando kubectl explain permite consultar a documentação de qualquer campo sem sair do terminal.

💎 4. Porque importa?

A homogeneidade estrutural dos manifestos viabilizou a revolução do GitOps. Se todos os aspectos da infraestrutura cabem em arquivos declarativos textuais, o repositório Git passa a ser o espelho matemático de todo o parque computacional em produção.

Veio substituir: Comandos imperativos ad-hoc disparados por desenvolvedores no terminal sem rastreabilidade de quem alterou o quê.

Pod: a unidade que o cluster agenda

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Uma equipe colocou dois microsserviços pesados não-relacionados (uma API de pagamentos e um worker de processamento de vídeos) rodando dentro do mesmíssimo Pod. Quando o worker de vídeo começou a processar múltiplos arquivos e consumiu 100% da CPU do Pod, a API de pagamentos começou a dar timeout em requisições HTTP e caiu junto. A separação em Pods independentes garantiu isolamento de ciclo de vida e agendamento proporcional nos nós do cluster.

🎯 1. O que é?

O Kubernetes não agenda nem gerencia containers individuais diretamente: a menor unidade atômica de agendamento e execução é o Pod. Um Pod encapsula um ou mais containers estreitamente acoplados que compartilham obrigatoriamente o mesmo Network Namespace (mesmo endereço IP e loopback localhost), o mesmo UTS Namespace (hostname) e podem compartilhar volumes de armazenamento, rodando invariavelmente no mesmo nó físico. Um Pod é projetado para ser efêmero e descartável: Pods nunca são consertados ou remendados; eles são sumariamente destruídos e substituídos por novas instâncias.

≈

Analogia do mundo real: Como um apartamento compartilhado por colegas de quarto. Os moradores dividem a mesma porta de entrada, o mesmo número de apartamento e a mesma linha telefônica (a rede e o IP do Pod), além de áreas comuns como cozinha e geladeira (os volumes compartilhados). Porém, cada morador tem seu próprio quarto individual (o container isolado com seus próprios processos). Eles conversam entre si chamando pelo corredor (via localhost), e quem está na rua enxerga apenas um único endereço predial.

🚀 2. Para que serve?

Serve para viabilizar padrões de co-alocação e ciclo de vida compartilhado:

  • Padrão Sidecar: Executar um container auxiliar junto com a aplicação principal (exemplo: Envoy Proxy para Service Mesh ou Fluentbit para coleta de logs locais).
  • Init Containers: Executar tarefas preliminares obrigatórias (como aguardar o banco estar acessível ou rodar migrações de schema) antes do container do app subir.
  • Compartilhamento de Memória IPC e Volumes: Troca de dados ultra-rápida entre processos locais sem cruzar a malha de rede externa.

💎 4. Porque importa?

Sem o conceito de Pod, os orquestradores antigos precisavam de regras complexas de afinidade ("coloque o container A obrigatoriamente na mesma máquina do container B e faça-os dividir a mesma porta"). O Kubernetes tornou a co-alocação uma propriedade intrínseca da unidade básica.

Veio substituir: Regras manuais frágeis de afinidade de nós para manter processos auxiliares juntos na mesma máquina física.

⚙️ 5. Como funciona por baixo dos panos? (O Pause Container)

Como dois containers separados conseguem dividir exatamente o mesmo IP e loopback 127.0.0.1?

  1. Ao criar um Pod, a primeira coisa que o Kubelet comanda o runtime a subir é um container especial invisível e microscópico chamado Pause Container (ou infra container).
  2. O Pause Container executa uma chamada de sistema montando os namespaces de rede (net) e IPC.
  3. Em seguida, os containers reais da aplicação e do sidecar são inicializados utilizando a flag --net=container:pause. Eles herdam e entram no mesmo network namespace já criado pelo container pause!
  4. Se o container da aplicação morrer e reiniciar, o Pause Container permanece vivo mantendo o IP e as portas do Pod intactos.

Síntese de Fixação: Pod (A Menor Unidade Agendável do Kubernetes)

O Que é um Pod?

O Pod encapsula um ou mais contêineres que compartilham o mesmo Network Namespace (mesmo IP e mesma porta localhost) e os mesmos volumes de armazenamento montados.

Um Pod, Um IP

Cada Pod recebe um endereço IP único dentro do cluster. Dois contêineres dentro do MESMO Pod podem conversar entre si via localhost:porta através de loopback de rede.

O Padrão Sidecar

Um contêiner principal com a aplicação de negócio + contêineres secundários colaboradores (coleta de logs com Fluentbit, proxy de service mesh Envoy, rotação de segredos do Vault).

⚠️
Colocar Toda a Arquitetura Dentro de um Único Pod:

Colocar API + Banco de Dados + Redis dentro do mesmo Pod é um erro crasso: eles não conseguem escalar de forma independente e morrem todos juntos. Contêineres só devem morar no mesmo Pod se tiverem ciclo de vida simbiótico inseparável (Sidecars).

💡
Modelo Mental de Decisão Técnica:

Pods são efêmeros e mortais! Nunca crie Pods soltos (Bare Pods) em produção com kind: Pod. Sempre use Deployment ou StatefulSet para garantir ressurreição automática.

Labels e selectors: o mecanismo que liga tudo

essencialo elo
💻 INCIDENTE REAL DE PRODUÇÃO

Um novo Deployment de teste foi aplicado com a label `app: checkout`, exatamente a mesma label utilizada pelo Deployment de produção no Service de checkout. O Service começou a balancear 50% das requisições de clientes reais para os Pods instáveis de homologação, causando 4.000 falhas de transação em 20 minutos. A padronização rigorosa de labels incluindo ambiente (`app: checkout`, `env: prod`, `version: v2`) e selectors específicos evitou colisões acidentais.

🎯 1. O que é?

No Kubernetes, os objetos não se referenciam rigidamente por nomes nem por IDs fixos; a amarração estrutural entre componentes é governada pelo mecanismo desacoplado de Labels (Rótulos chave-valor) e Selectors (Seletores de Correspondência). O Deployment supervisiona os Pods cujas labels casem com o seu spec.selector.matchLabels; o Service direciona requisições de balanceamento para os Pods cujas labels coincidam com o seu próprio spec.selector. É este mecanismo único e universal que conecta toda a topologia do cluster.

≈

Analogia do mundo real: Como as cores de crachás e pulseiras em uma grande conferência com milhares de participantes. A equipe de segurança não consulta uma folha de papel com o nome de cada pessoa que entra: a regra de acesso diz simplesmente "quem estiver com a pulseira verde tem acesso à Sala de Engenharia". Quando um novo participante chega e recebe uma pulseira verde, ele entra imediatamente sem que nenhuma lista precise ser reescrita. Retirar a pulseira verde revoga o acesso no mesmo instante.

🚀 2. Para que serve?

Serve para desacoplar as entidades dinâmicas que nascem e morrem dos balanceadores:

  • Roteamento Dinâmico de Tráfego: O Service não precisa saber quando um Pod morreu ou nasceu; o EndpointSlice atualiza a lista baseado na correspondência das labels.
  • Filtros de CLI e Observabilidade: Filtrar com precisão recursos no cluster: kubectl get pods -l app=orderflow,ambiente=prod.
  • Deploys Canário (Canary Releases): Manter 4 Pods com a versão estável e 1 Pod com a versão nova, ambos compartilhando a label app: orderflow, permitindo que o Service distribua 20% do tráfego para a versão de teste.

💎 4. Porque importa?

Em arquiteturas distribuídas elásticas, manter listas estáticas de IPs ou nomes de máquinas em arquivos de configuração de balanceadores (como no Apache ou Nginx tradicional) exigia recarregar o proxy a cada instante em que uma máquina entrava ou saía.

Veio substituir: Arquivos de configuração de balanceador com listas estáticas de IPs que exigiam recarregamento constante (reload) a cada alteração.

🛠️ 3. Como usar / Como aplicar? (O Elo Label ↔ Selector)

O alinhamento estrito que liga o Deployment ao Service:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  selector:
    matchLabels:
      app: order-service        # 1. O Deployment supervisiona Pods com esta label
  template:
    metadata:
      labels:
        app: order-service      # 2. E carimba os Pods criados com ela!
    spec:
      containers:
        - name: app
          image: orderflow:1.4.2
          ports: [{ containerPort: 8080 }]
---
apiVersion: v1
kind: Service
metadata:
  name: order-service
spec:
  selector:
    app: order-service          # 3. O Service busca Pods com esta label e gera os Endpoints!
  ports:
    - port: 80
      targetPort: 8080
⚙️ 5. Como funciona por baixo dos panos? (Endpoints e EndpointSlices)

O que acontece quando você cria o Service acima?

  1. O EndpointSlice Controller observa a criação do Service e lê seu spec.selector.
  2. O controlador consulta o etcd por todos os Pods que possuem a label app: order-service E que estejam com o status Ready=True (passando no ReadinessProbe).
  3. Ele gera um objeto EndpointSlice contendo os IPs privados desses Pods.
  4. O kube-proxy em cada nó do cluster lê esse EndpointSlice e programa regras de NAT no kernel (via iptables ou IPVS) para balancear as conexões que chegam no IP virtual do Service (ClusterIP).

Deployment e ReplicaSet: a cadeia de controle

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Um operador tentou deletar um Pod com defeito manualmente usando `kubectl delete pod [nome]` esperando que ele sumisse para sempre. O Pod sumiu e reapareceu 1 segundo depois em outro nó. Ele então tentou deletar o ReplicaSet correspondente. O incidente serviu para demonstrar a hierarquia de controle: o Deployment controla os ReplicaSets, e os ReplicaSets garantem o número de réplicas de Pods; para parar a aplicação, deve-se alterar o número de réplicas no Deployment (`kubectl scale deployment --replicas=0`).

🎯 1. O que é?

O Deployment é o controlador declarativo de nível superior responsável pelo ciclo de vida e versionamento de aplicações stateless (sem estado). Ele não gerencia Pods diretamente: ele comanda ReplicaSets. A cada alteração na especificação do Pod (como atualização de imagem ou variáveis), o Deployment cria um novo ReplicaSet e coordena a transição gradual e contínua de réplicas através da estratégia de RollingUpdate, garantindo que o serviço nunca fique indisponível e permitindo rollbacks instantâneos para versões anteriores.

≈

Analogia do mundo real: Como a troca de turno de enfermeiros em um hospital de emergência. O Diretor Geral (o Deployment) supervisiona as escalas de atendimento. Para mudar o plantão da noite (o ReplicaSet novo), ele não manda todos os enfermeiros do dia irem embora de uma vez (o que deixaria os pacientes desamparados). Ele faz os novos enfermeiros assumirem seus leitos aos poucos enquanto os antigos encerram seus relatórios. E se a nova equipe não souber operar um equipamento novo, o Diretor aciona o plantão anterior que ainda está no prédio (o rollback imediato).

🚀 2. Para que serve?

Serve para assegurar disponibilidade ininterrupta durante lançamentos e resiliência a bugs:

  • Zero-Downtime Releases: Atualizar a versão de produção sob carga massiva de clientes sem rejeitar uma única requisição HTTP.
  • Rollback Determinístico em Segundos: Se a versão nova lançar erros 500, o comando kubectl rollout undo reverte as réplicas para o ReplicaSet estável anterior em 2 segundos.
  • Histórico Versionado: Rastrear revisões anteriores com o comando kubectl rollout history.

💎 4. Porque importa?

No início do Kubernetes existia apenas o ReplicationController, e atualizações eram feitas pelo comando cliente imperativo kubectl rolling-update. Se a conexão SSH ou a bateria do notebook do engenheiro caísse no meio do processo, o cluster ficava em um estado inconsistente com duas versões rodando indefinidamente sem ninguém no controle. O Deployment trouxe a lógica de rollout para dentro do control plane.

Veio substituir: O comando imperativo kubectl rolling-update e deploys manuais que causavam indisponibilidade temporária de sistemas.

⚙️ 5. Como funciona por baixo dos panos? (A Dança do RollingUpdate)

Quando você atualiza a imagem no manifesto e aplica kubectl apply:

  1. O DeploymentController detecta que o podTemplateSpec mudou e cria um novo ReplicaSet (ex: order-service-v2 com 0 réplicas). O ReplicaSet antigo (order-service-v1) possui 3 réplicas.
  2. Como maxSurge=1, ele escala v2 para 1 réplica (total: 4 Pods no cluster).
  3. O Kubelet baixa a imagem e inicia o container da v2. Ele dispara a ReadinessProbe.
  4. Assim que a v2 passa no readiness (status Ready), o EndpointSlice adiciona o novo Pod no balanceador.
  5. Como agora existem 4 Pods saudáveis e maxUnavailable=0, o controlador escala o ReplicaSet v1 de 3 para 2 réplicas (enviando SIGTERM gracioso para um Pod antigo).
  6. O ciclo se repete até que v2 atinja 3 réplicas e v1 chegue a 0 réplicas. O ReplicaSet v1 permanece salvo com 0 réplicas para possibilitar o rollback imediato!

A Hierarquia de Controle

aprofundamento
💻 INCIDENTE REAL DE PRODUÇÃO

Dois times de desenvolvimento aplicaram seus manifestos no namespace `default` sem especificar namespace. Ambas as aplicações possuíam um Service com o mesmo nome `api-gateway`. O segundo deploy sobrescreveu o Service do primeiro time, sequestrando todo o tráfego da aplicação vizinha. A criação de namespaces dedicados (`ns-pagamentos`, `ns-catalogo`, `ns-logistica`) com ResourceQuotas e NetworkPolicies isolou os domínios de trabalho.

🎯 1. O que é?

Um Namespace é um agrupamento lógico e virtual de recursos dentro de um mesmo cluster físico de Kubernetes. Ele fornece um escopo de nomes isolado (permitindo que múltiplos times utilizem recursos com o mesmo nome order-service sem colisão), um perímetro para cotas de consumo de hardware (ResourceQuotas e LimitRanges) e uma fronteira para controle de permissões de acesso via RBAC (Role-Based Access Control). No entanto, há um detalhe que surpreende a maioria dos engenheiros: Namespaces NÃO isolam o tráfego de rede por padrão.

≈

Analogia do mundo real: Como os andares de um edifício comercial de escritórios. O 3º andar pertence ao time de Engenharia e o 4º andar pertence ao time de Finanças. Cada andar tem sua própria sala "Reunião 01" e sua própria cota de mesas. Porém, o elevador e as escadas do prédio são totalmente abertos: qualquer funcionário do 3º andar pode entrar no elevador e andar livremente pelos corredores do 4º andar, a menos que a administração instale portas com crachá e biometria — que é exatamente o papel de uma NetworkPolicy.

🚀 2. Para que serve?

Serve para viabilizar multitenancy corporativo e governança de recursos:

  • Segregação de Ambientes e Equipes: Ambientes de desenvolvimento, homologacao e producao organizados no mesmo cluster (ou clusters dedicados).
  • Cotas de Capacidade (ResourceQuota): Impedir que um time de testes consuma toda a memória física do cluster e deixe a produção sem recursos.
  • Delegação de Permissões RBAC: Permitir que desenvolvedores tenham acesso total de leitura e escrita no namespace dev, mas apenas permissão de visualização no namespace prod.

💎 4. Porque importa?

Criar um cluster físico separado para cada pequeno time ou micro-projeto gera custos exorbitantes de infraestrutura e sobrecarga operacional de gerenciar dezenas de control planes. Namespaces viabilizam o compartilhamento seguro e eficiente da mesma infraestrutura física.

Veio substituir: A proliferação de dezenas de clusters pequenos e subutilizados operados individualmente por cada equipe.

Service: o endereço estável para Pods efêmeros

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Um microsserviço cliente configurou a URL de conexão para outro serviço usando diretamente o IP de um Pod (`http://10.244.2.45:8080`). Quando o Pod foi reiniciado após uma atualização, o IP antigo deixou de existir e as requisições começaram a falhar com Connection Refused. A substituição do IP direto pelo nome estável do Service Kubernetes (`http://pagamento-service.pagamentos.svc.cluster.local`) garantiu resolução automática e balanceamento interno via kube-proxy e CoreDNS.

🎯 1. O que é?

Como os Pods são descartáveis e recebem novos endereços IP dinâmicos a cada reinicialização ou rollout, o Service atua como uma abstração de rede que fornece um endereço IP virtual estável e imutável (ClusterIP) associado a um nome DNS interno no CoreDNS. Ele intercepta requisições enviadas a esse endereço único e as balanceia de forma transparente entre o conjunto dinâmico de Pods saudáveis selecionados pelo seu spec.selector, garantindo que mudanças na topologia de réplicas nunca quebrem os clientes.

≈

Analogia do mundo real: Como o número telefônico oficial do SAC de um banco (ex: 0800 123 4567). Você como cliente liga sempre para esse mesmíssimo número memorizado. Na central, cinquenta atendentes entram e saem de seus turnos ao longo do dia, trocando de mesas e ramais continuamente. O cliente nunca precisa saber o nome ou o ramal de quem vai atender; o sistema comuta a chamada para qualquer operador disponível no momento.

🚀 2. Para que serve?

Serve para desacoplar a comunicação de rede da efemeridade dos containers:

  • ClusterIP (padrão): expõe um Service por um IP virtual acessível dentro do cluster. É uma escolha comum para comunicação interna, mas não é automaticamente adequada a todo banco, broker ou workload; considere descoberta, persistência, exposição e requisitos do serviço.
  • NodePort: Abre uma porta estática de alto nível (faixa 30000-32767) em todos os nós físicos do cluster. Útil para testes em laboratório local.
  • LoadBalancer: Solicita automaticamente à API do provedor de nuvem (AWS ELB, GCP Cloud LB) um balanceador gerenciado externo com IP público real.

💎 4. Porque importa?

Em arquiteturas de microsserviços sem Kubernetes, cada linguagem precisava adotar bibliotecas proprietárias de Service Discovery (como Netflix Eureka, Consul ou ZooKeeper), exigindo que a aplicação fizesse polling contínuo de registros e balanceamento client-side (Ribbon). O Kubernetes absorveu essa complexidade para dentro do kernel do sistema operacional via kube-proxy.

Veio substituir: Servidores externos de Service Discovery complexos (Eureka/Consul) e arquivos de balanceador com listas de IPs atualizadas manualmente.

⚙️ 5. Como funciona por baixo dos panos? (O Kube-Proxy e o ClusterIP Fantasma)

O ClusterIP não é uma placa de rede real nem uma interface virtual: ele é um IP virtual fantasma!

  1. O kube-apiserver aloca um IP da sub-rede do Service (ex: 10.96.0.45) e grava no etcd.
  2. O daemon kube-proxy em cada Worker Node programa regras de iptables (ou IPVS / eBPF) na tabela NAT do kernel Linux do nó.
  3. Quando um container envia um pacote TCP para 10.96.0.45:80, antes do pacote sair para a placa de rede física, o módulo Netfilter do kernel intercepta o pacote.
  4. Ele reescreve o IP de destino (Destination NAT - DNAT) para o IP real de um dos Pods saudáveis da lista de endpoints (ex: 10.244.2.14:8080), aplicando distribuição randômica (round-robin ou random weighted). O pacote trafega direto de Pod para Pod sem nenhum proxy no meio do caminho!

Pods morrem, nascem e mudam de IP constantemente a cada deploy ou reschedule. Clientes não podem depender de IPs voláteis de Pods.

Ingress: uma porta de entrada para todos os serviços

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Uma empresa criou um Service do tipo `LoadBalancer` para cada um dos seus 18 microsserviços. Como cada LoadBalancer provisionava um Classic ELB físico independente na AWS, a empresa passou a pagar R$ 12.000/mês apenas em custos fixos de balanceadores ociosos. A consolidação dos serviços através de um único Ingress Controller (NGINX Ingress) compartilhando um único Application Load Balancer com roteamento por host e path reduziu os custos em 85%.

🎯 1. O que é?

O Ingress é um objeto declarativo de Camada 7 (HTTP/HTTPS) que define regras inteligentes de roteamento externo — baseadas em nomes de host (domínios e subdomínios) e caminhos de URL (paths) — apontando para os Services internos do cluster, com suporte a terminação de TLS/SSL. No entanto, o Ingress é apenas um manifesto de regras inerte: quem de fato lê as regras e atende as conexões de rede é o Ingress Controller (um reverse proxy como NGINX Ingress Controller, Traefik, HAProxy ou AWS ALB Controller) rodando como Pod no cluster.

≈

Analogia do mundo real: Como a portaria e a recepcionista de um grande condomínio empresarial. Existe um único endereço público na calçada e uma única porta de entrada física (o balanceador de borda). O Ingress é a placa de diretório afixada na parede: "Consultoria X fica no 2º andar; Advocacia Y fica no 5º andar". O Ingress Controller é a recepcionista sentada na bancada que atende o visitante, confere o documento de identidade (o certificado TLS) e comanda o elevador para o andar correto. Ter a placa sem a recepcionista na bancada não encaminha ninguém.

🚀 2. Para que serve?

Serve para centralizar e otimizar a exposição externa de todas as aplicações do cluster:

  • Consolidação de Custos (FinOps): Em vez de provisionar 20 Load Balancers de nuvem (um para cada microsserviço, custando $40/mês cada), utiliza-se um único Load Balancer externo apontando para o Ingress Controller.
  • Roteamento por Caminho e Host: Roteia api.loja.com/pedidos para o Service de Pedidos e api.loja.com/catalogo para o Service de Catálogo.
  • Terminação TLS e Certificados Automáticos: Integração nativa com cert-manager e Let's Encrypt para emitir e renovar certificados SSL/TLS automaticamente a cada 90 dias sem intervenção humana.

💎 4. Porque importa?

Expor microsserviços utilizando Services do tipo LoadBalancer de forma indiscriminada gera dezenas de IPs públicos, esgota cotas no provedor de nuvem, encarece a fatura e pulveriza o gerenciamento de certificados SSL em dezenas de lugares distintos.

Veio substituir: Múltiplos Load Balancers de nuvem individuais e servidores de proxy reverso manuais mantidos fora do cluster.

ConfigMap e Secret: configuração fora da imagem

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Uma rotação emergencial de credencial de banco de dados exigiu atualizar 12 microsserviços. Como a senha estava gravada diretamente no código e no Dockerfile, foi necessário recompilar 12 imagens, rodar a esteira inteira de CI e fazer deploy de cada aplicação, demorando 4 horas com o banco exposto. 🎯 1. O que é?

O Kubernetes desacopla parâmetros de runtime das imagens através de dois recursos declarativos: o ConfigMap (utilizado para dados de configuração em texto claro não-sensíveis, como URLs de APIs, flags de perfil e timeouts) e o Secret (utilizado para armazenar credenciais sensíveis, senhas, tokens e certificados TLS). No entanto, um aviso vital desde o primeiro dia: Secrets no Kubernetes padrão são apenas codificados em base64, NÃO são criptografados nativamente. Qualquer pessoa com acesso de leitura (RBAC) ao namespace ou ao etcd consegue decodificar a senha em um único comando.

≈

Analogia do mundo real: Como um envelope pardo comum versus um envelope lacrado com fita adesiva. Os dois separam o conteúdo do resto da correspondência da empresa, mas nenhum deles resiste a alguém curioso que pegue o envelope na mão. Tratar o Secret padrão como um cofre inviolável é a origem clássica de vazamentos; para segurança real, você precisa de um cofre bancário blindado com tranca criptográfica (HashiCorp Vault ou AWS Secrets Manager).

🚀 2. Para que serve?

Serve para separar o código imutável de suas parametrizações de ambiente:

  • Injeção Flexível: Configurações e segredos podem ser injetados no Pod como Variáveis de Ambiente (envFrom) ou montados como Arquivos em Volume (volumeMounts).
  • Tratamento Especializado de Segredos: Permissões RBAC distintas (permitir que a equipe leia ConfigMaps mas não Secrets) e rotação de certificados TLS.
  • Centralização: Mudar a URL de um parceiro em um único ConfigMap atualiza todos os Deployments que o referenciam.

💎 4. Porque importa?

O base64 foi introduzido na especificação de Secrets apenas para viabilizar o transporte seguro de caracteres especiais e dados binários (como chaves SSH e certificados) dentro de documentos YAML/JSON, nunca como barreira de segurança criptográfica.

Veio substituir: A injeção de senhas em código-fonte ou no Dockerfile, que exigia recompilar a imagem para trocar um timeout ou credencial.

  3. Sealed Secrets (Bitnami): Permite criptografar o YAML assimetricamente para que ele possa ser versionado com segurança no Git público (GitOps seguro).

Probes: liveness, readiness e startup

essencialprodução
💻 INCIDENTE REAL DE PRODUÇÃO

Um Pod Java Spring Boot demorava 45 segundos para inicializar. Como o `livenessProbe` foi configurado com `initialDelaySeconds: 10` e sem `startupProbe`, o kubelet assumiu que a aplicação havia travado aos 15 segundos e matou o Pod com SIGKILL. O Pod entrou em loop eterno de reinicializações e nunca conseguia subir. A adição de um `startupProbe` tolerando até 60 segundos com `readinessProbe` desacoplado permitiu que o Spring Boot inicializasse com tranquilidade antes de receber tráfego.

🎯 1. O que é?

As Probes (Sondagens de Saúde) são mecanismos periódicos executados diretamente pelo Kubelet para avaliar a integridade dos containers através de três perguntas ontologicamente distintas com consequências operacionais opostas:

  • StartupProbe: "O container já terminou de inicializar?" (Segura as outras duas probes durante o bootstrap lento de JVMs).
  • LivenessProbe: "A aplicação travou em deadlock ou corrompeu a memória?" Se falhar, o Kubelet mata o container com SIGKILL e recria o Pod.
  • ReadinessProbe: "A aplicação está apta a receber requisições de clientes agora?" Se falhar, o Kubelet corta o tráfego removendo o Pod dos Endpoints do Service, mantendo o container vivo.

≈

Analogia do mundo real: Como uma loja de departamentos em um shopping center. A ReadinessProbe é a placa de "Aberto / Fechado para Almoço" na porta de vidro: quando a equipe sai para almoçar por 40 minutos, a placa é virada para "Fechado", nenhum cliente entra, mas a loja física continua intacta. A LivenessProbe é o laudo da Defesa Civil e dos Bombeiros: se as paredes estiverem rachando e o teto prestes a desabar, o prédio é interditado e demolido na marreta. Confundir as duas faz a administração do shopping demolir o prédio inteiro apenas porque a equipe fechou a porta para almoçar!

🚀 2. Para que serve?

Serve para proteger o sistema contra incidentes em cascata e deploys com indisponibilidade:

  • Zero-Downtime Rollout: O Deployment aguarda a ReadinessProbe aprovar antes de prosseguir com a troca de réplicas.
  • Degradação Graciosa: Se o banco de dados oscilar, os Pods saem do balanceador sem reiniciar, retornando ao tráfego assim que o banco estabilizar.
  • Recuperação de Deadlocks: Reinicia threads travadas sem necessidade de intervenção de operadores de madrugada.

💎 4. Porque importa?

Antigamente existia apenas um único endpoint genérico /health. Se o banco ficasse indisponível por 2 minutos, todos os 50 Pods do cluster falhavam no health, eram mortos simultaneamente pelo Kubelet e tentavam subir juntos. Ao reiniciar, 50 instâncias Spring Boot abriam pools de conexão simultaneamente contra o banco convalescente, derrubando o banco de forma definitiva em um efeito cascata catastrófico.

Veio substituir: O endpoint único /health que misturava integridade de processo com conectividade externa.

Síntese de Fixação: Probes de Saúde (Liveness, Readiness e Startup)

Liveness Probe (Estou Vivo?)

Checa se a aplicação não travou em deadlock ou thread hang. Se falhar por 'failureThreshold' vezes consecutivas, o Kubelet MATA o contêiner e o reinicia.

Desativa temporariamente a Liveness e Readiness durante a inicialização (ex: aplicações legadas que demoram 90 segundos para subir), evitando que o Kubelet as mate antes de acordarem.

Liveness deve checar apenas: 'A JVM local e o servidor HTTP interno respondem?'. Readiness deve checar: 'Posso processar a próxima requisição de cliente agora?'.

Requests, limits e QoS: o contrato de recursos

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Pods críticos de processamento financeiro foram implantados sem `requests` e `limits` de memória definidos nos manifestos. Quando um vizinho no mesmo nó sofreu memory leak e a máquina atingiu 98% de uso de RAM, o Linux OOM Killer elegeu e matou o Pod financeiro (classificado com classe de QoS `BestEffort`). A configuração explícita de `requests` iguais a `limits` garantiu a classe de QoS `Guaranteed`, tornando o Pod o último a ser terminado em caso de pressão de memória.

🎯 1. O que é?

O contrato de recursos de computação no Kubernetes é governado por dois valores essenciais: o Request (Reserva Garantida), que representa a quantidade mínima de CPU e memória que o Kubelet e o Scheduler reservam exclusivamente para aquele Pod; e o Limit (Teto Máximo), que estabelece o limite estrito que o container não pode ultrapassar. A relação matemática entre Requests e Limits determina automaticamente a Classe de Qualidade de Serviço (QoS Class) do Pod, que dita quem sobrevive e quem é sumariamente eliminado quando a memória do servidor físico esgota.

≈

Analogia do mundo real: Como fazer reserva em um restaurante concorrido. O Request é a reserva da mesa: você garantiu que 4 cadeiras estarão desocupadas esperando por você na sexta-feira à noite. O Limit é o consumo máximo permitido na mesa. Se você chegar ao restaurante sem reserva prévia (sem requests), você só senta se sobrar alguma banqueta no balcão — e se a casa lotar com clientes que fizeram reserva, você é a primeira pessoa convidada a se retirar do salão.

🚀 2. Para que serve?

Serve para assegurar estabilidade de infraestrutura e previsibilidade de agendamento:

  • Decisão do Scheduler: O Kube-Scheduler utiliza estritamente a soma dos Requests (e não o uso real de CPU) para decidir em qual Worker Node o Pod cabe.
  • Isolamento contra Vizinhos Barulhentos (Noisy Neighbors): Impede que um container com vazamento de memória monopolize a RAM do servidor físico e derrube os outros serviços.
  • Diferenciação de Recursos: Memória RAM é um recurso não-compressível (ou o container tem RAM, ou morre por OOM); CPU é um recurso compressível (se faltar CPU, o processo apenas executa mais devagar via throttling de CFS).

💎 4. Porque importa?

Sem declaração de limites, aplica-se a "Lei da Selva": um único container consumindo 100% de CPU ou vazando memória derruba todos os Pods vizinhos e o próprio sistema operacional do nó hospedeiro.

Veio substituir: A prática antiga de hospedar uma única aplicação por servidor físico para evitar interferência mútua, que resultava em 85% de ociosidade de hardware.

🛠️ 3. Como usar / Como aplicar? (As 3 Classes de Qualidade de Serviço - QoS)
Classe QoS Regra de Configuração Comportamento Sob Pressão de Memória
Guaranteed requests == limits para CPU e Memória em todos os containers. Prioridade máxima. O último a ser despejado (evicted) pelo nó.
Burstable Possui requests definidos, mas limits > requests. Despejado após os BestEffort caso ultrapasse o request reservado.
BestEffort Sem nenhum requests e sem limits declarados. O primeiro a morrer sumariamente assim que o nó entrar em MemoryPressure.
⚙️ 5. Como funciona por baixo dos panos? (Throttling de CPU vs OOMKilled de Memória)

Como o kernel Linux gerencia os dois limites via Cgroups:

  • Memória (cgroup memory.max): Se o processo da aplicação tentar alocar 1 byte além do limits.memory, o kernel aciona o OOM Killer imediatamente, matando o container com sinal SIGKILL (Exit 137).
  • CPU (cgroup cpu.max): O limit de CPU (ex: 500m = meio núcleo) é traduzido pelo kernel no agendador CFS (Completely Fair Scheduler). Se o container tentar consumir 100% de CPU, o kernel não mata o container: ele apenas corta as fatias de tempo (CPU Throttling), fazendo a aplicação responder com lentidão extrema.
☕ 6. Sintonizando a JVM Spring Boot com os Recursos do Kubernetes
CÓDIGO & PRÁTICA

O manifesto correto sincronizando limites de container com o heap do Java:

spec:
  containers:
    - name: app
      image: orderflow:1.4.2
      resources:
        requests:
          memory: "512Mi"
          cpu: "250m"
        limits:
          memory: "512Mi" # Guaranteed para memória evita despejo!
          cpu: "1000m"   # Burstable para CPU permite usar folga da máquina
      env:
        - name: JAVA_TOOL_OPTIONS
          # Reserva 75% da RAM do container para a Heap (~384MB),

⚠️ 7. Onde "quebra" em produção? (Falhas Reais & Armadilhas)
  • Subir Pods em Produção sem Requests (QoS BestEffort): Se a máquina física entrar em estresse temporário, o Kubelet escolhe os Pods BestEffort para matar e liberar espaço. Sua aplicação de produção é descartada pelo cluster sem aviso.
  • Alocar 100% da Memória do Container para a Heap do Java: Passar -Xmx512m em um container com limit de 512MB. A JVM consome memória além da Heap (Metaspace, CodeCache, stacks de threads e buffers de rede Netty). Quando a memória total atinge 520MB, o kernel executa OOMKilled brutal no container.
  • Requests Irrealisticamente Altos: Declarar requests.cpu: 4 quando o app consome apenas 0.2 núcleos. O Scheduler reserva 4 CPUs inteiras do nó: poucos Pods cabem na máquina e novos Pods ficam eternamente em Pending por falsa escassez de recursos.

Síntese de Fixação: Requests, Limits e Classes de QoS (Contratos de Recursos)

Requests (O Que o Pod Garante Para Agendamento)

Utilizado pelo kube-scheduler para decidir qual nó tem capacidade livre. Se o nó não tiver a soma dos requests livres, o Pod não é agendado lá.

Limits (O Teto Máximo Rígido Permitido)

CPU Limit: o kernel aplica throttling (limita o tempo de CPU com CFS quota). Memory Limit: se estourar o limite, o kernel dispara SIGKILL imediato (OOMKilled - Exit Code 137)!

Classes de QoS (Quality of Service)

Guaranteed (Requests == Limits em todos os contêineres: última a ser expulsa em sufoco do nó), Burstable (Requests < Limits: padrão comum) e BestEffort (sem requests nem limits: primeira a ser morta quando faltar memória no nó).

⚠️
O Perigo do Throttling Severo por CPU Limit Muito Baixo:

Configurar um limite de CPU muito baixo (ex: cpu: 100m) faz a CFS quota do Linux 'congelar' as threads da aplicação a cada milissegundo, explodindo a latência p99 de 10ms para 3.000ms! Muitos engenheiros modernos omitem CPU limits e controlam apenas Requests e Memory Limits.

💡
Modelo Mental de Decisão Técnica:

Em aplicações críticas, configure sempre Guaranteed QoS (requests de memória = limits de memória) para evitar que o nó expulse seus pods em momentos de disputa de RAM.

PV, PVC e StorageClass: o disco desacoplado do Pod

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Um cluster Kubernetes executando em nuvem precisou drenar um nó para manutenção. O Pod de banco de dados tinha um volume persistente vinculado a uma zona de disponibilidade específica (`us-east-1a`). Ao ser reagendado em um nó da zona `us-east-1b`, o Pod ficou preso em estado `Pending` com erro `Volume node affinity conflict`, pois discos de bloco em nuvem não podem ser montados entre zonas diferentes. A utilização de StorageClasses com topologia Multi-AZ e StatefulSets zone-aware resolveu o bloqueio.

🎯 1. O que é?

O subsistema de armazenamento persistente do Kubernetes implementa um desacoplamento em três camadas através da interface CSI (Container Storage Interface):

  • PVC (PersistentVolumeClaim): O tíquete de requisição do desenvolvedor — "Preciso de 20GB de disco SSD com acesso exclusivo".
  • StorageClass: O provisionador dinâmico configurado pelo time de infraestrutura que conversa com o driver de storage (AWS EBS gp3, Azure Managed Disk, Ceph ou Google Persistent Disk).
  • PV (PersistentVolume): O volume físico ou virtual real provisionado na nuvem que é associado (bound) à claim e sobrevive integralmente à destruição do Pod.

≈

Analogia do mundo real: Como o guarda-volumes ou chapelaria de um teatro ou aeroporto. Você não escolhe o armário físico nem sabe a marca do cadeado: você apenas entrega sua bagagem e recebe um cartão com comprovante impresso (a Claim). Se você for embora e um colega vier com o mesmo comprovante no dia seguinte, ele recebe exatamente a mesma bagagem de volta. O armário não pertence à pessoa física; pertence à reserva comprovada.

🚀 2. Para que serve?

Serve para assegurar portabilidade de manifestos entre nuvens e persistência de dados:

  • Agnosticismo de Infraestrutura: O desenvolvedor declara o mesmo YAML de PVC no cluster local (Kind/Minikube), na AWS (EKS) ou no Google Cloud (GKE) sem alterar uma linha.
  • Sobrevivência a Falhas de Nós: Se o Worker Node morrer, o Kubelet desanexa o volume EBS daquela VM e anexa na nova VM onde o Pod foi re-agendado.
  • Expansão Dinâmica de Disco: Aumentar o tamanho do PVC de 20GB para 50GB online sem parar o container (via allowVolumeExpansion: true).

💎 4. Porque importa?

No início do Kubernetes, os manifestos traziam identificadores rígidos do provedor de nuvem embutidos (como awsElasticBlockStore: volumeID: vol-012345). Isso impedia que a mesma aplicação rodasse em múltiplos ambientes e exigia privilégios de administrador de nuvem para quem criava Pods.

Veio substituir: Identificadores proprietários de storage chumbados nos manifestos de aplicação e volumes acoplados ao disco local do nó (HostPath).

⚙️ 5. Como funciona por baixo dos panos? (Os Modos de Acesso)

O Access Mode é o parâmetro mais incompreendido do Kubernetes:

  • ReadWriteOnce (RWO): O volume pode ser montado para leitura e escrita por um único nó físico por vez. Quase todos os discos de bloco de nuvem (AWS EBS, Azure Disk, GCP PD) operam exclusivamente em RWO. Se o Pod A está no Nó 1 e você tenta subir o Pod B no Nó 2 apontando para o mesmo PVC RWO, o Pod B fica preso em Pending com erro de Multi-Attach error for volume!
  • ReadWriteMany (RWX): O volume pode ser montado concorrentemente por múltiplos nós físicos simultâneos. Exige protocolos de arquivo em rede como NFS, AWS EFS, Azure Files ou CephFS.
  • ReadOnlyMany (ROX): Montagem somente leitura compartilhada entre múltiplos nós (útil para conjuntos fixos de dados ou modelos de IA).

⚠️ 7. Onde "quebra" em produção? (Falhas Reais & Armadilhas)
  • Escalar Deployment com Volume RWO para 2 Réplicas: A segunda réplica será agendada em outro nó e entrará em CrashLoop ou Pending eterno, acusando FailedAttachVolume: Volume is already attached to another node. Síntese de Fixação: Armazenamento no K8s (PV, PVC e StorageClass)

O Desacoplamento do Armazenamento

Assim como Pods são separados de Nodes, o armazenamento durável é desacoplado do ciclo de vida dos contêineres através de abstrações em camadas.

A Tríade de Armazenamento

StorageClass (SC): define o provisionador de infraestrutura (AWS EBS gp3, Azure Disk, NFS).
PersistentVolumeClaim (PVC): o pedido de aluguel feito pela aplicação ('Preciso de 20GB ReadWriteOnce').
PersistentVolume (PV): o disco real provisionado e conectado.

AccessModes Clássicos

ReadWriteOnce (RWO: montado por um único nó - padrão de discos de bloco EBS/SSD), ReadWriteMany (RWX: montado por múltiplos nós simultaneamente - exige sistemas de arquivos distribuídos como NFS/EFS/Ceph).

⚠️
Tentar Usar ReadWriteOnce (RWO) em Múltiplos Pods em Nós Diferentes:

Se você criar um Deployment com 3 réplicas montando o mesmo PVC EBS com ReadWriteOnce, os Pods que caírem em servidores físicos diferentes entrarão em erro Multi-Attach error for volume e nunca subirão! Para múltiplos pods compartilhando dados, use RWX (NFS/EFS) ou S3/MinIO.

💡
Modelo Mental de Decisão Técnica:

StorageClass é a imobiliária; o PVC é o contrato de aluguel assinado pelo desenvolvedor; o PV é a chave do imóvel físico entregue pelo provedor de nuvem.

StatefulSet: quando a identidade importa

aprofundamento
💻 INCIDENTE REAL DE PRODUÇÃO

Uma equipe implantou um cluster de Kafka usando um `Deployment` tradicional com 3 réplicas montando o mesmo PersistentVolume compartilhado. Como Pods de Deployment possuem nomes aleatórios e efêmeros, os nós do Kafka sobrescreveram os logs uns dos outros e o cluster sofreu corrupção total de partições. A migração para `StatefulSet` garantiu identificadores ordinais fixos (`kafka-0`, `kafka-1`, `kafka-2`), nomes de rede estáveis e discos PVC dedicados para cada réplica.

🎯 1. O que é?

Enquanto o Deployment trata os Pods como gado ("cattle") — anônimos, intercambiáveis e com hashes aleatórios gerados no nome —, o StatefulSet é o controlador de cargas com estado projetado para sistemas que exigem Identidade Estável e Previsível. Ele garante quatro propriedades fundamentais: 1) Nomes ordinais estáveis (pg-0, pg-1, pg-2); 2) DNS estável individual via Headless Service; 3) Discos persistentes exclusivos para cada réplica via volumeClaimTemplates; 4) Ordem sequencial estrita de inicialização e encerramento gracioso.

≈

Analogia do mundo real: Como os músicos em uma orquestra sinfônica. Em um coral de cem pessoas, qualquer cantor pode trocar de lugar na fila sem alterar a apresentação. Mas em uma orquestra, o primeiro violino é o primeiro violino: tem sua partitura específica, sua cadeira fixa e entra em um compasso ordenado. Se você trocar a cadeira do pianista com a do trompetista ou mandar todos tocarem fora de sequência, a orquestra desmorona em cacofonia.

🚀 2. Para que serve?

Serve para hospedar clusters de dados distribuídos que possuem papéis definidos:

  • Clusters de Banco de Dados: Primário de escrita (pg-0) e réplicas de leitura (pg-1, pg-2) com replicação contínua de WAL.
  • Brokers com Particionamento: Apache Kafka ou RabbitMQ em cluster, onde cada nó responde por partições específicas e precisa do seu disco original.
  • Bancos NoSQL e Caches Distribuídos: Cassandra, MongoDB Replica Sets e Redis Cluster com nós que se conhecem nominalmente.

💎 4. Porque importa?

Antes do StatefulSet, engenheiros tentavam rodar bancos no Kubernetes criando múltiplos Deployments individuais com 1 réplica cada, amarrando serviços manuais e volumes estáticos — uma arquitetura artesanal impossível de escalar.

Veio substituir: Gambiarras com múltiplos Deployments individuais de 1 réplica para tentar simular identidade estável em bancos.

🛠️ 3. Como usar / Como aplicar? (StatefulSet com VolumeClaimTemplates)

Estrutura de manifesto de StatefulSet com discos dedicados por réplica:

apiVersion: v1
kind: Service
metadata:
  name: postgres-headless
spec:
  clusterIP: None       # HEADLESS SERVICE: Não aloca IP virtual, expõe DNS por réplica!
  selector:
    app: postgres
  ports:
    - port: 5432
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres-headless # Conecta ao Headless Service para geração de DNS
  replicas: 3
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres:16-alpine
          volumeMounts:
            - name: pg-storage
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates: # CRIA UM PVC INDIVIDUAL E EXCLUSIVO PARA CADA RÉPLICA!
    - metadata:
        name: pg-storage
      spec:
        accessModes: [ ReadWriteOnce ]
        resources:
          requests:
            storage: 20Gi
⚙️ 5. O que o StatefulSet Garante vs O que Ele NÃO Resolve

O que o StatefulSet Garante Nativamente

  • Nome Estável: postgres-0, postgres-1, postgres-2 — sempre previsíveis.
  • DNS Dedicado por Pod: Cada réplica ganha um domínio exclusivo: postgres-0.postgres-headless.svc.cluster.local.
  • Volume Dedicado que Segue o Pod: O PVC pg-storage-postgres-0 é amarrado para sempre ao Pod postgres-0. Se ele morrer, o novo postgres-0 remonta o mesmo disco.
  • Ordem Estrita: O Pod 1 só inicia após o Pod 0 estar Ready. Na redução de escala, o Pod 2 é destruído antes do Pod 1.

O que o StatefulSet NÃO Resolve Sozinho

  • Replicação de Dados: O K8s não sabe o que é um banco relacional; quem replica dados é o Postgres via streaming replication.
  • Eleição de Líder e Quórum: A gestão de quem é líder/primário é do motor do banco ou de um Operator (como CloudNative-PG).
  • Failover Automático sem Perda: Exige lógica de consenso distribuído (Raft/Paxos).
  • Backup e Restore: Continua sendo responsabilidade operacional estrita da sua equipe.

Síntese de Fixação: StatefulSet (Quando a Identidade dos Pods Importa)

Por Que Deployments Falham em Bancos de Dados?

Em um Deployment, os Pods são intercambiáveis, têm nomes aleatórios (app-x7z1) e compartilham o mesmo volume ou perdem identidade. Bancos distribuídos (Kafka, Mongo, Postgres Cluster) exigem identidade fixa e ordem previsível.

As Garantias do StatefulSet

1. Identidade de rede estável e previsível (meu-db-0, meu-db-1, meu-db-2); 2. Inicialização e encerramento estritamente ordenados (sobe o 0, depois o 1, depois o 2); 3. VolumeClaimTemplates dedicados.

VolumeClaimTemplates Exclusivos

Cada réplica do StatefulSet ganha seu próprio disco dedicado e exclusivo (PV/PVC). Se o pod meu-db-1 morrer e ressuscitar em outro nó, o Kubernetes conecta exatamente o mesmo disco com os dados do nó 1 nele!

⚠️
Excluir StatefulSet Não Apaga os Discos (PVCs):

Por medida de segurança máxima contra perda de dados acidental, quando você deleta um StatefulSet, o Kubernetes NÃO deleta os PersistentVolumeClaims (PVCs) associados! Eles permanecem retidos no cluster até exclusão manual explícita.

💡
Modelo Mental de Decisão Técnica:

Aplicações stateless (APIs, Web)? Use Deployment. Cargas com estado persistente, clusters de banco distribuído com eleição de líder e identidades estáveis? Use StatefulSet ou Kubernetes Operators dedicados.

Rollout e rollback sem derrubar ninguém

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Um deploy de uma nova versão de backend quebrou todas as requisições por um erro de sintaxe. O operador entrou em pânico e começou a deletar manifestos manualmente para tentar consertar, apagando configurações que funcionavam. A execução de um simples comando `kubectl rollout undo deployment/api-prod` reverteu o cluster instantaneamente para o ReplicaSet anterior saudável em 3 segundos, eliminando o tempo de indisponibilidade enquanto o time corrigia o bug no Git.

🎯 1. O que é?

O Rolling Update com Zero-Downtime é a substituição progressiva e atômica de réplicas antigas por novas instâncias sem interromper o atendimento aos usuários. Ele opera sobre um tripé mandatório de confiabilidade: 1) ReadinessProbe honesta que atesta que o novo Pod está de fato pronto para receber conexões; 2) Encerramento gracioso (Graceful Shutdown) garantido pela forma exec no ENTRYPOINT e terminationGracePeriodSeconds; 3) Compatibilidade retroativa de banco de dados entre as duas versões de código que convivem ativamente durante a janela de transição.

≈

Analogia do mundo real: Como trocar os quatro pneus de um caminhão com ele em movimento na estrada. Só é possível trocar uma roda por vez, com uma ferramenta especial, certificando-se de que a nova roda está perfeitamente parafusada e rodando antes de soltar a próxima. Tentar trocar todas as rodas ao mesmo tempo é forçar o caminhão a capotar — que é o que ocorre quando o readiness probe está ausente ou mal configurado.

🚀 2. Para que serve?

Serve para eliminar janelas de manutenção noturnas e conferir segurança psicológica aos deploys:

  • Deploy em Horário Comercial: Lançar dezenas de atualizações por dia sem impactar clientes ativos.
  • Reversão Imediata (Rollback): Se métricas apontarem aumento de erros 5xx, reverter o cluster para o estado anterior em 3 segundos via kubectl rollout undo.
  • Controle Fino de Capacidade: maxSurge: 1 e maxUnavailable: 0 garantem que a capacidade computacional disponível nunca cai abaixo do contratado.

💎 4. Porque importa?

No modelo tradicional, o deploy exigia parar o serviço (downtime), aplicar scripts de banco, subir a versão nova e torcer para funcionar. Se falhasse, o processo de rollback levava horas de desespero com o sistema fora do ar.

Veio substituir: Janelas de manutenção na madrugada de sábado e deploys manuais com indisponibilidade inevitável.

🛠️ 3. Como usar / Como aplicar?

Comandos padronizados para orquestrar e monitorar rollouts em produção:

# 1. Atualizar a imagem de um Deployment disparando o rollout
kubectl set image deployment/order-service app=registry.empresa.com/orderflow@sha256:novo

# 2. Acompanhar a progressão bloqueando a esteira até o sucesso:
kubectl rollout status deployment/order-service --timeout=120s

# 3. O Botão de Emergência: Desfazer o deploy imediatamente caso falhe:
kubectl rollout undo deployment/order-service
⚙️ 5. Como funciona por baixo dos panos? (A Coexistência das Duas Versões)
As duas versões convivem ativamente — e isso tem consequências arquiteturais diretas: Durante o rollout, Pods da versão antiga (v1) e da versão nova (v2) dividem o mesmo balanceador e atendem tráfego concorrente. Se a v2 exigir uma coluna nova que a v1 não conhece, o intervalo do deploy torna-se um incidente grave de banco. A regra mandatória de arquitetura é o Padrão Expand and Contract (Migração em Três Passos):
  1. Passo 1 (Deploy de Banco Aditivo): Adicionar a nova coluna como opcional (nullable ou com default), sem alterar o código Java em produção. Ambas as versões continuam funcionando.
  2. Passo 2 (Deploy da Aplicação): Atualizar a aplicação para ler e gravar na coluna nova. Durante o rollout, v1 grava no modelo antigo e v2 grava no modelo novo sem conflito.
  3. Passo 3 (Limpeza Posterior): Em uma janela futura, remover colunas legadas e tornar a nova coluna obrigatória (NOT NULL).

Síntese de Fixação: Estratégias de Rollout e Rollback Sem Downtime

RollingUpdate (Padrão do Deployment)

Substitui réplicas antigas por novas de forma gradual. Controlado por dois parâmetros de ouro: maxSurge (quantos pods extras podem ser criados acima do desejado) e maxUnavailable (quantos pods podem ficar indisponíveis durante a troca).

Blue-Green Deployment

Sobe o ambiente Green (versão nova) 100% paralelo ao Blue (versão antiga). Testa em produção e vira o seletor do Service ou Ingress de uma só vez para o Green. Rollback instantâneo.

Canary Deployment

Envia uma fração minúscula de tráfego real (ex: 5%) para a versão nova (Canário). Monitora métricas de erro e latência com Prometheus; se tudo estiver estável, promove gradualmente para 100%.

⚠️
Configurar maxUnavailable: 100% por Engano:

Se você configurar maxUnavailable: 100%, o Kubernetes matará todos os Pods antigos de uma vez antes de subir os novos, causando indisponibilidade total e queda das sessões de clientes ativos!

💡
Modelo Mental de Decisão Técnica:

Em produção corporativa: configure maxSurge: 25% e maxUnavailable: 0. Dessa forma, nenhuma réplica antiga é desligada antes que uma nova réplica saudável esteja comprovadamente pronta e aprovada pela Readiness Probe.

Escala: HPA e o gargalo que ele não resolve

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Um Horizontal Pod Autoscaler (HPA) escalou a aplicação de 5 para 80 réplicas durante um pico de Black Friday baseado em uso de CPU. Porém, como o banco de dados PostgreSQL subjacente tinha capacidade máxima de 150 conexões e cada Pod abria 10 conexões, o HPA causou o colapso total do banco por exaustão de pool. O time aprendeu que o HPA resolve apenas o gargalo da camada de aplicação sem estado e deve ter tetos máximos alinhados à capacidade dos recursos downstream.

🎯 1. O que é?

O HPA (Horizontal Pod Autoscaler) é o controlador do Kubernetes que ajusta dinamicamente a quantidade de réplicas de um Deployment ou StatefulSet baseando-se no consumo observado de métricas (utilização de CPU, memória ou métricas customizadas de negócio como requisições/segundo e profundidade de filas RabbitMQ/Kafka). Ele monitora continuamente o cluster e calcula a proporção matemática necessária para convergir a carga observada para a meta declarada.

≈

Analogia do mundo real: Como abrir mais caixas registradoras em um hipermercado durante a véspera de Natal. Abrir de 5 para 20 caixas resolve perfeitamente enquanto o gargalo for a velocidade de passar as compras. Porém, se o gargalo for o estacionamento lotado ou uma única porta de saída com catraca emperrada, abrir vinte caixas apenas move a fila para outro lugar — e agora a fila está estrangulando o banco de dados onde ninguém estava prestando atenção.

🚀 2. Para que serve?

Serve para alinhar a capacidade computacional ao tráfego em tempo real:

  • Absorção de Picos Repentinos: Escalar de 3 para 20 réplicas durante uma promoção relâmpago ou Black Friday.
  • Otimização de Custos (FinOps): Reduzir automaticamente para 2 réplicas na madrugada quando o tráfego despenca, liberando servidores na nuvem.
  • Autonomia Operacional: Evita que equipes fiquem de plantão aumentando réplicas manualmente via terminal no meio da noite.

💎 4. Porque importa?

Manter a infraestrutura superdimensionada para o pico 24 horas por dia desperdiça centenas de milhares de dólares em servidores ociosos durante 90% do mês. O HPA fecha o laço econômico da nuvem elástica.

Veio substituir: Dimensionamento fixo para o pico com desperdício de 80% e comandos de escala disparados às pressas durante incidentes.

⚙️ 5. Como funciona por baixo dos panos? (A Conta que Derruba o Banco)

O algoritmo de cálculo de réplicas do HPA:

ReplicasDesejadas = ceil( ReplicasAtuais * ( MetricaAtual / MetricaAlvo ) )
A conta fatal que quase ninguém faz antes de ligar o HPA: Suponha que sua aplicação Spring Boot utilize um pool HikariCP padrão com 10 conexões máximas ao banco. Com 3 réplicas, você consome 30 conexões. Sob carga, o HPA escala para 20 réplicas: 20 réplicas x 10 conexões = 200 conexões abertas. Um PostgreSQL padrão suporta max_connections = 100. O HPA acabou de derrubar o banco de dados por esgotamento de conexões! Antes de aumentar o teto do HPA, dimensione toda a cadeia a jusante (pool Hikari, max_connections do banco e PgBouncer).

⚠️ 7. Onde "quebra" em produção? (Falhas Reais & Armadilhas)
  • HPA sem requests.cpu Definido no Container: A métrica do HPA é calculada como uma porcentagem do request declarado. Se você omitir o requests.cpu, o HPA não tem base matemática de divisão e entra em estado <unknown>, recusando-se a escalar.
  • Oscilação Contínua de Escala (Flapping / Efeito Ioiô): O tráfego sobe, o HPA escala réplicas; a CPU cai, o HPA reduz réplicas; a CPU sobe de novo. Sem a diretiva behavior.scaleDown.stabilizationWindowSeconds: 300, o cluster gasta CPU destruindo e criando Pods incessantemente.
  • Escalar Cargas Limitadas por I/O Usando Métrica de CPU: Aplicações que passam 90% do tempo aguardando respostas lentas de APIs externas ou de disco possuem baixo consumo de CPU (threads bloqueadas). O HPA baseado em CPU acha que o app está ocioso e não escala. Cargas com I/O intensivo devem escalar via KEDA por taxa de requisições ou latência.

RBAC e ServiceAccount: privilégio mínimo no cluster

essencial
💻 INCIDENTE REAL DE PRODUÇÃO

Um Pod de relatórios foi comprometido através de uma vulnerabilidade RCE em uma biblioteca open-source. Como o Pod utilizava a ServiceAccount padrão `default` que havia recebido permissões globais de `cluster-admin` por conveniência durante testes, o invasor utilizou o token montado em `/var/run/secrets/kubernetes.io/serviceaccount/token` para listar e roubar todos os Secrets de todos os clientes do cluster. A implementação de RBAC restritivo com privilégio mínimo e a desativação de montagem automática de tokens evitaram o vazamento.

🎯 1. O que é?

O RBAC (Role-Based Access Control) é o subsistema de autorização do Kubernetes que governa quais identidades podem executar quais operações (verbos: get, list, create, delete) sobre quais recursos da API. Usuários humanos autenticam-se com certificados ou tokens OIDC; aplicações rodando dentro de Pods autenticam-se utilizando uma ServiceAccount. A regra suprema de segurança é o Princípio do Menor Privilégio: nenhuma aplicação deve possuir permissões além daquelas estritamente necessárias para sua operação — e aplicações que não interagem com a API do K8s devem ter seus tokens de acesso desativados.

≈

Analogia do mundo real: Como o crachá magnético de um técnico terceirizado em um datacenter bancário. O crachá autoriza a entrada estritamente na Sala de Racks 03 entre 14h e 16h. Conceder um crachá de "Acesso Irrestrito à Diretoria e aos Cofres" (o temido cluster-admin) apenas "porque é mais rápido e evita burocracia" é a falha elementar que transforma um incidente corriqueiro em vazamento de milhões de registros.

🚀 2. Para que serve?

Serve para blindar o cluster contra ataques laterais e abusos de privilégios:

  • Isolamento de Pipelines de CI/CD: A ServiceAccount da esteira de deploy só tem permissão de aplicar manifestos no namespace desenvolvimento, sem tocar na producao.
  • Mitigação de Comprometimento de Containers: Se um invasor invadir o container através de uma falha de RCE, a ServiceAccount vazia impede que ele liste segredos ou controle outros nós.
  • Auditoria e Conformidade: Todo verbo executado fica registrado nos logs de auditoria do kube-apiserver associado à identidade exata do requisitante.

💎 4. Porque importa?

Nos primeiros anos do Kubernetes, Pods recebiam por padrão tokens com privilégios amplos montados no diretório /var/run/secrets/kubernetes.io/serviceaccount/. Qualquer invasão de container concedia acesso direto de leitura e escrita à API inteira do cluster.

Veio substituir: Tokens compartilhados com privilégios universais e a ausência de controle de acesso granulado na API.

  kind: Role

Helm e o empacotamento dos manifestos

aprofundamento
💻 INCIDENTE REAL DE PRODUÇÃO

Uma empresa gerenciava 35 arquivos YAML puros duplicados para cada um de seus 4 ambientes (dev, hml, uat, prod). Em um deploy de segurança, uma variável de configuração crítica foi alterada manualmente em dev e homologação, mas esquecida em produção, gerando uma quebra de release de 5 horas. A adoção de Helm Charts com um único template parametrizado e arquivos de sobreposição `values-dev.yaml` e `values-prod.yaml` eliminou a divergência de configurações entre ambientes.

🎯 1. O que é?

O Helm é o gerenciador de pacotes padrão do Kubernetes (frequentemente comparado ao apt ou brew para clusters). Ele empacota uma coleção completa de manifestos YAML relacionados (Deployments, Services, ConfigMaps, Ingress, HPA) em um artefato versionado e distribuível chamado Chart. Utilizando uma engine de templates Go, o Helm permite parametrizar qualquer valor via arquivos values.yaml específicos por ambiente (dev, staging, prod) e gerencia instalações, upgrades atômicos e rollbacks em bloco de toda a stack através de um histórico de releases.

≈

Analogia do mundo real: Como uma receita culinária profissional com tabela de porções ajustáveis. A receita-base é exatamente a mesma para servir 2 pessoas ou 100 convidados em um banquete. O que muda é apenas a tabela de variáveis com as quantidades de farinha e açúcar. Manter pastas de YAML duplicadas para cada ambiente é como reescrever a receita inteira à mão em vinte cadernos diferentes — no primeiro erro de cópia, o bolo desanda.

🚀 2. Para que serve?

Serve para governar a distribuição e ciclo de vida de aplicações complexas:

  • Consumo de Software de Terceiros: Instalar ferramentas complexas (Prometheus, Grafana, Nginx Ingress, Cert-Manager) com um único comando: helm install ingress-nginx ....
  • Parametrização Multi-Ambiente: O mesmo Chart é implantado em Dev (com 1 réplica e 256MB) e em Produção (com 10 réplicas, HPA e 2GB) alternando apenas o arquivo values-prod.yaml.
  • Operações Atômicas: Se um upgrade falhar durante a subida de um novo Service, a flag --atomic reverte automaticamente todos os recursos para a release anterior.

💎 4. Porque importa?

A proliferação de manifestos duplicados com pequenos ajustes gerava scripts bash frágeis com sed e envsubst para substituir variáveis antes do kubectl apply. O Helm transformou o empacotamento em padrão industrial com histórico auditável.

Veio substituir: Pastas duplicadas de YAMLs por ambiente e scripts de automação com sed substituindo strings no escuro.

🛠️ 3. Como usar / Como aplicar? (Comandos Essenciais do Helm CLI)
# 1. Instalar uma release a partir de um Chart local passando arquivo de valores:
helm install order-service ./chart -f values-prod.yaml -n producao

# 2. Atualizar com espera e reversão atômica em caso de falha:
helm upgrade order-service ./chart -f values-prod.yaml --wait --atomic --timeout=120s

# 3. Listar as revisões ativas no namespace:
helm list -n producao
helm history order-service -n producao

# 4. O COMANDO MAIS ÚTIL DO HELM: Renderizar o YAML final para inspeção sem aplicar:
helm template order-service ./chart -f values-prod.yaml

# 5. Reverter toda a release para uma revisão anterior:
helm rollback order-service 2 -n producao
⚙️ 5. Como funciona por baixo dos panos? (Helm v3 sem Tiller)

No Helm v3, o antigo daemon com privilégios totais (Tiller) foi completamente eliminado:

  • O Helm é um cliente puro que opera sob o mesmo contexto e permissões RBAC do seu kubectl.
  • O estado de cada release é gravado de forma criptográfica diretamente no namespace como um Secret do tipo helm.sh/release.v1.
  • Ao disparar um upgrade ou rollback, o Helm calcula a diferença entre o Secret da release anterior e a nova especificação, enviando um patch atômico para o kube-apiserver.
☕ 6. Helm vs Kustomize: A Decisão Arquitetural
CÓDIGO & PRÁTICA

Quando utilizar cada abordagem no ecossistema:

A diretriz de escolha: Nem todo projeto exige Helm.
  • Adote Kustomize (embutido nativamente no kubectl -k) para gerenciar os microsserviços internos do seu time: ele utiliza YAML puro com herança e sobreposições (overlays), sem a complexidade de linguagens de template com chaves {{ ... }}.
  • Adote Helm para consumir aplicações complexas do ecossistema open-source (como operadores de banco, Redis, Kafka, Ingress e monitoramento) e quando você precisar distribuir seu produto para múltiplos clientes em clusters diferentes.
⚠️ 7. Onde "quebra" em produção? (Falhas Reais & Armadilhas)

Como pesquisar

essencialdiagnóstico
1. O que é?

A habilidade de consultar com precisão a documentação e utilizar as ferramentas de inspeção do próprio terminal (como kubectl explain) para descobrir esquemas e resolver falhas com agilidade.

≈

Analogia do mundo real: Consultar o manual técnico do fabricante com o número da peça exata em vez de tentar adivinhar sua especificação pelo formato visual.

2. Para que serve?

Permite navegar pelas propriedades de qualquer recurso de manifesto YAML sem precisar decorar a estrutura completa de cabeça.

4. Por que importa?

Com centenas de objetos e campos na API do Kubernetes, saber consultar a especificação no terminal economiza horas de busca desordenada na web.

3. Como usar / Como aplicar?
  1. Use kubectl explain para inspecionar campos e tipos de dados de qualquer recurso.
  2. Leia a seção de Events ao executar kubectl describe para entender por que um Pod não subiu.
  3. Ao buscar na web, use os termos exatos do erro ou do Event (ex: ImagePullBackOff, CrashLoopBackOff).
5. Como funciona por baixo dos panos?

O kubectl explain consulta o esquema OpenAPI fornecido pelo kube-apiserver do cluster ativo, garantindo informações condizentes com a versão exata do ambiente.

6. Comandos essenciais de inspeção
TERMINAL & CLI 
# Navegar na documentação do campo spec.containers
kubectl explain deployment.spec.template.spec.containers

# Inspecionar detalhes e eventos de um pod com falha
kubectl describe pod meu-pod-xyz

# Filtrar pods com problemas no namespace
kubectl get pods --field-selector status.phase!=Running
7. Onde quebra em produção? (Falhas Reais & Armadilhas)
  • Copiar manifestos sem conferir a versão da API: Recursos como Ingress mudaram de extensions/v1beta1 para networking.k8s.io/v1. Sempre confira a versão suportada pelo cluster.

Praticar na sua stack

essencialprojetos
1. O que é?

A aplicação progressiva dos conceitos de containerização e orquestração na sua própria aplicação de trabalho (ex: API Spring Boot com PostgreSQL), avançando por etapas mensuráveis.

≈

Analogia do mundo real: Fazer um test drive no trânsito real após treinar na pista fechada de autoescola: colocar sua própria carga de trabalho sob o orquestrador revela gargalos e configurações que nenhum exemplo didático mostra.

2. Para que serve?

Consolida a integração de ponta a ponta: do código compilado e empacotado até a operação resiliente com réplicas e probes em produção.

4. Por que importa?

Projetos reais com Dockerfiles multi-stage, health probes e limites adequados de memória demonstram maturidade técnica concreta em portfólio e entrevistas.

3. Como usar / Como aplicar?
  1. Crie um Dockerfile multi-stage enxuto para a sua aplicação.
  2. Configure um docker-compose.yml conectando aplicação e banco de dados.
  3. Crie manifestos de Deployment e Service para rodar no kind local.
  4. Adicione ConfigMaps, Secrets, livenessProbe e readinessProbe.
  5. Configure HPA e simule testes de carga para verificar escalabilidade.
5. Como funciona por baixo dos panos?

Ao isolar a aplicação em containers leves e definir contratos de probes e limites de recursos, o orquestrador assume a recuperação automática de falhas com previsibilidade.

5. HPA e testes de carga com k6
6. Deploy em cluster de nuvem (EKS/AKS)
