O que o OrderFlow é, e o que não é

O OrderFlow é um sistema de pedidos de uma loja. O domínio é comum de propósito: você não gasta tempo entendendo o negócio e pode se concentrar na engenharia. Ele é o veículo de treino.

Sozinho, um e-commerce de exemplo não se destaca num portfólio. O que conta é o que os marcos deixam no repositório: contrato verificado, teste de falha, golden set, tabela de custo, RFC e ambiente no ar. Depois dele, o passo seguinte é o carro-chefe: aplicar as mesmas práticas num problema seu.

Depois ou em paralelo

Projetos de IA: por onde começar.

"Projeto de IA" confunde porque o nome sugere que o trabalho é sobre o modelo. Quase nunca é. Um projeto de IA é a combinação de três escolhas: um formato, um problema e uma medida.

FormatoO que o sistema fazComo se mede
ExtraçãoLê um documento e devolve dados estruturados.Acerto por campo.
Assistente com RAGResponde perguntas com base em documentos.Resposta correta, com a fonte citada.
Agente com ferramentasExecuta uma tarefa chamando outros sistemas.Tarefa concluída, sem ação indevida.
IA no desenvolvimentoRevisa código, gera testes, documenta.Achados úteis contra falsos alarmes.
PlataformaControla acesso, custo e qualidade para outros times.Custo por sistema e regressões bloqueadas.

Quatro projetos, um de cada formato

O OrderFlow já cobre RAG, agente e plataforma dentro de um sistema só. Estes quatro são projetos separados e menores, cada um num repositório próprio. Comece pelo primeiro: é o menor e ensina a base dos outros (saída estruturada, validação e avaliação).

1 · Extração · comece por este

Extrator de notas fiscais

Recebe o PDF de uma nota fiscal e devolve um JSON validado: emitente, data, itens e total.

Medida: acerto por campo num conjunto de notas.

Tempo: uma a duas semanas. Roteiro completo abaixo.

2 · IA no desenvolvimento

Revisor de pull request

Roda no pipeline, lê o diff e comenta os problemas que encontra. Você pode usar no seu próprio repositório.

Medida: em 20 diffs com defeitos conhecidos, quantos ele acha e quantos alarmes falsos dá.

Tempo: duas semanas. Roteiro completo abaixo.

3 · Assistente com RAG

Assistente do seu acervo de estudos

Responde perguntas sobre este acervo citando o tópico de origem e gera perguntas de revisão.

Medida: em 40 perguntas, quantas respostas estão certas e apontam para o tópico certo.

Tempo: duas a três semanas. Roteiro completo abaixo.

4 · Agente com ferramentas

Agente que reage a eventos do Kafka

Um pedido atrasa, o evento chega e o agente decide: avisar o cliente, oferecer um cupom ou passar para uma pessoa.

Medida: em 30 cenários, quantas decisões batem com a regra do negócio, e nenhuma ação é repetida.

Tempo: três semanas. Roteiro completo abaixo.

Roteiro completo · projeto 1

Extrator de notas fiscais

Você recebe o PDF de uma nota fiscal eletrônica (o DANFE) e devolve os dados num formato fixo, conferidos por regras. O projeto é em Python, para praticar a linguagem que as vagas pedem.

Por que este projeto funciona como primeiro

  • A resposta certa já existe. Toda nota tem um arquivo XML com os mesmos dados do PDF, em formato estruturado. O XML vira o seu gabarito, sem você rotular nada à mão.
  • A IA só entra onde faz sentido. O XML se lê com código comum. O modelo é usado para o PDF, que é o que chega quando alguém manda a nota por e-mail ou foto.
  • Dá para conferir com regra. A soma dos itens tem que bater com o total, a chave tem 44 dígitos, o CNPJ tem dígito verificador.

Cuidado com os dados

Nota fiscal tem CNPJ, CPF, nome e endereço. Use notas de compras suas, mantenha a pasta de dados fora do Git e nunca publique notas reais. Para o repositório público, crie algumas notas fictícias.

Os cinco passos do projeto

  1. Dados e gabarito. Pares de PDF e XML, e um programa que transforma o XML na resposta esperada.
  2. Extração. O texto do PDF vai ao modelo, que devolve o JSON no formato do contrato (saída estruturada).
  3. Validação. Regras de código conferem a resposta; o que falha é marcado para revisão humana, não aceito em silêncio.
  4. Avaliação. Acerto por campo em todas as notas, comparado com a versão anterior, rodando no pipeline.
  5. Entrega. Uma API que recebe o PDF, o custo por nota medido e um README com os números.

Primeira sessão (90 minutos): o gabarito, sem IA

Nesta sessão você não chama nenhum modelo. O objetivo é ter a resposta certa de cada nota, porque sem ela não há como saber se a extração funciona.

  1. Crie o repositório extrator-notas e o projeto: uv init, depois uv add pydantic pypdf e uv add --dev pytest.
  2. Crie a pasta dados/, coloque-a no .gitignore e guarde nela 5 notas suas, cada uma com o PDF e o XML.
  3. Escreva o contrato em modelo.py (abaixo).
  4. Escreva gabarito.py, que lê o XML e devolve uma NotaFiscal (abaixo).
  5. Escreva um teste que roda o gabarito nas 5 notas e confere que a soma dos itens bate com o total.
  6. Extraia o texto de um PDF com o pypdf e leia o que saiu. Anote o que veio fora de ordem ou quebrado: é com isso que o modelo vai ter que lidar.
# modelo.py: o contrato da saída. É ele que o modelo de IA vai ter que preencher.
from datetime import date
from decimal import Decimal
from pydantic import BaseModel, Field

class Item(BaseModel):
    descricao: str
    quantidade: Decimal
    valor_unitario: Decimal
    valor_total: Decimal

class NotaFiscal(BaseModel):
    chave: str = Field(pattern=r"^\d{44}$")
    cnpj_emitente: str = Field(pattern=r"^\d{14}$")
    data_emissao: date
    valor_total: Decimal
    itens: list[Item]


# gabarito.py: lê o XML da nota e devolve a resposta certa, sem IA nenhuma.
import xml.etree.ElementTree as ET
from modelo import Item, NotaFiscal

NS = {"n": "http://www.portalfiscal.inf.br/nfe"}

def gabarito(caminho_xml: str) -> NotaFiscal:
    inf = ET.parse(caminho_xml).getroot().find(".//n:infNFe", NS)
    texto = lambda caminho, no=inf: no.findtext(caminho, namespaces=NS)
    return NotaFiscal(
        chave=inf.get("Id").removeprefix("NFe"),
        cnpj_emitente=texto("n:emit/n:CNPJ"),
        data_emissao=texto("n:ide/n:dhEmi")[:10],
        valor_total=texto("n:total/n:ICMSTot/n:vNF"),
        itens=[
            Item(
                descricao=texto("n:prod/n:xProd", det),
                quantidade=texto("n:prod/n:qCom", det),
                valor_unitario=texto("n:prod/n:vUnCom", det),
                valor_total=texto("n:prod/n:vProd", det),
            )
            for det in inf.findall("n:det", NS)
        ],
    )

Pronto quando: uv run pytest passa, e para cada uma das 5 notas você tem o texto do PDF e o JSON esperado lado a lado.

Sessões seguintes

  1. Primeira extração. Envie o texto de uma nota ao modelo pedindo a resposta no formato de NotaFiscal. Compare com o gabarito, campo a campo. Leia antes: saída estruturada.
  2. Medir em todas. Rode nas 5 notas e monte a tabela de acerto por campo. Descubra qual campo erra mais e por quê. Leia antes: golden set e regressão.
  3. Validar e corrigir. Adicione as regras (soma, chave, CNPJ). Quando uma falhar, devolva o erro ao modelo uma vez; se falhar de novo, marque para revisão.
  4. Crescer o conjunto. Chegue a 30 notas, de emitentes e formatos diferentes. Ponha a avaliação no pipeline.
  5. API e custo. Exponha com FastAPI, registre tokens e custo por nota e teste um modelo mais barato com a mesma bateria. Leia antes: Python para quem vem de Java.

Pronto quando o projeto termina

  • O README mostra o acerto por campo em pelo menos 30 notas e o custo médio por nota.
  • O pipeline falha se o acerto de algum campo cair em relação à versão anterior.
  • Uma nota com a soma dos itens errada é marcada para revisão, não aceita.
  • Nenhum dado real de nota está no repositório.

Em Java: o mesmo contrato é um record, e o Spring AI preenche com .entity(NotaFiscal.class). Refazer o passo 2 em Java depois de terminar em Python é um bom exercício curto.

Roteiro completo · projeto 2

Revisor de pull request

Um programa que roda no pipeline a cada pull request, lê o diff, pede a um modelo uma lista de problemas num formato fixo e publica os achados como comentário. O projeto é em Python e você usa no seu próprio repositório.

O que este projeto ensina

  • Medir um sistema que dá opinião. Um revisor tem dois jeitos de errar: deixar passar um defeito e reclamar do que está certo. Você mede os dois.
  • Criar o gabarito plantando defeitos. Você pega código que funciona, insere um defeito conhecido e guarda onde ele está. Assim a resposta certa existe.
  • Tratar entrada como dado. O diff é texto escrito por outra pessoa e pode conter instruções para o modelo. É o caso mais direto de prompt injection.

Cuidados

  • Use só repositórios seus. Código de empresa não vai a um modelo externo sem autorização.
  • A chave da API fica nos segredos do pipeline, nunca no repositório. Pull requests vindos de forks não recebem segredos, e isso é proposital.
  • O revisor comenta; ele não aprova nem bloqueia sozinho. A decisão continua com uma pessoa.

Os cinco passos do projeto

  1. Casos. Diffs com defeito plantado e diffs limpos, cada um com os achados esperados.
  2. Revisão estruturada. O diff vai ao modelo, que devolve uma lista de achados no formato do contrato.
  3. Pontuação. Um programa compara os achados com os esperados e conta acertos, defeitos perdidos e alarmes falsos.
  4. Pipeline. O revisor roda no GitHub Actions e comenta no pull request.
  5. Limites. Tamanho máximo de diff, arquivos ignorados, custo por revisão e defesa contra instruções dentro do diff.

Primeira sessão (90 minutos): os casos e a pontuação, sem IA

Nesta sessão você monta o conjunto de casos e o programa que dá a nota. Sem isso, toda mudança de prompt vira impressão.

  1. Crie o repositório revisor-pr: uv init, uv add pydantic, uv add --dev pytest.
  2. Escolha 6 trechos de código seu que funcionam e plante um defeito em cada: condição invertida, recurso não fechado, SQL montado por concatenação, segredo no código, falta de tratamento de nulo e consulta dentro de laço.
  3. Gere o diff de cada um com git diff e salve em casos/01.diff a casos/06.diff. Junte mais 4 diffs limpos, de mudanças boas.
  4. Para cada diff, escreva casos/NN.json com os achados esperados. Nos diffs limpos, a lista é vazia.
  5. Escreva o contrato e a função de pontuação (abaixo).
  6. Teste a pontuação com respostas inventadas: uma perfeita, uma vazia e uma cheia de alarmes falsos.
# modelo.py: o formato que o modelo de IA vai ter que devolver
from typing import Literal
from pydantic import BaseModel

class Achado(BaseModel):
    arquivo: str
    linha: int
    categoria: Literal["logica", "recurso", "seguranca", "segredo", "nulo", "desempenho"]
    comentario: str

class Revisao(BaseModel):
    achados: list[Achado]


# pontuar.py: compara o que o revisor achou com o que era esperado
from modelo import Achado

def mesmo(a: Achado, b: Achado) -> bool:
    return (a.arquivo == b.arquivo and a.categoria == b.categoria
            and abs(a.linha - b.linha) <= 3)          # tolera 3 linhas de diferença

def pontuar(esperados: list[Achado], obtidos: list[Achado]) -> dict:
    encontrados = [e for e in esperados if any(mesmo(e, o) for o in obtidos)]
    falsos = [o for o in obtidos if not any(mesmo(e, o) for e in esperados)]
    return {
        "encontrados": len(encontrados),
        "perdidos": len(esperados) - len(encontrados),
        "alarmes_falsos": len(falsos),
    }

Pronto quando: você tem 10 pares de diff e gabarito, e os testes da pontuação passam nos três casos inventados.

Sessões seguintes

  1. Primeira revisão. Envie um diff ao modelo pedindo a resposta no formato de Revisao e pontue. Leia antes: saída estruturada e estruturar e testar prompts.
  2. Medir nos 10 casos. Monte a tabela de encontrados, perdidos e alarmes falsos. Mude o prompt uma coisa de cada vez e veja o que acontece com os dois números.
  3. Defesa. Crie um diff com um comentário pedindo ao modelo para aprovar tudo. O revisor precisa continuar apontando o defeito. Leia antes: Lab 9 · Prompt injection.
  4. Pipeline. Rode no GitHub Actions a cada pull request e publique os achados como comentário. Ignore arquivos gerados e diffs acima de um tamanho.
  5. Custo e modelo. Registre tokens e custo por revisão e rode a mesma bateria num modelo mais barato. Leia antes: golden set e regressão.

Pronto quando o projeto termina

  • O README mostra, para pelo menos 20 casos, quantos defeitos plantados o revisor acha e quantos alarmes falsos dá nos diffs limpos.

Roteiro completo · projeto 3

Assistente do seu acervo de estudos

Um assistente que responde perguntas sobre este acervo citando o tópico de origem, diz que não sabe quando o acervo não cobre o assunto e gera perguntas de revisão. O projeto é em Python, com PostgreSQL e pgvector no Docker.

O que este projeto ensina

  • Separar a busca da resposta. A maioria dos erros de um RAG está na busca: o trecho certo não foi recuperado. Você mede a busca sozinha, antes de gerar qualquer resposta.
  • Preparar o texto. Os tópicos têm exercícios com alternativas erradas. Se elas forem indexadas, o assistente vai citar respostas erradas como se fossem conteúdo.
  • Você é o usuário. Você conhece o acervo, então percebe na hora quando a resposta está errada ou aponta para o tópico errado.

Cuidados

  • Indexe só as páginas públicas do site. A pasta privado/ e as suas notas pessoais ficam de fora.
  • Dá para fazer o projeto inteiro sem custo, com embeddings e modelo locais no Ollama. A qualidade é menor, e isso também é um dado para comparar.
  • A resposta precisa trazer o link do tópico. Sem a fonte, você não tem como conferir.

Os cinco passos do projeto

  1. Corpus e perguntas. Os tópicos extraídos dos HTML, e perguntas com o tópico onde está a resposta.
  2. Busca. Embeddings no pgvector, e a medida de recuperação: o tópico certo aparece entre os cinco primeiros?
  3. Resposta. O modelo responde só com os trechos recuperados, cita o tópico e recusa quando não há trecho que sustente.
  4. Melhorar pela medida. Tamanho dos trechos, busca híbrida e reordenação entram só se a medida de recuperação pedir.
  5. Uso. Uma linha de comando ou API, e o modo que gera perguntas de revisão a partir de um tópico.

Primeira sessão (90 minutos): o corpus e as perguntas, sem IA

Nesta sessão você transforma as páginas em registros limpos e escreve as perguntas do gabarito. Nenhum modelo é chamado.

  1. Crie o repositório assistente-acervo: uv init, uv add beautifulsoup4, uv add --dev pytest.
  2. Escreva extrair.py (abaixo), que lê os HTML das trilhas e dos cadernos e grava um registro por tópico em corpus.jsonl.
  3. Abra o corpus.jsonl e leia três registros inteiros. Confira que as alternativas dos exercícios não estão lá.
  4. Escreva 20 perguntas em perguntas.jsonl, cada uma com o documento e o id do tópico onde está a resposta.
  5. Inclua 4 perguntas que o acervo não responde, marcadas para recusa.
  6. Escreva um teste que confere que todo id citado nas perguntas existe no corpus.
# extrair.py: um registro por tópico, sem os exercícios (eles contêm respostas erradas)
import json
from pathlib import Path
from bs4 import BeautifulSoup

def topicos(caminho: Path):
    sopa = BeautifulSoup(caminho.read_text(encoding="utf-8"), "html.parser")
    for artigo in sopa.select("article.topic"):
        for bloco in artigo.select(".topico-fechamento, svg, button"):
            bloco.decompose()
        yield {
            "doc": caminho.stem,
            "id": artigo.get("id"),
            "titulo": artigo.h3.get_text(" ", strip=True),
            "texto": artigo.get_text(" ", strip=True),
            "url": f"{caminho.parent.name}/{caminho.name}#{artigo.get('id')}",
        }

if __name__ == "__main__":
    raiz = Path("../site-estudos")
    with open("corpus.jsonl", "w", encoding="utf-8") as saida:
        for pasta in ("trilhas", "cadernos"):
            for html in sorted((raiz / pasta).glob("*.html")):
                for registro in topicos(html):
                    saida.write(json.dumps(registro, ensure_ascii=False) + "\n")

# {"pergunta": "Qual o melhor time de futebol do Brasil?", "recusar": true}

Pronto quando: o corpus.jsonl tem um registro por tópico, sem texto de exercício, e você tem 24 perguntas com o tópico esperado ou a marca de recusa.

Sessões seguintes

  1. Busca. Suba o PostgreSQL com pgvector, gere os embeddings e busque. Meça em quantas das 20 perguntas o tópico certo aparece entre os cinco primeiros. Leia antes: chunks e RAG com pgvector.
  2. Olhar os erros. Para cada pergunta em que a busca falhou, leia o que veio no lugar. Decida se o problema é o tamanho do trecho, a pergunta ou a falta de busca por palavra exata.
  3. Resposta com citação. Gere a resposta só com os trechos recuperados, com o link do tópico. Teste as 4 perguntas de recusa. Leia antes: alucinação e ancoragem.
  4. Melhorar e medir de novo. Teste uma mudança por vez (trechos menores, busca híbrida) e compare com a medida anterior. Leia antes: Lab 10 · Ragas.
  5. Perguntas de revisão. Dado um tópico, o assistente gera três perguntas com gabarito. Confira à mão se as respostas estão no texto.

Pronto quando o projeto termina

  • O README mostra a taxa de recuperação e a taxa de respostas corretas em pelo menos 40 perguntas, antes e depois de cada melhoria.
  • Toda resposta traz o link do tópico de origem.
  • As perguntas fora do acervo são recusadas.
  • Nenhum conteúdo privado foi indexado.

Agente que reage a eventos do Kafka

Quando um pedido atrasa, um evento chega pelo Kafka e um agente decide o que fazer: avisar o cliente, oferecer um cupom, passar o caso para uma pessoa ou não fazer nada. Este projeto é em Java, com Spring Boot, Spring Kafka e Spring AI, para juntar as três coisas que você mais quer mostrar.

Quando um agente se justifica aqui

  • Se a decisão coubesse numa tabela, um if resolveria. O agente só faz sentido porque o evento traz um texto livre: a observação da transportadora ("destinatário ausente", "carga extraviada", "endereço não localizado"). Interpretar esse texto é o trabalho do modelo.
  • O modelo decide, o código limita. O valor máximo do cupom, a regra de uma ação por pedido e a exigência de aprovação humana ficam em código, não no prompt.
  • Eventos se repetem. O Kafka entrega pelo menos uma vez. Um agente que age duas vezes manda dois cupons.

Cuidados

  • No laboratório, as ferramentas só gravam o que fariam. Nenhum e-mail ou cupom real é enviado.
  • Nunca deixe o modelo escolher um valor sem limite conferido no código.
  • Uma ação com custo alto fica pendente de aprovação de uma pessoa.

Os cinco passos do projeto

  1. Cenários e ferramentas. A tabela de decisão escrita à mão, e as ferramentas com as guardas em código.
  2. Decisão. O agente recebe o evento, usa as ferramentas e decide. Você mede contra os cenários.
  3. Kafka. O agente passa a ser acionado pelo evento, com tópico de erro e consumo idempotente.
  4. Limites. Número máximo de passos, teto de valor e aprovação humana para o caso caro.
  5. Operação. Rastro de cada decisão, custo por evento e reprocessamento sem repetir ação.

Primeira sessão (90 minutos): os cenários e as guardas, sem IA

Nesta sessão você define o que é a decisão certa e constrói as ferramentas com as proteções. O modelo ainda não entra.

  1. Crie o projeto agente-atrasos com Spring Boot, Spring Kafka, JDBC e PostgreSQL no Docker Compose.
  2. Escreva o evento e as ações possíveis como tipos Java (abaixo).
  3. Escreva 15 cenários em cenarios.json: o evento e a ação esperada. Inclua casos em que a observação da transportadora muda a decisão.
  4. Crie a tabela acao_pedido com restrição única no pedido e o registro de ações (abaixo).
  5. Implemente as ferramentas como métodos que só registram a ação, com o teto do cupom conferido em código.
  6. Escreva dois testes: registrar duas ações para o mesmo pedido (a segunda é recusada) e pedir um cupom acima do teto (é recusado).
// os tipos do problema
record PedidoAtrasado(String eventoId, String pedidoId, int diasAtraso, BigDecimal valor,
                      boolean clienteVip, String observacaoTransportadora) {}

enum Acao { AVISAR, CUPOM, ESCALAR, NADA }

record Cenario(String nome, PedidoAtrasado evento, Acao esperada) {}

// a guarda que o modelo não consegue contornar: no máximo uma ação por pedido
// CREATE TABLE acao_pedido (pedido_id TEXT PRIMARY KEY, acao TEXT NOT NULL,
//                           evento_id TEXT NOT NULL, criada_em TIMESTAMPTZ DEFAULT now());
@Service
class RegistroDeAcoes {
    private final JdbcTemplate jdbc;
    RegistroDeAcoes(JdbcTemplate jdbc) { this.jdbc = jdbc; }

    boolean registrar(String pedidoId, Acao acao, String eventoId) {
        int linhas = jdbc.update("""
            INSERT INTO acao_pedido (pedido_id, acao, evento_id) VALUES (?, ?, ?)
            ON CONFLICT (pedido_id) DO NOTHING""", pedidoId, acao.name(), eventoId);
        return linhas == 1;        // false: esse pedido já teve uma ação
    }
}

// a ferramenta: o teto é conferido aqui, não no prompt
@Component
class Ferramentas {
    private static final BigDecimal TETO = new BigDecimal("0.10");   // 10% do pedido
    private final RegistroDeAcoes registro;
    private final PedidoRepository pedidos;
    Ferramentas(RegistroDeAcoes registro, PedidoRepository pedidos) {
        this.registro = registro; this.pedidos = pedidos;
    }

    String emitirCupom(String pedidoId, BigDecimal valor, String eventoId) {
        BigDecimal maximo = pedidos.valorDe(pedidoId).multiply(TETO);
        if (valor.compareTo(maximo) > 0) return "recusado: valor acima do teto de " + maximo;
        return registro.registrar(pedidoId, Acao.CUPOM, eventoId)
            ? "cupom registrado" : "recusado: pedido já teve uma ação";
    }
}

Pronto quando: você tem 15 cenários com a ação esperada, e os dois testes das guardas passam.

Sessões seguintes

  1. Primeira decisão. Exponha as ferramentas ao modelo com o Spring AI e rode os 15 cenários. Conte quantas decisões batem. Leia antes: tool calling e o loop agêntico.
  2. Olhar a trajetória. Nos cenários errados, veja quais ferramentas foram chamadas e com quais argumentos. Leia antes: como avaliar um agente.
  3. Ligar ao Kafka. Consuma o tópico de pedidos atrasados, com tópico de erro. Publique o mesmo evento duas vezes e confira que só uma ação é registrada. Leia antes: Spring Kafka e DLT.
  4. Limites. Ponha um máximo de passos por evento e deixe o cupom acima de um valor pendente de aprovação.
  5. Operação. Registre o rastro e o custo de cada decisão e reprocesse um dia de eventos sem repetir nenhuma ação. Leia antes: reprocessamento e OrderFlow AI · Etapa 8.

Pronto quando o projeto termina

  • O README mostra, em pelo menos 30 cenários, quantas decisões batem com a esperada, e o custo médio por evento.
  • O mesmo evento entregue duas vezes gera uma ação só.
  • Um pedido de cupom acima do teto é recusado pelo código, mesmo que o modelo insista.
  • O reprocessamento de um dia de eventos não repete nenhuma ação.

Em Python: o mesmo agente pode ser escrito com um framework de agentes consumindo o Kafka. Fazer só o passo 2 em Python, com os mesmos cenários, é uma boa comparação entre as duas stacks.
