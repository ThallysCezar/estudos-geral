Quando dividir o frontend

Micro frontends resolvem um problema de organização entre times, não de desempenho.

Micro Frontends: decomposição vertical, autonomia e a Lei de Conway na interface

essencialarquitetura frontend
💻 CENÁRIO HIPOTÉTICO DE PRODUÇÃO

Uma grande operação de e-commerce possuía um monólito SPA em React com 80 desenvolvedores contribuindo no mesmo repositório. Qualquer alteração no botão de favoritar exigia rebuild de 45 minutos da aplicação inteira, bateria regressiva global e deploy bloqueante na sexta-feira à noite. A decomposição em 4 micro frontends verticais (Catálogo, Checkout, Conta e Shell) reduziu o tempo de CI/CD para 3 minutos por squad, permitindo deploys autônomos múltiplos por dia sem risco de quebra cruzada.

Direto: Micro Frontend (MFE) é um estilo arquitetural no qual uma aplicação web de frontend é decomposta em módulos verticais autônomos, entregues e operados de forma independente por equipes alinhadas a domínios de negócio. Em vez de manter um único monólito de interface, cada time desenvolve, testa e implanta sua fatia de experiência do usuário, integrando-a em tempo de execução no navegador sob uma casca hospedeira comum.

≈

As Lojas em um Shopping Center. O shopping center (Shell/Host) fornece a infraestrutura compartilhada: corredores, iluminação, banheiros e segurança geral (layout base, autenticação, roteamento principal). Cada loja (MFE Remoto) organiza seu estoque, decora sua vitrine e atende seu cliente com total autonomia, sem precisar fechar o shopping para trocar uma arara de roupas.

Como surgiu

A consolidação dos microsserviços no backend revelou um novo gargalo organizacional: enquanto os serviços de APIs escalavam de forma ágil com deploys contínuos, todas as equipes colidiam no mesmo repositório monolítico de frontend (SPA), gerando conflitos de merge diários e bloqueios na esteira de homologação.

Veio substituir: monólitos gigantes de frontend em SPAs onde dezenas de equipes disputavam commits no mesmo bundle compilado.

O mecanismo

A aplicação é dividida em um Shell (ou Host), responsável pelo layout mestre, autenticação global e roteamento primário, e múltiplos Remotes (micro frontends de domínio). Em tempo de execução no navegador, o Shell faz a carga dinâmica (Dynamic Import) dos fragmentos remotos via HTTP, montando a interface unificada na tela do usuário.

Para que serve

Desbloquear o trabalho paralelo de dezenas de desenvolvedores, reduzir o tempo de build e permitir que cada equipe implante melhorias no seu domínio de negócio sem sincronização nem aprovações cruzadas.

Por que é importante

A Lei de Conway dita que os sistemas refletem as estruturas de comunicação da empresa. Tentar operar equipes autônomas com um monólito de frontend gera atrito cultural, burocracia de releases e fragilidade operacional na produção.

Como usar

No shell, cada rota de domínio aponta para um remote, carregado só quando o usuário entra nela. O shell não importa código dos remotes no build: ele pede o módulo pelo nome.

// shell: app.routes.ts (Angular + Native Federation)
import { Routes } from '@angular/router';
import { loadRemoteModule } from '@angular-architects/native-federation';

export const routes: Routes = [
  { path: '', component: HomeComponent },
  {
    path: 'catalogo',
    loadComponent: () =>
      loadRemoteModule('catalogo', './Component').then(m => m.CatalogoComponent),
  },
  {
    path: 'checkout',
    loadChildren: () =>
      loadRemoteModule('checkout', './routes').then(m => m.CHECKOUT_ROUTES),
  },
];

Um dos desafios mais críticos de micro frontends integrados no mesmo DOM é o vazamento de CSS global. Uma classe .btn-primary { padding: 20px } definida pelo Checkout pode distorcer visualmente o Catálogo. Para mitigar esse risco sem recorrer ao Shadow DOM (que isola bem, mas complica estilos globais, foco e integração com alguns frameworks), as abordagens recomendadas pela indústria são: CSS Modules com hashes únicos compilados por componente, Styled Components / Emotion com escopo por nó, ou frameworks de utilitários atômicos com prefixos exclusivos (Tailwind com prefixo chk-, cat-).

  • Adotar Micro Frontends para equipes minúsculas: com um time só, não existe o gargalo entre times que MFE resolve; sobra a complexidade de tooling, versionamento e deploy.
  • Poliglotismo inconsequente de frameworks: misturar React, Angular e Vue na mesma página carrega vários runtimes, aumenta o peso da página e piora o tempo de carregamento.

Estratégias de composição: build, servidor, borda, iframe e runtime no navegador

essencialdecisão de integração
💻 CENÁRIO HIPOTÉTICO DE PRODUÇÃO

Uma loja juntou as telas de três times publicando cada parte como pacote npm, importado pelo app principal. Na prática, toda mudança do time de Recomendações exigia um novo release do app inteiro, e o time de Produto vivia esperando versões dos outros. O nome era micro frontend, mas o deploy continuava único. A página de produto, que precisava de bom SEO, passou a ser composta no servidor; a área logada passou a carregar os remotes em runtime. Cada time voltou a publicar sozinho.

Direto: Compor é decidir quando e onde as partes dos times viram uma página. Há cinco caminhos: no build (cada parte é um pacote que o app compila junto), no servidor (o servidor monta o HTML com fragmentos de cada time), na borda (a CDN faz essa montagem), por iframe (cada parte é uma página isolada dentro da outra) e em runtime no navegador (o shell baixa o JavaScript dos remotes e monta tudo no mesmo DOM). Só os quatro últimos permitem deploy independente de verdade.

≈

Montar um jornal. Composição no build é imprimir todos os cadernos juntos: se o caderno de esportes atrasa, o jornal inteiro atrasa. Composição no servidor é a gráfica que encaixa os cadernos prontos na hora de rodar. Iframe é entregar cada caderno num envelope separado dentro do jornal. Runtime é o leitor recebendo a capa e buscando cada caderno quando abre aquela seção.

Como surgiu

Antes das SPAs, portais já montavam páginas no servidor com Server Side Includes (SSI) e, nas CDNs, com Edge Side Includes (ESI). Portais corporativos usavam iframes. Com as SPAs, a integração foi para o navegador: o single-spa organizou isso em 2018 e o Module Federation do Webpack 5, em 2020, tornou o carregamento em runtime o caminho mais citado.

Veio substituir: o pacote npm compartilhado como forma de integrar times, que obrigava todos a republicar juntos, e os portais feitos só de iframes.

O mecanismo

No build, o host declara as partes como dependências e o empacotador gera um bundle só, com um deploy só. No servidor ou na borda, o HTML é montado antes de chegar ao navegador: cada fragmento vem de um serviço do time, com timeout próprio. No iframe, cada parte tem documento, JavaScript e CSS isolados, e a conversa entre elas passa por postMessage. Em runtime, o shell resolve a URL do remote, baixa o módulo e o renderiza no mesmo DOM, compartilhando o framework.

Para que serve

Escolher a forma de integração pelo que a tela precisa: SEO e primeira pintura rápida pedem servidor ou borda; isolamento forte de um sistema legado pede iframe; uma área logada muito interativa pede runtime no navegador.

Por que é importante

A estratégia define o que o time ganha. Escolher composição no build e chamar de micro frontend dá o custo da divisão sem o benefício do deploy independente. Uma mesma aplicação pode, e costuma, combinar estratégias diferentes por área.

Como usar

Composição no servidor com Spring: o controller busca o HTML de cada time e monta a página. O fragmento opcional tem tratamento de falha, para não derrubar a página inteira.

@Controller
class PaginaProdutoController {

  private final RestClient rest = RestClient.create();

  @GetMapping("/produto/{id}")
  String pagina(@PathVariable String id, Model model) {
    // fragmento obrigatório: sem ele a página não faz sentido
    model.addAttribute("detalhe", rest.get()
        .uri("http://catalogo/fragmentos/produto/{id}", id)
        .retrieve().body(String.class));
    // fragmento opcional: se falhar, a página sai sem ele
    model.addAttribute("recomendacoes",
        fragmentoOuVazio("http://recomendacao/fragmentos/produto/" + id));
    return "produto";   // no template: <div th:utext="${detalhe}"></div>
  }

  private String fragmentoOuVazio(String url) {
    try {
      return rest.get().uri(url).retrieve().body(String.class);
    } catch (RestClientException e) {
      return "";
    }
  }
}

Com Edge Side Includes, a página cacheada na CDN carrega marcações como <esi:include src="/fragmentos/carrinho"/>, e a CDN substitui cada uma pelo fragmento do time antes de entregar a resposta. Isso permite cachear a parte estável da página por muito tempo e a parte pessoal por pouco. Varnish e Akamai implementam ESI, cada um com o seu subconjunto da especificação; confira o que o seu provedor suporta antes de desenhar a página em cima disso.

  • Iframe como solução geral: resolve isolamento, mas complica rotas e links diretos, altura da página, acessibilidade, foco do teclado e SEO.

Native Federation

Como o navegador carrega e compartilha módulos de vários times sem o runtime do Webpack.

Native Federation por baixo dos panos: ESM nativo, W3C Import Maps e adeus ao Webpack

essencialweb standards
💻 CENÁRIO HIPOTÉTICO DE PRODUÇÃO

Uma equipe migrou suas aplicações corporativas para o build system moderno do Angular baseado em esbuild e Vite, alcançando uma aceleração de 75% nos tempos de compilação. No entanto, o sistema legado de Micro Frontends utilizava o Module Federation Plugin proprietário do Webpack, que não funcionava com esbuild. A adoção de Native Federation desbloqueou o uso do novo compilador de alta performance preservando 100% da federação dinâmica em produção sem alterar os contratos dos micro frontends.

Direto: Native Federation é uma tecnologia criada por Manfred Steyer para implementar federação de módulos em micro frontends de forma completamente agnóstica de empacotador. Em vez de depender de patches internos proprietários do Webpack, o Native Federation utiliza padrões W3C oficiais: ECMAScript Modules (ESM) nativos do navegador e W3C Import Maps. Isso permite federar aplicações construídas com Vite, esbuild, Rollup ou Webpack sem prender o projeto a um empacotador.

≈

A Lista Telefônica do Prédio. O Module Federation antigo do Webpack era como ter um mensageiro particular com código secreto que só entregava pacotes se você contratasse o serviço da mesma transportadora. O Native Federation com Import Maps é uma lista telefônica pública afixada no saguão: qualquer mensageiro moderno lê o endereço padronizado e entrega a encomenda na porta certa sem exigir intermediários exclusivos.

Como surgiu

O Module Federation revolucionou a indústria com o Webpack 5 em 2020, mas acoplou fortemente os projetos à arquitetura interna do Webpack. Com a chegada de ferramentas mais rápidas, escritas em Go e Rust (como esbuild e Vite), a comunidade precisava de uma solução de federação baseada em padrões abertos da web.

Veio substituir: a dependência obrigatória do runtime proprietário do Webpack ContainerPlugin para carregar módulos remotos.

O mecanismo

No build, o Native Federation analisa as dependências compartilhadas e os módulos expostos, gerando artefatos ESM nativos. No runtime, o navegador recebe um <script type="importmap"> que mapeia aliases de pacotes (como '@angular/core') para URLs absolutas em CDN. Ao chamar import(), o carregador de módulos do navegador resolve o nome pelo import map, baixa o módulo e reaproveita o que já foi carregado.

Para que serve

Permitir o uso de empacotadores modernos ultrarrápidos (Vite, esbuild, Rspack) em arquiteturas de micro frontends, eliminando a dependência do Webpack e acelerando drasticamente o ciclo de desenvolvimento (HMR).

Por que é importante

Adotar padrões oficiais do W3C garante longevidade arquitetural. As primitivas de ESM e Import Maps são suportadas nativamente por todos os navegadores modernos, reduzindo o volume de código de runtime enviado aos usuários.

Como usar

O shell inicializa a federação antes de subir a aplicação. O manifesto diz onde está o remoteEntry.json de cada remote; a partir dele a biblioteca monta o import map.

// shell: main.ts
import { initFederation } from '@angular-architects/native-federation';

initFederation('federation.manifest.json')
  .catch(err => console.error(err))
  .then(() => import('./bootstrap'))   // a aplicação de verdade sobe depois
  .catch(err => console.error(err));

// shell: public/federation.manifest.json
{
  "catalogo": "http://localhost:4201/remoteEntry.json",
  "checkout": "http://localhost:4202/remoteEntry.json"
}
Para ir alémPolyfills com es-module-shims e Otimização com modulepreload

Embora W3C Import Maps sejam suportados nativamente pelos navegadores evergreen (Chrome 89+, Safari 16.4+, Firefox 108+), ambientes legados corporativos exigem polyfills. O es-module-shims intercepta e emula Import Maps com overhead ínfimo. Além disso, para eliminar cascatas de requisições de rede (waterfalls) em conexões lentas, utiliza-se a tag <link rel="modulepreload" href="...">, instruindo o navegador a baixar e pré-compilar módulos ESM críticos em segundo plano antes da execução.

  • Bloqueio por CORS no servidor de módulos remotos: arquivos ESM carregados de origens distintas falham se o servidor HTTP não enviar o cabeçalho Access-Control-Allow-Origin; libere a origem do shell, não *.

O contrato do federation.config.js: exposes, shared, singleton e strictVersion

essencialconfiguração técnica
💻 CENÁRIO HIPOTÉTICO DE PRODUÇÃO

Em uma aplicação de portal financeiro, o Shell carregava a biblioteca de estado global na versão 2.1 e um micro frontend remoto carregava a versão 1.8. Como a biblioteca dependia de contexto único na janela global, a aplicação disparava o erro fatal 'Multiple instances of state runtime detected' e travava a navegação do usuário. A configuração estrita de singleton: true e strictVersion: true no federation.config.js interceptou a incompatibilidade em tempo de teste e forçou o alinhamento da dependência compartilhada.

Direto: O arquivo federation.config.js é o manifesto de configuração declarativa do Native Federation que define as fronteiras e contratos de um micro frontend. Ele determina a identidade da aplicação (name), quais componentes ou rotas são tornados públicos para consumo externo (exposes), quais remotos são consumidos (remotes) e como as bibliotecas npm de terceiros são compartilhadas e deduplicadas em tempo de execução (shared).

≈

O Contrato de Locação e Regimento Interno. Em um edifício compartilhado, o regimento especifica quais áreas são públicas para todos os moradores (exposes), onde estão os prestadores de serviço terceirizados (remotes) e quais regras são inegociáveis para evitar caos predial: apenas uma empresa cuida dos elevadores (singleton) e qualquer desvio no padrão de segurança interdita a operação (strictVersion).

Como surgiu

Nos primórdios das arquiteturas distribuídas no navegador, o compartilhamento de código dependia de scripts globais injetados em tags <script> e objetos colidindo em window. Esse modelo causava sobrescritas acidentais de versões e bugs silenciosos impossíveis de rastrear.

Veio substituir: scripts globais em window sem controle de versão semântica e duplicação descontrolada de frameworks em memória.

O mecanismo

O federation.config.js é lido pelo plugin de build para gerar os metadados da federação (o remoteEntry.json, com os módulos expostos e as dependências compartilhadas) e o import map usado em tempo de execução. Ao configurar singleton: true, o runtime assegura que apenas uma instância da biblioteca seja mantida na memória. O atributo strictVersion: true emite erro explícito caso o remote exija uma faixa SemVer incompatível.

Para que serve

Garantir integridade arquitetural em tempo de execução, impedindo que múltiplos bundles carreguem instâncias duplicadas de bibliotecas sensíveis a estado ou versões mutuamente incompatíveis.

Por que é importante

Bibliotecas como React, Angular Router e stores globais mantêm estados em instâncias de memória do módulo. Carregar duas instâncias quebra a reatividade da interface e pode causar vazamento crítico de memória no navegador.

Como usar

O mecanismo

Comunicação e orquestração desacoplada: CustomEvent, BroadcastChannel e sincronização de rotas

essencialpadrões de eventos
💻 CENÁRIO HIPOTÉTICO DE PRODUÇÃO

O micro frontend de Carrinho precisava atualizar o contador de itens no micro frontend de Cabeçalho (Header). Semanas depois, o squad do Cabeçalho refatorou a arquitetura interna e renomeou o método para setItemCount(), quebrando silenciosamente o fluxo de compras de toda a plataforma em produção. Direto: A comunicação entre micro frontends deve ser baseada em padrões de acoplamento frouxo para preservar a autonomia de desenvolvimento e deploy das equipes. Se um micro frontend invocar métodos internos ou referenciar classes de outro remoto, cria-se um monólito distribuído no navegador. Os três padrões nativos recomendados são: CustomEvent para o mesmo documento, BroadcastChannel para comunicação multi-abas e a History API para delegação de rotas filhas.

Como surgiu

Veio substituir: estados globais acoplados em window e chamadas síncronas a métodos de instâncias de outros componentes.

O mecanismo

Ao emitir uma ação, o remote dispara um CustomEvent nativo em window com um payload imutável em detail. Outros remotes registram addEventListener('cart:updated', handler). Para sincronizar abas distintas, o BroadcastChannel publica mensagens pela mesma origem sem passar por servidores de rede.

Para que serve

Permitir que micro frontends colaborem e troquem dados essenciais sem conhecer a implementação interna, a linguagem ou o framework dos outros módulos participantes da tela.

Por que é importante

O acoplamento rígido de código em tempo de execução anula toda a justificativa de adotar micro frontends. A comunicação assíncrona por eventos é a salvaguarda que preserva a independência operacional das equipes.

Como usar

O contrato do evento mora num pacote só de tipos, versionado. Quem emite não sabe quem escuta; quem escuta confere a versão antes de usar o payload.

// remote carrinho: emite

  detail: { versao: 1, quantidade: 3 },
}));

// remote header: escuta
window.addEventListener('cart:updated', (e) => {
  const d = (e as CustomEvent<CartUpdatedV1>).detail;
  if (d.versao !== 1) return;          // versão desconhecida: ignora em vez de quebrar
  badge.textContent = String(d.quantidade);
});

// logout em todas as abas da mesma origem
const canal = new BroadcastChannel('sessao');
canal.postMessage({ tipo: 'logout' });
canal.onmessage = (m) => { if (m.data.tipo === 'logout') location.assign('/login'); };

Autenticação e estado compartilhado: o login acontece uma vez, no shell

essencialsegurança
💻 CENÁRIO HIPOTÉTICO DE PRODUÇÃO

Num portal com cinco micro frontends, cada time integrou o login do Keycloak por conta própria. O usuário via o redirecionamento de login mais de uma vez ao navegar, cada remote guardava o token no localStorage com uma chave diferente, e o logout de um não derrubava a sessão dos outros. A correção concentrou o login no shell e passou aos remotes só uma biblioteca compartilhada com dois métodos: obter o token atual e obter os dados básicos do usuário.

Direto: Num sistema de micro frontends, a sessão tem um dono: o shell. Ele faz o login OIDC uma vez, guarda o token e renova quando precisa. Os remotes recebem um contrato pequeno, normalmente uma biblioteca compartilhada como singleton, para pedir o token atual e saber quem é o usuário. O mesmo vale para outros estados transversais (idioma, tema). O estado de negócio, como o conteúdo do carrinho, fica dentro do remote dono dele.

≈

A pulseira do evento. Você mostra o documento uma vez, na entrada (o shell), e recebe uma pulseira. Cada palco (remote) só confere a pulseira; nenhum deles pede o documento de novo, e nenhum guarda a sua carteira.

Como surgiu

As primeiras arquiteturas de micro frontends repetiram o que cada SPA fazia sozinha: cada remote com o seu login. Outras tentaram resolver o compartilhamento com uma store global (Redux em window), o que acoplou todos os times ao formato daquele estado.

Veio substituir: o login feito por cada micro frontend e a store global com o estado de todo mundo.

O mecanismo

O shell faz o fluxo Authorization Code com PKCE no Keycloak e guarda o token de acesso em memória. Uma biblioteca, por exemplo @loja/auth, é declarada como singleton no shared de todos: assim shell e remotes usam a mesma instância. O shell grava o token nela; os remotes só leem. Cada API Spring valida o JWT de forma independente. Uma variante mais segura é o BFF: o token fica no servidor, e o navegador só tem um cookie HttpOnly.

Para que serve

Dar ao usuário um login só, um logout que vale para tudo e um único lugar para renovar o token; e evitar que cada time reimplemente autenticação do seu jeito.

Por que é importante

Todos os remotes rodam na mesma origem. Um XSS no código de qualquer time consegue ler o que estiver no localStorage de todos. Quanto menos lugares guardam o token, e quanto menos ele fica exposto ao JavaScript, menor o estrago de uma falha.

Como usar

A biblioteca compartilhada é o contrato inteiro. O shell grava, os remotes leem. No backend, cada API Spring valida o token como resource server, como no tópico de Keycloak.

  },
  token(): string {
    if (!tokenAtual) throw new Error('sem sessão');
    return tokenAtual;
  },
  usuario() { return usuarioAtual; },
};

A correção tirou o CSS global dos remotes: o shell passou a definir os tokens de cor e espaçamento, o design system virou um pacote versionado e cada remote escopou os próprios estilos.

Direto: Duas coisas diferentes precisam ser resolvidas juntas. A consistência vem de um design system publicado como pacote versionado: tokens (cores, espaçamentos, tipografia) e componentes. O isolamento vem de escopar o CSS de cada time, para que nada de um vaze para o outro. O único CSS global de propósito são os tokens, definidos pelo shell.

≈

O manual de identidade visual de uma rede de franquias. Toda loja usa as mesmas cores, a mesma fonte e o mesmo logo (os tokens). Mas cada franqueado arruma a sua loja por dentro, e a reforma de uma não muda a parede da loja vizinha (o CSS escopado).

Como surgiu

Nas primeiras integrações, cada remote trazia a própria cópia do CSS do framework e do reset. Como o CSS é global por natureza, a ordem de carregamento decidia qual regra vencia, e ela mudava conforme a navegação do usuário.

Veio substituir: cada remote carregando a sua cópia do CSS global e sobrescrevendo, sem querer, o dos outros.

O mecanismo

O shell define os tokens como custom properties em :root. Custom properties são herdadas, inclusive para dentro do Shadow DOM, então todos os remotes usam os mesmos valores. Os componentes do design system vêm de um pacote compartilhado (singleton) ou como Web Components. Cada remote escopa o seu CSS: o encapsulamento emulado do Angular faz isso por padrão nos componentes; CSS Modules geram nomes únicos; um prefixo por time resolve o que sobra. @layer define a ordem das camadas, para que o resultado não dependa de quem carregou primeiro.

Para que serve

Deixar a aplicação com cara de um produto só, mesmo feita por vários times, sem que a mudança de estilo de um time quebre a tela de outro.

Por que é importante

O usuário não sabe que existem times. Para ele, botões diferentes em telas vizinhas são defeito. E vazamento de CSS é um dos bugs mais comuns e mais difíceis de rastrear em micro frontends, porque depende da ordem de navegação.

Como usar

O shell define os tokens e a ordem das camadas; o remote usa os tokens dentro da sua camada e com o seu prefixo.

/* shell: a única coisa global de propósito */
@layer reset, design-system, remotes;

:root {
  --cor-primaria: #bd93f9;
  --cor-texto: #f8f8f2;
  --espaco-2: 8px;
  --raio: 6px;
}

/* remote checkout: tudo na camada dele e com o prefixo do time */
@layer remotes {
  .chk-botao {
    background: var(--cor-primaria);
    color: var(--cor-texto);
    padding: var(--espaco-2);
    border-radius: var(--raio);
  }
}
Para ir alémShadow DOM: isolamento total, com custo

Um Web Component com Shadow DOM isola o CSS nos dois sentidos: nada entra, nada sai. Custom properties atravessam a fronteira, então os tokens continuam funcionando. O custo aparece em estilos globais que você quer que entrem (fontes, reset), em foco e formulários, e na integração com alguns frameworks. Use quando o remote é de fato uma ilha, como um widget de terceiro.

Performance: o custo de dividir e como medir e cortar

importanteweb vitals
💻 CENÁRIO HIPOTÉTICO DE PRODUÇÃO

Depois da migração para micro frontends, o LCP da home piorou em celulares. O trace do DevTools mostrou uma cascata: o shell baixava o manifesto, depois o remoteEntry.json de cada remote, depois o módulo, e só então as dependências. Dois remotes ainda traziam cada um a sua cópia de uma biblioteca de datas. Com pré-carregamento do remote da home, compartilhamento da biblioteca e orçamento de tamanho no CI, a home voltou ao tempo de antes da migração.

Direto: Micro frontends quase sempre custam desempenho: há mais requisições, existe o risco de baixar a mesma dependência duas vezes, e um arquivo só é descoberto depois de outro, em cascata. O trabalho é medir com os Core Web Vitals (LCP, INP e CLS) e cortar: compartilhar o que é grande, pré-carregar o que a primeira tela precisa, adiar o resto e pôr um orçamento de tamanho por remote no CI.

≈

Pedir comida de vários restaurantes. Se cada restaurante só começa a preparar depois que o anterior entregou, o jantar demora a soma de todos. O app que avisa todos ao mesmo tempo (pré-carregamento) e junta as bebidas num pedido só (dependência compartilhada) faz tudo chegar quase junto.

Como surgiu

A promessa inicial dos micro frontends era organizacional, e o desempenho ficou em segundo plano. Com o Google usando Core Web Vitals como sinal de ranqueamento desde 2021, e com o INP substituindo o FID em março de 2024, o custo de dividir passou a aparecer em métricas que o negócio acompanha.

Veio substituir: a medição só na máquina do desenvolvedor e a ideia de que dividir o frontend é neutro para o usuário.

O mecanismo

A cascata típica é: shell → manifesto → remoteEntry.json → módulo do remote → dependências. Cada etapa só é descoberta quando a anterior termina. <link rel="modulepreload"> manda o navegador baixar um módulo antes de ele ser pedido; HTTP/2 permite muitas requisições na mesma conexão; arquivos com hash no nome podem ter cache longo e imutável; dependências grandes declaradas como shared são baixadas uma vez. O orçamento de tamanho falha o build quando um remote passa do limite.

Para que serve

Manter os ganhos organizacionais sem que o usuário pague com uma página mais lenta; e dar a cada time um limite claro de quanto peso ele pode adicionar.

Por que é importante

Desempenho é recurso compartilhado: cada remote que cresce piora a página de todos, e nenhum time sozinho vê o total. Sem orçamento e medição, a página degrada aos poucos, um deploy de cada vez.

Como usar

No Angular, o orçamento fica no angular.json de cada remote e quebra o build quando passa do limite. Os arquivos com hash vão com cache longo; o que não tem hash (manifesto, remoteEntry.json num caminho fixo) vai sem cache.

// angular.json, em projects.<remote>.architect.build.configurations.production
"budgets": [
  { "type": "initial", "maximumWarning": "300kB", "maximumError": "500kB" },
  { "type": "anyComponentStyle", "maximumWarning": "4kB", "maximumError": "8kB" }
]

<!-- shell: index.html, pré-carregando o que a home usa -->
<link rel="modulepreload" href="https://cdn.loja.com/catalogo/v42/vitrine.js">

# cabeçalhos por tipo de arquivo
/catalogo/v42/vitrine-3f9a1c.js   Cache-Control: public, max-age=31536000, immutable
/federation.manifest.json         Cache-Control: no-cache
Para ir alémDados de campo contra dados de laboratório

O Lighthouse mede numa máquina e numa rede simuladas (dados de laboratório). Os usuários reais, com celulares variados, aparecem nos dados de campo: o relatório CrUX do Chrome ou a biblioteca web-vitals enviando as métricas para a sua observabilidade. Em micro frontends, os dados de campo por rota mostram qual remote está pesando, coisa que o laboratório, rodando só a home, não mostra.

  • Framework duplicado: sem singleton, duas cópias de React ou Angular dobram o peso e ainda quebram em runtime.
  • Carregar todos os remotes na abertura: a home paga por telas que o usuário talvez nunca abra.
  • Medir só na máquina do time: notebook rápido e rede boa escondem o problema que aparece no celular do usuário.

Testes, versionamento e deploy independente: publicar sozinho sem quebrar o vizinho

importanteentrega contínua
💻 CENÁRIO HIPOTÉTICO DE PRODUÇÃO

O time de Checkout renomeou o módulo exposto de ./Component para ./routes. Os testes do próprio remote passaram, o deploy saiu numa terça à tarde, e o shell passou a mostrar o fallback de indisponível no checkout. Ninguém tinha testado o contrato entre os dois. A correção trouxe três mudanças: um teste de contrato no CI do Checkout, deploy em pasta versionada e promoção só pelo manifesto. Voltar à versão anterior passou a ser trocar uma linha.

Direto: Deploy independente só é seguro com duas garantias. A primeira é testar, no CI de cada time, o contrato com o resto: o que o remote expõe, os eventos que emite e as dependências compartilhadas. A segunda é publicar cada versão numa pasta imutável e promover trocando o manifesto. Voltar atrás é apontar o manifesto para a versão anterior, sem rebuild.

≈

A troca de uma peça num carro de corrida. Antes de montar, a equipe confere se a peça nova encaixa no mesmo suporte (teste de contrato). A peça antiga fica no box (pasta versionada). Se a nova der problema na volta de teste, a troca de volta leva segundos (rollback pelo manifesto).

Como surgiu

Com o deploy independente, os testes E2E feitos só no app integrado viraram gargalo: são lentos, instáveis e rodam tarde demais. A prática dos testes de contrato, já usada entre microsserviços, foi trazida para o frontend. A publicação em pastas imutáveis veio da mesma ideia das imagens de contêiner com tag: o artefato não muda depois de publicado.

Veio substituir: a bateria de E2E integrada como única garantia e o deploy que sobrescreve os arquivos da versão anterior.

O mecanismo

A pirâmide fica assim: testes unitários e de componente dentro do remote; um teste de contrato no CI do produtor, que confere que os módulos expostos e os tipos dos eventos continuam compatíveis; poucos E2E de fumaça no shell integrado, em homologação. O pipeline publica em /checkout/v43/, roda a fumaça contra essa versão e só então troca a linha do checkout no manifesto. Um canário é possível servindo manifestos diferentes para uma parte dos usuários.

Para que serve

Permitir que cada time publique várias vezes por dia sem coordenação, com a segurança de que não quebrou o shell nem os vizinhos e de que pode voltar atrás em segundos.

Por que é importante

Sem contrato testado, a independência vira sorte: a quebra aparece em produção, na tela de outro time. E sem rollback rápido, cada incidente dura o tempo de um novo build.

Como usar

No CI do time, a versão vai para uma pasta própria com cache imutável, passa pela fumaça e só depois o manifesto muda. O teste de contrato roda antes de tudo isso.

# CI do time Checkout
npm ci && npm test                       # unitários + contrato dos exposes e eventos
npm run build

aws s3 sync dist/checkout "s3://loja-mfe/checkout/v$BUILD/" \
  --cache-control "public,max-age=31536000,immutable"

npx playwright test --grep @fumaca-checkout   # shell de homologação apontando para v$BUILD

# promoção: só o manifesto muda
jq --arg u "https://cdn.loja.com/checkout/v$BUILD/remoteEntry.json" \
   '.checkout = $u' manifesto.json > novo.json
aws s3 cp novo.json s3://loja-mfe/federation.manifest.json --cache-control "no-cache"

# rollback: o mesmo comando com a versão anterior
Para ir alémMudança que quebra o contrato: expanda, migre, contraia

Para renomear um módulo exposto ou mudar o formato de um evento sem quebrar ninguém, siga três passos. Primeiro, exponha os dois (o antigo e o novo) ou emita as duas versões do evento. Depois, espere os consumidores migrarem. Só então remova o antigo. É a mesma técnica usada para mudar colunas de banco sem parada.

  • Mudar o que é exposto sem transição: renomear um módulo ou um campo de evento quebra o shell na hora. Expanda, migre, contraia.
  • Major de dependência compartilhada sem coordenação: com strictVersion, um remote com uma major nova recusa carregar; sem ele, quebra em runtime. Planeje esse salto entre os times.
