Ambiente e projeto

Onde o Python mora, onde ficam as dependências e como o projeto se organiza.

Ambiente, dependências e pyproject.toml

essencial

Direto: O pyproject.toml é o pom.xml do Python: descreve o projeto e as dependências. Cada projeto tem o próprio ambiente virtual (.venv), uma pasta com o interpretador e as bibliotecas só daquele projeto. Ferramentas como o uv criam o ambiente, instalam as dependências e travam as versões num arquivo de lock.

o caso

Você instala o FastAPI com pip install fastapi direto no Python do sistema. Um mês depois, outro projeto precisa de uma versão diferente da mesma biblioteca, e atualizar uma quebra a outra. No Java isso não acontece porque o Maven resolve as dependências por projeto no ~/.m2 e monta o classpath de cada build. No Python, sem um ambiente virtual por projeto, todos os projetos dividem a mesma pasta de bibliotecas.

≈

Analogia. É como ter uma caixa de ferramentas por obra em vez de uma única caixa para todas. Cada obra leva só o que precisa, na versão que precisa, e o que acontece numa não estraga a outra.

Como surgiu

O Python instalava pacotes num lugar global do sistema. Isso funcionava com um projeto por máquina e virou problema quando vários projetos com versões diferentes passaram a conviver.

Veio substituir: o pip install no Python do sistema e o requirements.txt sem versão travada, que davam builds diferentes em máquinas diferentes.

O mecanismo

O ambiente virtual é uma pasta (.venv) com um link para o interpretador e um diretório site-packages próprio. Ativar o ambiente só coloca essa pasta na frente do PATH; o python e o pip passam a apontar para ela.

O pyproject.toml declara as dependências com faixas de versão; o arquivo de lock (por exemplo, uv.lock) grava as versões exatas que foram resolvidas. É o mesmo papel das versões fixas no pom.xml com o dependencyManagement.

Para que serve

Ter builds reproduzíveis: qualquer pessoa (ou o CI, ou o Docker) recria o mesmo ambiente com um comando, sem depender do que está instalado na máquina.

Por que é importante

Quase todo "na minha máquina funciona" em Python vem daqui. É a primeira coisa que uma vaga de AI Engineer espera que você saiba fazer sem pensar, e a base de qualquer imagem Docker de projeto Python.

a ponte com o Javapom.xml ↔ pyproject.toml; mvn install ↔ uv sync; ~/.m2 ↔ .venv/ (só que por projeto); mvn exec:java ↔ uv run.

Como usar.

uv init meu-chat          # cria pyproject.toml
cd meu-chat
uv add fastapi uvicorn    # adiciona e trava no uv.lock
uv add --dev pytest       # dependência só de desenvolvimento
uv run uvicorn main:app --reload
Para ir alémpip, venv e Poetry: as outras formas

Sem o uv, o caminho padrão da própria linguagem é python -m venv .venv, ativar o ambiente e usar pip install. O Poetry é outra ferramenta popular que também usa o pyproject.toml e um lock. Em projetos antigos você vai encontrar requirements.txt: é só uma lista de pacotes, sem a descrição do projeto.

Ferramentas mudam rápido; confira na documentação qual é a recomendada hoje.
armadilhas
  • Esquecer de ativar o ambiente e instalar no Python do sistema. Com uv run isso não acontece.
  • Commitar a pasta .venv. Ela vai no .gitignore; o que se commita é o pyproject.toml e o lock.
  • Não commitar o lock. Sem ele, o build de amanhã pode trazer versões diferentes das de hoje.

Módulos, pacotes e imports

essencial

Direto: Cada arquivo .py é um módulo e cada pasta com módulos é um pacote. O import carrega o módulo e executa o código dele uma vez. Não há public e private: por convenção, nomes começados com _ são internos. O bloco if __name__ == "__main__": é o equivalente ao public static void main.

o caso

Você organiza o projeto como no Java, com uma classe por arquivo e pastas profundas. Logo aparecem imports como from app.services.llm.provider.openai_provider import OpenAIProvider e um erro de import circular entre dois serviços. Em Python, módulos agrupam várias classes e funções relacionadas, e a estrutura costuma ser mais rasa.

≈

Analogia. O módulo é uma gaveta com tudo de um assunto, não uma gaveta por objeto. No Java cada ferramenta tem sua caixinha; no Python a gaveta "chaves" guarda todas as chaves juntas.

Como surgiu

O Python organiza código por arquivo desde o início. Os pacotes vieram para agrupar módulos em pastas, e a convenção do sublinhado substituiu os modificadores de acesso, porque a linguagem confia no programador.

Veio substituir: a ideia de uma classe pública por arquivo e de visibilidade controlada pelo compilador.

O mecanismo

No primeiro import, o Python procura o módulo nos caminhos de sys.path (o classpath), executa o arquivo de cima a baixo e guarda o resultado em sys.modules. Os imports seguintes reaproveitam esse objeto.

Quando o arquivo é executado direto (python main.py), a variável __name__ vale "__main__"; quando é importado, vale o nome do módulo. Por isso o código de inicialização fica dentro daquele if.

Para que serve

Organizar o projeto em partes com responsabilidade clara, evitar imports circulares e separar o que é público do que é interno.

Por que é importante

Projetos de IA crescem rápido (rotas, provedores, RAG, ferramentas). Uma estrutura de pacotes simples é o que mantém o projeto navegável e testável quando ele passa de três arquivos.

a ponte com o Javapackage ↔ pasta; classe pública por arquivo ↔ módulo com várias definições; classpath ↔ sys.path; private ↔ prefixo _ (convenção); main ↔ if __name__ == "__main__".

armadilhas
  • Import circular. Dois módulos que se importam no topo falham; mova o que é comum para um terceiro módulo.
  • Código pesado no topo do módulo. Ele roda no import; conexões e leituras ficam em funções.
  • Dar ao arquivo o nome de uma biblioteca (json.py, fastapi.py): o seu arquivo é importado no lugar dela.

A linguagem pelo olhar do Java

O que muda de comportamento: tipos, coleções, funções e exceções.

Tipagem dinâmica, type hints e mypy

essencial

Direto: Em Python o tipo pertence ao valor, não à variável: a mesma variável pode guardar um número e depois um texto. As anotações de tipo (def total(itens: list[int]) -> int) documentam a intenção, mas o interpretador não as confere. Quem confere é uma ferramenta estática, como o mypy ou o pyright, que faz o papel do compilador do Java.

o caso

Uma função recebe preco e, num caminho raro, alguém passa o preço como texto vindo de um formulário. No Java o compilador recusaria; no Python o código roda e o erro aparece só quando preco * 1.1 repete o texto em vez de multiplicar. Rodar o mypy no CI teria pego isso antes do deploy.

≈

Analogia. A anotação de tipo é a placa "cuidado, piso molhado": avisa quem lê, mas não impede ninguém de passar. O mypy é o segurança que lê as placas e barra quem vai escorregar, antes de abrir a loja.

Como surgiu

O Python nasceu sem tipos declarados, para ser rápido de escrever. Com bases de código grandes, faltava o que o compilador do Java dá de graça: saber o que cada função recebe e devolve. As anotações entraram na linguagem e as ferramentas de checagem vieram em seguida.

Veio substituir: a documentação de tipos em comentários e docstrings, que ninguém conferia e ficava desatualizada.

O mecanismo

As anotações ficam guardadas no atributo __annotations__ da função ou da classe e não mudam a execução. O mypy lê o código sem executar e acusa as incompatibilidades, como um javac que só avisa.

Os tipos usam a sintaxe moderna: list[str], dict[str, int], str | None (o Optional). Bibliotecas como o Pydantic e o FastAPI leem essas anotações em tempo de execução e as usam para validar.

Para que serve

Ter a segurança e o autocompletar de uma linguagem tipada sem perder a flexibilidade do Python, e dar ao Pydantic e ao FastAPI a informação de que eles precisam.

Por que é importante

Todo código Python profissional moderno é anotado, e as bibliotecas de IA dependem das anotações para validar e gerar schemas. Para quem vem do Java, é o que torna o Python legível.

a ponte com o Javatipo declarado na variável ↔ anotação opcional; javac ↔ mypy; Optional<T> ↔ T | None; generics List<String> ↔ list[str].

Como usar.

def total(precos: list[float], desconto: float | None = None) -> float:
    soma = sum(precos)
    return soma * (1 - desconto) if desconto else soma

total(["10", "20"])   # roda até quebrar; o mypy acusa antes:
# error: List item 0 has incompatible type "str"; expected "float"
Para ir alémStrict, Any e o custo de anotar tudo

O mypy em modo --strict exige anotação em tudo e recusa o Any implícito. Comece sem o strict num projeto existente e aperte aos poucos. O Any desliga a checagem daquele valor: é a saída de emergência, não o padrão.

armadilhas
  • Achar que a anotação é verificada ao rodar. Sem mypy no CI, ela é só documentação.
  • Usar None sem declarar. nome: str = None está errado; o certo é nome: str | None = None.
  • Anotar com Any para calar o erro. Isso desliga a checagem, não resolve o problema.

Coleções e compreensões

essencial

Direto: As coleções vêm na linguagem: list (≈ ArrayList), dict (≈ HashMap, mas mantém a ordem de inserção), set e tuple (lista imutável). As compreensões, como [p.total for p in pedidos if p.pago], fazem numa linha o que no Java é um stream().filter().map().toList().

o caso

Você porta um método que filtra pedidos pagos e soma o total. A versão Java tem um stream com quatro operações; a primeira versão em Python tem um for com append, igual ao Java antigo. Um colega reescreve como sum(p.total for p in pedidos if p.pago): uma linha, mais rápida e mais fácil de ler.

≈

Analogia. A compreensão é o pedido feito ao garçom de uma vez ("todos os sucos, sem gelo") em vez de pedir item por item. O resultado é o mesmo; a frase diz o que você quer, não os passos.

Como surgiu

O Python sempre teve listas e dicionários como tipos centrais. As compreensões vieram da programação funcional para substituir o laço com append, que era o jeito mais comum e mais verboso de montar uma coleção.

Veio substituir: o laço for com uma lista vazia e append a cada item, e o uso de map e filter com lambdas.

O mecanismo

A list é um array dinâmico de referências; o dict é uma tabela hash que guarda a ordem de inserção. A tupla é imutável e pode ser chave de dicionário.

Uma compreensão entre colchetes monta a lista inteira na memória; entre parênteses vira um gerador, que produz um item por vez, como um Stream preguiçoso. Para somar ou percorrer uma vez, o gerador gasta menos memória.

Para que serve

Transformar e filtrar dados com pouco código, que é a maior parte do trabalho com respostas de APIs, documentos e resultados de busca num projeto de IA.

Por que é importante

É o código que você mais vai escrever em Python. Ler e escrever compreensões com fluência é o que faz seu código parecer de quem sabe Python, e não de quem traduziu do Java.

a ponte com o JavaArrayList ↔ list; HashMap/LinkedHashMap ↔ dict; Set.of ↔ set; List.of imutável ↔ tuple; stream().filter().map() ↔ compreensão.

Como usar.

pagos = [p for p in pedidos if p.pago]              # filter
totais = [p.total for p in pagos]                   # map
por_id = {p.id: p for p in pedidos}                 # toMap
soma = sum(p.total for p in pedidos if p.pago)      # gerador, sem lista
primeiro, *resto = totais                           # desempacotar
Para ir alémQuando não usar compreensão

Se a compreensão precisa de dois for e dois if, ou de efeitos colaterais (gravar, imprimir), volte para o laço comum. Compreensão é para montar uma coleção a partir de outra; se ela não cabe numa leitura, ficou grande demais.

armadilhas
  • Montar lista só para somar ou percorrer. Use o gerador (parênteses) e economize memória.
  • Mudar a lista enquanto percorre. Remover itens dentro do for pula elementos; monte uma lista nova.
  • Usar lista como chave de dicionário. Lista é mutável e não pode; use tupla.

Funções, argumentos e decorators

essencial

Direto: Funções são objetos: podem ser passadas, guardadas e devolvidas. Argumentos podem ter valor padrão e ser passados pelo nome, o que substitui a sobrecarga de métodos do Java. *args e **kwargs recebem argumentos extras. Um decorator (@algo) é uma função que envolve outra e acrescenta comportamento, como o AOP do Spring.

o caso

No Java você teria três sobrecargas de buscar(texto), buscar(texto, limite) e buscar(texto, limite, filtro). Em Python é uma função só, com valores padrão, chamada como buscar("pgvector", limite=5). E para medir o tempo de cada chamada ao LLM, em vez de repetir o cronômetro em cada função, você escreve um decorator @medir_tempo.

≈

Analogia. O decorator é a capa de chuva: a pessoa (a função) continua a mesma, mas sai de casa com uma camada a mais por cima. Tirar a capa não muda a pessoa.

Como surgiu

Como o Python não tem sobrecarga de métodos, os argumentos com nome e valor padrão cumprem esse papel. Os decorators vieram para trocar o padrão de envolver funções à mão por uma sintaxe curta.

Veio substituir: a sobrecarga de métodos e o código de log, cache ou medição copiado em cada função.

O mecanismo

@medir_tempo em cima de def chamar() é só um atalho para chamar = medir_tempo(chamar): o decorator recebe a função e devolve outra que a envolve. É o que um proxy do Spring faz, só que explícito e sem container.

Na chamada, os argumentos posicionais vêm primeiro, depois os nomeados. Tudo que sobra cai em *args (tupla) e **kwargs (dicionário).

Para que serve

Escrever funções flexíveis sem sobrecarga e acrescentar comportamento transversal (log, cache, retry, medição) sem repetir código.

Por que é importante

O FastAPI, o pytest e as bibliotecas de IA são construídos com decorators (@app.get, @pytest.fixture, @tool). Entender o mecanismo é entender como essas bibliotecas funcionam.

a ponte com o Javasobrecarga ↔ valores padrão e argumentos com nome; varargs ↔ *args; lambda ↔ lambda (só uma expressão); AOP e anotações com proxy ↔ decorator.

Como usar.

import functools, time

def medir_tempo(func):
    @functools.wraps(func)
    def envolta(*args, **kwargs):
        ini = time.perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            print(f"{func.__name__}: {time.perf_counter() - ini:.2f}s")
    return envolta

@medir_tempo
def buscar(texto: str, limite: int = 3, filtro: str | None = None): ...

buscar("pgvector", limite=5)
Para ir alémDecorators com parâmetro

@retry(tentativas=3) é um decorator que recebe parâmetros: é uma função que devolve o decorator. Isso dá três funções aninhadas. Na prática, bibliotecas como a tenacity já fazem retry assim; escreva o seu só para entender o mecanismo.

armadilhas
  • Lista ou dicionário como valor padrão. def f(itens=[]) compartilha a mesma lista entre chamadas; use None e crie dentro.
  • Esquecer o functools.wraps. Sem ele, a função decorada perde o nome e a documentação, e o FastAPI e o pytest se confundem.
  • Lambda grande. Lambda tem uma expressão só; se precisa de mais, escreva uma função com nome.

Exceções e context managers

essencial

Direto: Exceções funcionam como no Java, com try/except/finally, mas não há checked exceptions: nada obriga a declarar ou tratar. O with é o try-with-resources: garante que o recurso (arquivo, conexão, cliente HTTP) seja fechado, mesmo com erro. Qualquer objeto com __enter__ e __exit__ funciona no with.

o caso

Seu serviço lê documentos para indexar no RAG e, sob carga, para de abrir arquivos com "too many open files". O código usava open() sem fechar quando a leitura falhava no meio. Trocar por with open(caminho) as f: fecha o arquivo em qualquer caso, como o try-with-resources do Java fecharia.

≈

Analogia. O with é a porta com mola: você entra, faz o que precisa e, saia como sair (calmo ou correndo), ela fecha sozinha atrás de você.

Como surgiu

O try/finally para fechar recursos era repetido em todo lugar e esquecido com frequência. O with entrou para empacotar esse padrão num protocolo que qualquer classe pode implementar.

Veio substituir: o try/finally manual com close() no finally, igual ao Java antes do try-with-resources.

O mecanismo

Ao entrar no with, o Python chama __enter__ e entrega o resultado à variável depois do as. Ao sair, normalmente ou por exceção, chama __exit__, que fecha o recurso. É o AutoCloseable do Java.

Para criar o seu, o decorator @contextmanager transforma uma função com yield num context manager: o que vem antes do yield é a abertura, o que vem depois é o fechamento.

Para que serve

Garantir que conexões, arquivos e clientes sejam liberados, e tratar falhas de APIs externas (como o provedor do LLM) de forma explícita.

Por que é importante

Serviços de IA vivem de chamadas externas que falham: timeout, limite de uso, resposta inválida. Tratar exceção com precisão e liberar recursos é o que separa um protótipo de um serviço que aguenta produção.

a ponte com o Javatry/catch/finally ↔ try/except/finally; checked exceptions ↔ não existem; try-with-resources ↔ with; AutoCloseable ↔ __enter__/__exit__; throw ↔ raise.

Como usar.

class LLMIndisponivel(Exception):
    pass

def responder(pergunta: str) -> str:
    try:
        with httpx.Client(timeout=10) as cliente:      # fecha sempre
            r = cliente.post(URL, json={"q": pergunta})
            r.raise_for_status()
            return r.json()["resposta"]
    except httpx.TimeoutException as e:
        raise LLMIndisponivel("o provedor não respondeu") from e
Para ir alémraise ... from e e a cadeia de causas

raise NovaExcecao(...) from e guarda a exceção original como causa, como o new RuntimeException(msg, e) do Java. O traceback mostra as duas. Sem o from, a causa ainda aparece, mas como "durante o tratamento, outra exceção ocorreu", o que confunde quem lê o log.

armadilhas
  • except: sem tipo ou except Exception: pass: engole tudo, até o Ctrl+C e os bugs. Capture o tipo específico.
  • Abrir recurso sem with. Se der erro no meio, o recurso fica aberto.
  • Perder a causa. Ao trocar a exceção, use raise ... from e.

Modelando dados

Onde o Java usa POJO, record e DTO com Bean Validation, o Python tem dataclass e Pydantic.

Classes, dataclass e duck typing

essencial

Direto: Classe em Python não declara campos nem tipos obrigatórios: os atributos nascem no __init__. O @dataclass gera construtor, __eq__ e __repr__ a partir de campos anotados, como um record. Não há interface: se o objeto tem o método que você chama, funciona (duck typing); para declarar o contrato, existe o Protocol.

o caso

Você porta um DTO Pedido do Java e escreve uma classe com __init__, getters e setters. Fica com o dobro de linhas e ninguém no time usa getter em Python. Pior: você escreve preco: int, alguém passa "10" e nada reclama, porque a anotação de tipo não é verificada em tempo de execução.

≈

Analogia. Duck typing é contratar pelo que a pessoa sabe fazer, não pelo diploma. Se ela sabe dirigir, serve para motorista; o Java pediria a carteira (a interface) antes de deixar sentar no banco.

Como surgiu

O Python nasceu dinâmico e pequeno, sem cerimônia de tipos. As anotações de tipo vieram depois, opcionais, e o @dataclass entrou para acabar com o código repetitivo das classes de dados.

Veio substituir: as classes escritas à mão, com __init__, __eq__ e __repr__ repetidos em cada uma, e os dicionários soltos usados como objeto.

O mecanismo

Tudo é objeto e os atributos ficam num dicionário da instância; por isso dá para criar um atributo em qualquer momento. O @dataclass lê as anotações da classe e gera os métodos na hora em que a classe é definida. Com frozen=True, a instância fica imutável, como um record.

As anotações de tipo são só metadados: o interpretador não as confere. Quem confere é uma ferramenta estática (mypy, pyright) ou uma biblioteca em tempo de execução, como o Pydantic.

Para que serve

Modelar os dados do domínio com pouco código e escolher o nível de garantia: dataclass para dados internos, Pydantic quando os dados vêm de fora e precisam ser validados.

Por que é importante

Todo o ecossistema de IA em Python (FastAPI, LangChain, SDKs dos provedores) é construído em cima de modelos Pydantic e dataclasses. Entender a diferença entre anotar e validar evita a maior parte dos bugs de quem vem do Java.

a ponte com o JavaPOJO ↔ classe comum; record ↔ @dataclass(frozen=True); interface ↔ Protocol; Bean Validation ↔ Pydantic; Lombok ↔ não precisa.

Como usar.

from dataclasses import dataclass
from typing import Protocol

@dataclass(frozen=True)
class Pedido:              # ~ record Pedido(String id, int total)
    id: str
    total: int

class Notificador(Protocol):   # ~ interface
    def enviar(self, msg: str) -> None: ...

def avisar(n: Notificador, p: Pedido) -> None:
    n.enviar(f"pedido {p.id}: {p.total}")
Para ir alémPydantic: quando o tipo precisa ser verdade

Troque @dataclass por class Pedido(BaseModel) do Pydantic e o tipo passa a ser conferido na criação: "10" vira 10 e "abc" gera um erro claro. É o equivalente a um DTO com Bean Validation, e é o que o FastAPI usa para ler o corpo dos pedidos.

armadilhas
  • Achar que a anotação valida. total: int aceita uma string em tempo de execução; só o Pydantic ou o mypy pegam.
  • Valor padrão mutável. Em dataclass, itens: list = [] é proibido; use field(default_factory=list).
  • Escrever getters e setters. Em Python se acessa o atributo direto; se precisar de lógica, use @property depois.

Pydantic: validação, settings e schemas

essencial

Direto: O Pydantic transforma anotações de tipo em validação de verdade: um BaseModel confere e converte os dados na criação e gera um erro claro quando algo está errado. Ele também lê configurações de variáveis de ambiente (BaseSettings) e gera o JSON Schema do modelo, que é o formato que os provedores de LLM usam para saída estruturada e tool calling.

o caso

O LLM devolve um JSON que deveria ter nome, valor e urgente. Às vezes vem valor: "R$ 10", às vezes falta urgente. Com dict e if, cada campo vira três linhas de verificação. Com um modelo Pydantic, Pedido.model_validate_json(texto) valida tudo de uma vez e diz exatamente qual campo falhou, e a mensagem de erro volta para o LLM tentar de novo.

≈

Analogia. O Pydantic é a conferência na entrada do armazém: cada caixa é aberta, contada e etiquetada antes de entrar. O que passou da porta está certo; o que não está certo nem entra.

Como surgiu

Com as anotações de tipo na linguagem, faltava usá-las para validar dados de fora em tempo de execução. O Pydantic ocupou esse espaço e virou a base do FastAPI e de boa parte das bibliotecas de IA.

Veio substituir: a validação manual de dicionários com if e as configurações lidas com os.environ.get espalhado pelo código.

O mecanismo

Ao definir a classe, o Pydantic lê as anotações e monta um validador (o núcleo é escrito em Rust, por isso é rápido). Na criação, ele converte o que dá ("10" vira 10, no modo padrão) e junta todos os erros numa ValidationError.

Field(...) acrescenta regras (mínimo, máximo, padrão, descrição). model_json_schema() gera o schema que o FastAPI publica em /docs e que você pode mandar ao LLM. BaseSettings, do pacote pydantic-settings, preenche o modelo com as variáveis de ambiente.

Para que serve

Por que é importante

Saída estruturada e tool calling, dois temas centrais das vagas de AI Engineer, são feitos com modelos Pydantic em quase todas as bibliotecas Python. É a ponte direta entre o seu código e o LLM.

FastAPI: rotas, validação e injeção de dependência

essencial

Direto: FastAPI é um framework web em que a rota é uma função com decorator (@app.get), os parâmetros e o corpo são lidos e validados pelos tipos (com Pydantic) e as dependências são injetadas com Depends(). A documentação OpenAPI sai pronta em /docs.

o caso

Você precisa expor um modelo de IA numa API. No Spring seriam um controller, um DTO com Bean Validation, um service com @Autowired e o springdoc para a documentação. No FastAPI, uma função de dez linhas faz o mesmo: lê o corpo, valida, recebe o serviço injetado e aparece documentada. É por isso que as vagas de IA pedem FastAPI.

≈

Analogia. É o Spring Boot com as anotações viradas em tipos: em vez de dizer ao framework o que cada parâmetro é com @RequestBody e @PathVariable, você declara o tipo e ele deduz o resto.

Como surgiu

Os frameworks web do Python (Flask, Django) são anteriores às anotações de tipo e ao async. O FastAPI foi feito em cima dos dois: usa os tipos para validar e documentar e roda sobre o ASGI, que suporta async.

Veio substituir: o Flask com validação escrita à mão e documentação separada, que era o caminho comum para APIs pequenas em Python.

O mecanismo

Ao subir, o FastAPI lê a assinatura de cada função de rota. O que está no caminho vira parâmetro de path, tipos simples viram query string e modelos Pydantic viram o corpo. Com isso ele monta a validação e o schema OpenAPI.

Depends(funcao) diz ao framework para chamar aquela função a cada pedido e passar o resultado; dá para encadear dependências e trocar por uma falsa nos testes com app.dependency_overrides. O servidor que roda a aplicação é o uvicorn, como o Tomcat embutido do Spring Boot.

Para que serve

Publicar serviços HTTP em Python com validação e documentação automáticas, que é a forma padrão de servir modelos e agentes de IA.

Por que é importante

Aparece em boa parte das vagas de AI Engineer e é a porta de entrada do Projeto 1 da trilha de IA. Para quem vem do Spring, é o ponto em que você fica produtivo em Python mais rápido.

a ponte com o Java@RestController + @PostMapping ↔ @app.post; DTO + @Valid ↔ modelo Pydantic; @Autowired ↔ Depends(); springdoc ↔ /docs; Tomcat ↔ uvicorn.

Rotas com def rodam num pool de threads; com async def, rodam no loop de eventos e precisam usar bibliotecas assíncronas (por exemplo, o cliente HTTP assíncrono do provedor). Chamar uma função bloqueante dentro de async def trava o servidor inteiro. Na dúvida, comece com def.

Async, asyncio e o GIL

aprofundamento

Direto: async def declara uma corrotina e await pausa a corrotina até a operação de I/O terminar, liberando o loop de eventos para atender outras. É o modelo do WebFlux, não o das threads. O GIL (trava global do interpretador) faz que só uma thread execute código Python por vez; por isso, para esperar I/O se usa async ou threads, e para conta pesada se usa processos.

o caso

Seu endpoint chama o LLM e o banco vetorial, e cada chamada leva 2 segundos. Com 50 usuários ao mesmo tempo, o servidor fica lento. Você muda para async def mas continua usando um cliente HTTP síncrono: agora fica pior, porque cada chamada trava o loop inteiro. Trocar para o cliente assíncrono e fazer await resolve: enquanto um pedido espera o LLM, os outros andam.

≈

Analogia. O loop de eventos é um garçom só, atendendo muitas mesas: anota o pedido, entrega na cozinha e vai para a próxima mesa enquanto o prato fica pronto. Uma chamada bloqueante é o garçom parado na porta da cozinha esperando: todas as mesas ficam sem atendimento.

Como surgiu

Servidores Python usavam uma thread ou um processo por pedido, e o GIL limitava o ganho das threads. O asyncio trouxe a concorrência cooperativa, em que milhares de esperas de I/O cabem numa thread só.

Veio substituir: as threads e processos por pedido e as bibliotecas de callbacks, que tornavam o código difícil de ler.

O mecanismo

Chamar uma async def não executa nada: devolve uma corrotina. O loop de eventos executa as corrotinas e, a cada await numa operação de I/O, troca para outra que esteja pronta. É concorrência numa thread, sem troca de contexto do sistema.

asyncio.gather(a(), b()) roda várias chamadas ao mesmo tempo e espera todas, como um CompletableFuture.allOf. O GIL não atrapalha o async, porque a espera de I/O acontece fora do código Python; ele atrapalha a conta pesada em várias threads, e para isso se usa multiprocessing.

Para que serve

Atender muitos usuários que esperam APIs lentas (LLM, banco vetorial, ferramentas) com poucos recursos, e fazer chamadas em paralelo dentro de um pedido.

Por que é importante

Serviços de IA passam a maior parte do tempo esperando o LLM. Saber quando usar async, e não misturar com código bloqueante, define a capacidade e a latência do serviço.

a ponte com o Javathreads da plataforma ↔ threads com GIL; virtual threads ↔ corrotinas (com await explícito); WebFlux e Mono ↔ async/await; CompletableFuture.allOf ↔ asyncio.gather.

Como usar.

import asyncio, httpx

async def buscar_contexto(q: str) -> list[str]: ...
async def chamar_llm(q: str, ctx: list[str]) -> str: ...

@app.post("/chat")
async def chat(p: Pergunta):
    async with httpx.AsyncClient() as c:          # cliente assíncrono
        docs, perfil = await asyncio.gather(      # em paralelo
            buscar_contexto(p.texto),
            carregar_perfil(p.usuario),
        )
    return {"resposta": await chamar_llm(p.texto, docs)}
Para ir alémPython sem GIL

Versões recentes do Python oferecem uma compilação experimental sem o GIL (free-threaded), em que threads executam código Python em paralelo. Ainda depende do suporte das bibliotecas. Para serviços de IA, que esperam I/O, o async continua sendo o caminho padrão.

Confira na documentação do Python o estado atual do modo sem GIL.
armadilhas
  • Função bloqueante dentro de async def (requests, time.sleep, driver síncrono): trava o loop e todos os pedidos.
  • Esquecer o await. A chamada devolve uma corrotina que nunca roda, e o Python só avisa com um warning.
  • Usar async para conta pesada. Async ajuda a esperar, não a calcular; para CPU, use processos.

Testar e entregar

Do pytest à imagem Docker: o caminho até o link no ar.

Testes com pytest

essencial

Direto: No pytest, um teste é uma função que começa com test_ e usa o assert comum do Python; a mensagem de falha mostra os valores. Fixtures (@pytest.fixture) preparam o que o teste precisa e são injetadas pelo nome do parâmetro. @pytest.mark.parametrize roda o mesmo teste com vários dados, e o TestClient do FastAPI faz o papel do MockMvc.

o caso

Você escreve os testes do chat como no JUnit: uma classe, um setUp, assertEquals em cada linha. Funciona, mas um colega reescreve com funções soltas, uma fixture para o cliente com o LLM falso e um parametrize com 20 perguntas. Os testes ficam com metade do tamanho, e cada caso que falha aparece com o nome e os valores no relatório.

≈

Analogia. A fixture é a bancada já montada antes da aula de laboratório: o aluno (o teste) chega, pede o que precisa pelo nome e encontra pronto; quando sai, alguém desmonta.

Como surgiu

O Python tem o unittest na biblioteca padrão, copiado do JUnit, com classes e métodos assertEqual. O pytest surgiu para reduzir essa cerimônia e virou o padrão da comunidade.

Veio substituir: o unittest com classes de teste, setUp/tearDown e um método de asserção para cada tipo de comparação.

O mecanismo

O pytest descobre os arquivos test_*.py e as funções test_*, e reescreve os assert para mostrar os valores quando falham. Quando um teste pede um parâmetro cliente, ele procura uma fixture com esse nome (no mesmo arquivo ou em conftest.py), executa e injeta o resultado, como uma injeção de dependência só para testes.

Uma fixture com yield faz a preparação antes do yield e a limpeza depois, como @BeforeEach e @AfterEach juntos.

Para que serve

Testar o código com pouca cerimônia e montar conjuntos de casos (inclusive as avaliações de um sistema de IA) que rodam no CI.

Por que é importante

As avaliações de um projeto de IA (os 20 casos de "pronto quando") viram testes parametrizados. É o que transforma "parece funcionar" em número que o CI confere a cada mudança.

a ponte com o JavaJUnit 5 ↔ pytest; @BeforeEach/@AfterEach ↔ fixture com yield; @ParameterizedTest ↔ @pytest.mark.parametrize; Mockito ↔ unittest.mock ou fixture com objeto falso; MockMvc ↔ TestClient.

Como usar.

import pytest
from fastapi.testclient import TestClient
from meu_chat.api import app, get_llm

class LLMFalso:
    def responder(self, texto: str) -> str:
        return f"eco: {texto}"

@pytest.fixture
def cliente():
    app.dependency_overrides[get_llm] = LLMFalso
    yield TestClient(app)
    app.dependency_overrides.clear()

@pytest.mark.parametrize("texto", ["oi", "qual o status do pedido 42?"])
def test_chat_responde(cliente, texto):
    r = cliente.post("/chat", json={"texto": texto})
    assert r.status_code == 200
    assert r.json()["resposta"] == f"eco: {texto}"
Para ir alémconftest.py e escopo de fixture

Fixtures em conftest.py ficam disponíveis para todos os testes da pasta, sem import. Com scope="session", a fixture é criada uma vez para a execução inteira, útil para subir um banco com Testcontainers (que também existe para Python). O padrão é uma por teste.

armadilhas
  • Chamar o LLM real nos testes. Fica lento, caro e instável; troque pela dependência falsa.
  • Fixture que não limpa. Sem a parte depois do yield, um teste afeta o seguinte.
  • Um teste com 20 asserts. Use parametrize: cada caso vira um teste com nome próprio no relatório.

Empacotar e rodar: Docker, uvicorn e configuração

essencial

Direto: Um serviço Python não vira um jar: ele roda como o código-fonte mais um ambiente com as dependências, servido pelo uvicorn. Em produção, isso vai numa imagem Docker que instala as dependências do lock, copia o código, roda com um usuário sem privilégios e lê a configuração de variáveis de ambiente.

o caso

A primeira imagem do seu serviço tem 2 GB e leva dez minutos para ser construída a cada mudança de uma linha. O Dockerfile copiava o projeto inteiro antes de instalar as dependências, então qualquer alteração invalidava o cache. Copiar primeiro o pyproject.toml e o lock, instalar, e só depois copiar o código faz o build seguinte levar segundos, e a imagem slim cai para algumas centenas de MB.

≈

Analogia. É a mudança de casa em que os móveis (as dependências) vão num caminhão que não muda, e só as caixas do dia a dia (o código) vão num carro a cada viagem. Refazer o caminhão a cada caixa é o build sem cache.

Como surgiu

Em Python não há um artefato único como o jar, e instalar dependências na máquina de produção dava ambientes diferentes. O container passou a carregar o interpretador e as bibliotecas junto com o código.

Veio substituir: o deploy por git pull e pip install direto no servidor, com o ambiente de produção diferente do de desenvolvimento.

O mecanismo

Cada instrução do Dockerfile gera uma camada em cache; quando um arquivo copiado muda, as camadas seguintes são refeitas. Por isso as dependências (que mudam pouco) vêm antes do código (que muda sempre). Um build em dois estágios instala tudo num estágio e copia só o ambiente pronto para uma imagem final menor.

O uvicorn é o servidor ASGI; em produção ele roda com mais de um worker (--workers) ou atrás de um orquestrador que escala containers. A configuração vem do ambiente e é lida pelo BaseSettings.

Para que serve

Entregar o serviço do mesmo jeito em qualquer lugar (sua máquina, o CI, a nuvem), com builds rápidos e imagens pequenas.

Por que é importante

O "pronto quando" de todo projeto da trilha termina num link no ar. Docker e CI/CD aparecem em boa parte das vagas, e uma imagem de 2 GB é uma das primeiras coisas que um revisor nota.

a ponte com o Javafat jar ↔ imagem com o código e o .venv; Tomcat embutido ↔ uvicorn; application.yml por ambiente ↔ variáveis de ambiente com BaseSettings; Jib/buildpacks ↔ Dockerfile em estágios.

Como usar.

FROM python:3-slim AS build
COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/uv
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev --no-install-project   # camada de dependências
COPY src ./src
RUN uv sync --frozen --no-dev

FROM python:3-slim
WORKDIR /app
COPY --from=build /app /app
USER nobody
ENV PATH="/app/.venv/bin:$PATH"
CMD ["uvicorn", "meu_chat.api:app", "--host", "0.0.0.0", "--port", "8000"]
Para ir alémFixar versões da imagem

No exemplo, python:3-slim e uv:latest deixam o build mudar sozinho com o tempo. Em produção, fixe a versão do Python e da imagem do uv (por tag de versão ou digest) e atualize de propósito, com o CI rodando os testes. Confira na documentação do uv o exemplo de Dockerfile recomendado.

armadilhas
  • Copiar tudo antes de instalar. Qualquer mudança no código refaz a instalação inteira.
  • Chave da API dentro da imagem ou no .env copiado. Ela vem do ambiente na hora de rodar; use .dockerignore.
  • Rodar como root e com --reload em produção. O reload é só para desenvolvimento.

método
