A trilha: do container ao cluster

Comece por aqui. Siga o caminho de cima para baixo, clique em qualquer nó para abrir o painel — e use o modo teste para revisar sem reler.

01

Por que containers existem

Antes de qualquer comando: o problema real que o Docker resolveu — e o que ele não é.

O problema: "na minha máquina funciona"

essenciala origem

Direto: container empacota a aplicação junto com todo o ambiente de que ela precisa — bibliotecas, versões, configuração de sistema. O que roda na sua máquina é literalmente o mesmo artefato que roda em produção, e por isso a frase perdeu o sentido.

≈

Como o contêiner marítimo. Antes dele, cada carga era embarcada de um jeito e cada porto precisava saber lidar com aquele formato específico. O contêiner padronizou a caixa: o navio, o guindaste e o caminhão não precisam saber o que tem dentro. O container de software fez a mesma coisa — o servidor não precisa mais saber que a sua aplicação usa Java 21 e uma versão específica de libssl.

Como surgiu

Isolamento de processos existe no Linux desde os anos 2000 — namespaces e cgroups foram sendo adicionados ao kernel ao longo de uma década, e o LXC já usava isso. O que o Docker trouxe em 2013 não foi a tecnologia de isolamento: foi a experiência. Um formato de imagem em camadas, um arquivo declarativo para construí-la, um registro público para compartilhar e um comando de uma linha para rodar. A adoção explodiu porque a barreira caiu de "configure o kernel" para docker run.

Veio substituir: o servidor configurado à mão com o passo a passo num documento, a máquina virtual inteira só para isolar uma aplicação, e a longa lista de dependências que o time de infraestrutura instalava antes de cada deploy.

Onde você usa isso no dia a dia

  • Subir Postgres e RabbitMQ para desenvolver, sem instalar nada na máquina.
  • Garantir que o CI roda exatamente o mesmo ambiente que produção.
  • Entregar a aplicação como imagem em vez de .jar mais instruções.

O ponto que muda o entendimento: container não é máquina virtual. Ele não tem sistema operacional próprio nem kernel próprio — é um processo comum do Linux, rodando no seu kernel, apenas com uma visão restrita do sistema. Por isso ele sobe em milissegundos e consome quase nada além do que a aplicação já consumiria.

Armadilhas
  • Tratar container como servidor. Entrar dentro dele, instalar coisa e "arrumar" é o oposto do modelo: a mudança some no próximo restart, porque o container é descartável.
  • Achar que container é seguro por padrão. Isolamento de processo não é fronteira de segurança forte — um container rodando como root com privilégios pode alcançar o host.
  • Esperar que resolva arquitetura. Empacotar um sistema mal desenhado só cria uma imagem de um sistema mal desenhado.
Pratique agoraRode docker run --rm -it alpine sh e depois, no host, ps aux | grep sh. O processo do container aparece na lista de processos do seu Linux — porque ele é um processo seu.

Namespaces e cgroups: o isolamento por dentro

essencialmecanismo

Direto: duas funcionalidades do kernel Linux fazem todo o trabalho. Namespaces controlam o que o processo enxerga — quais outros processos, qual rede, qual sistema de arquivos. Cgroups controlam o quanto ele pode consumir — CPU, memória, I/O.

≈

Como um quarto de hotel. O namespace é a porta: você só enxerga o seu quarto, não os dos outros hóspedes, e para você aquele é o mundo inteiro. O cgroup é o limite de consumo: quanta água quente e quanta energia aquele quarto pode gastar, para que um hóspede de banho longo não deixe o prédio sem água.

Como surgiu

Os namespaces entraram no kernel aos poucos, a partir de 2002, cada tipo resolvendo um recurso: PID, rede, montagem, usuário, IPC, hostname. Os cgroups vieram do Google em 2007, com um objetivo direto — impedir que um serviço consumisse toda a máquina compartilhada. Quando as duas peças amadureceram, o container virou possível; faltava só alguém empacotar a experiência, que foi o que o Docker fez.

Veio substituir: o chroot, que só isolava o sistema de arquivos e era trivialmente contornável, e a separação por máquina virtual, que era a única alternativa com isolamento sério.

Onde você usa isso no dia a dia

  • Ao definir --memory e --cpus num container — isso é cgroup.
  • Ao descobrir que a JVM dentro do container via a memória da máquina inteira.
  • Ao investigar por que um container não enxerga um processo ou uma rede.

Vale conhecer os principais namespaces porque cada um explica um comportamento que confunde no começo. O PID faz o processo principal do container ser o PID 1 — e PID 1 tem regras especiais de sinal, o que explica por que às vezes docker stop demora dez segundos e mata à força. O network dá ao container a própria interface e as próprias portas, o que explica por que você precisa publicar porta para acessar de fora. O mount dá a ele a própria visão do sistema de arquivos, que é a imagem.

# cgroup: limitar o que o container pode consumir
docker run --memory=512m --cpus=1.5 minha-app

# ver o isolamento acontecendo, do lado de dentro
docker run --rm -it alpine sh -c 'ps aux'      # só enxerga os próprios processos
docker run --rm -it alpine sh -c 'ip addr'     # a própria interface de rede

# e do lado de fora, no host
ps aux | grep java          # o processo do container está aqui
cat /sys/fs/cgroup/memory.max
Por que isso importa para você especificamente. A JVM antiga lia a memória da máquina, não a do cgroup — e dimensionava o heap para um valor que o container não podia usar, sendo morta pelo kernel sem nenhum stack trace. As JVMs modernas leem o limite do cgroup, mas o dimensionamento continua sendo sua responsabilidade. É exatamente o OOMKilled da parte 10 do roadmap de Java, visto agora do lado de fora.
Armadilhas
  • Container sem limite de memória. Ele pode consumir a máquina inteira e derrubar os vizinhos — o cgroup só limita se você configurar.
  • Confundir isolamento com segurança. O namespace de usuário é o único que separa privilégio de verdade, e ele não vem ativo por padrão em toda configuração.
  • Processo que ignora SIGTERM. Como PID 1, ele não tem os handlers padrão — se a aplicação não tratar o sinal, o encerramento gracioso não acontece.
Pratique agoraRode um container com --memory=256m e uma aplicação Java sem MaxRAMPercentage. Depois com. Compare o heap que a JVM escolheu nos dois casos.

Imagem e container: molde e instância

essencial

Direto: a imagem é o molde — somente leitura, imutável, versionada. O container é uma instância em execução daquele molde, com uma fina camada de escrita por cima que morre junto com ele.

≈

Como classe e objeto. A imagem é a classe: existe uma, definida e imutável. O container é o objeto: você instancia quantos quiser da mesma classe, cada um com o próprio estado em memória — e quando ele morre, o estado morre junto. Salvar dentro do container é como guardar informação num campo de objeto e esperar que sobreviva ao fim do programa.

Como surgiu

A separação entre molde imutável e instância descartável foi a decisão de projeto mais importante do Docker. Ela permitiu que a imagem fosse conteúdo endereçável — identificada pelo hash do que contém — e portanto compartilhável, cacheável e verificável. É o que torna possível dizer com certeza que a imagem testada no CI é bit a bit a mesma que subiu em produção.

Veio substituir: o servidor mutável, atualizado incrementalmente ao longo de anos, do qual ninguém conseguia reproduzir uma cópia idêntica.

Onde você usa isso no dia a dia

  • Ao entender por que o arquivo que você criou dentro do container sumiu.
  • Ao subir dez réplicas da mesma imagem.
  • Ao promover a mesma tag de imagem de homologação para produção.
docker images          # os moldes disponíveis
docker ps -a           # as instâncias, rodando ou paradas

# a camada de escrita morre com o container:
docker run --rm -it alpine sh -c 'echo oi > /tmp/a.txt; cat /tmp/a.txt'
docker run --rm -it alpine sh -c 'cat /tmp/a.txt'   # não existe mais
Armadilhas
  • Guardar dado dentro do container. Some no restart e não é visto pelas outras réplicas — o mesmo princípio de "sem estado" da arquitetura, agora no nível do processo.
  • Usar docker commit para criar imagem. Gera uma imagem que ninguém sabe reproduzir. Imagem se constrói a partir de Dockerfile versionado.
  • Confundir stop com rm. Parar mantém a instância e a camada de escrita; remover apaga.
Pratique agoraCrie um arquivo dentro de um container, saia, entre de novo e observe. Depois faça o mesmo com um volume montado e compare.

Docker, containerd e a OCI: quem faz o quê

aprofundamento

Direto: "Docker" hoje é um conjunto de peças. O CLI é o que você digita; o daemon recebe as ordens; o containerd gerencia o ciclo de vida; o runc efetivamente cria o processo isolado. E os formatos de imagem e execução são padrão aberto — a OCI.

≈

Como pedir comida por aplicativo. Você usa o app (CLI), que manda o pedido para a plataforma (daemon), que aciona o restaurante (containerd), que tem um cozinheiro que de fato prepara (runc). Você fala com o app, mas quem cozinha é outro — e é por isso que o Kubernetes conseguiu trocar o app sem trocar o cozinheiro.

Como surgiu

No começo o Docker era um binário monolítico. Conforme o ecossistema cresceu, ficou claro que o mercado não queria depender de uma única empresa para o formato de imagem — daí nasceu a Open Container Initiative, que padronizou o formato de imagem e o runtime. O Docker doou o containerd para a CNCF, e o Kubernetes acabou removendo a camada Docker por completo em 2022, falando direto com o containerd.

Veio substituir: o formato proprietário e o acoplamento a um fornecedor único de runtime.

Onde você usa isso no dia a dia

  • Ao ler que "o Kubernetes removeu o Docker" e precisar entender que suas imagens continuam funcionando.
  • Ao usar Podman ou nerdctl e ver que os comandos são praticamente os mesmos.
  • Ao investigar por que o daemon precisa de privilégio e o que isso implica.

A consequência prática é tranquilizadora: a imagem que você constrói com Docker roda em qualquer runtime compatível com a OCI. O Kubernetes não executa "containers Docker" — executa containers OCI, e a sua imagem é um deles. A depreciação do dockershim não afetou nenhuma imagem existente; afetou apenas quem dependia do daemon Docker dentro dos nós do cluster.

Armadilhas
  • Montar o socket do Docker dentro de um container. /var/run/docker.sock dá controle total do host a quem estiver lá dentro. É acesso de root disfarçado.
  • Assumir que "Docker morreu no Kubernetes". O formato de imagem continua o mesmo; mudou só o componente que roda dentro do nó.
Pratique agoraRode docker info e localize o runtime em uso. Depois ctr ou crictl, se disponíveis, para ver a camada de baixo.

02

A imagem: camadas, cache e Dockerfile

Onde a maioria das imagens fica lenta, pesada e insegura — e como consertar as três coisas.

Camadas: por que a ordem do Dockerfile importa tanto

essencialo pulo do gato

Direto: cada instrução do Dockerfile cria uma camada imutável, identificada por hash. Se nada mudou naquela camada nem nas anteriores, o Docker reaproveita do cache. Por isso o que muda pouco vai em cima, o que muda toda hora vai embaixo.

≈

Como uma pilha de transparências. Cada folha desenha por cima da anterior e o resultado é a soma. Se você troca a folha do meio, todas as de cima precisam ser redesenhadas. Colocar a folha que você troca todo dia na base da pilha significa refazer tudo, todo dia.

Como surgiu

O sistema de arquivos em camadas veio de tecnologias de union filesystem, e resolveu dois problemas de uma vez. O primeiro é armazenamento: dez imagens baseadas na mesma base compartilham as camadas dela, em vez de dez cópias. O segundo é transferência: ao enviar uma imagem nova para o registro, só sobem as camadas que mudaram — o que transforma um upload de 400 MB num de 12 MB.

Veio substituir: a imagem monolítica de máquina virtual, que precisava ser copiada inteira a cada versão.

Onde você usa isso no dia a dia

  • Toda vez que o build demora cinco minutos por causa de uma linha de código alterada.
  • Ao reduzir o tempo do pipeline sem mudar nada da aplicação.
  • Ao economizar banda e espaço no registro.
Cache inútil — rebuild total sempre
FROM eclipse-temurin:21-jdk
WORKDIR /app
COPY . .                    ← qualquer .java muda TUDO
RUN ./mvnw package          ← baixa as dependências de novo
CMD ["java","-jar","target/app.jar"]

# 4 min a cada alteração de uma linha
Cache aproveitado
FROM eclipse-temurin:21-jdk
WORKDIR /app
COPY mvnw pom.xml ./            ← muda pouco
COPY .mvn .mvn
RUN ./mvnw dependency:go-offline  ← fica em cache
COPY src src                     ← muda sempre, e só isto rebuilda
RUN ./mvnw package -o

# 20 s a cada alteração de uma linha

A regra tem um corolário que vale ouro: uma camada nunca fica menor. Se você instala algo numa camada e apaga na seguinte, o arquivo continua ocupando espaço na imagem — apenas ficou invisível. Por isso instalar e limpar precisa acontecer no mesmo RUN, e por isso um segredo copiado e depois removido continua recuperável na imagem publicada.

Armadilhas
  • COPY . . logo no início. Invalida o cache a cada alteração de qualquer arquivo, inclusive do README.
  • Apagar em camada posterior. O arquivo continua lá, ocupando espaço e recuperável.
  • Segredo em ARG ou em camada intermediária. Fica no histórico da imagem — qualquer um com a imagem consegue extrair.
Pratique agoraConstrua a mesma aplicação com os dois Dockerfiles acima, altere uma linha de código e reconstrua os dois. Cronometre.
Prova de domínioDiante de um Dockerfile, você prevê quais camadas serão invalidadas por uma alteração de código e sabe reordená-lo.

Multi-stage: construir num lugar, entregar em outro

essencial

Direto: o build precisa de JDK, Maven e código-fonte; a execução precisa só do .jar e de uma JRE. O multi-stage permite compilar num estágio e copiar apenas o artefato para uma imagem final enxuta.

≈

Como uma marcenaria e a sala de estar. A serra, a lixadeira e a serragem são indispensáveis para fazer a mesa — e nenhuma delas vai para a sala junto com ela. Entregar a imagem com o JDK e o Maven dentro é entregar a mesa com a oficina em volta.

Como surgiu

Antes de 2017 a prática era o "padrão do construtor": um Dockerfile compilava, outro empacotava, e um script fora do Docker orquestrava os dois. Funcionava e era frágil. O multi-stage trouxe isso para dentro de um único arquivo, com a regra simples de que só o que é copiado explicitamente sobrevive para o estágio seguinte.

Veio substituir: os dois Dockerfiles e o shell script de cola — e as imagens de 800 MB que carregavam a cadeia de compilação para produção.

Onde você usa isso no dia a dia

  • Toda imagem de aplicação Java, Node ou Go.
  • Ao reduzir a superfície de ataque da imagem em produção.
  • Ao economizar tempo de download em cada deploy e em cada nó do cluster.
# ---------- estágio de build ----------
FROM eclipse-temurin:21-jdk AS build
WORKDIR /app
COPY mvnw pom.xml ./
COPY .mvn .mvn
RUN ./mvnw dependency:go-offline
COPY src src
RUN ./mvnw clean package -DskipTests -o

# ---------- estágio final ----------
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
RUN addgroup -S app && adduser -S app -G app     # não rode como root
COPY --from=build /app/target/*.jar app.jar
USER app
EXPOSE 8080
ENTRYPOINT ["java","-XX:MaxRAMPercentage=75","-jar","/app/app.jar"]

# resultado: ~180 MB em vez de ~800 MB, sem JDK nem Maven na imagem final
Ganho duplo, e o segundo é o que importa mais. A redução de tamanho acelera o deploy e economiza registro. Mas o ganho real é de segurança: a imagem final não tem compilador, nem gerenciador de pacotes, nem shell de build. Quem conseguir executar código lá dentro encontra um ambiente vazio — e a maior parte das ferramentas de exploração depende justamente do que você acabou de remover.
Armadilhas
  • Alpine com JVM sem atenção. Alpine usa musl em vez de glibc; funciona bem com imagens Temurin preparadas, mas bibliotecas nativas de terceiros podem falhar. Teste antes de assumir.
  • Rodar como root. É o padrão, e é errado. Crie um usuário e use USER.
  • Copiar o diretório inteiro do build. COPY --from=build /app /app traz de volta tudo que você queria deixar para trás.
Pratique agoraConverta o Dockerfile do seu projeto para multi-stage e compare docker images antes e depois. Depois tente rodar sh dentro da imagem final.

ENTRYPOINT, CMD e o processo PID 1

essencial

Direto: o ENTRYPOINT define o executável e o CMD define os argumentos padrão — que podem ser sobrescritos na linha de comando. E o processo que sobe vira PID 1, o que tem consequência direta no encerramento gracioso.

≈

Como um aparelho e o controle remoto. O ENTRYPOINT é o aparelho — sempre o mesmo, é o que a caixa faz. O CMD é o canal em que ele liga por padrão, e qualquer um pode trocar sem trocar o aparelho.

Como surgiu

A dualidade existe porque há dois casos de uso legítimos: a imagem que é uma aplicação — e aí o executável é fixo — e a imagem que é uma caixa de ferramentas, em que o usuário escolhe o comando. A confusão vem da forma shell versus a forma exec: escrever o comando como string faz o Docker embrulhar num /bin/sh -c, e aí o shell vira PID 1 e não repassa os sinais.

Veio substituir: os scripts de inicialização que precisavam capturar sinais manualmente para encerrar direito.

Onde você usa isso no dia a dia

  • Ao descobrir que docker stop sempre demora dez segundos.
  • Ao investigar por que o shutdown gracioso do Spring não acontece no container.
  • Ao permitir sobrescrever argumentos sem reconstruir a imagem.
Forma shell — sinais perdidos
ENTRYPOINT java -jar /app/app.jar

# vira: /bin/sh -c "java -jar /app/app.jar"
# PID 1 = sh, e o sh NÃO repassa SIGTERM
# → docker stop espera 10s e mata à força
# → nenhum shutdown gracioso acontece
Forma exec — sinais chegam
ENTRYPOINT ["java","-jar","/app/app.jar"]

# PID 1 = java, recebe o SIGTERM direto
# → o Spring encerra graciosamente
# → docker stop termina em 2s, sem perder requisição
A ponte com o Spring. Aquele server.shutdown=graceful da parte 08 do Spring completo só funciona se o SIGTERM chegar ao processo Java. Com a forma shell, ele nunca chega — e o encerramento gracioso que você configurou fica inerte, sem nenhum erro que denuncie. É um dos casos mais comuns de configuração correta anulada por detalhe de empacotamento.
Armadilhas
  • Forma shell por hábito. É a forma mais escrita e a que quebra sinais. Use sempre a lista JSON.
  • Script de entrada sem exec. Se o script precisa existir, termine com exec java -jar ... para o Java assumir o PID 1.
  • Aplicação que ignora SIGTERM. Como PID 1 ela não tem handler padrão: se o código não tratar, nada acontece.
Pratique agoraSuba o mesmo container nas duas formas, rode docker stop e cronometre. A diferença entre 2 e 10 segundos é o sinal chegando ou não.

Imagem enxuta e segura: o que não deve estar lá

essencial

Direto: tudo que está na imagem é superfície de ataque e é peso em cada deploy. Uma boa imagem tem a aplicação, o runtime e nada mais — sem shell de build, sem gerenciador de pacotes, sem segredo, sem rodar como root.

≈

Como viajar com bagagem de mão. Quanto menos você leva, mais rápido embarca, menos paga e menos tem para perder. E o que você deixou em casa não pode ser roubado no aeroporto.

Como surgiu

As primeiras imagens copiavam distribuições completas por conveniência — 900 MB para rodar um serviço de 30 MB. Quando o volume de deploys cresceu e as varreduras de vulnerabilidade começaram a apontar centenas de CVEs vindas de pacotes que ninguém usava, a indústria caminhou para imagens mínimas: Alpine, slim, e por fim distroless, que não tem nem shell.

Veio substituir: a imagem baseada numa distribuição completa, com compilador, editor e ferramentas de rede embutidos por acidente.

Onde você usa isso no dia a dia

  • Ao passar por uma varredura de segurança da empresa.
  • Ao reduzir o tempo de pull em cada nó do cluster.
  • Ao revisar o Dockerfile de alguém num PR.

A lista de verificação

  • Base slim, alpine ou distroless, com versão fixada — nunca :latest.
  • Multi-stage, com o estágio final sem cadeia de build.
  • Usuário não-root criado e ativado com USER.
  • Sem segredo em ARG, ENV ou camada.
  • .dockerignore com .git, target, .env, node_modules.
  • HEALTHCHECK ou probe no orquestrador.
  • Varredura no pipeline, falhando em vulnerabilidade crítica.

Por que cada item importa

  • :latest torna o build não reproduzível: o mesmo Dockerfile gera imagens diferentes em dias diferentes.
  • Sem shell na imagem final, quem conseguir executar código lá dentro fica sem ferramentas.
  • Root no container mais uma falha de configuração no host é caminho para escapar do isolamento.
  • O .dockerignore evita mandar o .git inteiro — que costuma conter segredo no histórico.
Armadilhas
  • Fixar só a tag menor. :21-jre muda com o tempo. Para reprodutibilidade total, fixe o digest @sha256:....
  • Distroless sem preparo. Sem shell, você não entra para depurar — precisa de um container efêmero de diagnóstico ou de uma variante com shell para desenvolvimento.
  • Varredura que só avisa. Relatório que não quebra o build vira ruído ignorado em duas semanas.
Pratique agoraRode uma varredura na imagem atual do seu projeto e conte as vulnerabilidades. Converta para multi-stage com base slim e rode de novo.
Prova de domínioVocê audita um Dockerfile pela lista acima e justifica cada item pelo risco que ele elimina.

Registry, tags e a promoção da imagem

essencial

Direto: o registro é onde as imagens vivem e de onde os nós as baixam. A tag é um apelido móvel; o digest é a identidade imutável. Promover entre ambientes significa mover a mesma imagem — nunca reconstruí-la.

≈

Como o número de série de um produto. "Modelo 2026" é a tag: aponta para um produto que pode mudar. O número de série é o digest: identifica exatamente aquela unidade. Para rastrear um recall, você usa o número de série — nunca o nome do modelo.

Como surgiu

O Docker Hub nasceu junto com o Docker e foi decisivo para a adoção: pela primeira vez era trivial compartilhar um ambiente inteiro. Com o uso corporativo vieram os registros privados, o controle de acesso e a assinatura de imagem — porque baixar e executar código de terceiro em produção é exatamente o que um registro faz.

Veio substituir: o artefato distribuído por FTP ou repositório de binário, sem nenhuma garantia de que o que roda é o que foi testado.

Onde você usa isso no dia a dia

  • Em todo pipeline: build, push, e o cluster fazendo pull.
  • Ao promover de homologação para produção.
  • Ao investigar qual versão exata está rodando num pod.

A regra que evita a maior parte dos incidentes de deploy: construa uma vez, promova o mesmo artefato. Reconstruir para produção significa que o que você testou não é o que subiu — mudou uma dependência transitiva, uma base foi atualizada, e o bug aparece só lá. A promoção correta é retaguear a mesma imagem, ou melhor, referenciá-la pelo digest.

# build uma vez, com identidade rastreável
docker build -t registro.empresa.com/pedidos:1.4.2 \
             -t registro.empresa.com/pedidos:$(git rev-parse --short HEAD) .
docker push registro.empresa.com/pedidos --all-tags

# promover: mesma imagem, outro apelido — sem rebuild
docker pull registro.empresa.com/pedidos:1.4.2
docker tag  registro.empresa.com/pedidos:1.4.2 registro.empresa.com/pedidos:prod
docker push registro.empresa.com/pedidos:prod

# em produção, referencie pelo digest — imutável de verdade
image: registro.empresa.com/pedidos@sha256:3f9c...
Armadilhas
  • :latest em produção. Ninguém sabe o que está rodando, e o rollback deixa de existir.
  • Tag móvel sobrescrita. Publicar de novo sobre a mesma tag apaga a versão anterior e destrói o histórico.
  • Reconstruir para promover. O artefato testado deixa de ser o artefato entregue.
  • imagePullPolicy: Always com tag fixa. Consome banda a cada restart sem nenhum ganho.
Pratique agoraPublique uma imagem com tag semântica e com o hash do commit, e depois descubra o digest dela com docker inspect. Use o digest num manifesto.
Prova de domínioVocê diferencia tag de digest, defende a promoção sem rebuild e sabe descobrir a versão exata rodando em produção.

Rodar e operar containers

O dia a dia no terminal: portas, dados, rede e configuração — tudo via Linux, sem interface gráfica.

docker run e o ciclo de vida do container

essencial

Direto: docker run faz três coisas numa só: baixa a imagem se não existir, cria um container a partir dela e o inicia. Entender que são três passos separados explica quase todo comportamento estranho.

≈

Como alugar um carro. Buscar o modelo no pátio (pull), preencher o contrato daquela unidade (create) e dar a partida (start). Você faz tudo no balcão numa transação só, mas são três etapas — e quando algo dá errado, saber em qual delas parou é o que resolve.

Como surgiu

A simplicidade do comando único foi decisão deliberada de produto: o Docker competia com ferramentas que exigiam vários passos e arquivos de configuração. Os comandos separados continuam existindo — docker create e docker start — mas quase ninguém usa, e é por isso que o modelo mental de três etapas se perde.

Veio substituir: a sequência de provisionar máquina, instalar dependências e iniciar serviço, que levava minutos ou horas.

Onde você usa isso no dia a dia

  • Subir Postgres e RabbitMQ para desenvolver em segundos.
  • Testar uma versão diferente de banco sem tocar na máquina.
  • Rodar uma ferramenta pontual sem instalá-la.
# as flags que você vai usar todo dia
docker run -d                      # detached: solta o terminal
           --name pedidos-db       # nome próprio; sem isso vem um aleatório
           -p 5432:5432            # porta do HOST : porta do CONTAINER
           -e POSTGRES_PASSWORD=x  # variável de ambiente
           -v pgdata:/var/lib/postgresql/data   # volume nomeado
           --restart unless-stopped
           postgres:16

docker ps                # o que está rodando
docker ps -a             # inclusive o que parou
docker logs -f pedidos-db          # acompanhar a saída
docker exec -it pedidos-db psql -U postgres   # entrar para investigar
docker stop pedidos-db && docker rm pedidos-db

A ordem do -p confunde todo mundo no começo e a regra é fixa: host primeiro, container depois. -p 8081:8080 significa "o que chegar na porta 8081 da minha máquina vai para a 8080 lá dentro". Sem publicar porta, o container roda normalmente e simplesmente não é alcançável de fora — o que costuma ser interpretado como "não subiu".

Armadilhas
  • Container que sai imediatamente. Container vive enquanto o processo principal vive. Se o comando termina, ele termina. docker ps -a e docker logs mostram o motivo.
  • Acumular containers parados. Ocupam disco silenciosamente. docker system df mostra e docker system prune limpa — com cuidado, porque remove volumes órfãos se você pedir.
  • Esquecer o --rm em testes. Cada execução deixa um container parado para trás.
Pratique agoraSuba um Postgres com volume nomeado, crie uma tabela, remova o container e suba outro com o mesmo volume. Os dados continuam lá.
Prova de domínioVocê explica por que um container "não sobe" olhando docker ps -a e docker logs, sem chutar.

Volumes e bind mounts: onde os dados sobrevivem

essencial

Direto: a camada de escrita do container morre com ele. Para o dado durar, ele precisa estar fora: num volume gerenciado pelo Docker, ou num bind mount que aponta para uma pasta da sua máquina.

≈

Como o armário do hotel e a sua mala. O que você deixa na gaveta do quarto some no check-out. O que está na mala vai com você. O volume é a mala guardada na recepção — o hotel cuida, mas é sua e sobrevive à troca de quarto.

Como surgiu

O bind mount veio primeiro, por ser a coisa mais natural: montar uma pasta do host. O problema apareceu em produção — caminho absoluto que só existe naquela máquina, permissões divergentes entre host e container, e nenhuma portabilidade. Os volumes nomeados vieram para dar ao Docker o controle do armazenamento, com backup, driver e ciclo de vida próprios.

Veio substituir: o dado dentro do container, que sumia a cada atualização de imagem.

Onde você usa isso no dia a dia

  • Banco de dados em desenvolvimento que não pode perder os dados a cada restart.
  • Código-fonte montado no container para recarregar sem rebuild.
  • Arquivos de configuração injetados sem entrar na imagem.
Bind mount — desenvolvimento
docker run -v $(pwd)/src:/app/src minha-app

· aponta para uma pasta SUA
· ótimo para editar e ver na hora
· ruim em produção: caminho e
  permissão dependem da máquina
Volume nomeado — dados
docker volume create pgdata
docker run -v pgdata:/var/lib/postgresql/data postgres:16

· o Docker gerencia
· portável, com backup e driver
· o certo para dado que precisa durar

Há um detalhe que consome tardes: permissão. O processo dentro do container roda com um UID que pode não corresponder ao dono da pasta no host. O resultado é "permission denied" num diretório que, olhando pelo host, parece perfeitamente acessível. A saída é alinhar o UID — rodando o container com o seu usuário — ou ajustar o dono da pasta montada.

docker volume ls
docker volume inspect pgdata          # onde ele mora de verdade no host
docker run --user $(id -u):$(id -g) ...   # alinhar UID e evitar dor de permissão

# backup de um volume, sem parar o serviço por muito tempo
docker run --rm -v pgdata:/dados -v $(pwd):/backup alpine \
  tar czf /backup/pgdata-$(date +%F).tar.gz -C /dados .
Armadilhas
  • Bind mount em produção. Acopla o container ao layout de uma máquina específica — o oposto da portabilidade.
  • docker system prune --volumes sem pensar. Apaga volumes não referenciados. Ali costuma estar o banco de desenvolvimento.
  • Volume compartilhado entre réplicas. Dois containers escrevendo no mesmo volume sem coordenação corrompem os dados.
Pratique agoraFaça o backup de um volume com o comando acima, apague o volume e restaure. É o exercício que transforma backup em algo em que você confia.
Prova de domínioVocê escolhe entre volume e bind mount pelo caso de uso e sabe diagnosticar erro de permissão pelo UID.

Redes: como containers se enxergam

essencial

Direto: containers na mesma rede definida por você se enxergam pelo nome, através de um DNS interno. Containers em redes diferentes não se enxergam. E localhost dentro do container é o próprio container — nunca o host.

≈

Como ramais de um prédio. Dentro da mesma empresa você liga para "financeiro" e cai lá. De fora, precisa do número completo e de alguém transferindo na portaria. E ligar para "o meu ramal" te conecta com você mesmo — que é exatamente o que localhost faz dentro do container.

Como surgiu

No início a ligação entre containers era feita com a flag --link, que injetava variáveis de ambiente e entradas de /etc/hosts — frágil e sem ordem definida. As redes definidas pelo usuário substituíram isso com um DNS embutido: qualquer container na rede resolve os outros pelo nome, e a ordem de subida deixa de importar para a resolução.

Veio substituir: a flag --link e a prática de descobrir o IP do container e passá-lo como variável.

Onde você usa isso no dia a dia

  • Aplicação falando com o banco pelo nome do serviço.
  • Ao receber "connection refused" apontando para localhost.
  • Ao isolar um conjunto de containers dos demais.
docker network create app-net

docker run -d --name pedidos-db --network app-net postgres:16
docker run -d --name pedidos-api --network app-net \
  -e DB_URL=jdbc:postgresql://pedidos-db:5432/pedidos \   # ← o NOME, não o IP
  -p 8080:8080 minha-app

# provando o DNS interno
docker exec -it pedidos-api getent hosts pedidos-db
O erro número um de quem começa. Configurar jdbc:postgresql://localhost:5432 na aplicação dentro do container. Dentro dele, localhost é ele mesmo — e não há banco ali. Da aplicação para o banco, use o nome do container ou do serviço. Só do seu terminal, no host, é que você usa localhost com a porta publicada.
Armadilhas
  • Depender da rede bridge padrão. Nela não há resolução por nome; só nas redes que você cria.
  • Publicar porta desnecessariamente. Se só a aplicação acessa o banco, ele não precisa de -p — e publicar expõe na sua máquina, às vezes na rede local.
  • Guardar IP de container. Muda a cada recriação. O nome é estável.
Pratique agoraSuba dois containers na mesma rede e faça um alcançar o outro pelo nome. Depois coloque-os em redes diferentes e confirme que não se enxergam.
Prova de domínioVocê explica por que localhost falha dentro do container e sabe quando publicar porta e quando não.

Configuração e segredos: o que entra por fora

essencial

Direto: a imagem é a mesma em todos os ambientes; o que muda entra por fora, como variável de ambiente ou arquivo montado. E segredo não é variável de ambiente comum — ele aparece em docker inspect, em log de processo e no histórico do shell.

≈

Como o mesmo aparelho vendido em vários países. A fábrica é uma só; o que muda é o adaptador de tomada na caixa. Fabricar um aparelho diferente por país seria o equivalente a construir uma imagem por ambiente — e é o que o 12-factor veio eliminar.

Como surgiu

O princípio vem direto do 12-factor: configuração vive no ambiente, não no artefato. Variável de ambiente virou o padrão por ser universal — funciona em qualquer linguagem e em qualquer sistema. O tratamento de segredo veio depois, quando ficou evidente que variável de ambiente é visível demais para credencial.

Veio substituir: o arquivo de propriedades embutido no artefato e o build diferente por ambiente.

Onde você usa isso no dia a dia

  • Mesma imagem em desenvolvimento, homologação e produção.
  • Credencial de banco vinda do cofre, não do repositório.
  • Ajustar timeout ou limite sem reconstruir nada.
# configuração comum: variável de ambiente
docker run -e SPRING_PROFILES_ACTIVE=prod -e ORDERS_TIMEOUT=800ms minha-app

# segredo: arquivo montado, nunca variável solta na linha de comando
docker run -v /run/secrets/db-pass:/run/secrets/db-pass:ro \
           -e DB_PASSWORD_FILE=/run/secrets/db-pass minha-app

# por que não usar -e para senha:
docker inspect pedidos-api | grep -i password    # está lá, em texto puro
history | grep POSTGRES_PASSWORD                 # e no seu histórico também
Armadilhas
  • Senha em -e ou em ENV do Dockerfile. No Dockerfile é pior: fica na imagem publicada para sempre.
  • .env commitado. Adicione ao .gitignore e ao .dockerignore no primeiro dia.
  • Configuração sem valor padrão nem validação. A aplicação sobe apontando para o lugar errado — o mesmo problema do @ConfigurationProperties da parte 03 do Spring.
Pratique agoraSuba um container com senha em -e e recupere-a com docker inspect. Depois faça pela via do arquivo montado e confirme que o inspect não mostra nada.
Prova de domínioVocê distingue configuração de segredo e sabe demonstrar por que variável de ambiente não serve para o segundo.

Diagnóstico: quando o container não sobe

essencialmétodo

Direto: quatro comandos resolvem a esmagadora maioria dos casos, sempre na mesma ordem: ps -a para ver o estado, logs para ver o erro, inspect para ver a configuração efetiva e exec para investigar por dentro.

≈

Como um carro que não liga. Primeiro você olha o painel (estado), depois escuta o barulho (log), depois confere se tem combustível e se a chave é a certa (configuração), e só então abre o capô (entrar dentro). Quem começa abrindo o capô perde meia hora.

Como surgiu

É a aplicação do método de investigação — sintoma, hipótese, evidência — ao contexto de containers. Cada comando corta o espaço de busca pela metade: o estado diz se chegou a rodar, o log diz o que a aplicação reclamou, o inspect diz se a configuração que chegou é a que você acha que mandou.

Veio substituir: o ciclo de reconstruir a imagem e tentar de novo, que resolve por acaso e não ensina nada.

Onde você usa isso no dia a dia

  • Container que sai imediatamente depois de subir.
  • Aplicação que sobe mas não responde na porta.
  • Erro de conexão com um serviço vizinho.
docker ps -a                     # 1. qual o status e o código de saída?
docker logs --tail 100 pedidos-api   # 2. o que a aplicação disse antes de morrer
docker inspect pedidos-api       # 3. env, portas, rede, montagens — o que REALMENTE chegou
docker exec -it pedidos-api sh   # 4. só agora: entrar e olhar por dentro

# se o container morre rápido demais para você entrar,
# suba um irmão com o mesmo ambiente e um shell:
docker run --rm -it --network app-net --entrypoint sh minha-app

Os sintomas mais comuns

  • Exited (0) na hora — o processo principal terminou. É comando de curta duração, não serviço.
  • Exited (1) — a aplicação falhou. O log tem a resposta.
  • Exited (137) — foi morto por falta de memória. Aumente o limite ou ajuste a JVM.
  • Restarting em loop — sobe e cai. O log de cada tentativa é igual: leia o primeiro.
  • Up, mas não responde — a aplicação escuta em 127.0.0.1 dentro do container, e não em 0.0.0.0.

O que quase sempre é

  • Variável de ambiente faltando ou com nome errado.
  • localhost onde deveria ser o nome do serviço.
  • Porta publicada diferente da que a aplicação escuta.
  • Permissão em volume montado.
  • Limite de memória baixo demais para a JVM.
Armadilhas
  • Reconstruir a imagem como primeiro passo. Custa minutos e raramente é a causa.
  • Ler só o fim do log. Em loop de restart, o erro original está na primeira tentativa.
  • Ignorar o código de saída. 137 e 143 dizem exatamente que foi sinal externo, não erro da aplicação.
Pratique agoraQuebre de propósito: remova uma variável de ambiente obrigatória, aponte para localhost, e reduza a memória a 64 MB. Diagnostique cada um usando só os quatro comandos.
Prova de domínioDado um container que não sobe, você chega à causa em menos de três minutos sem reconstruir a imagem.

Compose: o ambiente inteiro num arquivo

O passo intermediário entre um container e um cluster — e o ponto em que ele deixa de bastar.

O que o Compose resolve

essencial

Direto: um sistema real tem aplicação, banco, cache e broker. O Compose descreve todos num arquivo declarativo e sobe o conjunto com um comando — com rede criada, nomes resolvidos e ordem cuidada.

≈

Como a lista de convidados de um jantar. Em vez de ligar para cada pessoa, combinar horário e explicar o endereço, você manda um convite com tudo. Quem organiza cinco jantares por semana não faz mais isso na mão.

Como surgiu

O Compose nasceu do projeto Fig, adquirido pelo Docker em 2014. O problema que resolvia era concreto: o README com dez comandos docker run em sequência, que ninguém conseguia executar sem errar. Transformar isso num arquivo versionado tornou o ambiente de desenvolvimento reproduzível — e virou o padrão de fato para desenvolver localmente.

Veio substituir: o script subir-ambiente.sh com uma sequência de comandos e o README com o passo a passo que sempre estava desatualizado.

Onde você usa isso no dia a dia

  • Subir o ambiente completo de desenvolvimento com um comando.
  • Rodar testes de integração no CI com banco e broker reais.
  • Entregar a um colega novo um ambiente que sobe de primeira.
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: pedidos
      POSTGRES_PASSWORD_FILE: /run/secrets/db-pass
    volumes: [ pgdata:/var/lib/postgresql/data ]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10

  broker:
    image: rabbitmq:3-management
    ports: [ "15672:15672" ]

  api:
    build: .
    depends_on:
      db:     { condition: service_healthy }    # espera ESTAR PRONTO, não só existir
      broker: { condition: service_started }
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/pedidos
    ports: [ "8080:8080" ]

volumes:
  pgdata:

O detalhe que economiza horas é o condition: service_healthy. O depends_on simples garante apenas a ordem de partida, não que o serviço esteja pronto para receber conexão — o Postgres leva alguns segundos entre iniciar e aceitar consulta. Sem healthcheck, a aplicação sobe, falha ao conectar e morre.

Armadilhas
  • depends_on sem healthcheck. A causa clássica do "funciona na segunda tentativa".
  • Usar o Compose como produção. Ele não tem escala, rollout, autocorreção nem distribuição entre máquinas. Para produção existe orquestrador.
  • Porta do banco publicada por padrão. Se só a aplicação acessa, não publique.
Pratique agoraSuba o ambiente do seu projeto com Compose, incluindo healthcheck. Derrube tudo com down -v e suba de novo: precisa funcionar de primeira, sempre.

Onde o Compose para — e por que existe Kubernetes

essenciala virada

Direto: o Compose descreve o que subir numa máquina. Ele não sabe distribuir entre várias, não recria o que morreu, não atualiza sem derrubar e não escala sozinho. Cada uma dessas ausências é uma razão pela qual o Kubernetes existe.

≈

Como abrir uma segunda loja. Uma pessoa organiza bem uma loja sozinha: sabe onde está cada coisa e resolve na hora. Com dez lojas em cidades diferentes, ela não dá conta — precisa de um sistema que saiba o que deveria existir em cada uma e reponha sozinho quando faltar.

Como surgiu

O Kubernetes veio do Borg, o orquestrador interno do Google, aberto em 2014. A tese central não foi "gerenciar containers" — foi reconciliação de estado desejado: você declara o que quer, e um laço de controle trabalha continuamente para que a realidade se pareça com a declaração. Container foi só a unidade escolhida.

Veio substituir: os scripts de deploy que executavam passos em ordem e falhavam pela metade sem ninguém saber em que ponto pararam.

Onde você usa isso no dia a dia

  • Ao explicar por que o time precisa de orquestrador — ou por que ainda não precisa.
  • Ao migrar de Compose para cluster.
  • Ao entender por que o Kubernetes parece complicado: ele resolve problemas que o Compose não tenta resolver.

O cluster: estado desejado e quem faz acontecer

A ideia que organiza todo o Kubernetes — e as peças que a executam.

Estado desejado: você declara, o cluster persegue

essenciala ideia central

Direto: você não manda o Kubernetes fazer nada. Você declara como o mundo deveria ser — "três réplicas desta imagem" — e laços de controle comparam continuamente o desejado com o real, agindo para fechar a diferença. Para sempre.

≈

Como o termostato. Você não liga e desliga o aquecedor: você diz "quero 22 graus". O termostato mede, compara e age — e continua fazendo isso enquanto existir. Se alguém abrir a janela, ele reage sozinho. Não há um "comando de aquecer": há um alvo e um laço.

Como surgiu

Veio do Borg, e a escolha foi consequência de escala: com dezenas de milhares de máquinas, roteiros imperativos falham no meio e ninguém sabe em que passo pararam. O modelo declarativo é autocorretivo — se um passo falhar, o laço tenta de novo na próxima iteração, sem que ninguém precise saber o que já foi feito.

Veio substituir: os scripts de deploy que executavam uma sequência de comandos e, ao falhar na etapa quatro de sete, deixavam o sistema num estado que ninguém sabia descrever.

Onde você usa isso no dia a dia

  • Ao apagar um Pod na mão e ver outro nascer em segundos.
  • Ao aplicar o mesmo manifesto duas vezes e nada mudar — porque já está no estado desejado.
  • Ao entender por que "consertar na mão" dentro do cluster nunca dura.

A consequência prática mais importante: o manifesto é a verdade, não o cluster. Se alguém alterar algo com kubectl edit e o manifesto no Git disser outra coisa, a próxima aplicação desfaz a alteração — e é assim que deve ser. Toda mudança nasce no arquivo versionado; o cluster é o resultado, não a fonte.

kubectl apply -f deployment.yaml     # declara o desejado
kubectl get pods                     # observa o real
kubectl delete pod pedidos-7d9f-abc  # apaga um na mão
kubectl get pods                     # outro já está nascendo — o laço agiu

kubectl diff -f deployment.yaml      # o que mudaria antes de aplicar
Armadilhas
  • Consertar com kubectl edit. Resolve por minutos e volta no próximo apply, sem deixar rastro do que foi feito.
  • Esperar resposta imediata. apply registra a intenção; a convergência leva tempo. rollout status é quem espera.
  • Achar que o cluster obedece ordens. Ele persegue um alvo. Se o alvo está errado, ele persegue o erro com a mesma diligência.
Pratique agoraNum cluster local, apague Pods repetidamente e veja o Deployment repô-los. Depois mude a réplica para zero e observe: o laço obedece o alvo, inclusive quando o alvo é nada.
Prova de domínioVocê explica reconciliação com o termostato e defende que toda mudança nasce no manifesto versionado.

Anatomia do cluster: control plane e nodes

essencial

Direto: o control plane decide (api-server, etcd, scheduler, controller-manager) e os nodes executam (kubelet, kube-proxy, runtime). Toda comunicação passa pelo api-server — nenhum componente fala diretamente com outro.

≈

Como uma central de táxi. A central recebe os pedidos e tem o registro de tudo (api-server e etcd), o despachante escolhe qual carro atende cada corrida (scheduler), e o motorista executa (kubelet). Nenhum motorista combina corrida direto com outro — tudo passa pela central, e é isso que mantém o registro coerente.

Como surgiu

A escolha de ter o api-server como único ponto de entrada é o que torna o sistema extensível: qualquer componente novo — inclusive os que você escrever — apenas observa e altera recursos pela mesma API, com a mesma autenticação e o mesmo modelo de permissão. É a razão de o ecossistema ter crescido tanto sem que o núcleo precisasse mudar.

Veio substituir: os orquestradores com agentes conversando entre si em malha, cujo estado divergia e ninguém conseguia auditar.

Onde você usa isso no dia a dia

  • Ao investigar por que um Pod ficou Pending — quase sempre é o scheduler.
  • Ao entender por que o cluster continua servindo tráfego mesmo com o control plane fora.
  • Ao ler um erro de permissão e saber que veio do api-server.

Control plane — decide

  • api-server — a porta única. Autentica, autoriza, valida e grava.
  • etcd — o banco de chave-valor que guarda todo o estado. É o item de backup do cluster.
  • scheduler — escolhe em qual node cada Pod novo vai rodar, por recurso e restrição.
  • controller-manager — os laços de reconciliação: Deployment, ReplicaSet, Node, e outros.

Node — executa

  • kubelet — o agente. Recebe o que deve rodar ali e garante que rode; reporta saúde.
  • runtime — containerd ou equivalente, que de fato cria os containers.
  • kube-proxy — programa as regras de rede que fazem o Service funcionar.
Detalhe que tranquiliza em incidente. Se o control plane cair, os Pods que já estão rodando continuam rodando e servindo tráfego. O que para é a capacidade de mudar o cluster: nada novo é agendado, nada é reconciliado, e o que morrer não será recriado. É uma degradação séria, mas não é uma queda — e saber disso muda a prioridade da resposta.
kubectl get nodes -o wide
kubectl get pods -n kube-system        # os componentes do próprio cluster
kubectl describe node <node>           # capacidade, alocado, condições
kubectl get events --sort-by=.lastTimestamp   # o que o cluster andou fazendo
Armadilhas
  • Não fazer backup do etcd. Ele é o cluster inteiro. Sem ele, sobra hardware.
  • Confundir node com Pod. Node é a máquina; Pod é a carga que roda nela.
  • Ignorar kubectl get events. É o log do que o cluster tentou fazer, e responde a maior parte dos "por que não subiu".
Pratique agoraSuba um cluster local com kind e liste os Pods de kube-system. Identifique cada componente da tabela acima rodando ali.
Prova de domínioVocê nomeia cada componente pela função e explica o que continua funcionando se o control plane cair.

kubectl e manifestos: a linguagem do cluster

essencial

Direto: tudo no Kubernetes é um recurso descrito em YAML com quatro campos obrigatórios: apiVersion, kind, metadata e spec. O kubectl é só um cliente HTTP conversando com o api-server.

≈

Como formulários padronizados. Muda o tipo do formulário, mas o cabeçalho é sempre o mesmo: qual formulário é este, quem é o interessado, e o que se pede. Depois que você entende o cabeçalho, qualquer formulário novo é só um corpo diferente.

Como surgiu

A uniformidade é deliberada: qualquer coisa — carga, rede, configuração, permissão e até extensões que você criar — é um recurso com a mesma estrutura e a mesma API. É isso que permite kubectl get funcionar igual para tudo, e é a base do GitOps: se todo o estado cabe em arquivos, o Git pode ser a fonte da verdade.

Veio substituir: a API específica por tipo de objeto e os comandos imperativos que não deixavam registro do que foi pedido.

Onde você usa isso no dia a dia

  • Ao versionar a infraestrutura junto com o código.
  • Ao descobrir os campos de um recurso sem abrir documentação.

  • Comandos imperativos em produção. kubectl run e scale não deixam rastro no Git e são desfeitos no próximo apply.

As cargas: Pod, Deployment e labels

Os objetos que você mais vai usar — e o mecanismo simples que liga todos eles.

Pod: a unidade que o cluster agenda

essencial

Direto: o Kubernetes não agenda containers — agenda Pods. Um Pod é um ou mais containers que compartilham rede e podem compartilhar volumes, sempre na mesma máquina. E ele é descartável: nunca se conserta um Pod, substitui-se.

≈

Como um apartamento compartilhado. Os moradores dividem o endereço e o telefone (a rede) e algumas áreas comuns (os volumes), mas cada um tem o seu quarto. Eles se falam por "aqui dentro" — localhost — e do lado de fora o prédio enxerga um endereço só.

Como surgiu

A abstração existe porque alguns processos precisam mesmo estar juntos: um servidor e um coletor de logs que lê o mesmo arquivo, uma aplicação e um proxy que intercepta o tráfego dela. Sem o Pod, seria preciso garantir coalocação por regra de agendamento — frágil e complicado. Com ele, "juntos" virou propriedade da unidade.

Veio substituir: as regras manuais de afinidade para manter dois containers na mesma máquina.

Onde você usa isso no dia a dia

  • Toda aplicação sua roda dentro de um.
  • Ao adicionar um sidecar de log ou de malha de serviço.
  • Ao investigar um Pod que não sai de Pending ou entra em CrashLoopBackOff.

Na prática, você quase nunca cria um Pod diretamente. Pod avulso não é recriado se o node cair — ninguém está reconciliando por ele. Quem cria Pods é um controlador: Deployment para aplicação sem estado, StatefulSet para carga com identidade, DaemonSet para um por node, Job e CronJob para tarefas que terminam.

Labels e selectors: o mecanismo que liga tudo

essencialo elo

Direto: objetos não se referenciam por nome no Kubernetes — se ligam por label. O Deployment gerencia os Pods cujas labels casam com o seu selector; o Service manda tráfego para os Pods cujas labels casam com o dele. É um mecanismo só, e explica quase toda ligação do cluster.

≈

Como crachás num evento. Ninguém tem uma lista com o nome de cada pessoa: as regras dizem "quem tem crachá verde entra na sala A". Quem chegar depois com crachá verde entra também, sem precisar atualizar lista nenhuma. Tirar o crachá te desliga da sala na hora.

Como surgiu

É herança direta do Borg e resolve um problema de escala: manter listas explícitas de membros não funciona quando os membros nascem e morrem o tempo todo. Com seleção por atributo, a associação é calculada continuamente — nada precisa ser atualizado quando um Pod novo aparece.

Veio substituir: a configuração de balanceador com lista de IPs, que precisava ser reescrita a cada mudança de instância.

Onde você usa isso no dia a dia

  • Ao descobrir que o Service não tem endpoint — é label que não casa.
  • Ao filtrar recursos: kubectl get pods -l app=pedidos.
  • Ao fazer um deploy canário mandando tráfego para um subconjunto.
spec:
  selector:
    matchLabels: { app: pedidos }      # o Deployment procura Pods com esta label
  template:
    metadata:
      labels: { app: pedidos }         # e carimba os Pods que cria com ela
---
kind: Service
spec:
  selector: { app: pedidos }           # o Service manda tráfego para os mesmos

# o diagnóstico que resolve 80% dos "o Service não responde":
kubectl get endpoints pedidos          # vazio? nenhum Pod casou com o selector
kubectl get pods --show-labels
O sintoma mais comum do cluster inteiro. "O Service não responde" quase sempre é label que não casa — uma diferença de maiúscula, um nome trocado entre o selector e o template. kubectl get endpoints responde na hora: se a lista está vazia, o problema não é rede nem aplicação, é seleção.
Armadilhas
  • Mudar o selector de um Deployment existente. É campo imutável: o cluster recusa, e você precisa recriar o objeto.
  • Selector amplo demais. Dois Deployments com o mesmo selector brigam pelos mesmos Pods.
  • Confundir label com annotation. Label é para seleção; annotation é metadado livre, não selecionável.
Pratique agoraQuebre o selector do seu Service de propósito e observe get endpoints esvaziar. Depois conserte e veja voltar.

Deployment e ReplicaSet: a cadeia de controle

essencial

Direto: o Deployment gerencia versões; ele cria um ReplicaSet por versão, e cada ReplicaSet garante o número de Pods daquela versão. Ao atualizar, o Deployment cria um ReplicaSet novo e move as réplicas gradualmente — é isso que torna o rollback trivial.

≈

Como turnos de uma equipe. O gerente (Deployment) organiza a troca: o turno novo (ReplicaSet novo) entra aos poucos enquanto o antigo sai, para que o atendimento nunca pare. E se o turno novo se revelar um desastre, o antigo ainda está cadastrado e volta na hora.

Como surgiu

No começo existia só o ReplicationController, que mantinha N cópias e não sabia atualizar. As atualizações eram feitas por um comando externo que orquestrava a troca — e falhava no meio, deixando duas versões sem ninguém no controle. O Deployment trouxe a atualização para dentro do modelo declarativo, mantendo o histórico de ReplicaSets como mecanismo natural de rollback.

Veio substituir: o kubectl rolling-update imperativo, que se perdia se o terminal fechasse no meio.

Onde você usa isso no dia a dia

  • Toda aplicação sem estado que você sobe.
  • Ao atualizar a versão da imagem em produção.
  • Ao voltar atrás depois de um deploy ruim.
apiVersion: apps/v1
kind: Deployment
metadata: { name: pedidos }
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }   # nunca abaixo de 3 servindo
  selector:
    matchLabels: { app: pedidos }
  template:
    metadata: { labels: { app: pedidos } }
    spec:
      containers:
        - name: app
          image: registro.empresa.com/pedidos@sha256:3f9c...   # digest, não tag móvel
          ports: [ { containerPort: 8080 } ]

O par maxSurge e maxUnavailable define o comportamento da troca. Com maxUnavailable: 0 e maxSurge: 1, o cluster sobe um Pod novo, espera ele ficar pronto e só então remove um antigo — capacidade nunca cai abaixo do declarado, ao custo de precisar de um pouco de folga. É o padrão certo para a maioria das aplicações.

kubectl rollout status deploy/pedidos      # acompanha a troca
kubectl rollout history deploy/pedidos     # as versões anteriores
kubectl rollout undo deploy/pedidos        # volta para a anterior — em segundos
Armadilhas
  • Rolling update sem readiness probe. O cluster acha que o Pod novo está pronto assim que o processo sobe, e manda tráfego para uma aplicação que ainda está iniciando.
  • Tag móvel na imagem. Sem mudar o manifesto, o Deployment não percebe que a imagem mudou — e o rollback aponta para a mesma tag.
  • Duas versões incompatíveis no ar. Durante o rollout as duas convivem: se a nova exige um esquema de banco que a antiga não entende, o intervalo é um incidente.
Pratique agoraFaça um rollout com maxUnavailable: 0 mantendo carga contínua e confirme zero erro. Depois suba uma imagem quebrada e use rollout undo.

Namespace: separar sem separar cluster

aprofundamento

Direto: namespace é um agrupamento lógico de recursos dentro do mesmo cluster. Serve para organizar, aplicar cota e limitar permissão — mas não isola rede por padrão, e essa é a confusão mais frequente.

≈

Como andares de um prédio. Cada andar tem sua numeração de salas e o correio interno sabe distinguir. Mas o elevador leva qualquer pessoa a qualquer andar, a menos que alguém programe restrição — que é exatamente o papel da NetworkPolicy.

Como surgiu

Nasceu da necessidade de compartilhar um cluster entre times sem que um esbarrasse no outro: nomes iguais em contextos diferentes, cota de recurso por grupo e permissão por escopo. O que ficou de fora deliberadamente foi o isolamento de rede — para não impor uma política de segurança a quem não precisava dela.

Veio substituir: um cluster por time ou por ambiente, com todo o custo de operar vários.

Onde você usa isso no dia a dia

  • Separar desenvolvimento, homologação e produção — quando o risco permite o mesmo cluster.
  • Dar a cada time o seu espaço com cota própria.
  • Ao descobrir que o recurso "sumiu" porque estava em outro namespace.
kubectl create namespace pedidos
kubectl apply -f k8s/ -n pedidos
kubectl config set-context --current --namespace=pedidos   # evita esquecer o -n

# DNS entre namespaces: nome completo
# <servico>.<namespace>.svc.cluster.local
curl http://estoque.catalogo.svc.cluster.local:8080/health

# isolamento de rede NÃO é automático — precisa de política
kubectl get networkpolicy -A
Armadilhas
  • Assumir isolamento de rede. Sem NetworkPolicy, qualquer Pod alcança qualquer outro, em qualquer namespace.
  • Produção e desenvolvimento no mesmo cluster. Namespace não protege contra erro de configuração no control plane nem contra vizinho barulhento.
  • Esquecer o -n. Metade dos "não achei o recurso" é isso.
Pratique agoraSuba a mesma aplicação em dois namespaces e alcance uma a partir da outra pelo FQDN. Depois aplique uma NetworkPolicy que bloqueie e confirme.

Rede: como o tráfego chega no Pod

O caminho completo, do navegador até o container — e onde ele costuma se perder.

Service: o endereço estável para Pods efêmeros

essencial

Direto: Pods nascem e morrem com IPs diferentes. O Service dá um IP e um nome DNS estáveis e distribui o tráfego entre os Pods que casam com o seu selector — que mudam o tempo todo, sem que ninguém precise reconfigurar nada.

≈

Como o número da central de atendimento. Você liga sempre para o mesmo número; quem atende é qualquer atendente disponível naquele momento. Se cinco entram e três saem no turno, o número não muda — e o cliente nunca soube que mudou alguém.

Como surgiu

É a resposta direta ao fato de o Pod ser descartável. Sem uma camada de indireção, qualquer cliente precisaria descobrir e acompanhar os IPs — o que devolveria o problema de configuração dinâmica que o cluster veio resolver. O Service é implementado pelo kube-proxy, que programa regras de rede no kernel de cada node.

Veio substituir: o balanceador com lista de IPs mantida à mão, e o registro de serviço externo que cada linguagem implementava do seu jeito.

Onde você usa isso no dia a dia

  • Aplicação falando com o banco ou com outro serviço pelo nome.
  • Distribuir carga entre réplicas sem configurar nada.
  • Ao investigar por que a chamada interna não chega.

São três tipos e a diferença é apenas o alcance. ClusterIP — o padrão — só é alcançável de dentro do cluster, e é o certo para comunicação entre serviços. NodePort abre a mesma porta em todos os nodes, útil em cluster local e raro em produção. LoadBalancer pede um balanceador ao provedor de nuvem e é o caminho normal para expor de verdade.

apiVersion: v1
kind: Service
metadata: { name: pedidos }
spec:
  selector: { app: pedidos }        # os Pods de destino
  ports:
    - port: 80                      # a porta DO SERVICE
      targetPort: 8080              # a porta DO CONTAINER

# de qualquer Pod do cluster:
curl http://pedidos/health                       # mesmo namespace
curl http://pedidos.producao.svc.cluster.local   # de outro namespace
O DNS interno é o que torna tudo simples. Cada Service ganha um registro automático, e o nome curto funciona dentro do mesmo namespace. É o equivalente exato do nome de serviço do Compose — a mesma ideia, num cluster distribuído. Quem entendeu rede no Compose já entendeu metade disso.
Armadilhas
  • Confundir port com targetPort. A primeira é por onde chamam o Service; a segunda é onde a aplicação escuta.
  • Aplicação escutando em 127.0.0.1. Dentro do container ela precisa escutar em 0.0.0.0, senão nada de fora do Pod alcança.
  • Esperar sessão fixa. O balanceamento é por conexão e não garante que o mesmo cliente caia sempre no mesmo Pod — é o motivo de a aplicação precisar ser sem estado.
Pratique agoraCrie um Service, escale para três réplicas e chame o endpoint várias vezes a partir de outro Pod, imprimindo o nome do Pod que respondeu. Veja o balanceamento acontecer.

Ingress: uma porta de entrada para todos os serviços

essencial

Direto: o Ingress é uma regra de roteamento HTTP — por host e por caminho — que aponta para Services. Quem executa a regra é o Ingress Controller, um proxy rodando no cluster. Sem controller instalado, o Ingress é um objeto inerte.

≈

Como a recepção de um prédio comercial. Um endereço só na rua; a recepcionista lê o que a pessoa procura e encaminha para a empresa certa. O Ingress é a lista de encaminhamento; o controller é a recepcionista. Ter a lista sem ninguém na recepção não encaminha ninguém.

Como surgiu

Sem Ingress, expor dez serviços significava dez balanceadores na nuvem — dez IPs, dez certificados, dez faturas. O Ingress consolidou isso num único ponto de entrada com roteamento em camada 7, terminação de TLS e certificado automático. É por isso que virou o padrão de exposição HTTP.

Veio substituir: um Service do tipo LoadBalancer por aplicação, com o custo multiplicado pelo número de serviços.

Onde você usa isso no dia a dia

  • Expor várias APIs sob o mesmo domínio, por caminho.
  • Terminar TLS num lugar só, com certificado renovado automaticamente.
  • Rotear por subdomínio para ambientes ou clientes diferentes.
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt
spec:
  ingressClassName: nginx
  tls:
    - hosts: [ api.loja.com ]
      secretName: api-tls
  rules:
    - host: api.loja.com
      http:
        paths:
          - path: /pedidos
            pathType: Prefix
            backend: { service: { name: pedidos, port: { number: 80 } } }
Armadilhas
  • Ingress sem controller. O objeto é aceito e nada acontece. É a causa número um de "criei e não funciona".
  • Esquecer o ingressClassName. Com mais de um controller, ninguém assume a regra.
  • Anotação de outro controller. As anotações são específicas: as do NGINX não funcionam no Traefik.
Pratique agoraInstale um controller no cluster local, exponha dois serviços por caminho no mesmo host e acompanhe o log do controller enquanto faz as requisições.
Prova de domínioVocê desenha o caminho navegador → LB → controller → Service → Pod e sabe em qual etapa investigar cada falha.

Quando a requisição não chega: o roteiro

essencialmétodo

Direto: problema de rede em cluster se resolve de dentro para fora, testando cada salto isoladamente. Começar pelo navegador é olhar o fim da cadeia e adivinhar o que aconteceu antes.

≈

Como testar uma tomada. Você não troca a fiação da rua: testa o aparelho, depois a tomada, depois o disjuntor, depois o quadro. Um teste por vez, do mais perto para o mais longe — o mesmo método de investigação da parte 05 do roadmap de Java.

Como surgiu

É o método de bisseção aplicado à rede do cluster. Cada camada — container, Pod, Service, Ingress, DNS externo — pode falhar de forma independente, e testar na ordem elimina metade das hipóteses a cada passo. Sem ordem, a investigação vira tentativa e erro em cinco camadas ao mesmo tempo.

Veio substituir: o ciclo de mexer no Ingress, no Service e no Deployment simultaneamente e reaplicar torcendo.

Onde você usa isso no dia a dia

  • "A aplicação subiu mas não responde."
  • Erro 502 ou 504 vindo do Ingress.
  • Um serviço interno não alcança o outro.
# 1. o container responde? (dentro do próprio Pod)
kubectl exec -it deploy/pedidos -- curl -s localhost:8080/actuator/health

# 2. o Pod responde de fora dele? (pelo IP do Pod, de outro Pod)
kubectl run tmp --rm -it --image=curlimages/curl -- sh
  curl http://10.244.1.7:8080/actuator/health

# 3. o Service tem destino?
kubectl get endpoints pedidos          # vazio = label não casa

# 4. o Service responde pelo nome?
  curl http://pedidos/actuator/health

# 5. o Ingress encaminha?
kubectl describe ingress api
kubectl logs -n ingress-nginx deploy/ingress-nginx-controller

# 6. só agora: DNS e certificado externos

Onde costuma parar

  • Parou no 1 — problema da aplicação, não do cluster.
  • Parou no 2 — escutando em 127.0.0.1 em vez de 0.0.0.0.
  • Parou no 3 — label do selector não casa, ou readiness reprovando.
  • Parou no 4 — targetPort errado.
  • Parou no 5 — falta controller, classe ou caminho errado.
  • Parou no 6 — DNS ou certificado.

Comandos que economizam tempo

  • kubectl port-forward svc/pedidos 8080:80 — testa o Service do seu terminal, pulando Ingress e DNS.
  • kubectl get events --sort-by=.lastTimestamp — o que o cluster tentou fazer.
  • kubectl describe pod — eventos e estado das probes no fim da saída.
  • kubectl logs --previous — o log da encarnação anterior, em CrashLoop.
Armadilhas
  • Mexer em várias camadas ao mesmo tempo. Quando voltar a funcionar, você não sabe o que era — e volta a acontecer.
  • Ignorar o readiness. Pod Running mas 0/1 não recebe tráfego, e o Service parece quebrado.
  • Testar só pelo navegador. Cache e certificado atrapalham o diagnóstico; use curl.
Pratique agoraQuebre um salto de cada vez — porta errada, label errada, sem controller — e confirme que o roteiro sempre aponta o passo certo.
Prova de domínioDiante de "não responde", você localiza o salto exato em menos de cinco minutos, sem alterar nada antes de ter a causa.

Configuração, probes e recursos

O que separa um Pod que "sobe" de um Pod que se comporta bem em produção.

ConfigMap e Secret: configuração fora da imagem

essencial

Direto: ConfigMap guarda configuração não sensível; Secret guarda credencial. E é importante saber desde o primeiro dia: Secret é apenas codificado em base64, não criptografado — sem configuração adicional, quem lê o etcd lê a senha.

≈

Como um envelope pardo e um envelope lacrado. Os dois separam o conteúdo do resto da correspondência, mas só um deles resiste a alguém curioso. Tratar o envelope pardo como cofre é a origem do problema.

Como surgiu

Os dois nasceram do mesmo princípio 12-factor de manter configuração fora do artefato. O Secret foi separado do ConfigMap para permitir tratamento diferenciado — permissão distinta, cifra em repouso, integração com cofre externo. O base64 nunca foi proteção: é só para permitir conteúdo binário no YAML, e a confusão com criptografia é quase universal.

Veio substituir: a configuração embutida na imagem, que obrigava a reconstruir para mudar um timeout.

Onde você usa isso no dia a dia

  • Perfil ativo, URLs e limites da aplicação.
  • Senha de banco e token de parceiro.
  • Certificado TLS usado pelo Ingress.
apiVersion: v1
kind: ConfigMap

Probes: liveness, readiness e startup

essencialprodução

Direto: três perguntas diferentes com três consequências opostas. Liveness: está sadio? Se falhar, o container é morto e recriado. Readiness: pode receber tráfego? Se falhar, sai do Service. Startup: já terminou de iniciar? Segura as outras duas enquanto isso.

≈

Como uma loja. Readiness é a placa "aberto/fechado": fechada por uma hora no almoço, ninguém demole a loja. Liveness é a vistoria estrutural: reprovou, o prédio é interditado. Confundir as duas faz o síndico demolir a loja porque ela fechou para o almoço.

Como surgiu

Existia um único conceito de saúde, e ele causava o pior comportamento possível: banco fora do ar por dois minutos derrubava e recriava todos os Pods, sobrecarregando o banco justamente na hora de ele se recuperar. Separar "está vivo" de "pode atender" resolveu isso. O startup probe veio depois, para aplicações de inicialização lenta — como as JVM — que eram mortas antes de terminar de subir.

Veio substituir: o único /health genérico, e o initialDelaySeconds chutado que ou era curto demais ou atrasava a entrada em serviço.

Onde você usa isso no dia a dia

  • Todo Deployment em produção — sem probe, o rolling update é cego.
  • Ao investigar restart em loop de um Pod que estava funcionando.
  • Ao evitar que tráfego chegue numa aplicação ainda iniciando.
    startupProbe:                       # dá tempo para a JVM subir
      httpGet: { path: /actuator/health/liveness, port: 8080 }
      failureThreshold: 30
      periodSeconds: 5                  # até 150s para iniciar, sem ser morto

    livenessProbe:                      # NÃO olhe dependência externa aqui
      httpGet: { path: /actuator/health/liveness, port: 8080 }
      periodSeconds: 10
      failureThreshold: 3

    readinessProbe:                     # AQUI sim: banco, broker, cache
      httpGet: { path: /actuator/health/readiness, port: 8080 }
      periodSeconds: 5
      failureThreshold: 2
A regra que evita o incidente em cascata. Liveness nunca olha dependência externa. Se o banco cair e o liveness reprovar, o orquestrador mata e recria todos os Pods — que subirão, tentarão conectar, falharão e serão mortos de novo, num ciclo que consome o cluster e impede a recuperação. Dependência externa é assunto de readiness: o Pod sai do balanceador, continua vivo, e volta sozinho quando o banco voltar.
Armadilhas
  • Sem startup probe numa JVM. O liveness mata o Pod antes de a aplicação terminar de subir — e o ciclo nunca fecha.
  • Probe que executa consulta cara. Com o probe rodando a cada cinco segundos em cada réplica, você criou carga constante no banco.
  • Readiness igual ao liveness. Você perdeu a distinção e voltou ao comportamento binário.
  • Sem readiness no rollout. O cluster manda tráfego para Pods que ainda não estão prontos.
Pratique agoraDerrube o banco com a aplicação no ar e confirme: readiness cai, liveness continua passando, o Pod sai do Service e volta sozinho quando o banco retorna.

Requests, limits e QoS: o contrato de recursos

essencial

Direto: request é o que o Pod reserva — e é o que o scheduler usa para decidir onde ele cabe. Limit é o teto. Estourar o limite de memória mata o container na hora; estourar o de CPU só o desacelera.

≈

Como reservar mesa num restaurante. O request é a reserva: garante que existe lugar para você. O limit é o quanto você pode ocupar no máximo. Sem reserva, você senta se sobrar — e é o primeiro a levantar quando a casa lota.

Como surgiu

Vem direto dos cgroups da primeira parte, agora expostos de forma declarativa e usados também para agendamento. A distinção entre memória e CPU não é arbitrária: memória não é compressível — ou tem, ou o processo morre. CPU é compressível — falta dela só faz o processo ir mais devagar.

Veio substituir: o "uma aplicação por máquina" que desperdiçava recurso, e a coabitação sem limite em que um vizinho barulhento derrubava os outros.

Onde você usa isso no dia a dia

  • Ao dimensionar um serviço novo.
  • Ao investigar Pod OOMKilled ou Pod eternamente Pending.
  • Ao entender por que o Pod é sempre o primeiro a ser despejado.
    resources:
      requests: { memory: "512Mi", cpu: "250m" }   # reserva — o scheduler usa isto
      limits:   { memory: "512Mi", cpu: "1000m" }  # teto

# memória: requests == limits  →  QoS Guaranteed, o último a ser despejado
# CPU: limite mais alto que o request permite aproveitar folga da máquina

# e a JVM precisa saber do limite:
env:
  - name: JAVA_TOOL_OPTIONS
    value: "-XX:MaxRAMPercentage=75 -XX:+UseG1GC"
Classe QoSQuando aconteceNo aperto
Guaranteedrequests == limits para tudoúltimo a ser despejado
Burstabletem request, limit maiordespejado depois do BestEffort
BestEffortsem request nem limito primeiro a morrer
Armadilhas
  • Sem requests. O Pod vira BestEffort e é o primeiro despejado quando o node aperta — inclusive em produção.
  • Limite de CPU muito baixo. O container é estrangulado e a latência sobe sem nenhum erro aparente: parece lentidão de aplicação.
  • JVM sem MaxRAMPercentage. É o OOMKilled clássico — o heap não cabe no limite do container.
  • Request muito alto. Reserva o que não usa e o Pod fica Pending por falta de node com espaço.
Pratique agoraSuba a aplicação com limite de 256Mi sem ajustar a JVM e observe o OOMKilled. Adicione MaxRAMPercentage e repita.
Prova de domínioVocê dimensiona requests e limits com base em medição, sabe a classe QoS resultante e relaciona o limite de memória ao heap da JVM.

Estado e armazenamento

A parte que o Kubernetes faz com menos naturalidade — e onde a decisão mais importante é não fazer.

PV, PVC e StorageClass: o disco desacoplado do Pod

essencial

Direto: o Pod não pede um disco: pede um PersistentVolumeClaim — "quero 20 GB com estas características". A StorageClass provisiona um PersistentVolume real e faz a ligação. O Pod morre, o volume fica.

≈

Como um guarda-volumes. Você não escolhe o armário nem sabe onde ele fica: entrega o comprovante (a claim) e recebe o seu conteúdo. Se você trocar de hóspede, o comprovante continua valendo — o armário não pertence à pessoa, pertence à reserva.

Como surgiu

A separação entre pedido e provisionamento existe porque o desenvolvedor não deveria precisar saber qual tecnologia de armazenamento a empresa usa. Antes, o manifesto trazia o caminho do NFS ou o identificador do disco da nuvem — e o mesmo YAML não rodava em outro lugar. Com StorageClass, o pedido é abstrato e o provisionamento é responsabilidade da plataforma.

Veio substituir: o volume declarado com detalhe de infraestrutura dentro do manifesto da aplicação.

Onde você usa isso no dia a dia

  • Banco de dados rodando dentro do cluster.
  • Upload de arquivo que precisa sobreviver ao restart do Pod.
  • Ao investigar Pod Pending esperando volume.
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: pgdata }
spec:
  accessModes: [ ReadWriteOnce ]     # um node por vez — o modo mais comum
  storageClassName: standard
  resources: { requests: { storage: 20Gi } }
---
      volumes:
        - name: dados
          persistentVolumeClaim: { claimName: pgdata }
      containers:
        - name: db
          volumeMounts:
            - { name: dados, mountPath: /var/lib/postgresql/data }

O modo de acesso é o detalhe que mais confunde. ReadWriteOnce significa montável por um node por vez — e é o que praticamente todo disco de bloco oferece. Se você tentar rodar duas réplicas em nodes diferentes com o mesmo PVC, a segunda fica Pending para sempre. Compartilhar entre nodes exige ReadWriteMany, que só alguns tipos de armazenamento suportam.

Armadilhas
  • Duas réplicas com o mesmo PVC ReadWriteOnce. A segunda nunca sobe, e a mensagem não é óbvia.
  • reclaimPolicy: Delete em dado importante. Apagar o PVC apaga o disco de verdade, sem confirmação.
  • Confiar em snapshot como backup. Snapshot no mesmo provedor, na mesma conta, cai junto no incidente que apagar tudo.
Pratique agoraSuba um Postgres com PVC, grave dados, apague o Pod e confirme que os dados voltam. Depois tente escalar para duas réplicas e observe a segunda travar.

StatefulSet: quando a identidade importa

aprofundamento

Direto: Deployment trata os Pods como gado — todos iguais e intercambiáveis. StatefulSet dá a cada um identidade estável, nome previsível, disco próprio e ordem de partida. É o que bancos e brokers em cluster exigem.

≈

Como poltronas numa orquestra. Num coral, qualquer voz pode ficar em qualquer lugar. Numa orquestra, o primeiro violino é o primeiro violino — tem lugar fixo, partitura própria e entra numa ordem. Trocar dois de lugar não é indiferente.

Como surgiu

O Kubernetes nasceu para carga sem estado, e por algum tempo a recomendação era não rodar banco nele. Ficou insustentável: as pessoas rodavam de qualquer jeito, com gambiarras. O StatefulSet trouxe as garantias que essas cargas precisam — nome estável, volume por réplica e ordem — sem prometer que o cluster resolve replicação e consistência, que continuam sendo do software.

Veio substituir: as combinações artesanais de Deployment com um Pod, volume fixo e Service dedicado para simular identidade.

Onde você usa isso no dia a dia

  • Banco, fila ou cache em cluster, com réplicas que se conhecem.
  • Qualquer carga em que a réplica precisa do seu disco, não de um disco qualquer.
  • Ao decidir se aquilo deveria mesmo rodar dentro do cluster.

O que o StatefulSet garante

  • Nome estável — pg-0, pg-1, pg-2, sempre os mesmos.
  • DNS por réplica — cada uma alcançável individualmente.
  • Volume próprio — um PVC por réplica, que a segue.
  • Ordem — sobe e desce em sequência, não em bloco.

O que ele não resolve

  • Replicação de dados — quem replica é o Postgres, não o Kubernetes.
  • Eleição de líder — é do software, ou de um operador.
  • Backup — continua sendo trabalho seu.
  • Failover correto — exige um operador que entenda daquele banco.
A pergunta honesta antes de começar. Rodar banco em Kubernetes é possível e é feito em produção — com um operador maduro, alguém que entenda daquele banco e um plano de backup testado. Se a empresa tem um serviço gerenciado disponível, ele quase sempre é a escolha certa: o custo mensal é menor que o custo de uma noite de recuperação mal feita. Deixe o cluster para o que é sem estado, que é onde ele brilha.
Armadilhas
  • Achar que StatefulSet dá alta disponibilidade. Ele dá identidade; disponibilidade é do software que roda ali.
  • Escalar para baixo sem entender. Os PVCs sobrevivem por padrão — e voltam a ser usados quando você escalar de novo.
  • Banco em cluster sem operador. No dia do failover, você descobre que ninguém no time sabe o procedimento.
Pratique agoraSuba um StatefulSet de três réplicas e observe os nomes, os PVCs e a ordem de partida. Depois escale para uma e veja os PVCs permanecerem.
Prova de domínioVocê lista o que o StatefulSet garante e o que não garante — e defende com argumento quando não rodar banco no cluster.

Operar: rollout, escala e diagnóstico

O que você faz depois que subiu — e o capstone que fecha a série.

Rollout e rollback sem derrubar ninguém

essencial

Direto: o rolling update troca as réplicas aos poucos, respeitando o readiness. Isso só funciona de verdade se três peças estiverem certas: probe honesta, shutdown gracioso e compatibilidade entre as duas versões que vão conviver.

≈

Como trocar os pneus com o carro andando. Só dá certo um de cada vez, confirmando que o novo está firme antes de tirar o próximo. Trocar os quatro juntos é parar o carro — que é exatamente o que acontece quando o readiness está errado.

Como surgiu

A substituição gradual resolveu o dilema entre janela de manutenção e risco. O que a tornou confiável foi a combinação com o readiness probe: o cluster não "espera dez segundos e torce" — ele pergunta ao Pod novo se ele já pode atender, e só então retira um antigo. Antes disso, deploy sem downtime era uma coreografia manual e frágil.

Veio substituir: a janela de manutenção noturna e o script de deploy que parava tudo, atualizava e rezava.

Onde você usa isso no dia a dia

  • Todo deploy de aplicação.
  • Ao reverter um deploy ruim em segundos.
  • Ao coordenar mudança de esquema de banco com deploy de código.
kubectl set image deploy/pedidos app=registro/pedidos@sha256:novo
kubectl rollout status deploy/pedidos --timeout=120s   # espera de verdade
kubectl rollout undo deploy/pedidos                    # volta para a anterior

# no manifesto, o que torna o rollout seguro:
  strategy:
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
  minReadySeconds: 10        # estabilidade mínima antes de contar como pronto
  spec:
    terminationGracePeriodSeconds: 30   # tempo para drenar antes do SIGKILL
As duas versões convivem — e isso tem consequência. Durante o rollout, a versão antiga e a nova atendem ao mesmo tempo. Se a nova exige uma coluna que a antiga não conhece, o intervalo é um incidente. A regra que resolve: mudança de esquema é sempre aditiva e vai em deploy separado. Primeiro adiciona a coluna (compatível com as duas), depois sobe o código que usa, e só num terceiro momento remove o que ficou obsoleto. É exatamente o versionamento de contrato da parte 06 do roadmap de Arquitetura, aplicado ao banco.
Armadilhas
  • Rollout sem readiness. O cluster acha que está pronto assim que o processo sobe, e manda tráfego para quem ainda está iniciando.
  • Sem shutdown gracioso. As requisições em andamento no Pod antigo são cortadas — e aqui volta o ENTRYPOINT em forma exec da parte 02.
  • Migração destrutiva junto com o deploy. Remover coluna enquanto a versão antiga ainda roda quebra tudo no meio da troca.
Pratique agoraFaça um rollout com carga contínua e confirme zero erro. Depois remova o readiness probe e repita — a diferença aparece no primeiro segundo.
Prova de domínioVocê faz deploy sem perder requisição e sabe descrever a sequência de três passos para mudança de esquema.

Escala: HPA e o gargalo que ele não resolve

essencial

Direto: o HPA aumenta e diminui o número de réplicas conforme uma métrica. Ele só funciona se a aplicação for sem estado, se houver requests definidos, e — o mais esquecido — se o gargalo for a aplicação, e não o banco.

≈

Como abrir mais caixas no supermercado. Resolve enquanto o gargalo é o atendimento. Se o problema é que só existe uma porta de saída, abrir dez caixas apenas move a fila de lugar — e agora ela está num lugar onde ninguém está olhando.

Como surgiu

Escalar manualmente exige alguém observando, o que não funciona em pico noturno nem em campanha inesperada. O HPA fecha o laço: mede, compara com o alvo e ajusta o número de réplicas — a mesma lógica de reconciliação que rege todo o resto do cluster, aplicada à quantidade.

Veio substituir: o dimensionamento fixo para o pico, que desperdiça recurso em 90% do tempo, e o kubectl scale feito às pressas durante o incidente.

Onde você usa isso no dia a dia

  • Serviço com carga que varia por horário ou por campanha.
  • Ao reduzir custo fora do horário de pico.
  • Ao descobrir que escalar a aplicação não melhorou nada.
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: pedidos }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: pedidos }
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }   # % do REQUEST
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300    # evita subir e descer sem parar
A conta que quase ninguém faz. Vinte réplicas com pool de dez conexões cada são duzentas conexões pedidas ao banco — e um PostgreSQL padrão aceita cem. O HPA acabou de transformar um problema de latência num incidente de banco. Antes de aumentar o teto, verifique a cadeia inteira: pool por réplica, limite do banco, e limite de quem você chama. Escalar a aplicação sem escalar o que está atrás só leva a fila para dentro do banco, exatamente como na parte 08 do roadmap de Arquitetura.
Armadilhas
  • HPA sem requests de CPU. A métrica é percentual do request: sem ele, não há base de cálculo e o HPA não funciona.
  • Oscilação. Sem janela de estabilização, o número de réplicas fica subindo e descendo o tempo todo.
  • Escalar carga com estado. Se o Pod guarda estado, mais réplicas é mais divergência.
  • Métrica errada. Serviço que passa a vida esperando I/O tem CPU baixa mesmo sobrecarregado — melhor escalar por requisições por segundo ou por profundidade de fila.
Pratique agoraGere carga, observe o HPA escalar e acompanhe as conexões no banco enquanto isso. É a forma mais rápida de enxergar o gargalo se mover.
Prova de domínioVocê configura HPA com a métrica adequada e verifica a cadeia inteira antes de aumentar o teto de réplicas.

RBAC e ServiceAccount: privilégio mínimo no cluster

essencial

Direto: toda ação no cluster passa pelo api-server e é autorizada por RBAC. Pessoas usam credencial própria; aplicações usam ServiceAccount. E toda ServiceAccount deve ter o mínimo — de preferência, nenhuma permissão.

≈

Como o crachá de um prestador de serviço. Ele entra, mas só nos andares de que precisa, e o crachá vence. Dar acesso mestre "porque é mais rápido" é o que transforma um incidente pequeno em comprometimento total.

Como surgiu

Nas primeiras versões o modelo de permissão era rudimentar e, na prática, quase todo mundo operava com acesso amplo. Com a adoção corporativa, o RBAC virou padrão e trouxe o modelo de papéis com escopo — por namespace ou por cluster. Hoje é a principal fronteira de segurança dentro do cluster.

Veio substituir: o acesso de administrador compartilhado entre todos e a ServiceAccount padrão com mais permissão do que deveria.

Onde você usa isso no dia a dia

  • Ao dar acesso a um time novo, limitado ao namespace dele.
  • Ao configurar o que o pipeline de CI pode fazer no cluster.
  • Ao ler um erro forbidden e entender o que falta.
# um papel mínimo, no escopo de um namespace
kind: Role
metadata: { namespace: pedidos, name: leitor }
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]         # só leitura
---
kind: RoleBinding
subjects: [ { kind: ServiceAccount, name: ci, namespace: pedidos } ]
roleRef: { kind: Role, name: leitor, apiGroup: rbac.authorization.k8s.io }

# a aplicação que não precisa falar com a API não deve receber token:
spec:
  automountServiceAccountToken: false

# antes de conceder, teste:
kubectl auth can-i delete pods --as=system:serviceaccount:pedidos:ci
Armadilhas
  • cluster-admin para resolver rápido. Vira permanente e ninguém revisa depois.
  • Token montado sem necessidade. Se a aplicação não fala com a API, o token só serve para quem invadir o Pod.
  • ClusterRole quando bastava Role. Escopo de cluster onde bastava um namespace multiplica o alcance de qualquer erro.
Pratique agoraCrie uma ServiceAccount de leitura, gere um contexto com ela e tente apagar um Pod. Confirme o forbidden com auth can-i.
Prova de domínioVocê concede o mínimo, testa com can-i antes de aplicar e desliga o token onde ele não é necessário.

Helm e o empacotamento dos manifestos

aprofundamento

Direto: uma aplicação real tem oito ou dez manifestos, quase iguais entre ambientes. O Helm empacota isso num chart com valores parametrizados, versão e capacidade de reverter o conjunto inteiro.

≈

Como uma receita com quantidades ajustáveis. A mesma receita serve para dois ou vinte pratos; o que muda é a tabela de quantidades. Manter vinte receitas quase idênticas é como manter uma pasta de YAML por ambiente — e elas divergem na primeira correção feita em só uma delas.

Como surgiu

A duplicação de manifestos entre ambientes foi um dos primeiros problemas de escala do Kubernetes: copiar, colar e trocar três valores, e depois esquecer de aplicar uma correção em um dos ambientes. O Helm resolveu com modelo mais valores, e trouxe algo que faltava: instalar e desinstalar um conjunto como unidade, com histórico e rollback.

Veio substituir: a pasta de YAML duplicada por ambiente e os scripts com sed substituindo valores antes do apply.

Onde você usa isso no dia a dia

  • Instalar componentes de terceiros — controller, monitoramento, operador.
  • Parametrizar a sua aplicação entre ambientes.
  • Reverter um conjunto inteiro de recursos de uma vez.
helm install pedidos ./chart -f values-prod.yaml
helm upgrade pedidos ./chart -f values-prod.yaml --atomic --wait
helm rollback pedidos 3          # volta o CONJUNTO inteiro
helm list

# depurar antes de aplicar — o comando mais útil do Helm:
helm template pedidos ./chart -f values-prod.yaml | less
Nem tudo precisa de Helm. Para a sua própria aplicação, kustomize — que já vem no kubectl — costuma bastar: uma base e sobreposições por ambiente, sem linguagem de modelo. O Helm brilha ao consumir software de terceiro e ao distribuir chart para outros times. Escolher pelo problema, não por ser o mais falado.
Armadilhas
  • Chart com valores demais. Parametrizar tudo é reinventar o YAML com sintaxe pior.
  • Chart de terceiro sem ler. helm template antes de instalar mostra exatamente o que vai entrar no cluster.
  • Modelo ilegível. Condicional dentro de condicional produz YAML que ninguém consegue depurar.
Pratique agoraEmpacote sua aplicação num chart mínimo com dois arquivos de valores e faça upgrade e rollback. Depois rode helm template e leia o resultado.
Prova de domínioVocê escolhe entre Helm e kustomize com justificativa e sempre revisa o template antes de instalar chart de terceiro.

Capstone: o OrderFlow em produção

projeto integrador

Direto: pegue o mesmo OrderFlow que você construiu em Java puro, migrou para Spring e projetou como arquiteto — e agora leve ao cluster, com imagem enxuta, probes corretas, recursos dimensionados e deploy sem perder requisição.

≈

Como entregar a obra. Você projetou, construiu e agora precisa passar na vistoria: hidráulica testada, elétrica dentro da norma, saída de emergência sinalizada. O prédio pode estar lindo — se a vistoria reprovar, ninguém mora nele.

O que ele cobre, parte por parte

  • 01–02 — imagem multi-stage, não-root, com ENTRYPOINT em forma exec.
  • 03 — configuração por variável, segredo fora do YAML versionado.
  • 04 — Compose para desenvolver, com healthcheck e dependência por saúde.
  • 05–06 — Deployment de três réplicas, com manifesto no Git.
  • 07 — Service e Ingress com TLS, e o roteiro de diagnóstico testado.
  • 08 — as três probes, requests e limits medidos, JVM ciente do cgroup.
  • 09 — Postgres com PVC — ou, com justificativa, gerenciado fora.
  • 10 — rollout sem erro sob carga, rollback ensaiado, RBAC mínimo.

Como conduzir

Quatro ou cinco quintas-feiras, uma camada por vez, tudo pelo terminal Linux — sem interface gráfica, que é como você vai encontrar em produção. Use kind para o cluster local: sobe em segundos e descarta sem dó.

Comece pela imagem, porque tudo depende dela. Depois Compose, depois cluster. Não pule para o cluster antes de a imagem estar enxuta e o container encerrar graciosamente — senão você vai depurar dois problemas ao mesmo tempo.

Isso substitui: seguir um tutorial que sobe um nginx e não ensina nada sobre a sua aplicação.

# A prova final não é "subiu" — é sobreviver aos próprios ataques:

# 2. rollout com carga contínua          → zero requisição perdida

# 5. limite de memória apertado          → sem OOMKilled, porque a JVM sabe do cgroup
