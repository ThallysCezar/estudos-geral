01

O modelo mental: um grafo de snapshots

Quase todo problema de Git vem de tratá-lo como histórico linear. Ele é um grafo — e commits são imutáveis.

Commit é snapshot, e o hash é do conteúdo inteiro

essencial

Direto: cada commit guarda o estado completo do projeto mais um ponteiro para o pai. O diferencial que você vê na tela é calculado na hora. E o identificador é o hash de tudo isso — então mudar qualquer campo cria um commit novo.

≈

Analogia. Não é um caderno onde você escreve as alterações; é uma pilha de fotografias do projeto inteiro, cada uma com um bilhete dizendo qual é a anterior. A "mudança" é o que você percebe comparando duas fotos — ela não está guardada em lugar nenhum.

Como funciona por dentro

São quatro objetos. O blob é o conteúdo de um arquivo. A tree é um diretório: nomes apontando para blobs e outras trees. O commit aponta para uma tree e para os pais. A tag anotada aponta para um commit, com autor e mensagem.

Tudo endereçado por hash do conteúdo. Dois arquivos idênticos em pastas diferentes são um blob só. Arquivo que não mudou entre commits não é duplicado: a tree nova aponta para o mesmo blob.

O que veio substituir: os sistemas anteriores — CVS, Subversion — guardavam diferenças por arquivo e um número de revisão central. Ramificar era caro, e mesclar, pior ainda. O Git inverteu: snapshot barato, ramificação trivial, e nenhuma autoridade central.

O que isso implica

  • amend não edita: cria outro commit.
  • rebase não move: recria, com hashes diferentes.
  • Reescrever histórico já compartilhado quebra o de quem puxou.
  • Nada se perde na hora: o objeto antigo fica sem nome até o coletor passar.

As quatro regras mais importantes deste documento saem todas daqui.

O grafo é dirigido e acíclico: as setas apontam para trás, dos filhos para os pais. Um merge tem dois pais; o commit inicial não tem nenhum. É por isso que o Git consegue encontrar a base comum entre dois branches — basta caminhar para trás até achar o ancestral compartilhado, que é exatamente o que merge e rebase fazem antes de qualquer coisa.

git log --oneline --graph --all
# * a1b2c3 (HEAD -> main) corrige calculo de juros
# |\
# | * d4e5f6 (feature/relatorio) adiciona exportacao
# |/
# * 9f8e7d base comum

git cat-file -p HEAD
# tree 4b825dc...
# parent 9f8e7d...
# author Thallys Cezar <...> 1789200000 -0300
# committer ...
Repare no git cat-file -p HEAD. Ele mostra o commit como o Git realmente o guarda: uma tree, um ou mais pais, autor, committer e mensagem. Não há nenhum "diff" ali. Rodar esse comando uma vez vale mais que dez explicações — e é o que transforma o Git de caixa preta em estrutura de dados.
armadilhas
  • Achar que o repositório guarda cópias completas em disco. Guarda logicamente; fisicamente o packfile comprime por delta entre objetos parecidos.
  • Confundir ~ com ^. HEAD~2 anda dois commits para trás; HEAD^2 escolhe o segundo pai — e só existe em merge.
  • Copiar hash na mão. A revision syntax nomeia quase tudo: main@{ontem}, HEAD~5, v1.3..v1.4.
pratique agoraRode git cat-file -p HEAD e depois git cat-file -p HEAD^{tree} num repositório seu. Você vai ver a estrutura inteira em dois comandos.
prova de domínioVocê explica por que um rebase produz hashes diferentes mesmo quando o conteúdo final é idêntico.

As três áreas — e por que o index existe

essencial

Direto: working tree são seus arquivos, index é a montagem do próximo commit, repositório é o histórico. O index existe para você escolher o que entra.

o caso

Você corrigiu um bug e, no caminho, também ajustou a indentação de dois arquivos e mudou uma porta no application.yml local para testar.

git add . manda os três para o mesmo commit. O revisor recebe um diff em que a correção real está enterrada em ruído — e a porta de teste vai para produção.

≈

Analogia. O index é a bancada de embrulho. Você não manda a loja inteira para o cliente: separa na bancada exatamente o que vai na caixa, confere, e só então fecha. Quem pula a bancada manda junto o que estava do lado.

O comando que mais rende nesta parte é git add -p. Ele percorre as alterações em pedaços e pergunta, um a um, se aquele vai para o commit. Com ele, a correção vira um commit e a indentação vira outro — sem precisar desfazer nada.

ComandoCompara / age entre
git diffWorking tree × index — o que você ainda não preparou.
git diff --stagedIndex × último commit — o que vai no commit.
git add -pEscolhe pedaços, não arquivos.
git restore arqDescarta a alteração local (volta do index).
git restore --staged arqTira do index, mantém no disco.
armadilhas
  • git add . sem olhar. É a origem do arquivo de configuração local versionado por engano.
  • Commitar sem ver o --staged. Um git diff --staged antes de cada commit pega quase todo acidente.
  • restore sem backup. Descartar alteração local é uma das poucas coisas que o reflog não recupera — nunca virou commit.
pratique agoraFaça duas alterações não relacionadas no mesmo arquivo e separe-as em dois commits usando só git add -p.
prova de domínioVocê explica a diferença entre git diff e git diff --staged apontando qual área cada um compara.
02

Integrar: a regra que encerra a discussão

Merge contra rebase não é questão de gosto. É uma pergunta sobre compartilhamento.

Rebase no que é seu, merge no que já é de todos

essenciala regra

Direto: merge preserva o grafo e não altera nada que já existe. Rebase recria commits e deixa o histórico linear. O critério de escolha é se o branch já foi compartilhado.

o caso

Você rebaseia o branch feature/checkout sobre a main e dá push --force. Mas um colega já tinha puxado esse branch e feito dois commits em cima.

Do lado dele, os commits que ele usou como base deixaram de existir no remoto. O próximo pull dele traz uma divergência que o Git não sabe resolver — e a "solução" improvisada costuma ser um merge que duplica todo o trabalho.

≈

Analogia. Merge é anexar uma errata ao livro já impresso: o texto original continua lá, e todo mundo consegue seguir. Rebase é reimprimir o livro com o texto corrigido no lugar — excelente antes de distribuir, desastroso depois que as pessoas já anotaram nas margens dos exemplares delas.

Merge

  • Ganha: histórico verdadeiro; nada é reescrito; seguro sempre.
  • Paga: o grafo fica mais difícil de ler com muitos ramos curtos.
  • Use: integrar na main, e sempre que o branch já foi puxado por alguém.

Sem divergência, o Git faz fast-forward — só move o ponteiro. --no-ff força o commit de merge quando você quer que o ramo fique visível.

Rebase

  • Ganha: linha reta, fácil de ler e de bisectar.
  • Paga: hashes novos; conflitos aparecem por commit; reescreve.
  • Use: arrumar o seu branch antes de abrir o PR.

É por isso que pull --rebase é um bom padrão: evita o commit de merge acidental que aparece toda vez que você puxa com trabalho local.

# o padrao que evita merge acidental em todo pull
git config --global pull.rebase true

# arrumar o seu branch antes do PR
git fetch origin
git rebase origin/main

# conflito? resolva, depois:
git add arquivo && git rebase --continue
git rebase --abort        # desistir e voltar ao estado anterior

# depois do rebase, ver o que mudou ALEM da base:
git range-diff origin/main@{1} origin/main HEAD
O range-diff é o comando mais subestimado do Git. Depois de rebasear, ele compara duas versões da mesma série de commits e mostra o que você realmente alterou, separado do ruído da reaplicação. Em revisão de PR rebaseado, é a diferença entre achar a mudança em segundos e não achar.
armadilhas
  • Rebasear branch compartilhado. Você transfere o problema para quem já puxou.
  • pull com trabalho não commitado. Cria merge no meio ou recusa. Faça stash antes, ou use --rebase --autostash.
  • Tratar como preferência estética. A pergunta é única: alguém já puxou isto?
pratique agoraNum repositório de teste, crie dois branches divergentes. Integre um com merge e outro com rebase, e compare git log --graph --all nos dois casos.
prova de domínioAlguém pergunta "merge ou rebase?". Você responde com uma pergunta de volta, e ela resolve o caso.

Conflito é decisão, não obstáculo

procedimento

Direto: o Git marca conflito quando os dois lados mudaram as mesmas linhas e ele não tem critério para escolher. Resolver não é apagar marcadores — é decidir.

≈

Analogia. Dois editores reescreveram o mesmo parágrafo. O revisor não joga um fora no escuro: lê os dois, entende o que cada um queria dizer, e escreve a versão que preserva as duas intenções. Muitas vezes a resposta certa não é nenhuma das duas.

O procedimento tem quatro passos, e o primeiro é o que quase todo mundo pula: entender o que cada lado estava resolvendo. Um git log --merge -p arquivo mostra só os commits que tocaram a região em conflito, dos dois lados — e costuma responder a pergunta em trinta segundos.

# 1. o que esta em conflito
git status
git diff --name-only --diff-filter=U

# 2. POR QUE cada lado mudou (o passo que resolve)
git log --merge -p caminho/arquivo

# 3. decidir e marcar resolvido
git add caminho/arquivo

# 4. concluir
git merge --continue      # ou: git rebase --continue

# desistir a qualquer momento:
git merge --abort
Cuidado com o significado de --ours e --theirs: eles se invertem entre merge e rebase. No merge, ours é o branch em que você está. No rebase, você está temporariamente sobre a base — então ours é o branch de destino e theirs é o seu trabalho. Usar no automático durante um rebase é a forma mais silenciosa de descartar o próprio código.
armadilhas
  • Apagar os marcadores e ficar com um lado. O trabalho do outro some sem aviso e sem rastro no diff.
  • Resolver sem rodar o teste. Um conflito resolvido compila e ainda assim quebra a regra de negócio.
  • Deixar marcador no commit. <<<<<<< em produção acontece mais do que se admite — um hook de pre-commit barra isso.
pratique agoraProvoque um conflito de propósito em dois branches e resolva usando git log --merge -p antes de escrever a resolução.
prova de domínioVocê explica por que --ours significa coisas diferentes em merge e em rebase.
03

Cirurgia: cherry-pick e bisect

Dois comandos que quase ninguém usa e que resolvem problemas caros em minutos.

Cherry-pick: transportar um commit, com rastro

essencialcaso real

Direto: aplica a mudança de um commit específico sobre o branch atual, criando um commit novo. E sempre com -x, que grava de onde ele veio.

o caso

Uma correção crítica entrou na main, e depois dela vieram três funcionalidades novas. O cliente está na release/1.4 e precisa só da correção.

Merge traria tudo. Refazer a correção à mão cria duas versões que vão divergir. O cherry-pick leva aquele commit isolado — e com -x, daqui a seis meses ainda dá para saber que os dois commits são a mesma coisa.

≈

Analogia. É fotocopiar uma página específica de um livro e encadernar em outro. O original continua no lugar; a cópia é um objeto novo. O -x é o carimbo dizendo de qual livro e de qual página ela veio — sem ele, ninguém sabe que são a mesma página.

git checkout release/1.4
git cherry-pick -x a1b2c3d

# a mensagem do commit novo ganha:
#   (cherry picked from commit a1b2c3d)

# um intervalo, atencao a ordem e ao ^:
git cherry-pick -x a1b2c3d^..f7e8d9c

# conflito no meio:
git cherry-pick --continue    # ou --abort, ou --skip
A prova de domínio que o material do vault já propunha é a melhor formulação: "você justifica por que cherry-pick é melhor que merge naquele caso". A resposta é sempre sobre escopo — você quer uma mudança, não a linha do tempo que a contém.
armadilhas
  • Cherry-pick em série no lugar de um merge. Duplica o histórico e cria conflito na integração seguinte.
  • Esquecer o -x. Perde-se a rastreabilidade, e a mesma correção parece duas coisas diferentes.
  • Levar só a correção e não o teste. O commit seguinte costuma ser o teste — leve os dois.
pratique agoraCrie um branch de release atrás da main, faça uma correção na main e leve só ela com -x. Depois leia o corpo da mensagem do commit resultante.
prova de domínioDado um pedido de "leva essa correção para a release", você decide entre cherry-pick e merge e justifica pela escopo da mudança.

Bisect: mil commits em dez testes

essencial

Direto: busca binária no histórico. Cada resposta corta o intervalo pela metade — e com um script, o Git faz sozinho.

o caso

O relatório mensal começou a sair com valor errado "faz umas semanas". Ninguém sabe quando. Entre a última versão comprovadamente boa e agora há 800 commits.

Com um teste que reproduz o erro, o bisect entrega o commit culpado em dez execuções. Sem ele, a alternativa é ler 800 diffs ou adivinhar.

≈

Analogia. É o jogo de adivinhar o número entre 1 e 1000. Perguntando "é maior que 500?" você chega em dez tentativas. Perguntar um por um levaria 500 em média — e é exatamente isso que fazer arqueologia manual no histórico significa.

É o mesmo mecanismo da busca binária que aparece na Biblioteca, no Entendendo Algoritmos, e o mesmo princípio de bisecção que o Como investigar qualquer problema usa para depuração em geral. Aqui ele está aplicado ao grafo de commits.

git bisect start
git bisect bad                 # o estado atual esta quebrado
git bisect good v1.3.0         # aqui comprovadamente funcionava

# o Git faz checkout no meio; teste e responda:
git bisect good     # ou: git bisect bad

# ... ~10 rodadas ...
# a1b2c3d is the first bad commit

git bisect reset               # SEMPRE, para sair do HEAD destacado

# automatico: script que retorna 0 = bom, !=0 = ruim
git bisect start HEAD v1.3.0
git bisect run ./reproduz.sh
O bisect run é o que muda o custo da ferramenta. Escrever um script de dez linhas que reproduz o erro e retorna o código certo transforma uma investigação de meia hora em um comando que roda enquanto você toma café. E o script vira, depois, um teste de regressão.
armadilhas
  • Esquecer o reset. Você continua trabalhando em HEAD destacado e os commits novos ficam órfãos.
  • Commits que não compilam no meio do intervalo. Use git bisect skip — e depois considere se o histórico deveria permitir isso.
  • Teste não determinístico. Um teste instável faz o bisect apontar o commit errado com toda a confiança.
pratique agoraNum repositório de teste, plante uma regressão num commit no meio de vinte. Ache com bisect manual, depois refaça com bisect run.
prova de domínioVocê estima, antes de começar, quantos testes o bisect vai precisar para um intervalo de N commits.
04

Desfazer e recuperar

A parte que dá coragem para usar o resto. Quem sabe recuperar experimenta; quem não sabe usa três comandos pelo resto da vida.

Restore, reset e revert: três intenções

essencial

Direto: restore mexe em arquivos, reset move o ponteiro do branch, revert cria um commit novo que desfaz outro. Só o terceiro é seguro em branch compartilhado.

≈

Analogia. restore é apagar o rascunho na mesa. reset é voltar o marcador de página para trás — o que veio depois continua no livro, só não está mais marcado. revert é escrever uma nova página dizendo "o capítulo 7 fica sem efeito" — todo mundo que já leu o livro consegue acompanhar.

ComandoO que fazSeguro em compartilhado?
restore arqDescarta alteração local do arquivo.Sim (não toca no histórico)
reset --soft HEAD~1Desfaz o commit, mantém tudo no index.Não
reset --mixed HEAD~1Desfaz e tira do index (padrão).Não
reset --hard HEAD~1Desfaz e descarta as alterações.Não
revert a1b2c3dCommit novo que desfaz aquele.Sim — é a única

O --soft é o mais útil e o menos conhecido: ele desfaz o commit mantendo tudo preparado no index. É o comando para "commitei cedo demais" — você recupera a montagem, ajusta e commita de novo, sem perder nada.

armadilhas
  • reset --hard com trabalho não commitado. Isso o reflog não recupera — nunca virou objeto. É a única perda realmente irreversível desta parte.
  • reset em branch que já foi empurrado. Use revert.
  • Confundir checkout antigo com os novos. switch troca de branch, restore mexe em arquivo. Os dois existem justamente porque o checkout fazia coisas demais.
pratique agoraFaça três commits, desfaça o último com --soft e veja o estado do index. Depois refaça com --mixed e compare.
prova de domínioVocê escolhe entre os três sabendo dizer o que acontece com o histórico de quem já puxou o branch.

O reflog: quase nada se perde de verdade

essencialcaso real

Direto: o reflog registra todo movimento local de HEAD e das refs, com o SHA anterior. Commits órfãos continuam no repositório por cerca de 30 dias.

o caso

git reset --hard HEAD~3 no branch errado. Três commits de trabalho "sumiram". O impulso é reclonar e refazer.

Eles não sumiram: o branch parou de apontar para eles. Os objetos continuam lá, sem nome. O reflog tem o SHA anterior, e um git branch resgate <sha> traz tudo de volta em dois comandos.

≈

Analogia. Você apagou o atalho da área de trabalho, não o arquivo. O reflog é o histórico de onde cada atalho apontava antes — e o faxineiro só passa depois de um mês.

git reflog
# a1b2c3d HEAD@{0}: reset: moving to HEAD~3
# f7e8d9c HEAD@{1}: commit: o trabalho que "sumiu"   <-- este
# 9a8b7c6 HEAD@{2}: commit: anterior

# PRIMEIRO salve, depois pense:
git branch resgate f7e8d9c

# reflog de um branch especifico:
git reflog show minha-branch

# se o reflog ja expirou, ainda ha uma chance:
git fsck --lost-found
A regra de ouro em qualquer acidente de Git: antes de tentar consertar, crie um branch no estado atual. git branch backup-$(date +%s) custa um segundo e transforma qualquer tentativa seguinte em reversível. A maioria das perdas reais acontece durante a tentativa de recuperação, não no acidente original.
armadilhas
  • Rodar gc --prune=now depois do acidente. Isso apaga exatamente os objetos órfãos que você ia recuperar.
  • Reclonar por pânico. O reflog é local — o clone novo não tem o seu. Reclonar destrói a única chance.
  • Achar que o reflog cobre tudo. Alteração não commitada nunca virou objeto; não há o que recuperar.
pratique agoraNum repositório de teste, faça cinco commits, dê reset --hard HEAD~3 e recupere pelo reflog. Repita até fazer sem consultar.
prova de domínioDiante de "apaguei meu trabalho", você sabe em que ordem agir — e qual é o único caso que realmente não volta.
05

Reescrever com segurança

Arrumar o histórico antes de mostrar é cortesia com quem vai revisar. Fazer isso sem apagar o trabalho dos outros é obrigação.

Rebase interativo e o par fixup + autosquash

essencial

Direto: commit --fixup=<sha> marca uma correção; rebase -i --autosquash a posiciona e funde sozinho. Muito melhor que reordenar na mão.

o caso

Seu branch tem oito commits: três de trabalho real e cinco do tipo "corrige typo", "ajusta teste", "esqueci o import". O revisor precisa ler oito diffs para entender três ideias.

≈

Analogia. É passar o rascunho a limpo antes de entregar. Ninguém quer ler as suas rasuras — quer ler o raciocínio final. O histórico é para o leitor futuro, não para o registro cronológico do seu dia.

# em vez de "corrige typo", marque a qual commit pertence:
git commit --fixup=a1b2c3d

# e no fim, o Git organiza sozinho:
git rebase -i --autosquash origin/main

# no editor, as acoes:
#   pick    mantem
#   reword  muda so a mensagem
#   squash  funde no anterior, juntando as mensagens
#   fixup   funde no anterior, DESCARTA a mensagem
#   edit    para no commit para voce alterar
#   drop    remove
Deixe o --autosquash sempre ligado: git config --global rebase.autosquash true. A partir daí, todo --fixup se organiza automaticamente no próximo rebase interativo — e você para de reordenar linha por linha no editor.
armadilhas
  • amend em commit já enviado. O hash muda e o remoto diverge; a partir daí só com --force-with-lease.
  • Limpar demais. Fundir tudo num commit gigante destrói a possibilidade de bisect e de revert cirúrgico. Um commit por ideia, não um por branch.
  • Rebase interativo longo sem backup. Faça git branch backup antes; é grátis.
pratique agoraFaça três commits e depois dois --fixup apontando para o primeiro. Rode rebase -i --autosquash e veja a ordenação automática.
prova de domínioVocê explica a diferença entre squash e fixup — e quando cada uma é a certa.

Nunca --force: sempre --force-with-lease

correção

Direto: --force sobrescreve o remoto sem olhar o que tem lá. --force-with-lease só sobrescreve se o remoto ainda estiver onde você viu pela última vez.

o caso

Você rebaseou o branch e vai publicar. Enquanto isso, um colega empurrou dois commits nele.

Com --force, os commits dele desaparecem do remoto e ninguém é avisado — do lado dele, o trabalho some. Com --force-with-lease, o push é recusado, porque o remoto não está mais onde você viu. E recusa é exatamente o resultado certo.

≈

Analogia. --force é substituir o documento na gaveta sem abrir para conferir. --force-with-lease é conferir se ainda é a versão que você tinha visto antes de trocar — e desistir se alguém mexeu.

# SEMPRE atualize o lease antes, senao ele fica desatualizado
git fetch origin
git push --force-with-lease origin minha-branch

# o alias que tira o dedo pesado do caminho:
git config --global alias.pushf "push --force-with-lease"

# se o push for recusado, e porque alguem empurrou.
# integre o trabalho da pessoa antes de insistir.
Uma sutileza que vale saber: o --force-with-lease compara com a sua cópia local de origin/branch. Se você rodar fetch logo antes sem olhar o resultado, o lease é atualizado e a proteção se esvazia. O par seguro é fetch → olhar → push.
armadilhas
  • --force por hábito. Funciona 99 vezes e destrói trabalho alheio na centésima.
  • Force em main. Configure proteção de branch no servidor; não dependa de disciplina.
  • Fetch cego antes do push. Atualiza o lease e anula a proteção.
pratique agoraCom dois clones do mesmo repositório, simule o conflito: empurre de um, rebaseie no outro e tente --force-with-lease. Veja a recusa acontecer.
prova de domínioVocê explica por que a recusa do --force-with-lease é o comportamento desejado, e não um obstáculo.
06

Segredo no histórico

A ordem das ações importa mais que a técnica — e quase todo mundo começa pela etapa errada.

Vazou uma credencial: a ordem certa

essencialordem importa

Direto: rotacione a credencial primeiro. É a única ação que realmente resolve. Limpar o histórico depois é higiene, não contenção.

o caso

Um application.yml com senha de banco foi commitado e empurrado. Alguém percebe duas horas depois.

O impulso é limpar o histórico. Mas enquanto você reescreve commits, a credencial continua válida — e se o repositório for público, varredores automáticos já a encontraram. O relógio que importa começou a correr no momento do push, não no da descoberta.

≈

Analogia. Você deixou a chave de casa cair na rua. A prioridade é trocar a fechadura, não sair procurando quem pegou a chave. Recuperar a chave é útil; trocar a fechadura é o que resolve.

A ordem

  • 1. Rotacione. Gere nova credencial e invalide a antiga. Agora.
  • 2. Limpe o histórico com git filter-repo.
  • 3. Force com lease e avise o time a reclonar.
  • 4. Previna: .gitignore e um hook que barre o padrão.

Por que reclonar

Depois da limpeza, todo clone existente ainda tem os objetos antigos no .git. Um pull não os remove. Se alguém empurrar a partir de um clone antigo, o segredo volta ao remoto.

Por isso o passo 3 tem duas partes, e a segunda — avisar — é a que costuma ser esquecida.

# 1. ROTACIONE. sempre primeiro.

# 2. limpar (git filter-repo, sucessor do filter-branch)
git filter-repo --path config/application.yml --invert-paths
# ou, so o valor:
git filter-repo --replace-text expressoes.txt

# 3. publicar e AVISAR
git push --force-with-lease --all
git push --force-with-lease --tags
# -> o time precisa RECLONAR, nao dar pull

# 4. prevenir
echo "*.env" >> .gitignore
echo "config/application-local.yml" >> .gitignore
armadilhas
  • Limpar antes de rotacionar. O erro de ordem mais caro que existe.
  • Achar que git rm resolve. Ele remove do estado atual; o histórico continua com o valor.
  • Esquecer os forks e as cópias em CI. Em serviço hospedado, o objeto pode continuar acessível por SHA mesmo após a limpeza — abra um chamado com o provedor.
  • Não avisar o time. Um push de clone antigo reintroduz tudo.
onde a teoria moraGestão de segredo, rotação e identidade de workload estão em Nuvem completo. Segredo fora da imagem e variável de ambiente, em Docker e Kubernetes completo e no aquecimento P08 do Laboratório.
pratique agoraNum repositório descartável, commite um arquivo com um valor falso, empurre para um remoto local e execute os quatro passos na ordem.
prova de domínioAlguém avisa que vazou uma chave. Você diz a primeira ação em menos de cinco segundos — e ela não envolve Git.
07

Colaborar: PR, versão e fluxo

As convenções existem para que a máquina verifique o que a máquina verifica melhor — e a pessoa revise o que só a pessoa revisa.

O tamanho do PR é a variável que decide a revisão

prática

Direto: PR grande recebe aprovação sem leitura. PR pequeno recebe comentário útil. O tamanho não é detalhe de processo — é o que determina se a revisão existe.

≈

Analogia. É a diferença entre pedir para alguém revisar uma página e entregar um calhamaço. Na página, a pessoa aponta a vírgula errada. No calhamaço, ela folheia, diz "parece bom" e assina.

A descrição do PR deve responder por quê. O o quê o diff já mostra; o que ele não mostra é a alternativa que você descartou, a restrição que motivou a escolha, e o que você decidiu deixar para depois. Um PR bem descrito é a versão curta de uma ADR.

E a regra que mais melhora a revisão: refatoração e mudança de comportamento não vão no mesmo PR. Misturados, ninguém consegue distinguir o que é movimentação de código do que é lógica nova — e é exatamente aí que o bug passa.

Conventional Commits (feat:, fix:, chore:) existem para que changelog e versão saiam automaticamente. Hooks dão retorno rápido localmente, mas são opcionais — podem ser pulados com --no-verify e não existem num clone novo. Por isso a CI precisa repetir: o hook é conveniência, a CI é garantia.

feat(pedido): aceita pagamento parcelado
fix(estoque): corrige contagem em compra simultanea
chore(deps): atualiza spring-boot para 3.3.4
refactor(checkout): extrai calculo de frete

# corpo: POR QUE, nao o que
# rodape: BREAKING CHANGE: ... / Refs: #123
onde a teoria moraADR, comunicação de decisão e a régua de profundidade estão em Arquitetura completo. Pipeline, rollback e GMUD, em Conceitos de Backend completo.
armadilhas
  • Refatoração junto com comportamento. Torna a revisão impossível.
  • Confiar só no hook. Metade do time nunca o instalou.
  • Descrição que repete o diff. Desperdiça o único campo em que você poderia explicar a decisão.
pratique agoraPegue o seu último PR e conte as linhas alteradas. Depois pense em como ele poderia ter sido dois ou três — e o que cada um teria como propósito.
prova de domínioVocê recusa educadamente um PR que mistura refatoração e comportamento, explicando o custo em vez de citar regra.

SemVer e o fluxo: escolha pela frequência de entrega

trade-off

Direto: MAIOR.MENOR.CORREÇÃO é um contrato com quem consome. E o fluxo de branches se escolhe pelo ritmo de entrega, não por hábito.

MAIOR quebra compatibilidade. MENOR acrescenta de forma compatível. CORREÇÃO conserta sem mudar contrato. O número existe para que quem consome decida se pode atualizar sem ler o changelog inteiro — subir MENOR numa mudança que quebra é quebrar quem confiou.

Use tag anotada (-a ou -s): é um objeto real, com autor, data e mensagem. A tag leve é um ponteiro solto. E tags não vão no push por padrão.

Trunk-based

Todos integram na main várias vezes ao dia, branches vivem horas. Exige CI rápida e feature flags.

Use quando: entrega contínua, time acostumado a integrar.

GitHub Flow

Um branch curto por mudança, PR, merge na main, deploy. É o meio-termo, e o padrão da maioria.

Use quando: entrega frequente com revisão obrigatória.

GitFlow — com develop, release/* e hotfix/* — foi desenhado para software com versões lançadas periodicamente e várias versões suportadas ao mesmo tempo. Para quem entrega continuamente, ele adiciona cerimônia sem benefício: merges intermináveis entre develop e main, e confusão sobre onde uma correção deve nascer.

git tag -a v1.4.0 -m "suporte a pagamento parcelado"
git push origin v1.4.0        # tags NAO vao no push normal

git describe --tags
# v1.4.0-12-ga1b2c3d
#   ^tag  ^commits depois  ^hash atual
armadilhas
  • Subir MENOR quando quebra contrato. Quebra quem atualizou confiando no número.
  • Tag leve em release. Sem autor, data nem mensagem — e não assinável.
  • GitFlow por padrão. Adotar por hábito custa caro em time que entrega toda semana.
pratique agoraRode git describe --tags no seu projeto e interprete as três partes do resultado.
prova de domínioDada uma mudança, você decide qual número sobe — e justifica pelo contrato, não pelo tamanho da alteração.
08

Investigar: arqueologia responsável

O histórico responde "o que mudou, quando e por quê". O objetivo é contexto, nunca culpado.

Log, pickaxe, blame e range-diff

profundidade

Direto: log -S acha quando um termo entrou; blame acha quem tocou por último; range-diff compara duas versões da mesma série.

o caso

Existe uma constante TAXA_FIXA = 0.07 no código. Ninguém sabe de onde veio nem se ainda vale.

git log -S "TAXA_FIXA" --oneline mostra o commit que a introduziu. A mensagem dele aponta o chamado, o chamado aponta a decisão — e em dois minutos você sabe se pode mexer.

≈

Analogia. O blame diz quem foi a última pessoa a assinar o documento. O pickaxe diz em que edição aquele parágrafo apareceu pela primeira vez. Para entender por que o parágrafo existe, o segundo quase sempre responde melhor.

ComandoResponde
git log -S "termo"Commits que adicionaram ou removeram o termo.
git log -p -- arquivoHistórico do arquivo, com o diff de cada commit.
git log --follow -- arqAtravessa renomeações.
git blame -w -C -L 40,60Autoria por linha, ignorando espaço e seguindo código movido.
git range-diff A..B C..DO que mudou entre duas versões da mesma série.
git log --merge -p arqDurante conflito: só os commits que tocaram a região.
O -w -C no blame muda o resultado completamente. Sem eles, quem reformatou o arquivo aparece como autor de tudo. Com eles, o Git ignora mudança de espaço e segue código movido entre arquivos — e aí a autoria reflete quem escreveu a lógica, não quem rodou o formatador.
armadilhas
  • Usar blame para achar culpado. O objetivo é contexto. E quem escreveu provavelmente tinha uma restrição que você não conhece.
  • Blame sem -w. Atribui tudo a quem formatou.
  • Revisar PR rebaseado pelo diff completo. Use range-diff; sem ele, a alteração real fica invisível no ruído.
pratique agoraEscolha uma constante estranha no seu código e ache o commit que a introduziu com log -S. Leia a mensagem.
prova de domínioVocê sabe quando usar -S em vez de blame — e explica por que o primeiro responde melhor "por quê".
09

Como aprender de verdade: vídeos, pesquisa e prática

Quase todo mundo usa três comandos de Git por medo dos outros. O antídoto é um repositório onde destruir é de graça.

O ciclo, as fontes e o laboratório dos cinco acidentes

obrigatório

Direto: ler aqui → criar um repositório de teste → destruir de propósito → recuperar pelo reflog → escrever o que aprendeu. A confiança de saber recuperar é o que libera as ferramentas boas.

O padrão é conhecido: a pessoa aprende add, commit e push, e nunca mais sai daí — porque errar no repositório do trabalho custa caro, e por isso nunca se experimenta. O resultado é uma década usando 5% da ferramenta.

Um mkdir lab-git && git init quebra esse ciclo. Ali você pode dar reset --hard errado, apagar branch, rebasear o que não devia, forçar push. Depois de recuperar três vezes pelo reflog, o medo passa — e aí rebase interativo, bisect e cherry-pick deixam de ser assustadores.

Canais e cursos em português. Rodrigo Branas tem material sólido de Git em PT-BR, incluindo fluxos de trabalho. Fabio Akita explica o funcionamento interno — que é o recorte dos marcos 01 e 08. Willian Justen e Código Fonte TV cobrem bem o básico e o fluxo de PR.

Em texto, a melhor referência única que existe é o Pro Git, de Chacon e Straub: está traduzido para o português e é gratuito no site oficial do Git. É o que eu consultaria antes de qualquer vídeo — e os capítulos 2, 3 e 10 cobrem, juntos, quase todo este documento.

o laboratório: cinco acidentes, cinco recuperações

# o laboratorio inteiro cabe em um diretorio
mkdir lab-git && cd lab-git && git init
for i in 1 2 3 4 5; do
  echo "linha $i" >> arquivo.txt
  git add . && git commit -m "commit $i"
done

# 1 — reset --hard perdendo tres commits
git reset --hard HEAD~3
git reflog                    # eles estao aqui
git branch resgate       # de volta

# 2 — commit no branch errado
git log --oneline -1          # anote o sha
git reset --hard HEAD~1       # tira daqui
git checkout -b certo && git cherry-pick 

# 3 — regressao plantada, achada com bisect
git bisect start && git bisect bad && git bisect good 

# 4 — historico baguncado
git commit --fixup= && git rebase -i --autosquash 

# 5 — segredo commitado: rotacione, limpe, force, avise
O que registrar em cada acidente: o comando que causou, o sintoma, a hipótese de recuperação, o comando que funcionou. Depois de cinco, você tem um runbook pessoal — e é ele que você vai abrir no dia em que acontecer de verdade, com pressa e com gente olhando.
