A plataforma: como o Java roda

Antes da linguagem, a máquina. Aqui mora metade dos "por quês".

A JVM e a promessa de rodar em qualquer lugar

essenciala fundação

Direto: o Java compila para uma máquina que não existe — a JVM. Cada sistema real implementa essa máquina em software, e por isso o mesmo arquivo compilado roda em Windows, Linux e Mac sem tocar em nada.

≈

Como uma tomada universal. Em vez de fabricar um aparelho diferente para cada país, você fabrica um só com plugue padrão — e cada país fornece o adaptador. O bytecode é o plugue padrão; a JVM é o adaptador que cada sistema operacional oferece.

Como surgiu

Nos anos 1990, a Sun montou um time para escrever software de eletrônicos — e esbarrou num muro: cada aparelho tinha um chip diferente, e C++ exigia recompilar (e frequentemente reescrever) para cada um. A saída foi radical: compilar para um processador imaginário e implementá-lo em software em toda parte. A linguagem nasceu como Oak, virou Java em 1995 e pegou carona na web; ficou porque o back-end corporativo precisava exatamente disso.

Veio substituir: o ciclo "compile para cada plataforma" do C/C++, e o gerenciamento manual de memória que vinha junto.

Onde você usa isso no dia a dia

  • Sua API sobe num container Linux, mas você desenvolve no Windows — e é o mesmo .jar.
  • O time roda macOS e o CI roda Ubuntu: mesmo build, mesmo artefato.
  • Você escolhe a versão do JDK do projeto sem trocar de código.

Na prática você lida com três siglas que confundem no começo. A JVM é a máquina virtual que carrega, verifica e executa. O JRE é a JVM mais as bibliotecas padrão — o mínimo para rodar. O JDK é o JRE mais as ferramentas de desenvolver: o compilador javac, o inspetor javap, o diagnóstico jcmd. Para trabalhar você instala o JDK, que contém todo o resto.

O caminho completo do texto ao processo tem quatro estações: você escreve .java; o javac traduz para .class (bytecode); o ClassLoader carrega cada classe na primeira vez que ela é usada; a JVM interpreta e, para o código que roda muito, o compilador JIT gera código nativo de verdade. Tudo isso dentro de um processo comum do sistema — aquele java que você vê no gerenciador de tarefas.

javac App.java     // gera App.class — o bytecode portável
java App           // a JVM carrega, verifica e executa
javap -c App       // abre o bytecode e desfaz a mágica
jcmd               // lista os processos Java vivos na máquina
Armadilhas
  • UnsupportedClassVersionError: você compilou para Java 21 e rodou numa JVM 17. Versão de compilação e de execução são coisas diferentes.
  • "Java é lento porque é interpretado": só as primeiras execuções são. Depois do aquecimento, o JIT entrega desempenho de código nativo.
Pratique agoraCompile uma classe no terminal, sem IDE, rode com java e abra o resultado com javap -c. Ver o bytecode uma vez muda sua relação com a linguagem.

Bytecode e ClassLoader: o carregamento por dentro

essencial

Direto: bytecode é o conjunto de instruções da JVM; e nenhuma classe entra na memória antes de ser usada — o ClassLoader busca, verifica e inicializa cada uma sob demanda.

≈

Como uma biblioteca com bibliotecário. Os livros não ficam todos na sua mesa: você pede um, o bibliotecário busca na estante, confere se está íntegro e só então entrega. E ele sempre pergunta primeiro ao acervo principal antes de aceitar um exemplar trazido de fora — é assim que ninguém troca a obra original por uma falsificada.

Como surgiu

A verificação de bytecode nasceu junto com os applets: código baixado da internet ia rodar na máquina de alguém, então a JVM precisava garantir que aquele binário não fizesse besteira — pilha coerente, tipos corretos, sem acesso indevido. Os applets morreram, a verificação ficou. A delegação hierárquica de carregamento veio pelo mesmo motivo: impedir que alguém substituísse classes do próprio Java.

Veio substituir: a ligação estática de C/C++, onde tudo é resolvido no link e um binário adulterado roda sem checagem.

Onde você usa isso no dia a dia

  • Todo ClassNotFoundException e NoClassDefFoundError que você depura.
  • Servidores de aplicação e plugins que isolam bibliotecas em loaders separados.
  • Agentes de APM (Datadog, New Relic) que reescrevem bytecode ao carregar.

O javac não gera código de máquina: gera instruções de uma máquina de pilha (aload, invokevirtual, ireturn). Como o formato é padronizado e independente de linguagem, Kotlin, Scala e Groovy compilam para ele e convivem no mesmo projeto, chamando as mesmas bibliotecas.

O carregamento acontece em três fases. Em loading, o loader localiza e lê os bytes. Em linking, a JVM verifica o bytecode, prepara os campos estáticos com valores padrão e resolve referências. Em initialization, roda o bloco static — e só aí, na primeira utilização real. Os loaders formam uma hierarquia com delegação ao pai: antes de carregar, cada um pergunta ao superior, e por isso a String que você usa é sempre a do JDK.

javap -c MinhaClasse
// 0: aload_0            ← empilha 'this'
// 1: invokevirtual #7   ← chama um método
// 4: ireturn            ← retorna um int da pilha
Os dois erros que todo mundo confunde
  • ClassNotFoundException — alguém pediu a classe pelo nome (ex.: Class.forName) e ela não está no classpath. É exceção: o código pediu e não achou.
  • NoClassDefFoundError — a classe existia quando você compilou e sumiu no runtime (jar faltando no deploy), ou o bloco estático dela explodiu na inicialização. É erro: o ambiente está inconsistente.
Pratique agoraRemova um jar do classpath e rode: veja qual dos dois erros aparece. Depois coloque um throw num bloco static e observe o segundo caso.

JIT: por que o Java acelera enquanto roda

essencialperformance

Direto: a JVM começa interpretando e, quando percebe que um trecho roda muito, compila esse trecho para código de máquina — otimizando com base no que de fato está acontecendo na sua execução.

≈

Como um tradutor simultâneo que vira dublador. No começo ele traduz frase por frase, ao vivo (lento, mas funciona já). Ao perceber que uma fala se repete o tempo todo, ele grava uma versão pronta e passa a tocar a gravação — muito mais rápido. E se o roteiro muda, ele descarta a gravação e volta a traduzir ao vivo até regravar.

Como surgiu

O Java estreou lento e carregou fama de linguagem de brinquedo. A HotSpot (1999) inverteu o jogo com uma tese: um compilador que observa a execução real pode otimizar melhor que um compilador estático, porque conhece os dados e os caminhos que o programa realmente toma — e não só o que o código permite em teoria.

Veio substituir: o interpretador puro (lento demais) e a compilação antecipada total do C++ (rápida, mas cega ao comportamento real).

Onde você usa isso no dia a dia

  • Sua API responde devagar nos primeiros minutos após o deploy: é o aquecimento.
  • Benchmarks caseiros que dão números absurdos e enganam decisões.
  • Health check e warm-up antes de liberar tráfego num rolling update.

A compilação é em camadas. O interpretador roda de imediato e coleta estatísticas. O C1 compila rápido, com otimizações leves. O C2 compila devagar e otimiza pesado: inlining (cola o corpo do método chamado dentro do chamador, o que habilita quase todas as outras otimizações), escape analysis (se um objeto não escapa do método, ele pode nem ser alocado no heap) e especulação (se até agora só uma implementação da interface apareceu, compila a chamada como direta, protegida por uma guarda).

E é aí que entra a parte elegante: quando uma aposta falha — aparece a segunda implementação —, a JVM faz deoptimization, descarta o código compilado, volta ao interpretador e recompila com a nova realidade. Tudo invisível, até você tentar medir performance sem saber que isso existe.

Medição que mente
long t0 = System.nanoTime();
for (int i = 0; i < 1_000; i++)
    metodo();
System.out.println(System.nanoTime()-t0);
// mediu o aquecimento, não o código
// e o JIT pode ter descartado a chamada
Medição confiável
@Benchmark
public void medido(Blackhole bh) {
    bh.consume(metodo());
}
// JMH: aquece, isola forks, repete
// Blackhole impede o descarte
Armadilha

Nunca tire conclusão de performance de um loop cronometrado à mão. Além do aquecimento, o JIT elimina código cujo resultado ninguém usa — seu "benchmark" pode estar medindo um método que sequer executou.

Pratique agoraRode um loop quente com java -XX:+PrintCompilation e observe os níveis de compilação surgindo em tempo real.

Maven: dependências e build reproduzível

essencialecossistema

Direto: o Maven resolve duas dores de uma vez — baixar as bibliotecas certas (e as bibliotecas delas) e compilar, testar e empacotar do mesmo jeito em qualquer máquina.

≈

Como uma receita com lista de compras automática. Você anota "quero fazer um bolo"; o sistema descobre sozinho que bolo precisa de farinha, que farinha vem daquele fornecedor, e traz tudo na quantidade certa. Se dois ingredientes exigirem versões diferentes do mesmo item, alguém precisa decidir qual fica — e é aí que moram os conflitos.

Como surgiu

Antes de 2004, cada projeto Java tinha um build artesanal em Ant e uma pasta lib/ com jars copiados na mão, sem ninguém saber a origem ou a versão. O Maven padronizou o layout, criou o repositório central e trouxe a resolução transitiva: você declara uma dependência, ele traz a árvore inteira.

Veio substituir: scripts Ant artesanais e a pasta lib/ versionada no repositório — a era do "na minha máquina compila".

Onde você usa isso no dia a dia

  • Todo mvn clean package antes de gerar a imagem Docker.
  • Quando um NoSuchMethodError aparece só em produção.
  • Ao subir a versão de uma lib e descobrir quem mais dependia dela.

O pom.xml declara a identidade do projeto (groupId:artifactId:version), as dependências e os plugins. O ciclo de vida encadeia fases previsíveis: compile → test → package → install. O problema recorrente é o conflito de versões — duas dependências trazem versões diferentes da mesma lib e o Maven escolhe a "mais próxima" na árvore, que nem sempre é a que você queria. Uma ferramenta resolve quase tudo:

mvn dependency:tree                                   // a árvore inteira, com versões
mvn dependency:tree -Dincludes=com.fasterxml.jackson  // filtra o suspeito
mvn clean package                                      // build limpo e reproduzível
Vindo do C#: o Maven é NuGet e MSBuild na mesma ferramenta; o pom.xml faz o papel do .csproj e o Maven Central é o nuget.org. A diferença cultural que surpreende: no Java o build roda igual fora da IDE — o IntelliJ apenas delega ao Maven, então o que passa no seu terminal passa no CI.
Armadilhas
  • NoSuchMethodError em runtime é quase sempre conflito de versão: compilou contra uma, rodou com outra.
  • Depender de SNAPSHOT de terceiros faz seu build mudar sem você mudar uma linha.
  • Fixe versões conflitantes em <dependencyManagement> em vez de torcer pela ordem da árvore.
Pratique agoraForce um conflito declarando duas libs que trazem Jackson em versões diferentes, rode dependency:tree, ache o culpado e resolva com dependencyManagement.

As versões que importam: 8, 11, 17 e 21

essencialJava 8 → 21

Direto: sai uma versão a cada seis meses, mas o mercado vive nas LTS. Conheça os quatro saltos — não cada release.

≈

Como as edições de um carro. A montadora ajusta detalhes todo ano, mas só algumas gerações mudam a plataforma. Você não precisa saber de cada facelift — precisa saber o que mudou de geração para geração e o que isso permite fazer.

Como surgiu

Até 2017 o Java lançava versões a cada três ou quatro anos, com atrasos históricos. A Oracle passou a lançar de seis em seis meses e a marcar algumas como LTS (suporte longo), separando o ritmo da inovação do ritmo da adoção corporativa.

Veio substituir: o ciclo lento e imprevisível em que o Java 7 demorou cinco anos e features prontas esperavam anos na fila.

Onde você usa isso no dia a dia

  • Ao escolher a imagem base do Dockerfile do serviço.
  • Quando uma feature nova não compila porque o projeto está no 11.
  • Ao planejar migração e justificar o esforço para o time.

O 8 (2014) foi o divisor de águas: lambdas, Streams, Optional e java.time mudaram como se escreve Java. O 11 (2018) modernizou a plataforma com var e o HttpClient, e removeu módulos antigos — o que quebra libs desatualizadas. O 17 (2021) consolidou a modelagem moderna: record, sealed, text blocks e switch como expressão. O 21 (2023) trouxe a virada da concorrência com as virtual threads, além de pattern matching maduro e Sequenced Collections.

Migrar do 8 ao 21 assusta menos do que parece se feito em dois passos: primeiro rode no runtime novo ainda compilando para o alvo antigo, tratando avisos de APIs internas e reflexão; depois suba o alvo de compilação e adote as features aos poucos. O que costuma travar não é seu código — são bibliotecas paradas há anos. E há ganho imediato sem tocar em nada: coletor de lixo melhor e inicialização mais rápida.

Pratique agoraRode um projeto Java 8 num JDK 21 sem recompilar e anote os avisos. Depois compile para 21 e troque um DTO por record.

Onde nascem os bugs "impossíveis": null, centavos que somem, acento quebrado e fuso horário.

Referências, null e passagem por valor

essencial

Direto: Java é sempre passagem por valor — mas o valor de uma variável de objeto é a referência. Por isso alterar o objeto dentro do método é visto por quem chamou, e reatribuir a variável não é.

≈

Como o endereço de uma casa. Você me dá um papel com o endereço; se eu pintar a casa, você vê a casa pintada (é a mesma). Mas se eu rabiscar outro endereço no meu papel, o seu papel continua apontando para a casa original. O papel é a variável; a casa é o objeto.

Como surgiu

O Java nasceu reagindo ao C++: ponteiros aritméticos causavam corrupção de memória e falhas de segurança difíceis de rastrear. A decisão foi manter a indireção (referência) e tirar o poder perigoso — sem aritmética de ponteiro, sem liberar memória na mão. O preço foi o null, que Tony Hoare, seu criador, chama de "erro de um bilhão de dólares".

Veio substituir: ponteiros de C/C++ e a responsabilidade manual de alocar e liberar memória.

Onde você usa isso no dia a dia

  • Cada NullPointerException que você investiga.
  • Ao passar uma lista para um método e ela voltar modificada (ou não).
  • Ao decidir entre mutar um objeto ou devolver uma cópia nova.
O que confunde
void desconta(Pedido p) {
    p = new Pedido();   // só a cópia local
    p.setTotal(ZERO);   // some ao sair
}
// quem chamou não vê nada
O que realmente acontece
void desconta(Pedido p) {
    p.setTotal(p.getTotal()
        .subtract(TEN)); // mesma casa
}
// quem chamou VÊ a alteração

Sobre o null: a defesa moderna é em três camadas. Valide na fronteira com Objects.requireNonNull(x, "mensagem") — falha imediatamente, com contexto, em vez de estourar três chamadas depois. Nunca devolva null onde uma coleção vazia serve (List.of()). E use Optional como retorno quando "não achei" é um resultado legítimo.

Vindo do C#: é idêntico ao comportamento de classes (reference types). O que não existe no Java: struct definido por você, ref/out, e os tipos anuláveis com ? do C# 8 — aqui todo objeto é anulável e a disciplina fica por sua conta.
Armadilha

Em cadeias longas (a.getB().getC().getD()), desde o Java 14 a mensagem do NPE diz exatamente qual elo era nulo. Leia a mensagem inteira antes de abrir o debugger — ela costuma já entregar a resposta.

Primitivos, wrappers e por que dinheiro nunca é double

essencialbug caro

Direto: primitivos guardam o valor e são rápidos; wrappers são objetos que cabem em coleções e podem ser nulos. E valor monetário se representa com BigDecimal criado de String — nunca double.

≈

Como medir com uma régua de polegadas. Se sua régua só tem marcas em frações de 2 (1/2, 1/4, 1/8), você nunca marca exatamente 0,1 — só se aproxima. O double é binário e tem exatamente esse problema com décimos: ele guarda o vizinho mais próximo, e o erro se acumula a cada conta.

Como surgiu

Os oito primitivos existem por desempenho: em 1995, criar um objeto para cada número era proibitivo. Quando os generics chegaram (Java 5), as coleções só aceitavam objetos — daí o autoboxing, a conversão automática entre int e Integer. Já o ponto flutuante segue o padrão IEEE 754, que é ótimo para ciência e péssimo para dinheiro.

Veio substituir: o boxing manual (new Integer(x)) que poluía todo código pré-Java 5.

Onde você usa isso no dia a dia

  • Toda soma de valores de pedido, imposto e desconto.
  • Ao comparar Integer vindo do banco com == e obter false misteriosamente.
  • Em loops quentes, onde boxing gera milhões de objetos descartáveis.
Errado — e vai para produção
double total = 0.1 + 0.2;
// 0.30000000000000004

double preco = 19.90;
double x = preco * 3;
// 59.699999999999996 → centavo somem
Correto
var preco = new BigDecimal("19.90");
var total = preco
    .multiply(BigDecimal.valueOf(3))
    .setScale(2, RoundingMode.HALF_EVEN);
// 59.70 exato
preco.compareTo(outro) == 0  // igualdade
Duas pegadinhas clássicas
  • Cache de Integer: Integer a=127,b=127; a==b dá true; com 128 dá false. O Java cacheia de −128 a 127. Compare wrappers sempre com .equals().
  • BigDecimal.equals: 2.0 e 2.00 não são "iguais" (escalas diferentes). Para valor, use compareTo(...) == 0.
  • Unboxing de null: um Integer nulo em conta aritmética estoura NPE — comum ao ler coluna nula do banco.
Pratique agoraSome 0.1 dez vezes com double e imprima. Repita com BigDecimal. Guarde o susto — ele te protege pelo resto da carreira.

String: imutabilidade, pool, Unicode e charset

essencial

Direto: String é imutável — toda "alteração" cria outro objeto. Por isso concatenar em loop é caro (use StringBuilder) e por isso ela é segura como chave e entre threads. E todo texto que cruza a fronteira do processo tem um charset: declare UTF-8 sempre.

≈

Como um documento impresso. Você não "edita" uma folha impressa: imprime outra com o texto novo. Isso é chato para rascunho (por isso existe o StringBuilder, que é o caderno) e ótimo para arquivo — ninguém altera sua cópia pelas suas costas.

Como surgiu

A imutabilidade foi decisão de projeto com três ganhos: permite o string pool (literais iguais compartilham o mesmo objeto), torna String segura como chave de mapa e entre threads, e permite cachear o hash. O UTF-16 interno veio da época em que 16 bits pareciam suficientes para todo o Unicode — o que deixou de ser verdade e explica o comportamento com emojis.

Veio substituir: o char* mutável e sem tamanho de C, origem histórica de estouro de buffer.

Onde você usa isso no dia a dia

  • Montagem de mensagens, logs, SQL e JSON.
  • Bug de acento (Ã©) que aparece só no servidor.
  • Contagem de caracteres em campos com emoji.
O(n²) — degrada em silêncio
String s = "";
for (var p : partes)
    s += p;   // cria um objeto por volta
O(n) — um objeto só no fim
var sb = new StringBuilder();
for (var p : partes)
    sb.append(p);
String s = sb.toString();

Sobre encoding: sempre que converter bytes em texto (ou o contrário) existe um charset envolvido, e omiti-lo faz o Java usar o padrão da plataforma. O Java 18 fixou UTF-8 como padrão, mas código que roda em JVMs antigas no Windows pega cp1252 — e é exatamente aí que o acento vira símbolo estranho entre a sua máquina e o servidor. Declarar explicitamente elimina a classe inteira de bugs.

Files.readString(caminho, StandardCharsets.UTF_8);
new String(bytes, StandardCharsets.UTF_8);
texto.getBytes(StandardCharsets.UTF_8);

"🚀".length();          // 2 — o emoji ocupa dois chars em UTF-16
"🚀".codePointCount(0, 2); // 1 — caracteres de verdade
Pratique agoraConcatene 100 mil strings com += e depois com StringBuilder, cronometrando. Depois imprima "🚀".length().

Tempo: Instant, ZonedDateTime, Duration e Clock

essencialJava 8+

Direto: guarde e transporte tempo como Instant (UTC); aplique fuso só na borda, para exibir ao humano. E injete um Clock em vez de chamar now() solto, para poder testar.

≈

Como um voo internacional. A decolagem aconteceu num único instante do universo; o que muda é o relógio de cada aeroporto ao descrevê-la. Guardar "14h" sem dizer onde é guardar uma informação incompleta — guardar o instante e converter na exibição é o que mantém tudo coerente.

Como surgiu

O Java viveu 18 anos com Date e Calendar: mutáveis, confusos (mês começava em zero!) e hostis a fuso horário. A comunidade migrou em massa para a biblioteca Joda-Time, e o Java 8 incorporou o mesmo desenho como java.time — imutável, explícito e correto.

Veio substituir: java.util.Date, Calendar e SimpleDateFormat (que ainda por cima não era thread-safe).

Onde você usa isso no dia a dia

  • Campos de criação e atualização em toda tabela.
  • Agendamentos, expiração de token e janelas de promoção.
  • Testes que precisam "viajar no tempo" sem esperar.

O modelo mental que resolve quase todo bug de data: o instante é um só; a representação local é que varia. Instant é o ponto na linha do tempo, em UTC — é o que vai para o banco. LocalDateTime é um horário de parede sem fuso: ambíguo por natureza, útil apenas para regras como "toda segunda às 9h". ZonedDateTime combina instante e regras de uma zona, incluindo horário de verão. E há uma distinção sutil que pega muita gente: Duration mede tempo físico (segundos), Period mede tempo de calendário — "um mês" não é 30 dias fixos.

Difícil de testar
boolean expirou(Instant limite) {
    return Instant.now().isAfter(limite);
}

Encapsulamento: o objeto que não aceita estado inválido

essencialdesign

Direto: encapsular não é "campo privado com getter e setter" — é garantir que o objeto nunca exista em estado inválido. A regra é validada no construtor e protegida em cada método que altera o estado.

≈

Como um caixa eletrônico. Ele não te entrega o cofre com um bilhete pedindo para você mesmo tirar o valor certo. Ele expõe operações ("sacar 200") e recusa o que viola a regra ("saldo insuficiente"). Um objeto com setters públicos para tudo é o cofre aberto: cada chamador precisa lembrar das regras — e um deles vai esquecer.

Como surgiu

A cultura de getters e setters para todo campo veio da especificação JavaBeans (1996), pensada para ferramentas visuais montarem componentes automaticamente. Virou hábito e se espalhou para o modelo de domínio, onde o efeito é o oposto do pretendido: as regras vazam para quem chama e o objeto vira um saco de dados. Domain-Driven Design popularizou a volta ao objeto que protege as próprias invariantes.

Veio substituir: o "modelo anêmico" — classes só com dados e serviços gigantes com toda a regra espalhada.

Onde você usa isso no dia a dia

  • Ao revisar um PR e ver setStatus() chamado em cinco lugares diferentes.
  • Quando um bug de estado inconsistente aparece "sem explicação".
  • Ao modelar entidades novas: quais operações existem, não quais campos existem.
Anêmico: a regra vaza

// de fazer os três, na ordem

public final class Pedido {
    private final UUID id;
    private final List<Item> itens = new ArrayList<>();
    private Status status = Status.ABERTO;

    public Pedido(UUID id) { this.id = Objects.requireNonNull(id); }

Interfaces, composição e polimorfismo

essencialdesign

Direto: a interface separa o contrato da implementação — quem chama depende do que o objeto faz, não de como ele faz. E composição ("tem um") envelhece melhor que herança ("é um") em quase todo caso real.

≈

Como uma tomada e um aparelho. A parede oferece um contrato (110V, dois pinos); qualquer aparelho que respeite o contrato funciona, e a parede não precisa saber se é um liquidificador ou um carregador. Trocar o aparelho não exige reformar a casa — é exatamente isso que a interface te dá no código.

Como surgiu

O Java nasceu sem herança múltipla de classes (dor conhecida do C++, com o "problema do diamante") e ofereceu interfaces como alternativa segura: múltiplos contratos, uma só implementação. Com o tempo, a experiência do setor mostrou que herança de classe acopla a subclasse aos detalhes internos do pai — o clássico "fragile base class" — e a orientação virou preferir composição.

Veio substituir: hierarquias profundas de herança, onde mudar a classe base quebrava filhos distantes.

Onde você usa isso no dia a dia

  • Ao trocar o envio de e-mail por uma fila sem tocar na regra de negócio.
  • Em todo teste que injeta um dublê no lugar da dependência real.
  • Ao integrar dois gateways de pagamento com a mesma interface.

O mecanismo por trás é o dynamic dispatch: a variável tem tipo declarado Notificador, mas a chamada resolve em tempo de execução para o objeto real. É isso que permite trocar implementações — inclusive por um mock — sem tocar em quem usa. E composição alcança o mesmo reuso da herança guardando o colaborador num campo e delegando, com a fronteira explícita na assinatura.

interface Notificador { void notificar(Pedido p); }

final class CheckoutService {
    private final Notificador notificador;          // composição: "tem um"
    CheckoutService(Notificador n) { this.notificador = n; }
    void finalizar(Pedido p) { /* regra */ notificador.notificar(p); }
}

// produção: new CheckoutService(new EmailNotificador(smtp))
// teste:    new CheckoutService(p -> enviados.add(p))   ← lambda como implementação
Sobrecarga não é sobrescrita

Sobrecarga (mesmo nome, parâmetros diferentes) é resolvida na compilação, pelo tipo declarado. Sobrescrita é resolvida em runtime, pelo objeto real. Por isso Object x = "texto"; f(x); chama f(Object) e não f(String) — decisão tomada pelo tipo da variável.

≈

Como um cardápio fixo. Se o restaurante declara que só existem três pratos, o caixa pode ter um preço para cada um e o sistema sabe que cobriu tudo. Se amanhã entrar um quarto prato, o caixa acusa na hora que falta preço — em vez de descobrir no fim do dia que alguém comeu de graça.

Como surgiu

O record (Java 16) tornou isso parte da linguagem. O sealed (17) veio junto, trazendo do mundo funcional a modelagem por soma de casos, com verificação exaustiva no compilador.

Veio substituir: POJOs gigantes gerados pela IDE, e boa parte do que se usava Lombok para resolver.

Onde você usa isso no dia a dia

  • Chaves compostas de mapas e caches.
  • Estados de um pedido, tipos de pagamento, resultados de uma operação.

Direto: equals define igualdade de conteúdo e hashCode precisa ser coerente com ele — conteúdo igual, hash igual. Quebrar isso faz o objeto sumir de mapas e conjuntos. E Optional torna a ausência visível no tipo de retorno.

≈

Como o arquivo de uma clínica. As fichas são guardadas em gavetas pela primeira letra do sobrenome (o hash) e, dentro da gaveta, comparadas pelo nome completo (o equals). Generics: erasure, invariância e a regra PECS

essencialJava 5+

Direto: generics dão segurança de tipo na compilação e são apagados no runtime. List<Gato> não é List<Animal> — e os curingas extends/super resolvem isso com uma regra simples: leio, então extends; escrevo, então super.

≈

Como uma caixa etiquetada. Uma caixa marcada "só gatos" não pode ser tratada como "caixa de animais" — se pudesse, alguém colocaria um cachorro nela e a etiqueta viraria mentira. Quando você só vai tirar coisas, aceita qualquer caixa de animais ou mais específica; quando só vai colocar gatos, aceita a caixa de gatos ou mais genérica.

Como surgiu

Até o Java 5 (2004), coleção guardava Object e você fazia cast na mão — descobrindo o erro em runtime, longe da causa. Os generics trouxeram a checagem para o compilador, mas havia milhões de linhas legadas: a decisão foi apagar o tipo na compilação (type erasure) para o bytecode continuar compatível. Compatibilidade comprou as limitações que vivemos até hoje.

Veio substituir: coleções de Object com cast manual e ClassCastException em produção.

Onde você usa isso no dia a dia

  • Toda assinatura de repositório, serviço e API genérica que você escreve.
  • Quando o compilador recusa passar List<Filho> onde se espera List<Pai>.
  • Ao desserializar JSON para List<User> e precisar do truque do TypeReference.

A invariância existe por segurança, não por capricho. Se List<Gato> fosse aceita como List<Animal>, alguém adicionaria um cachorro nela com a bênção do compilador — e a lista de gatos estaria corrompida. Quando você precisa de flexibilidade, o curinga entra, e o mnemônico PECS (Producer Extends, Consumer Super) decide qual usar.

static <T> void copiar(List<? extends T> origem,    // PRODUZ T: só leio dela
                       List<? super T> destino) {   // CONSOME T: só escrevo nela
    for (T item : origem) destino.add(item);
}
copiar(List.of(new Gato()), new ArrayList<Animal>());  // compila e é seguro
Onde o erasure te morde
  • Sobrecarga impossível: f(List<String>) e f(List<Integer>) viram o mesmo método após o apagamento.
  • Não existe new T[] nem instanceof List<String> — o tipo não sobrevive ao runtime.
  • Por isso bibliotecas usam new TypeReference<List<User>>(){}: a subclasse anônima "congela" o tipo no bytecode, tornando-o legível por reflexão.

essencial

Direto: escolha a coleção pela pergunta que você mais faz aos dados, e a implementação pelo custo dessa pergunta. Em 90% dos casos: ArrayList, HashMap, HashSet e ArrayDeque.

≈

Como organizar uma cozinha. Temperos que você pega o tempo todo ficam na prateleira à mão (HashMap: acesso direto). A fila de pratos para lavar segue a ordem de chegada (Queue). A lista de compras aceita repetido e tem ordem (List). E o conjunto de chaves da casa não pode ter duplicata (Set). Você não guarda tudo do mesmo jeito — guarda pelo uso.

Como surgiu

Antes do Java 1.2 existiam apenas Vector e Hashtable, sincronizados à força e sem uma hierarquia comum. O Collections Framework (1998), desenhado por Joshua Bloch, introduziu as interfaces (List, Set, Map) separadas das implementações — o que permite trocar a estrutura sem reescrever quem a usa.

Veio substituir: Vector e Hashtable, que pagavam custo de sincronização mesmo em uso de thread única.

Onde você usa isso no dia a dia

  • Ao processar um lote e precisar de "já vi este identificador?".
  • Em filas internas de trabalho antes de mandar para um executor.

HashMap por dentro: hash, colisão, árvore e resize

essencialentrevista

Direto: o HashMap acha a chave em tempo constante porque o hash aponta direto para um "balde". Colisões viram lista e, se crescerem demais, árvore. Passar de ~75% da capacidade dispara um resize caro.

≈

Como um armário de guarda-volumes. Em vez de procurar sua bolsa em todos os compartimentos, a etiqueta diz o número — você vai direto. Se duas bolsas dividem o mesmo compartimento (colisão), você confere as duas. Se um compartimento vira um monte com quinze bolsas, o atendente organiza aquele monte para não ter que revirar tudo. E quando o armário enche, trocam por um maior e reorganizam todas as etiquetas.

Como surgiu

A estrutura hash é clássica da computação, mas o Java 8 fez um acréscimo importante: baldes com muitas colisões passaram a virar árvores balanceadas. O motivo foi segurança — existiam ataques que forjavam milhares de chaves colidindo de propósito, degradando o mapa para uma lista e derrubando servidores web.

Veio substituir: a Hashtable sincronizada e as buscas lineares em listas de pares.

Onde você usa isso no dia a dia

  • Ao indexar registros do banco por ID para cruzar com outra lista.
  • Em caches em memória e agrupamentos por chave.
  • Ao carregar dados em massa e perceber lentidão inesperada (resizes).

Lambdas e interfaces funcionais

essencialJava 8

Direto: lambda é uma função anônima cujo tipo é uma interface funcional — qualquer interface com um único método abstrato. É o que permite passar comportamento como argumento.

≈

Como dar uma instrução em vez de um objeto. Antes você contratava um funcionário inteiro (uma classe anônima de seis linhas) para executar uma tarefa de um segundo. Agora você entrega um bilhete com a instrução: "para cada pedido, pegue o total". Mesmo efeito, sem a burocracia de contratar.

Como surgiu

Passar comportamento sempre foi possível em Java — com classes anônimas verbosas. O Java 8 trouxe a sintaxe curta e, por baixo, algo mais esperto que gerar uma classe por lambda: a instrução invokedynamic constrói a implementação na primeira chamada. Lambda não é açúcar sintático para classe anônima; é um mecanismo mais leve.

Veio substituir: classes anônimas de Runnable, Comparator e listeners — o "código cerimonial" que dominava Java pré-8.

Onde você usa isso no dia a dia

  • Ordenar listas por qualquer critério, sem criar classes.
  • Filtrar e transformar coleções com Streams.
  • Injetar comportamento em testes sem framework de mock.

Streams: pipeline, laziness e Collectors

essencialJava 8

Direto: um Stream descreve o que fazer com uma sequência e não executa nada até a operação terminal. O poder de verdade está nos Collectors — agrupar, contar e somar numa única passada.

≈

Como uma linha de produção. Você monta as estações (filtrar, transformar) mas nada se move até alguém ligar a esteira na ponta. E cada peça percorre a linha inteira antes da próxima entrar — por isso, se você só precisa da primeira peça aprovada, a linha para assim que ela sai, sem processar o resto.

Como surgiu

Chegou junto com as lambdas no Java 8, com dois objetivos: código declarativo sobre coleções (dizendo o resultado, não o laço) e a possibilidade de paralelizar sem reescrever. A inspiração veio de LINQ (.NET) e das linguagens funcionais, adaptada ao Collections Framework existente.

             reducing(BigDecimal.ZERO, Pedido::total, BigDecimal::add)));

var receita = pedidos.stream()
    .filter(Pedido::isPago)
    .map(Pedido::total)
    .reduce(BigDecimal.ZERO, BigDecimal::add);
Armadilhas
  • parallelStream() usa o ForkJoinPool comum da JVM inteira. Só compensa com coleção grande e trabalho de CPU independente; com I/O dentro, vira gargalo para todo mundo.
  • Stream não substitui todo for: laço com estado, índice ou saída complexa fica mais claro imperativo.
  • Efeito colateral dentro de map/filter (mutar coisas de fora) quebra o modelo e inviabiliza o paralelismo.
Vindo do C#: é o LINQ na sintaxe de métodos — Where vira filter, Select vira map, GroupBy vira groupingBy, Aggregate vira reduce. A execução adiada é a mesma ideia. O que não existe no Java é a query syntax (from x in ...).

Falhas, recursos, testes e investigação

Falhar bem é design. Achar a causa é método — não sorte.

Exceções: checked, unchecked e a causa raiz

essencial

Direto: capture onde você consegue agir; nas fronteiras entre camadas, traduza para o vocabulário da camada — sempre preservando a causa original. E leia o Caused by de baixo para cima: a raiz é o último.

≈

Como um problema numa obra. O pedreiro não liga para o dono dizendo "erro 500 na argamassa". Ele avisa o mestre de obras, que traduz para "a laje vai atrasar dois dias porque o cimento veio errado". Cada nível fala a linguagem do seu interlocutor — mas a nota fiscal do cimento errado (a causa) acompanha o processo inteiro.

Como surgiu

O Java apostou numa ideia que nenhuma linguagem mainstream copiou depois: exceções checked, que o compilador obriga a tratar ou declarar. A intenção era forçar o programador a encarar falhas previsíveis. Décadas depois, o efeito colateral ficou claro — catch vazios e throws Exception genéricos só para calar o compilador. A prática moderna preferiu unchecked.

Veio substituir: códigos de retorno (-1, null) que o chamador podia ignorar em silêncio, como em C.

Onde você usa isso no dia a dia

  • Em toda integração: banco fora, timeout de API, arquivo ausente.
  • Ao decidir o status HTTP que sua API devolve para cada falha.
  • Ao abrir um stack trace de 80 linhas às 3h da manhã.
Cria bug invisível
try {
    repo.salvar(pedido);
} catch (Exception e) {
    // silêncio: ninguém sabe que falhou
}
// ou: e.printStackTrace(); e segue
Traduz e preserva
try {
    repo.salvar(pedido);
} catch (SQLException e) {
    throw new RepositorioException(
        "falha ao salvar pedido " + id, e);
}   // a causa viaja junto

Como ler um stack trace em trinta segundos: a primeira linha dá o tipo e a mensagem; procure o primeiro at do seu pacote para saber onde no seu código; e vá até o último Caused by — ali está a raiz. Se houver vários erros no log, investigue o primeiro na linha do tempo: os seguintes costumam ser consequência.

Pratique agoraProvoque uma SQLException real (consulte uma tabela inexistente), deixe-a subir traduzida e leia o trace de baixo para cima até a raiz.

try-with-resources e a posse dos recursos

essencialJava 7+

Direto: todo recurso tem um dono, e o dono fecha — inclusive quando o código explode no meio. O try-with-resources torna isso automático para qualquer AutoCloseable.

≈

Como uma chave emprestada. Quem pega a chave devolve na portaria ao sair — mesmo que saia correndo por causa de um incêndio. E devolve na ordem inversa de quem pegou por último. Vazamento de conexão é sempre alguém que saiu com a chave no bolso.

Como surgiu

Antes do Java 7, fechar corretamente exigia finally aninhado, com try dentro do finally para tratar exceção no próprio close. Era tão verboso que quase todo mundo errava em algum caminho — e vazava conexão em produção. A sintaxe nova moveu essa responsabilidade para o compilador.

Veio substituir: o padrão try/finally aninhado e os utilitários IOUtils.closeQuietly que mascaravam erros.

Onde você usa isso no dia a dia

  • Toda operação JDBC: Connection, Statement e ResultSet.
  • Leitura de arquivos e chamadas HTTP com corpo em stream.
  • Executors do Java 19+, que também são AutoCloseable.
Java 6: fácil de errar
Connection c = null;
try {
    c = ds.getConnection();
    // ...
} finally {
    if (c != null) {
        try { c.close(); }
        catch (SQLException ignored) {}
    }
}
Java 7+: impossível esquecer
try (var c = ds.getConnection();
     var ps = c.prepareStatement(sql);
     var rs = ps.executeQuery()) {
    while (rs.next()) processa(rs);
}
// fecha rs, ps e c nessa ordem,
// com ou sem exceção

Há um detalhe elegante: se o corpo lança uma exceção e o close também, a do corpo prevalece e a do close vira suppressed — aparece no trace sem esconder a causa primária. O conceito por trás é ownership: quem abre, fecha; quem recebe um recurso já aberto não é dono e não deve fechar; quem cria e devolve transfere a posse. Quase todo vazamento em produção é uma quebra silenciosa dessa regra.

Vindo do C#: é o using, e AutoCloseable equivale a IDisposable. Até o cuidado com exceção dupla é análogo. A disciplina de posse é idêntica nas duas linguagens.
Pratique agoraEscreva um AutoCloseable que imprime no close, abra três no mesmo try e lance uma exceção. Observe a ordem de fechamento e o suppressed.

Testes: comportamento, integração e determinismo

essencial

Direto: teste bom quebra exatamente quando o comportamento quebra — e só então. Unidade testa a regra com dependências controladas; integração testa contra o real (banco em container); ambos precisam ser determinísticos.

≈

Como o alarme de incêndio. Se ele dispara quando você faz torrada, você acaba tirando a bateria — e aí ele não te salva no dia do incêndio. Suíte de teste instável tem o mesmo destino: o time começa a ignorar o vermelho, e ela perde toda a função.

Como surgiu

O JUnit (1997, de Kent Beck e Erich Gamma) inaugurou o teste automatizado como parte do desenvolvimento. O salto mais recente foi o Testcontainers: em vez de simular o banco com um H2 em memória — que aceita SQL diferente e esconde bugs —, o teste sobe o PostgreSQL real em Docker e derruba no fim.

Veio substituir: o teste manual pelo Postman e os bancos em memória que "quase" se comportam como o de produção.

Onde você usa isso no dia a dia

  • Ao corrigir um bug: primeiro o teste que o reproduz, depois o conserto.
  • Ao refatorar: a suíte é a rede de segurança.
  • No pipeline, barrando merge quando algo regride.
@Test
void naoFinalizaPedidoVazio() {
    var pedido = new Pedido(UUID.randomUUID());          // arrange
    assertThrows(IllegalStateException.class,
                 pedido::finalizar);                      // act + assert
}

@Test

    try (var pg = new PostgreSQLContainer<>("postgres:16")) {
        pg.start();
        var repo = new JdbcPedidoRepo(dataSource(pg));
        repo.salvar(pedido);
        assertEquals(pedido, repo.buscar(pedido.id()).orElseThrow());

}
O que torna um teste instável (flaky)
  • Depender de Instant.now() em vez de um Clock injetado.
  • Depender da ordem de execução ou de dados deixados por outro teste.
  • Thread.sleep arbitrário em vez de esperar por uma condição.
  • Chamar rede externa de verdade — o teste falha quando a internet oscila.

Troubleshooting: sintoma, hipótese, evidência

essencialhabilidade-mãe

Direto: investigar não é adivinhar — é cortar o espaço de busca pela metade com um teste barato por vez. A pergunta de ouro é sempre: o que mudou desde a última vez que funcionava?

≈

Como achar o disjuntor certo. Você não troca a fiação da casa inteira: desliga tudo, liga um circuito por vez e observa. Em sete testes você isola o problema entre cem possibilidades. Mexer em três coisas ao mesmo tempo é o oposto — quando volta a funcionar, você não sabe o porquê, e o problema retorna.

Por que isso é método, não talento

A diferença entre quem resolve em vinte minutos e quem passa dois dias raramente é conhecimento de linguagem — é ter um procedimento. Quem tem método faz uma pergunta por vez e deixa a resposta eliminar metade das hipóteses; quem não tem, testa mudanças aleatórias e perde a referência do que já descartou.

Veio substituir: o "vou mexer aqui e ver se melhora", que resolve por acaso e não ensina nada.

Onde você usa isso no dia a dia

  • Incidente em produção com pressão do time.
  • Bug que só acontece no ambiente do cliente.
  • Lentidão sem causa aparente após um deploy.

As ferramentas de corte no mundo Java: no tempo, git bisect encontra o commit culpado em passos logarítmicos; no fluxo, um curl direto no serviço do meio diz se o problema está antes ou depois dele; no código, reduza ao menor main que reproduz; na JVM, um thread dump mostra onde tudo está parado agora. E se não há erro nenhum no log, só existem duas possibilidades: o código não chegou lá (adicione um log de entrada), ou alguém engoliu a exceção.

As fronteiras por onde os dados entram e saem do seu processo.

Arquivos: Path, charset e leitura em fluxo

essencial

Direto: I/O tem dois mundos — bytes (binário) e caracteres (texto) — e a ponte entre eles é sempre um charset. Arquivo pequeno se lê inteiro; arquivo grande se lê em fluxo, com memória constante.

≈

Como beber de uma mangueira. Você não precisa encher um tanque com toda a água antes de beber: consome enquanto passa. Ler um log de 10 GB com readAllBytes é tentar encher o tanque — e ele não cabe na cozinha.

Como surgiu

A API original (java.io.File, 1996) era limitada: não informava por que uma operação falhava, tratava mal links simbólicos e ignorava metadados. O Java 7 trouxe o java.nio.file com Path e Files — mensagens de erro reais, operações atômicas e suporte a sistemas de arquivos diferentes.

Veio substituir: java.io.File, cujos métodos devolviam apenas boolean sem dizer o motivo da falha.

Onde você usa isso no dia a dia

  • Importação de CSV enviado pelo cliente.
  • Leitura de logs para gerar relatório pós-deploy.
  • Escrita de arquivos de saída e manipulação de diretórios.
Estoura com arquivo grande

// 10 GB na memória = OutOfMemory

  • Files.lines sem try-with-resources vaza descritor de arquivo — é recurso como conexão.
  • Ler upload externo com readAllBytes sem limite é convite a negação de serviço.
  • Omitir o charset faz o Java usar o padrão da plataforma: abre certo na sua máquina, quebra o acento no servidor.

HttpClient: timeout, retry, backoff e idempotência

essencialJava 11+

Direto: toda chamada de rede pode falhar ou demorar para sempre. Então: todo request tem timeout, trata status fora do 2xx, e só é re-tentado se a operação for idempotente.

≈

Como ligar para alguém que não atende. Você não fica com o telefone no ouvido a tarde inteira (timeout), e não liga cinquenta vezes seguidas (backoff: espera um pouco mais a cada tentativa). E antes de repetir um pedido, pensa se repetir causa dano — reenviar "confirme minha presença" é inofensivo; reenviar "transfira mil reais" não é.

Como surgiu

Por quase vinte anos o Java só tinha o HttpURLConnection, uma API dos anos 90 sem timeout decente nem HTTP/2 — todo projeto sério importava uma biblioteca externa. O Java 11 trouxe um cliente moderno, fluente, com HTTP/2, modo assíncrono e timeouts de verdade.

Veio substituir: HttpURLConnection e a dependência obrigatória de bibliotecas de terceiros para o básico.

Onde você usa isso no dia a dia

  • Integração com gateway de pagamento, correios, serviços internos.
  • Chamadas entre microsserviços do seu próprio sistema.
  • Consumo de APIs públicas em jobs agendados.
var client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(3))      // conectar
        .build();
var req = HttpRequest.newBuilder(URI.create(url))
        .timeout(Duration.ofSeconds(5))             // o request inteiro
        .header("Idempotency-Key", operacaoId)      // deduplicação no servidor
        .POST(HttpRequest.BodyPublishers.ofString(json))
        .build();

var res = client.send(req, HttpResponse.BodyHandlers.ofString());
if (res.statusCode() / 100 != 2)
    throw new IntegracaoException("api respondeu " + res.statusCode());
A regra que evita cobrar o cliente duas vezes

GET, PUT e DELETE são idempotentes por contrato: repetir dá o mesmo resultado. POST não é. Se precisa re-tentar um POST, mande uma chave de idempotência única e faça o servidor deduplicar por ela. Retry cego em POST é a origem clássica do pagamento duplicado.

Pratique agoraChame uma API sem timeout apontando para um IP que não responde e veja a thread pendurada indefinidamente. Adicione o timeout e repita.

Parsing e fronteiras não confiáveis

essencialsegurança

Direto: todo dado que cruza a fronteira do seu processo é suspeito. Valide formato, limites e significado na borda, uma vez — e daí para dentro circule só tipo forte já validado.

≈

Como a portaria de um prédio. A conferência de identidade acontece uma vez, na entrada. Depois disso, quem está circulando lá dentro já foi verificado. Se cada andar tivesse que reconferir, ou ninguém confere (e entra qualquer um), ou todo mundo perde tempo repetindo a mesma checagem.

Por que isso é arquitetura, não detalhe

Quando um Map<String,Object> ou um DTO sem validação circula pelo sistema, cada camada precisa desconfiar de novo — e alguma esquece. Concentrar a validação na borda e converter para um tipo que não consegue representar estado inválido elimina a dúvida do resto do código.

Veio substituir: validações espalhadas em if por todas as camadas, e o famoso NPE três chamadas depois da entrada.

Onde você usa isso no dia a dia

  • Todo endpoint que recebe JSON.
  • Importação de planilha e arquivo de parceiro.
  • Mensagens consumidas de fila.
record NovoPedido(String cliente, BigDecimal total) {
    NovoPedido {                                   // valida na construção
        if (cliente == null || cliente.isBlank())
            throw new DadosInvalidos("cliente é obrigatório");
        if (total == null || total.signum() <= 0)
            throw new DadosInvalidos("total deve ser positivo");
    }
}
// na borda: JSON → NovoPedido. Daqui pra dentro, é impossível estar inválido.
Segurança no parsing
  • Nunca desserialize objetos Java nativos (ObjectInputStream) vindos de fora: é execução remota de código esperando acontecer. Use JSON com tipo fixo.
  • Limite tamanho de payload e profundidade de estrutura — parser sem limite é vetor de negação de serviço.
  • Não ecoe dados sensíveis no log de erro do parsing.

SQL e JDBC: dados sem ORM

Entenda a fundação. Depois disso, o Hibernate vira vidro transparente.

SQL: por que ele existe e por que não morre

essencial1970 → hoje

Direto: o SQL é declarativo — você descreve o resultado que quer e o banco decide como obtê-lo. Essa separação é o que o mantém vivo há cinquenta anos, e é onde mora o desempenho.

≈

Como pedir num restaurante. Você diz o prato, não a receita: não instrui o chef a "aquecer a panela em fogo médio por três minutos". O chef (o otimizador) conhece a cozinha, os ingredientes disponíveis e escolhe o caminho mais rápido. O EXPLAIN é você espiando qual caminho ele escolheu.

Como surgiu

Em 1970, Edgar Codd publicou na IBM o modelo relacional: dados como relações manipuladas por uma álgebra formal, com independência entre a forma lógica e o armazenamento físico. A linguagem construída sobre isso virou o SQL. A revolução foi separar o o quê do como — antes, o programador navegava ponteiro a ponteiro pelos registros (modelo em rede/hierárquico) e qualquer mudança na estrutura quebrava todos os programas.

Veio substituir: bancos hierárquicos e em rede, onde a consulta era um programa de navegação escrito à mão.

Onde você usa isso no dia a dia

  • Toda tela de listagem com filtro e ordenação.
  • Relatórios, fechamentos e conciliações.
  • Quando uma consulta que era rápida fica lenta com o crescimento da tabela.

Três conceitos sustentam o resto. Constraints são a garantia que nenhum código dá: PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK. A aplicação valida para dar mensagem bonita; o banco valida para garantir — com várias instâncias da aplicação escrevendo ao mesmo tempo, só a constraint segura a unicidade de verdade. Joins reconstroem o que a normalização separou. E índices são a estrutura (árvore B) que permite ao banco pular direto às linhas em vez de varrer a tabela inteira.

Sem índice: varre tudo
EXPLAIN ANALYZE
SELECT * FROM pedido
WHERE status = 'PAGO';

-- Seq Scan on pedido
-- (cost=0.00..18334.00 rows=1000)
-- lê 1.000.000 de linhas
Com índice: vai direto
CREATE INDEX idx_pedido_status_data
    ON pedido (status, data);

-- Index Scan using idx_pedido_status_data
-- (cost=0.42..8.44 rows=1000)
-- lê só o necessário
Detalhes que separam níveis
  • Filtrar coluna do lado direito de um LEFT JOIN no WHERE transforma ele em INNER JOIN silenciosamente — a condição vai no ON.
  • Índice não é grátis: cada escrita atualiza cada índice. Índice demais deixa o INSERT lento.
  • Função sobre a coluna (WHERE upper(nome) = ?) costuma invalidar o índice — a menos que você crie um índice sobre a expressão.
Pratique agoraCrie uma tabela com 100 mil linhas via generate_series, rode a consulta sem índice e leia o Seq Scan. Crie o índice e compare o plano e o tempo.

JDBC: DataSource, driver, Connection e pool

essenciala fundação de tudo

Direto: JDBC é a API padrão do Java para bancos relacionais. A cadeia inteira é DataSource → pool → Connection → PreparedStatement → driver → banco → ResultSet. A Connection é sessão e fronteira de transação — e é emprestada, não sua.

≈

Como as linhas telefônicas de um call center. Ninguém instala uma linha nova a cada ligação: existe um feixe de linhas já abertas que os atendentes pegam e devolvem. "Desligar" devolve a linha ao feixe — não arranca o cabo da parede. Se um atendente esquece o telefone fora do gancho, aquela linha some do feixe; com poucos esquecimentos, o call center inteiro para.

Como surgiu

O JDBC (1997) copiou a ideia do ODBC da Microsoft: uma API única no lado da aplicação, e cada banco fornece um driver que traduz para o seu protocolo de rede. É por isso que trocar PostgreSQL por MySQL não muda seu código — muda o driver e a URL. O pool veio depois, quando ficou evidente que abrir conexão por requisição não escala.

Veio substituir: APIs proprietárias por banco (cada fabricante com sua biblioteca C) e a conexão aberta a cada operação.

Onde você usa isso no dia a dia

  • Está por baixo de todo acesso a dados: JPA, Hibernate, JdbcTemplate, jOOQ.
  • Quando a aplicação congela inteira e o CPU está baixo (pool esgotado).
  • Ao dimensionar o pool para não saturar o banco em produção.
final class JdbcPedidoRepo {
    private final DataSource ds;                    // o pool mora aqui, injetado
    JdbcPedidoRepo(DataSource ds) { this.ds = ds; }

    Optional<Pedido> buscar(UUID id) {
        var sql = "SELECT id, status, total FROM pedido WHERE id = ?";
        try (var c  = ds.getConnection();           // pega emprestada do pool
             var ps = c.prepareStatement(sql)) {
            ps.setObject(1, id);
            try (var rs = ps.executeQuery()) {
                return rs.next() ? Optional.of(mapeia(rs)) : Optional.empty();
            }
        } catch (SQLException e) {
            throw new RepositorioException("falha ao buscar pedido " + id, e);
        }
    }   // close() devolve a conexão ao pool — não fecha o socket
}
Armadilhas que derrubam produção
  • Guardar Connection em campo de singleton: sessão não é thread-safe nem eterna.
  • Aumentar o pool como primeira reação à lentidão: mais conexões num banco saturado geram mais fila dentro do banco. Ache a consulta lenta primeiro.
  • Sintoma típico de pool esgotado: timeouts em tudo ao mesmo tempo, com CPU baixa. Procure o vazamento, não o hardware.
⚡ Ponte de Arquitetura: O pool e a ilusão do escalonamento infinito

No código Java isolado, maximum-pool-size=10 parece inofensivo. Porém, no cluster Kubernetes (ver Docker e Kubernetes), se o seu HPA (Horizontal Pod Autoscaler) escalar o serviço de 2 para 25 réplicas durante um pico de tráfego, você terá 25 × 10 = 250 conexões simultâneas disparadas contra um PostgreSQL cujo max_connections pode ser de apenas 100.

Sem um proxy de conexões dedicado (PgBouncer/AWS RDS Proxy) ou retenção controlada via fila e backpressure (ver Mensageria), o escalonamento horizontal da sua aplicação vira um ataque de negação de serviço (DDoS) autoinduzido contra o banco de dados.

Pratique agoraConfigure o pool com tamanho 2, "esqueça" um close num endpoint e chame três vezes. Assista a aplicação congelar. Conserte e repita.

PreparedStatement e ResultSet: SQL injection morre aqui

essencialsegurança

Direto: o PreparedStatement envia o comando e os valores por canais separados — o dado do usuário nunca é interpretado como SQL. Isso mata injection estruturalmente, sem depender de sanitização.

≈

Como preencher um formulário impresso. O texto do formulário já está impresso e os campos são lacunas: por mais que alguém escreva "ignore o texto acima" numa lacuna, isso continua sendo conteúdo do campo, não uma instrução nova. Concatenar string é o contrário: é deixar a pessoa escrever o formulário inteiro.

Como surgiu

SQL injection é a vulnerabilidade mais antiga ainda ativa em produção, listada há décadas no topo do OWASP. Os parâmetros existem no JDBC desde o início, mas por muito tempo se ensinou "escapar aspas" — abordagem que sempre teve brecha. A separação entre comando e dado foi a resposta definitiva, com o bônus de o banco reaproveitar o plano de execução.

Veio substituir: concatenação de string com escape manual de aspas — defesa frágil e fácil de esquecer.

Onde você usa isso no dia a dia

  • Toda consulta que recebe qualquer valor de fora.
  • Filtros dinâmicos de tela de busca.
  • Revisão de código: concatenação em SQL é bloqueio imediato de PR.

// → devolve a tabela inteira

Transações: ACID e a mesma Connection

essencial

Direto: transação é "tudo ou nada", e ela vive dentro de uma Connection: todos os comandos da unidade usam a mesma conexão, com autoCommit desligado, terminando num único commit ou rollback.

≈

Como uma transferência bancária. Debitar de uma conta e creditar na outra são duas operações que precisam valer juntas. Se a luz acabar no meio, ou as duas aconteceram ou nenhuma — jamais só o débito. O commit é o momento em que o par inteiro se torna oficial.

Como surgiu

O conceito de transação com as propriedades ACID foi formalizado por Jim Gray nos anos 70-80, resolvendo o problema central de sistemas concorrentes com falhas: como manter dados corretos quando várias operações acontecem ao mesmo tempo e a máquina pode cair a qualquer instante. É a base sobre a qual todo sistema financeiro funciona.

Veio substituir: gravações soltas em arquivo, onde uma falha no meio deixava o estado inconsistente sem forma de recuperar.

Onde você usa isso no dia a dia

  • Salvar pedido e itens, dar baixa em estoque, registrar pagamento.
  • Qualquer operação que toca duas ou mais tabelas.
  • Ao entender o que o @Transactional do Spring faz por baixo.
Erro arquitetural comum
void inserePedido(Pedido p) {
  try (var c = ds.getConnection()) { ... }
}
void baixaEstoque(Pedido p) {
  try (var c = ds.getConnection()) { ... }
}
// duas conexões = duas transações
// o "tudo ou nada" morreu em silêncio
Correto: a conexão é passada
try (var c = ds.getConnection()) {
  c.setAutoCommit(false);
  try {
    inserePedido(c, pedido);   // recebem
    baixaEstoque(c, pedido);   // a MESMA
    c.commit();
  } catch (Exception e) { c.rollback(); throw e; }
}
Por que o Spring "amarra" a conexão à thread

Justamente para você não precisar passar a Connection de método em método: o @Transactional guarda a conexão da transação atual num contexto ligado à thread e a repassa por baixo dos panos. Sabendo disso, o comportamento dele deixa de ser mágica — e você entende por que chamada interna não abre transação nova.

Pratique agoraImplemente o fluxo correto, lance uma exceção proposital entre os dois comandos e confirme no banco que nada foi salvo.

Isolamento, locks e o lost update

essencialconcorrência

Direto: duas transações mexendo no mesmo dado é rotina. O nível de isolamento define o que uma enxerga da outra — e o lost update (ler, modificar, gravar em paralelo) passa ileso pelo nível padrão.

≈

Como dois garçons anotando na mesma comanda. Os dois leem "total: 100", cada um soma o próprio item e escreve o novo total. O segundo sobrescreve o primeiro, e um item some da conta. Ninguém errou de propósito — o processo é que permitia isso.

Por que o padrão não protege

O nível READ COMMITTED (padrão no PostgreSQL e no SQL Server) garante que você não lê dado não confirmado — mas não impede que dois leiam o mesmo valor, calculem em cima e gravem. Subir o isolamento resolve ao custo de mais conflitos e abortos; por isso a prática comum é manter o padrão e proteger os pontos críticos com técnicas específicas.

Veio substituir: travar a tabela inteira, que era a defesa antiga e matava a concorrência.

Onde você usa isso no dia a dia

  • Saldo, estoque, contador de vagas, limite de crédito.
  • Duas requisições do mesmo usuário chegando juntas (duplo clique).
  • Job em paralelo processando o mesmo registro.
-- 1) ATÔMICO: a melhor opção quando a conta cabe no SQL
UPDATE conta SET saldo = saldo + 10 WHERE id = ?;

-- 2) PESSIMISTA: tranca a linha até o commit; o concorrente espera
SELECT saldo FROM conta WHERE id = ? FOR UPDATE;

-- 3) OTIMISTA: detecta o conflito em vez de prevenir
UPDATE conta SET saldo = ?, versao = versao + 1
WHERE id = ? AND versao = ?;      -- 0 linhas afetadas = alguém passou na frente
Como escolher
  • A conta cabe no SQL? Use o update atômico — simples e sem conflito.
  • Precisa ler, decidir em Java e gravar, com alta disputa? Pessimista (FOR UPDATE).
  • Disputa rara e você quer evitar travas? Otimista com coluna de versão e re-tentativa. É o mesmo princípio do CAS na concorrência de threads.
Pratique agoraAbra dois terminais no psql, faça o lost update na mão (BEGIN nos dois, leia, some, grave) e veja o valor errado. Depois resolva com FOR UPDATE e observe o segundo esperar.

Batch, streaming e paginação por keyset

essencialvolume

Direto: volume muda tudo. Inserir muitas linhas pede batch (uma viagem para várias linhas); ler muitas pede fetch size (fluxo); e paginar fundo pede keyset, não OFFSET.

≈

Como fazer compras. Você não vai ao mercado uma vez por item — enche o carrinho e passa uma vez no caixa (batch). E para achar a página 5.000 de um catálogo, ninguém conta as 100 mil primeiras: você usa o marcador de onde parou (keyset). O OFFSET é literalmente contar tudo de novo a cada página.

Por que o OFFSET degrada

Para servir OFFSET 100000 LIMIT 20, o banco precisa produzir e descartar as 100 mil primeiras linhas — a cada requisição. O custo cresce linearmente com a profundidade da página, e a lentidão só aparece quando os dados crescem. O keyset usa a última chave vista como ponto de partida, servido direto pelo índice, com custo constante.

Veio substituir: paginação por número de página em APIs de alto volume — é por isso que feeds infinitos usam cursor.

Onde você usa isso no dia a dia

  • Importação e migração de dados em massa.
  • Exportação de relatório com milhões de linhas.
  • API de listagem com scroll infinito.
OFFSET: piora com a profundidade
SELECT * FROM pedido
ORDER BY data DESC
OFFSET 100000 LIMIT 20;
-- produz e joga fora 100 mil linhas
Keyset: custo constante
SELECT * FROM pedido
WHERE (data, id) < (?, ?)   -- último visto
ORDER BY data DESC, id DESC
LIMIT 20;
-- vai direto pelo índice
// batch: agrupa as viagens de rede
var ps = c.prepareStatement("INSERT INTO item (pedido_id, sku, qtd) VALUES (?,?,?)");
int n = 0;
for (var item : itens) {
    ps.setObject(1, item.pedidoId()); ps.setString(2, item.sku()); ps.setInt(3, item.qtd());
    ps.addBatch();
    if (++n % 500 == 0) ps.executeBatch();     // lotes de 500
}
ps.executeBatch();

// leitura em fluxo (no Postgres exige autoCommit=false para respeitar o fetchSize)
c.setAutoCommit(false);
ps.setFetchSize(1_000);

Por que o JPA/Hibernate existe — e o que ele esconde

essencialo próximo passo

Direto: o ORM automatiza o mapeamento objeto↔tabela que você acabou de escrever à mão. Adote-o depois de dominar JDBC — porque os bugs famosos dele são exatamente os pontos onde a automação vaza.

≈

Como o câmbio automático. Ele troca as marchas por você e, na maior parte do tempo, melhor do que você faria. Mas quem nunca dirigiu manual não entende por que o carro "patinou" na subida — e é justamente nessa hora que saber o que acontece embaixo do capô resolve.

Como surgiu

No início dos anos 2000, todo projeto Java tinha centenas de DAOs repetitivos mapeando ResultSet para objeto. Gavin King criou o Hibernate para eliminar esse trabalho mecânico, e ele se tornou o padrão JPA. O problema que resolve é real: o impedance mismatch, a distância entre objetos (herança, grafos, referências) e tabelas (linhas, chaves, joins).

Veio substituir: os DAOs artesanais escritos à mão — e boa parte do código que você viu nos tópicos anteriores.

Onde isso te pega no dia a dia

  • N+1: 100 pedidos viram 101 consultas ao acessar os itens de cada um.
  • LazyInitializationException: acessar relação preguiçosa fora da sessão.
  • Flush inesperado: o Hibernate adia os UPDATEs e decide a hora sozinho.
O N+1 acontecendo
var pedidos = repo.findAll();     // 1 query
for (var p : pedidos)
    p.getItens().size();          // +100 queries
// log mostra 101 SELECTs
A cura
@Query("SELECT p FROM Pedido p "
     + "JOIN FETCH p.itens "
     + "WHERE p.status = :s")
List<Pedido> buscarComItens(Status s);
// 1 query só
Critério de adoção, sem religião

CRUD rico em entidades e relações: o JPA economiza muito código. Consultas complexas, relatórios e alto volume: SQL explícito (JdbcTemplate ou jOOQ) costuma ser mais simples, mais previsível e mais rápido. Os dois convivem no mesmo projeto — escolha por caso de uso.

Pratique agoraLigue spring.jpa.show-sql=true num projeto com relação lazy, provoque o N+1 e conte as consultas no log. Corrija com JOIN FETCH e conte de novo.

Injeção por construtor e o composition root

essencialdesign

Direto: injeção de dependência não precisa de framework — é passar as dependências pelo construtor. O composition root é o único ponto do sistema (o main) onde tudo é montado.

≈

Como uma cozinha profissional. O chef não sai da cozinha para comprar tomate no meio do preparo: os ingredientes chegam prontos na bancada. Quem compra é outra função, feita uma vez, antes do serviço começar. Uma classe que dá new na própria dependência é o chef abandonando a panela para ir ao mercado.

Como surgiu

O termo "inversão de controle" ganhou tração nos anos 2000 com o Spring, num contexto de aplicações Java EE difíceis de testar — tudo dependia de um servidor de aplicação rodando. A ideia central é simples e anterior aos frameworks: em vez de a classe buscar o que precisa, ela declara o que precisa e recebe pronto.

Veio substituir: o new espalhado, os singletons globais e o padrão Service Locator, que escondiam o acoplamento em vez de expô-lo.

Onde você usa isso no dia a dia

  • Todo @Service com dependências no construtor.
  • Ao escrever um teste que injeta um dublê no lugar do repositório real.
  • Ao trocar uma implementação (e-mail → fila) sem tocar na regra.
Acoplado e intestável
class CheckoutService {
  private final PedidoRepo repo =
      new JdbcPedidoRepo(...);  // casado
  // teste precisa de banco real
}
Desacoplado e testável
class CheckoutService {
  private final PedidoRepo repo;
  CheckoutService(PedidoRepo repo) {
      this.repo = repo;         // recebe
  }
  // teste: new CheckoutService(fake)
}
Sinais de injeção mal feita
  • new de infraestrutura dentro da regra de negócio.
  • Injeção por campo (@Autowired no atributo): o objeto existe incompleto por um instante e não dá para instanciar no teste sem framework. Construtor + final garante objeto sempre válido.
  • Buscar dependência num registro global: esconde o acoplamento em vez de mostrá-lo na assinatura.
Pratique agoraEscreva um mini-app com o main montando três camadas à mão e um teste que injeta fakes. Depois compare com o que o Spring faz automaticamente.

Ports e adapters: pacotes que protegem a regra

arquitetura

Direto: a regra de negócio fica no centro, sem importar nada de framework; as bordas (HTTP, banco, fila) são adapters que implementam ports definidos pelo domínio. As dependências apontam para dentro.

≈

Como os plugues de um notebook. O aparelho define os encaixes (USB, HDMI); os periféricos se adaptam a eles. O notebook não muda porque você trocou o monitor. Se a regra de negócio importasse jakarta.servlet, seria como soldar o monitor na placa-mãe.

Como surgiu

Alistair Cockburn formulou a arquitetura hexagonal em 2005 para resolver uma dor concreta: aplicações em que a lógica de negócio estava tão presa ao framework web e ao banco que testar exigia subir tudo. Clean Architecture e Onion Architecture são variações da mesma ideia central.

Veio substituir: a divisão em camadas técnicas (controllers/services/repositories) onde a regra dependia da infraestrutura em vez do contrário.

Onde você usa isso no dia a dia

  • Ao testar a regra sem subir o Spring inteiro.
  • Ao trocar o banco ou o broker de mensagens.
  • Ao organizar um projeto novo do zero.

O teste prático é abrir sua classe de regra e olhar os import. Se ela importa org.springframework, jakarta.servlet ou java.sql, a regra está acoplada à tecnologia. Com ports e adapters, o domínio define a interface e a infraestrutura a implementa — e o composition root liga as duas pontas.

// domínio: zero imports de framework
public interface PedidoRepositorio {                 // port (definido pelo domínio)
    Optional<Pedido> buscar(UUID id);
    void salvar(Pedido p);
}
final class JdbcPedidoRepo implements PedidoRepositorio { /* adapter */ }

// pacote por funcionalidade, não por tipo técnico:
// com.loja.pedidos        ← Pedido, PedidoRepositorio, CheckoutService
// com.loja.pedidos.jdbc   ← JdbcPedidoRepo
// com.loja.pedidos.web    ← PedidoController
Pacote por funcionalidade envelhece melhor

Agrupar por tipo técnico (controllers, services) espalha uma feature por quatro pastas e torna tudo público. Agrupar por funcionalidade mantém a feature junta e permite usar package-private como fronteira real: só o que outras features precisam fica público.

Pratique agoraAudite os imports da sua camada de regra num projeto real e liste as violações. Extraia um port para a pior delas.

Anotações, reflection e proxies: a mágica revelada

mecanismosexplica o Spring

Direto: uma anotação sozinha não faz nada — é apenas um metadado. Alguém precisa lê-la via reflection, e o comportamento (transação, cache, log) entra através de um proxy que embrulha o seu objeto.

≈

Como um post-it numa pasta. Escrever "urgente" na pasta não faz nada acontecer: alguém precisa ler o post-it e agir. E quem age não é você — é o assistente que intercepta a pasta antes de ela chegar à mesa, faz o que o post-it manda e só então entrega. Se você passar a pasta direto para a sua própria mesa, sem passar pelo assistente, o post-it é ignorado.

Como surgiu

Anotações chegaram no Java 5 (2004) para substituir a configuração em XML que dominava o ecossistema — o famoso "XML hell" dos primeiros Spring e EJB. Reflection existia desde o início, e a combinação das duas permitiu que frameworks descobrissem e configurassem seu código sem você registrar nada manualmente.

Veio substituir: arquivos XML gigantes declarando cada bean, cada transação e cada mapeamento.

Onde isso te aparece no dia a dia

  • Toda anotação do Spring, JPA, Jackson e JUnit que você usa.
  • Quando "a anotação não está funcionando" e ninguém sabe por quê.
  • Ao investigar por que o @Transactional não abriu transação.
// um mini-JUnit em seis linhas — a "mágica" é só reflection:
for (Method m : MinhaClasseDeTeste.class.getDeclaredMethods()) {
    if (m.isAnnotationPresent(Test.class)) {
        var instancia = MinhaClasseDeTeste.class.getDeclaredConstructor().newInstance();
        m.invoke(instancia);
        System.out.println("ok: " + m.getName());
    }
}

O proxy fecha o quebra-cabeça. O Spring não entrega o seu objeto para os outros beans: entrega um embrulho que intercepta cada chamada, executa o antes e o depois (abrir transação, checar cache, medir tempo) e delega ao objeto real. Isso explica o bug mais famoso do ecossistema.

Não abre transação
@Service
class PedidoService {
  public void processar() {
      this.salvar();   // chamada interna:
  }                    // pula o proxy!
  @Transactional
  public void salvar() { ... }
}
Abre normalmente
@Service
class PedidoService {
  private final Persistencia p;
  public void processar() {
      p.salvar();      // outro bean:
  }                    // passa pelo proxy
}
Diagnóstico instantâneo de "anotação não funciona"
  • Ninguém escaneia aquele pacote (fora do component scan).
  • A chamada é interna (this.metodo()) e pulou o proxy.
  • O método é private ou final — o proxy não consegue interceptar.

Threads, interrupção e cancelamento cooperativo

essencial

Direto: uma thread de plataforma é um recurso caro do sistema operacional. E não existe "matar" thread em Java: existe pedir que ela pare (interrupção) e ela cooperar.

≈

Como pedir para um cirurgião parar. Você não puxa o médico no meio da operação — avisa que a cirurgia foi cancelada e ele encerra num ponto seguro, fechando o paciente. Matar uma thread no meio de uma escrita deixaria locks presos e dados pela metade; por isso o Thread.stop() foi abandonado ainda nos anos 90.

Como surgiu

O Java nasceu com threads na linguagem (raro na época) e com um stop() que matava a thread de imediato. A prática mostrou que era impossível usar isso com segurança — locks ficavam presos, invariantes quebravam — e o método foi depreciado, substituído pelo modelo cooperativo de interrupção.

Veio substituir: Thread.stop() e suspend(), que corrompiam estado de forma imprevisível.

Onde você usa isso no dia a dia

  • Timeouts de framework que precisam abortar uma operação.
  • Shutdown gracioso do app, encerrando workers.
  • Cancelar um job longo a pedido do usuário.
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // restaura a flag: quem chamou precisa saber
    return;                                // e encerra cooperativamente
}

// loop de trabalho cancelável:
while (!Thread.currentThread().isInterrupted()) {
    processaProximo();
}
O erro que quebra o cancelamento de todo mundo

Capturar InterruptedException e não fazer nada apaga a flag de interrupção. Quem estava acima (o pool, o timeout do framework) perde a informação e o cancelamento morre ali. Regra: ou propague a exceção, ou restaure a flag.

Java Memory Model: visibilidade e happens-before

essencialo bug mais traiçoeiro

Direto: o bug mais difícil da concorrência não é corromper dado — é uma thread nunca ver o que a outra escreveu. O JMM define quando uma escrita se torna visível: apenas através de relações happens-before.

≈

Como dois escritórios com quadros de avisos próprios. O escritório A atualiza o quadro dele; o escritório B continua lendo o quadro antigo, para sempre, porque ninguém combinou quando sincronizar. O volatile é a regra que diz "toda escrita vai ao mural central e toda leitura busca lá" — sem isso, cada thread vive na sua própria fotografia.

Como surgiu

O modelo original de 1995 era ambíguo e permitia comportamentos que ninguém conseguia justificar. Foi reescrito na JSR-133 (Java 5) por especialistas em concorrência, criando a semântica formal de happens-before — o contrato que diz exatamente quando uma escrita de uma thread é garantidamente visível para outra.

Veio substituir: o modelo de memória vago do Java 1, onde volatile e a inicialização segura de objetos tinham garantias mal definidas.

Onde você usa isso no dia a dia

  • Flags de shutdown lidas por várias threads.
  • Caches e singletons inicializados sob concorrência.
  • Bugs que só acontecem em produção, sob carga, e nunca no seu notebook.
Pode nunca terminar
private boolean pronto = false;

// thread B:
while (!pronto) { }
usa(dados);
// o JIT pode ler 'pronto' uma vez
// e transformar em while(true)
Termina, com garantia
private volatile boolean pronto = false;

// thread A: dados = calcula();
//           pronto = true;
// B vendo pronto==true garante
// que B também vê 'dados' completo
volatile garante visibilidade, não atomicidade

contador++ são três operações (ler, somar, gravar) e volatile não as torna indivisíveis: duas threads incrementando perdem atualizações. Para contagem use AtomicInteger; para blocos, synchronized ou Lock.

Pratique agoraRode o loop sem volatile e veja-o não terminar. Adicione a palavra-chave e repita — a diferença é assustadora e didática.

synchronized, Lock, atomics e CAS

essencial

Direto: três níveis de ferramenta — synchronized (simples: exclusão + visibilidade), ReentrantLock (controle fino: tentar, desistir por timeout, condições) e atomics via CAS (sem bloquear ninguém, para operações pequenas).

≈

Como o banheiro de um avião. O synchronized é a tranca: um por vez, quem chega espera. O Lock é a tranca com display — você vê se está ocupado, decide esperar dois minutos ou voltar depois. E o CAS é outra filosofia: você entra, faz, e se alguém tiver usado no meio do caminho, refaz — sem ninguém ficar parado na porta.

Como surgiu

O Java 1 tinha apenas synchronized — correto, mas rígido: sem timeout, sem tentativa, sem múltiplas condições. O pacote java.util.concurrent (Java 5), projetado por Doug Lea, trouxe locks explícitos, coleções concorrentes e as classes atômicas baseadas em instruções do processador.

Veio substituir: o par wait()/notify() e locks artesanais, notoriamente difíceis de acertar.

Onde você usa isso no dia a dia

  • Contadores de métricas e estatísticas em memória.
  • Cache compartilhado entre requisições.
  • Seções críticas que atualizam estado compartilhado.
// nível 1 — simples e correto na maioria dos casos
private final Object lock = new Object();
synchronized (lock) { saldo = saldo.add(valor); }

// nível 2 — controle: tentar sem ficar preso
if (lock2.tryLock(200, TimeUnit.MILLISECONDS)) {
    try { transfere(); } finally { lock2.unlock(); }   // unlock SEMPRE no finally
} else { registraContencao(); }

// nível 3 — sem bloqueio, via compare-and-swap
private final AtomicLong processados = new AtomicLong();
processados.incrementAndGet();

// o que o CAS faz por baixo:
int atual;
do { atual = valor.get(); }
while (!valor.compareAndSet(atual, atual + 1));   // falhou? alguém mudou: refaz
Deadlock em uma frase

Duas threads, dois locks, ordens opostas: cada uma segura um e espera o outro, para sempre. Prevenção: adquira locks sempre na mesma ordem global. Diagnóstico: jcmd <pid> Thread.print aponta o ciclo explicitamente.

Executors, filas e backpressure

essencialprodução

Direto: um pool de threads é threads mais uma fila — e o comportamento sob pico é definido pela fila, não pelas threads. Fila ilimitada esconde o problema até virar falta de memória.

≈

Como a fila de um restaurante. Com fila infinita na calçada, o restaurante aceita todo mundo e as pessoas esperam três horas por uma mesa — a experiência é péssima e ninguém avisou. Com fila limitada, o maître diz "hoje não vai dar" na porta: você se decepciona em cinco segundos em vez de três horas. Rejeitar cedo é mais honesto que aceitar e falhar depois.

Como surgiu

Criar uma thread por tarefa não escala: threads de plataforma são caras. O ThreadPoolExecutor (Java 5) padronizou o reaproveitamento com uma anatomia configurável — núcleo, máximo, fila e política de rejeição. A discussão sobre backpressure veio depois, com sistemas distribuídos e a percepção de que aceitar trabalho ilimitado é uma forma de falha.

Veio substituir: new Thread() por requisição e pools artesanais sem política de saturação.

Onde você usa isso no dia a dia

  • Consumidores de fila e workers de background.
  • Ao investigar por que a latência subiu sem a CPU subir.

CompletableFuture: compor chamadas assíncronas

essencialJava 8

Direto: representa um valor que ficará pronto, componível como um pipeline: thenApply transforma, thenCompose encadeia outro futuro, thenCombine junta dois paralelos, orTimeout impõe prazo.

≈

Como pedir dois pratos ao mesmo tempo. Se você pedir a entrada, esperar chegar, e só então pedir a bebida, o jantar demora a soma dos dois. Pedindo juntos, demora o mais lento. É exatamente o ganho de combinar dois futuros independentes em vez de encadear chamadas.

Como surgiu

O Future original (Java 5) só permitia perguntar "já acabou?" e bloquear esperando — não dava para encadear nem combinar. O CompletableFuture (Java 8) trouxe composição declarativa, tratamento de falha e timeouts, seguindo o caminho das Task do .NET e das promises do JavaScript.

Veio substituir: callbacks aninhados e future.get() bloqueante espalhado pelo código.

Onde você usa isso no dia a dia

  • Consultar dois serviços independentes e juntar o resultado.
  • Disparar trabalho em background sem segurar a resposta HTTP.
  • Impor prazo total a uma composição de chamadas.
var precoF   = supplyAsync(() -> buscaPreco(id), pool);     // 300ms
var estoqueF = supplyAsync(() -> buscaEstoque(id), pool);   // 300ms

Oferta oferta = precoF
    .thenCombine(estoqueF, Oferta::new)          // total ~300ms, não 600ms
    .orTimeout(2, TimeUnit.SECONDS)               // prazo do conjunto
    .exceptionally(e -> Oferta.indisponivel(id))  // degrada com dignidade
    .join();
Armadilhas
  • thenApply recebe função que devolve valor; thenCompose recebe função que devolve outro future. Trocar os dois cria o CompletableFuture<CompletableFuture<X>> acidental.
  • Omitir o executor nos métodos *Async joga tudo no ForkJoinPool comum da JVM — I/O ali atrapalha o resto da aplicação.
  • Chamar join() dentro de um estágio desperdiça a thread do pool e convida deadlock.
Vindo do C#: equivale à Task, e a composição substitui o await. A diferença honesta: sem açúcar de async/await, cadeias longas ficam verbosas — e é exatamente esse problema que as virtual threads resolvem no próximo tópico.
Pratique agoraImplemente o combine acima com dois serviços simulados de 300 ms e prove no relógio que o total é ~300 ms.

Virtual threads: escalar a espera, não os recursos

essencialJava 21 · a virada

Direto: a virtual thread é gerenciada pela JVM, não pelo sistema operacional — custa quase nada e você pode ter milhões. Ao bloquear em I/O ela se desmonta e libera a thread real para outra tarefa.

≈

Como um garçom que não fica parado. No modelo antigo, cada mesa exigia um garçom dedicado, que ficava de pé esperando o cliente decidir — e o restaurante só atendia tantas mesas quanto tivesse garçons. Agora, quando o cliente pega o cardápio, o garçom vai atender outra mesa e volta quando chamado. A espera deixou de consumir recurso; só o atendimento consome.

Como surgiu

Um problema de vinte anos: servidores atendem N requisições simultâneas, mas threads de plataforma custam cerca de 1 MB cada. As saídas eram limitar N (fila na porta) ou abandonar o modelo simples e mergulhar em programação reativa — que resolve a escala ao custo de complexidade para o time inteiro. O Project Loom atacou a raiz: em vez de abandonar a thread, barateá-la.

Veio substituir: boa parte da necessidade de programação reativa e de cadeias de CompletableFuture só para não bloquear.

Onde você usa isso no dia a dia

  • APIs que passam a vida esperando banco e outros serviços.
  • Consumidores que processam milhares de mensagens concorrentes.
  • Migração: no Spring Boot 3.2+, basta uma propriedade para o servidor usá-las.
Antes: 200 threads, 50 s
var pool = Executors
    .newFixedThreadPool(200);
for (var t : dezMilTarefas)
    pool.submit(() -> esperaUmSegundo(t));
// 10.000 / 200 = 50 rodadas
Depois: 10 mil threads, ~1 s
try (var ex = Executors
     .newVirtualThreadPerTaskExecutor()) {
  for (var t : dezMilTarefas)
      ex.submit(() -> esperaUmSegundo(t));
}   // todas esperam ao mesmo tempo
Cuidados reais
  • Pinning: bloquear dentro de synchronized pode prender a virtual thread ao carrier (JVMs 21 a 23; resolvido no 24). Em caminho quente de I/O, prefira ReentrantLock.
  • Não faça pool de virtual threads — elas são descartáveis: crie uma por tarefa.
  • Só ajudam em trabalho de espera (I/O). Trabalho de CPU continua limitado pelo número de núcleos.
  • ThreadLocal com milhões de threads consome memória; o substituto moderno é ScopedValue.
Pratique agoraRode os dois blocos acima e compare o tempo total e a memória. A diferença entre 50 s e 1 s explica sozinha por que isso foi a maior mudança do Java 21.

Memória do processo: heap, stacks, metaspace e nativa

essencialcontainer

Direto: o processo Java usa bem mais memória que o heap — cada thread tem stack, o metaspace guarda classes, e JIT, GC e buffers consomem memória nativa. Em container, o limite corta o total, não só o heap.

≈

Como a bagagem de um voo. O limite de peso é da mala inteira, não só das roupas. Se você calcular só as roupas e esquecer o notebook, os sapatos e o necessaire, vai ser barrado no check-in. Definir -Xmx igual ao limite do container é exatamente isso — e o "barrado" se chama OOMKilled.

Como surgiu o problema

Por anos a JVM olhava a memória da máquina, não do container: rodando num servidor de 64 GB com limite de 512 MB no cgroup, ela dimensionava o heap para o valor errado e era morta pelo kernel sem nenhum aviso. As JVMs modernas leem os limites do container (UseContainerSupport), mas o dimensionamento correto continua sendo sua responsabilidade.

Veio substituir: o -Xmx fixo copiado de tutoriais, que ignora a memória fora do heap.

Onde isso te pega no dia a dia

  • Pod que morre sem log e sem stack trace nenhum.
  • Aplicação com heap folgado e mesmo assim reiniciando.
  • Ao dimensionar recursos de um serviço no Kubernetes.
Convite ao OOMKilled
# container: limite 1Gi
java -Xmx1g -jar app.jar
# heap cabe, mas stacks + metaspace
# + nativa estouram o limite
# → kernel mata, sem stack trace
Com folga para a parte nativa
java -XX:MaxRAMPercentage=75 \
     -XX:+UseG1GC \
     -jar app.jar
# a JVM lê o limite do container
# e reserva margem automaticamente
Distinga as duas mortes
  • OOMKilled (sem log, pod some): o container estourou o limite total. Veja em kubectl describe pod.
  • OutOfMemoryError (com stack trace): o heap encheu. Outro problema, outra cura — heap dump e análise de retenção.
Pratique agoraRode seu app no Docker com limite apertado e provoque as duas mortes. Aprender a distingui-las pelos sintomas economiza horas em incidente.

Garbage Collector: alcançabilidade, gerações e vazamento

essencial

Direto: o GC não coleta "o que você não usa mais" — coleta o que não é alcançável a partir das raízes. Vazamento em Java é retenção lógica: uma referência viva segurando um grafo inteiro.

≈

Como a faxina de um escritório. A regra do faxineiro é simples: se ninguém tem o objeto na mesa nem numa gaveta rastreável, ele descarta. Se você guardou uma caixa numa sala com etiqueta "guardar para sempre", ela nunca sai — mesmo que ninguém abra há três anos. O cache estático é essa caixa: o GC não consegue ler a sua intenção, só as referências.

Como surgiu

A coleta automática de lixo foi uma das apostas centrais do Java: eliminar de vez a classe de bugs mais custosa do C/C++ (uso após liberação, dupla liberação, vazamentos). A hipótese geracional — a maioria dos objetos morre jovem — surgiu de observação empírica e permitiu coletas frequentes e baratas na área nova.

Veio substituir: malloc/free manuais e os bugs de memória que assombravam sistemas grandes em C++.

Onde isso te pega no dia a dia

  • Memória que cresce lentamente até o app reiniciar sozinho.
  • Pausas de GC afetando a latência da API.
  • Cache caseiro que nunca expira nada.
// retenção lógica: alcançável não significa útil

// curas possíveis:
// 1. expiração de verdade (Caffeine com maximumSize e expireAfterWrite)
// 2. remoção explícita quando a sessão termina
// 3. WeakHashMap para metadados que podem sumir com o objeto
Escolha do coletor, sem misticismo
  • G1 (padrão): equilibra pausa e vazão. Certo para 95% dos serviços.
  • ZGC: pausas de sub-milissegundo mesmo em heaps enormes — para latência crítica.
  • Parallel: máxima vazão aceitando pausas — para processamento em lote.
  • Shenandoah: como o ZGC, mira pausas curtas independentes do tamanho do heap; faz o trabalho de compactação concorrentemente com a aplicação. Origem Red Hat, e é o padrão de fato em builds OpenJDK dessa linha — se a sua JVM não é a Oracle, confira qual dos dois você tem antes de copiar flags de tuning da internet.
  • Antes de trocar coletor ou ajustar flags, ligue -Xlog:gc* e olhe: a maioria dos "problemas de GC" é vazamento ou heap mal dimensionado.
Pratique agoraCrie o vazamento acima num loop, rode com -Xlog:gc* e assista a geração old crescer a cada coleta até o OutOfMemoryError.

Diagnóstico: jcmd, thread dump, heap dump e JFR

essencialkit de incidente

Direto: a JVM viva responde perguntas, e o jcmd é o canivete. Travou? thread dump. Memória crescendo? heap dump. Lento sem causa óbvia? JFR, que grava tudo com cerca de 1% de custo.

≈

Como exames médicos. O thread dump é a radiografia: uma foto instantânea de onde cada thread está. O heap dump é a tomografia: o retrato completo do que ocupa espaço. O JFR é o Holter: grava o funcionamento ao longo do tempo, para você ver o que acontece quando o problema aparece.

Por que isso é diferencial

A maioria dos desenvolvedores, diante de um incidente, reinicia o serviço e torce. Quem sabe extrair evidência da JVM em execução resolve a causa em vez do sintoma — e sai da investigação com uma explicação, não com uma superstição. São três comandos, e eles cabem na memória.

Veio substituir: o "reinicia e vê se melhora" e os println espalhados às pressas em produção.

Onde você usa isso no dia a dia

  • Aplicação travada, sem responder, mas viva.
  • Memória subindo sem explicação ao longo de horas.
  • Latência que piorou depois de um deploy.
jcmd                                          # lista os PIDs das JVMs
jcmd 4242 Thread.print > dump1.txt            # 3x com 10s → compare: presas no mesmo lugar?
jcmd 4242 GC.heap_dump /tmp/heap.hprof        # abra no Eclipse MAT: relatório de dominadores
jcmd 4242 JFR.start duration=120s filename=/tmp/gravacao.jfr
jcmd 4242 VM.flags                            # as flags realmente em uso
jcmd 4242 VM.native_memory summary            # o mapa de memória completo
Decore os três

Em incidente você não tem tempo de pesquisar. Thread.print para travamento, GC.heap_dump para memória, JFR.start para lentidão. Com isso você chega em qualquer investigação com evidência em dois minutos — e o thread dump aponta deadlock explicitamente, com o ciclo desenhado.

Performance: medir primeiro, otimizar depois

evidência

Direto: intuição sobre performance erra quase sempre. O ciclo correto é: medir o todo → achar o gargalo real → provar no micro com JMH → otimizar → medir de novo. Nessa ordem.

≈

Como consertar um vazamento de água. Você não troca todos os canos da casa: fecha registros até descobrir qual trecho perde pressão. Otimizar sem perfilar é trocar canos ao acaso — dá trabalho, custa caro e o vazamento continua.

Por que medir na JVM é traiçoeiro

Aquecimento do JIT, eliminação de código morto (o compilador descarta seu benchmark se o resultado não é usado), inlining e uma coleta de lixo no meio da medição — tudo conspira contra números caseiros. O JMH, o harness oficial, resolve isso: aquece, isola em processos separados, repete e usa Blackhole para impedir o descarte.

Veio substituir: o System.nanoTime() em volta de um laço, que produz números convincentes e errados.

Onde você usa isso no dia a dia

  • Ao decidir entre duas implementações numa revisão de código.
  • Ao investigar por que um endpoint ficou lento.
  • Ao justificar (ou recusar) uma otimização proposta.
A hierarquia da otimização
  1. Algoritmo e estrutura de dados — sair de O(n²) para O(n log n) vale mais que qualquer micro-ajuste.
  2. I/O e viagens de rede — batch, cache, resolver N+1. É onde estão os maiores ganhos em sistemas reais.
  3. Alocação em caminho quente — objetos criados desnecessariamente em loop.
  4. Micro-otimizações — e só agora. A maioria dos ganhos reais mora nos dois primeiros.

    for (var p : partes) sb.append(p);
    bh.consume(sb.toString());     // impede o JIT de descartar o trabalho
}

essencial

≈

Além do horizonte: JNI, Panama, Valhalla e Vector API

aprofundaro que vem por aí

Direto: quatro frentes que redefinem os limites da JVM. JNI e Panama resolvem "como chamar código nativo". Valhalla resolve "por que um List<Integer> gasta tanta memória". Vector API resolve "como usar as instruções SIMD do processador". Você provavelmente não vai usar nenhuma delas amanhã — e entender o problema que cada uma ataca muda como você lê o resto da plataforma.

≈

Como as obras que você vê da janela do escritório. Não mudam o seu dia hoje, mas mudam o bairro em dois anos. Quem acompanha entende por que certas ruas estão interditadas agora — e por que a lentidão que você aceita hoje é considerada um problema por quem projeta a plataforma.

Como surgiu

As quatro nascem da mesma tensão: a JVM trocou controle por segurança e portabilidade, e essa troca tem um custo mensurável. Objetos têm cabeçalho e vivem espalhados no heap; chamar código nativo é caro e frágil; o processador tem instruções vetoriais que o Java não alcança. Os projetos da OpenJDK atacam cada uma dessas contas sem abrir mão da segurança de memória — e é isso que os torna difíceis e lentos de entregar.

Veio substituir: Panama veio substituir o JNI (código C, compilação por plataforma, falha de segmentação derrubando a JVM inteira); Vector API veio substituir a esperança de que o compilador JIT vetorizasse o seu laço sozinho; Valhalla vem substituir os truques de arrays paralelos de primitivos que bibliotecas de alta performance usam para fugir do custo do boxing.

  • Ao ler que uma biblioteca "removeu a dependência de JNI".

Valhalla, em uma frase que explica o resto. Hoje, um Integer é um objeto no heap: cabeçalho, alinhamento e um ponteiro para chegar até ele. Um List<Integer> com um milhão de elementos é um milhão de objetos espalhados, e percorrer isso é um festival de cache miss — enquanto um int[] é um bloco contíguo. Valhalla quer permitir declarar tipos cujos valores são achatados na memória, sem cabeçalho e sem indireção: você escreve um tipo com nome e métodos, e a JVM o trata como um primitivo composto. O lema do projeto resume: códigos como uma classe, funciona como um int. É por isso que ele demora — mexe no fundo do modelo de objetos, e a compatibilidade com vinte anos de código é a parte difícil.
Armadilhas
  • Sair usando Panama para "otimizar". Você acabou de sair da segurança de memória da JVM. Só com necessidade concreta — falar com uma biblioteca C que não tem equivalente Java.
  • Esperar Valhalla para resolver um problema de hoje. Se a memória é gargalo agora, a resposta é int[], long[] e coleções de primitivos, não esperar uma release futura.
  • Achar que Vector API acelera qualquer laço. Ela ajuda em processamento numérico regular sobre grandes arrays; fora disso, não muda nada.
  • Confundir Panama com Loom. Panama é interoperabilidade com o nativo; Loom é concorrência — e Loom, esse sim, já está na Parte 09 e você usa hoje.
